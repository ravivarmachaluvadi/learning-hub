Lab 16 · The JVM Underneath: One Machine, Many Threads

Multithreading in Java — how one program does several things at once, and every way that goes wrong

Tell a friend: Ana and Ben each add one box to the stockroom and write the new total on the same whiteboard. Both can read 10 before either walks back to write, so both write 11, and one box vanishes from the record. Threads are Ana and Ben, the whiteboard is a field in memory, and count++ is the walk. Fixing it needs two promises, not one: nobody else is half-way through my job while I do it, and when I finish somebody can see it. Locks, volatile, wait, atomics and pools are all one of those promises or the bill for it, and none of them throws an exception when you get it wrong.

BEGINNER MODEL — stages 1 to 9

1. Why would a program ever do two things at once?

In one breath: A program that does one thing at a time must finish the slow thing before it starts the next one. Threads let it start the next one anyway. That is the whole upside, and the rest of this lab is the bill.

A program normally does one thing at a time. It reads a line, does it, reads the next. That is fine until one of those things is slow. Waiting for a database, a payment provider or a file all count. While your program waits, it does nothing else. Every other customer queues behind the slow one.

A modern machine has many CPU cores sitting idle during that wait. Multithreading is the ability to have several places in your program running at once. A slow customer no longer blocks a fast one, and eight cores do eight things instead of one.

What does it cost to go without? Three prices, and each is concrete. Read the right-hand column as "what the user actually experiences".

If you only ever run one thing at a time What it costs
a web server handling one request at a time 100 users sharing one 200-millisecond database call wait 20 seconds for the last one
a report that could use eight cores using one it takes eight times as long
code that must watch a socket and a timer at once it cannot be written at all without contorting it

That is the good news, and it is the entire upside. Everything from here on is the bill.

Before you turn the page, one belief worth killing. People say concurrency bugs are rare, so they are not a priority. They are not rare. They are rare per run and certain per fleet. A race that shows up in one execution in ten thousand happens roughly forty times a second in a service handling four hundred thousand requests a second. And it never throws. The number is just wrong, and it stays wrong.

2. Why does the stockroom tally say 11 when Ana and Ben each added a box?

In one breath: Two people can both read the same number before either of them writes a new one. The second write then does not build on the first. One box disappears from the record and nobody is at fault.

A warehouse has a whiteboard in the stockroom with one number on it: how many boxes of paper we have. Two workers, Ana and Ben, both need to record that they have added a box.

Here is what a worker actually does. She walks to the stockroom and reads the number off the board. She writes it on her own notepad and walks back to her desk. She adds one on the notepad. She walks back to the stockroom and writes her new number on the board.

Three separate actions, with walking in between: read, change, write.

Today the board says 10. Ana adds a box. Ben adds a box. The board should say 12.

  • Ana walks in, reads 10, notes it down, walks out.
  • Ben walks in and reads 10, because Ana has not written anything yet. He notes it down and walks out.
  • Ana comes back and writes 11.
  • Ben comes back and writes 11.

The board says 11. Two boxes were added. One of them has vanished from the record, and nothing anywhere went wrong in a way anyone can see. Ana did her job perfectly. Ben did his job perfectly. Nobody made a mistake. There is no complaint to file, no alarm to ring, and no way to tell later that it happened.

🔮 Predict: Ana and Ben each add exactly one box, starting from 10. Over every possible ordering of their walks, what values can the board end up showing?

Reveal

11 or 12, never 13. You get 12 when one finishes completely before the other starts. You get 11 when both read before either writes. It can never be 13, because neither worker ever writes anything other than the number they read, plus one. Nobody invents a value out of nothing.

If you guessed that a write could be lost entirely, look again. Both writes land on the board. The second one simply carries a number that went stale while its owner was walking.

This is not a guess. Scenario 1 of the visualization is exactly this, and the checker walks every interleaving of the two threads rather than sampling one. From a start of 0, the complete set of reachable answers is {1, 2}. The bad outcome is not exotic. It is half the state space.

Where does this lab take you from here? Stop at any checkpoint and you still have something whole.

3. Surely count++ is one action — isn't it?

In one breath: The naive solution says Ana and Ben made a simple job complicated, because in Java the whole thing is one line. That line is about to lose a box.

The obvious objection is that Ana and Ben made it complicated. In Java the whole thing is one line:

count++;              // surely this is one action?

It looks atomic. It is one statement, one semicolon, one keystroke's worth of thought. Surely the machine does it in one go.

4. What if one line is really three — and volatile cannot save it?

In one breath: count++ is Ana's three trips, written in machine instructions. Behind it hides a second, completely separate problem: your write may never be looked at again by anybody.

It is not one action. count++ compiles to roughly:

int r = count;        // read  memory      -> CPU register
r     = r + 1;        // add   inside the CPU only
count = r;            // write CPU register -> memory

Those are Ana's three trips. The register r is her notepad. Memory is the whiteboard.

Open scenario 1 in the visualization and cause the bug yourself. Run Thread A one step, and it reads 0 — that is Ana reading the board. Run Thread B one step, and it also reads 0 — that is Ben reading the same board. Then let each finish. The engine counts the machine steps for you, so compare the two runs.

What you drive Machine steps Final count What that means
A reads, B reads, then both finish 8 1 two boxes added, one record
a sequential run: A to the end, then B 8 2 the answer everybody expected

Same code, same two threads, same eight steps. Only the order changed.

Now comes the part that makes this a deep problem rather than an annoying one. A reasonable person, having understood the above, says this: the problem is that Ana and Ben cannot see each other's writes, so let me make the board more visible. Java has a keyword for exactly that idea. Marking a field so that every read goes all the way to memory, and every write is published to memory, is called making it volatile. The keyword is volatile.

It does not fix this. Making the board more visible says nothing about what happens between your read and your write. Ana still reads 10. While she is walking back to her desk with her notepad, Ben reads a genuinely fresh, perfectly visible 10.

So there are two different problems wearing the same clothes, and no single keyword covers both. The table names them; the rest of the lab keeps them apart.

5. What exactly do we have to guarantee?

In one breath: Two promises. Nobody else is half-way through my job while I am doing it. And when I finish, somebody else can actually see that I did.

Stated in plain words, and this is the whole rest of the lesson:

  1. When a piece of work must happen as a unit, no other thread may be part-way through the same piece of work at the same time.
  2. When one thread finishes writing, there must be some guarantee that another thread will actually see it.

Requirement 1 is about which orderings are possible. Requirement 2 is about which values are legal to see. They are separate, and a correct program needs both.

Ana and Ben's lost box is requirement 1 failing. The worker who never goes home is requirement 2 failing. Keep those two pictures apart and the rest of this lab is bookkeeping.

Say it back. Without using the words thread, atomic or visible, tell a friend why two people each adding one box can leave the tally showing that one box arrived.

A good answer sounds like "Each of them copies the number down before changing it. If they both copy it down before either walks back, the second one writes a total that was already out of date. Both totals are correct for the number each person copied. The board only keeps the last one written."

6. What does one key on the stockroom door actually buy?

In one breath: A lock is not a speed limit. It does not make Ana walk faster. It makes the world in which Ben walks in during her trips stop existing.

The invention is embarrassingly simple: put a single key on the stockroom door. You may not enter without holding the key, and there is only one key.

The key does not make Ana walk faster. It does not turn her three trips into one trip. What it does is make the interleaving where Ben walks in during Ana's trips cease to exist. A lock is a deletion of possibilities, not a speed limit.

And here is the part people miss. Java attaches the second guarantee to the same key. Handing the key back publishes everything you wrote. Taking the key up throws away everything you were remembering privately on your notepad.

One mechanism, both requirements. That is why synchronized is the default answer, and why everything else in this lab is either a refinement of it or an escape from it.

🔮 Predict: Ana takes the key, reads 10, and then her manager stops her for a long chat before she writes 11. What is Ben doing meanwhile, and what does the board show?

Reveal

Ben is standing at the door doing nothing, and the board still says 10. That is both the point and the price. The tally is safe and Ben is stalled.

If you guessed "Ben goes and does something else", you are describing a thread pool with other jobs queued, not a lock. A thread that wants a held key is stopped dead until it gets it. Section 11's fifth failure is this chat running for thirty seconds while fifty people queue at the door.

7. What do engineers call the things Ana and Ben just did?

In one breath: You have already felt every idea in this section. Now each one gets its real name, so the rest of the lab can say it in one word instead of a paragraph.

This is the lab's terminology, and each name below marks a distinction you have already met in the stockroom. Minor terms are defined at first use later on; these are the load-bearing ones.

Who is running, and what do they share?

Ana is not the program. Ana is a position in the program, and it is the position that is currently running. She is somewhere in the middle of the instruction sheet, holding her own notepad. Engineers call that a thread.

Technically it is an independent flow of execution with its own program counter and its own stack, meaning its local variables and its method-call chain. It shares one heap with every other thread in the process, and that heap holds all objects and all fields.

The word exists to separate the thing that runs from the program. A program is text. A thread is a position in that text, and there can be many.

In scenario 1, Thread A and Thread B run identical code but each has its own r. r lives on the stack, so it is private: Ana's notepad. count is a field, so it is shared: the whiteboard.

You have already met a variant of this. In java-virtual-threads a virtual thread is one of these whose stack lives on the heap, multiplexed onto a small number of carrier threads. Everything in this lab applies to virtual threads unchanged. Same memory model, same locks, same bugs.

The whiteboard has a name too. Data that more than one thread can both read and change is shared mutable state. Technically: any location reachable from two threads where at least one access is a write. That phrase names the only thing that causes these bugs. Shared-and-immutable is safe. Mutable-but-not-shared is safe. Only the intersection hurts, and naming the intersection tells you where to attack.

count is shared and mutable. r is mutable but not shared. A String is shared but not mutable. Neither of the last two can produce a race.

What exactly is going wrong?

When the answer depends on who happened to get there first, engineers call it a race condition. Technically: correctness depends on the relative timing of operations in different threads, when nothing in the program constrains that timing.

The word exists to make one point. The bug is not in any one line. Every line in scenario 1 is correct. The defect lives in the set of orderings the program permits.

Ana and Ben's particular race has two more precise names. Its shape is check-then-act, or more usefully read-modify-write: read a value, decide something from it, write a value derived from it. Its result is a lost update, which is a completed write silently overwritten by a write derived from stale data.

That name will follow you around. isolation-levels and optimistic-vs-pessimistic-locking both call this exact thing a lost update. It is the same bug at three scales: between two CPU registers, between two database transactions, and between two HTTP requests.

The property Ana needed and did not have is atomicity: all of it happens, or none of it, with no visible middle. Precisely, an operation is atomic with respect to a set of threads if those threads can never observe it half-done.

The word exists because "one line of code" and "one indivisible action" are different things, and only the second one is worth anything. count = 5 is atomic for an int. count++ is not. Assignment to a long or a double is not guaranteed atomic on 32-bit JVMs unless the field is volatile [JVM rule, not this lab's model — JLS §17.7].

The property the never-stopping worker needed is a different one. Visibility is whether your write ever shows up for somebody else. Precisely: whether a read in thread B is permitted to return a value written by thread A. The word exists to separate "when did it happen?" from "who is allowed to see it?". Scenario 2 has no timing problem at all, because the write definitely happened first, and it is still broken.

Visibility's guarantee has a formal name you have met. java-memory-model calls it happens-before. If action X happens-before action Y, then whatever X wrote is visible to Y. Two edges matter here. Releasing a lock happens-before any later acquisition of that same lock. A write to a volatile field happens-before any later read of that same field. Without such an edge, there is no promise at all.

What are the tools called?

The bit of code only one worker may be inside at a time is the critical section. In scenario 3 it is the three lines between synchronized (lock) { and }. Precisely, it is a region of code protected so that at most one thread executes it concurrently for a given lock.

The guarantee that only one worker is inside is mutual exclusion, and the property of enforcing it has its own word for a reason. The critical section is where. Mutual exclusion is the guarantee. You choose the first. The runtime provides the second.

The key on the door is a lock. In Java it is not something extra you create. Every Java object already has one, called its intrinsic lock or its monitor. synchronized (obj) acquires it and releases it on exit, including when an exception is thrown.

A monitor has three parts. There is an owner, an entry set of threads blocked trying to get in, and a wait set of threads that have deliberately gone to sleep inside it. The entry set is the queue at the door. The wait set is the waiting room down the corridor. All three parts are shown in the visualization's Locks panel. In scenario 5, buffer is the monitor, and two consumers sit in its wait set while the producer holds it.

Why "monitor"? It is Hoare's 1974 name for "a lock plus a place to wait". Mutual exclusion alone cannot express "wait until there is something to consume". You need both, so Java bolted both onto every object. Compare distributed-locking, whose lock service is this same idea rebuilt out of messages, and which loses mutual exclusion in the process. Here the JVM releases a dead thread's monitors for you. There, nobody can tell death from slowness.

When everyone is politely waiting for someone else, forever, that is deadlock. Technically it is a cycle in the "thread X holds a lock thread Y wants" graph. With plain synchronized there is no timeout and no detection. The threads simply stop. The word exists to distinguish stopped because of a cycle from stopped because it is slow. Those look identical from outside and have completely different cures. Scenario 4 is two transfers in opposite directions, each holding one account and asking for the other, and it ends with both threads BLOCKED.

Hiring a new worker for every box is expensive, so real systems keep a fixed crew and a queue of jobs. That is a thread pool, driven by an ExecutorService holding N worker threads that repeatedly take tasks from a shared queue. It exists because creating a thread costs a system call and roughly a megabyte of reserved stack [JVM rule, not this lab's model], so one thread per request stops scaling. The last name is the escape hatch. Compare-and-set, usually written CAS, means "write this, but only if nobody has touched it since I looked". It is a single CPU instruction. It compares a memory location to an expected value, writes a new one only if they match, leaves no gap in between, and returns whether it succeeded.

It exists because the gap between read and write is the entire bug, and hardware can eliminate the gap without any thread having to wait. Scenario 6 is Ana and Ben again: both read 0, Ana's compare-and-set succeeds, and Ben's is refused. That refusal is not an error. Ben simply retries from 1 and wins.

You have met this primitive twice already. optimistic-vs-pessimistic-locking's conditional UPDATE … WHERE version = ? is compare-and-set. And linearizability named compareAndSet as the canonical atomic operation. Same primitive, three labs.

8. Which mental models should you carry — and where do they lie to you?

In one breath: Keep two pictures. The friendly one is Ana walking to a whiteboard. The precise one is several program counters sharing one heap. The friendly one lies in exactly three places.

The simple model is the stockroom. Workers walk between their desks and a whiteboard. Reading takes a trip. Thinking happens at the desk. Writing takes another trip. There is one key on the door, and a bell to call people out of the waiting room.

The engineering model is the same machine, stated precisely. Several program counters advance independently through code. Each has a private stack of locals, parameters and its call chain. Each may keep field values in CPU registers. All of them share one heap.

Between any two machine instructions of any thread, any other thread may execute any number of its own. A monitor is a record {owner, entry set, wait set}. The Java Memory Model defines a partial order called happens-before. A read may return a write's value only where that order allows it, or where an unlucky data race lets it.

🔮 Predict: Ana writes 11 on the board. Ben is in a loop, reading the board over and over, and his field is not marked volatile. How long can he keep reading 10?

Reveal

Forever. Not "for a while". The compiler is allowed to notice that Ben's loop never writes the field, hoist the read out of the loop, and emit machine code that reads it exactly once.

If you guessed "a few microseconds, until the cache line syncs", you are reasoning about hardware and the answer is compilers. Nothing in the machine code ever asks memory again, so no amount of waiting helps. That is lie number one below, and it is the biggest one in the analogy.

Where the story lies to you — three places, and each one matters.

  1. A person will eventually glance at the board again. A CPU may genuinely never look. This is the biggest lie in the analogy. In the stockroom, "stale" means "out of date for a while". In Java it can mean forever. The compiler is allowed to hoist a non-volatile field read out of a loop entirely, so the machine code contains no re-read at all. Scenario 2 is not a slow worker. It is a worker who has been optimised into never checking.
  2. The analogy makes your own actions look ordered. From outside, they are not. If Ana writes the board and then writes her diary, everyone agrees that is the order. In Java, without a happens-before edge, another thread may observe those two writes in the opposite order. That is the java-memory-model lab's reordering and store-buffer material. This lab's visualization does not model reordering; it models one shared memory with private copies. The simplification is deliberate, and it is why the two labs are separate.
  3. A locked door with a dead worker inside is obvious. A hung thread holding a monitor is not. In real terms this is better than it sounds. If a thread dies, the JVM releases its monitors. But if it merely hangs, say on an HTTP call with no timeout, it holds the lock forever. Every other thread then piles into the entry set. That is the single most common Java production incident in this whole area, and section 13 shows what it looks like on a dashboard.

INTERMEDIATE MODEL — stage 10

10. How would you build the fix yourself, and where would it break?

In one breath: Nobody hands you the right answer first. You try the obvious thing, watch it fail, and the failure tells you the next refinement. Six versions, and every strange-looking rule at the end is the scar of a failure in the middle.

Rather than hand you java.util.concurrent, this stage builds the answer the way a smart engineer actually arrives at it. The obvious version comes first. Then comes the failure that forces the next refinement. Ana and Ben stay on stage the whole way: Ana is Thread A, Ben is Thread B, and the whiteboard is still count.

v1 — why doesn't volatile fix the counter?

Ana and Ben cannot see each other's writes, so make the board maximally visible.

volatile int count;      // now everybody sees my writes
void increment(){ count++; }

Why it looks right. It attacks the visibility problem from scenario 2 head-on. Marking the field volatile really does give a happens-before edge on every read and every write of it.

Why it breaks. Run scenario 1's interleaving in your head, with perfect visibility switched on. Ana reads 0, truthfully. Ben reads 0, also truthfully, because Ana has not written yet. Both write 1. The keyword did its job flawlessly and the update is still lost.

The lesson, precisely. volatile makes single reads and single writes visible and ordered. It does not join a read and a write into one action. It is the right tool for exactly one shape: a flag that one thread writes and others read, which is scenario 2. It is the wrong tool for anything of the form read, decide, write.

v2 — what does one lock actually change?

Give the stockroom its single key.

synchronized (lock) { count++; }

This is scenario 3, and the checker settles it exhaustively rather than by example. It enumerates every possible schedule of both threads through the locked version and finds no schedule producing anything but 2. The same code with the lock removed, driven through the identical interleaving, lands on 1.

Below is a hand-worked trace, taken from the engine's own log for scenario 3 with "let the scheduler choose" selected. Read it as Ana and Ben with one key between them. The fourth column is the state of the world after that step.

Step Thread Instruction Result
1 A (Ana) LOCK lock Ana owns the monitor; her private copies are discarded
2 B (Ben) LOCK lock refused — Ben goes to BLOCKED, and his program counter does not move
3 A r = count Ana reads 0 from memory
4 A r = r + 1 Ana's register holds 1; memory still holds 0
5 A count = r memory now holds 1

Two things in that trace deserve their own sentence.

Step 2 is the whole of mutual exclusion. Ben did not run slower. Ben did not run at all. His program counter stayed put. Interleavings were not discouraged. They were removed from the set of possible executions.

Step 8's guarantee comes from step 6, not from luck. The monitor gave a happens-before edge. Had Ana used no lock, Ben could legally have read 0 at step 8 even after Ana wrote 1.

🔮 Predict: A lock's first job is mutual exclusion. What is its second job, and which earlier scenario does that second job fix?

Reveal

Visibility — it fixes scenario 2 as well. Releasing a monitor publishes everything you wrote inside it. Acquiring the same monitor discards your private copies. So synchronized is a complete answer to both requirements from section 5, which is exactly why it is the default and why volatile is a specialist tool.

If you guessed "speed" or "fairness", the lock gives you neither. The guarantee is one-way and lock-specific. It only helps threads that acquire the same monitor. A reader that skips the lock gets no promise at all, even if every writer takes it religiously. That is the mistake behind almost every "but I do synchronize the writes" bug report.

v3 — two locks, and what kills a service?

One lock around everything is correct and slow. Two threads touching completely unrelated accounts still queue for the same key. So you use one lock per account. Now a transfer needs two.

synchronized (from) {
  synchronized (to) { … }        // Thread A: from=accountA, to=accountB
}                                // Thread B: from=accountB, to=accountA

This is scenario 4, and it stops dead. The run ends run = STUCK, with both threads BLOCKED, accountA owned by Ana and accountB owned by Ben.

The cause fits in one sentence, and the sentence is worth memorising: a thread was holding a lock while asking for another one. Every deadlock has that shape. The four classic conditions are mutual exclusion, hold-and-wait, no preemption and circular wait. They are just that sentence expanded, and the practical attack is always the last one.

The refinement is a global order on locks. Always take accountA before accountB. Order them by account id, by System.identityHashCode, by anything at all, as long as everybody agrees. A cycle needs someone to go "up" while someone else goes "down", and a total order makes that impossible. Turn on the ordering option in scenario 4 and the same code completes.

A second refinement, for when a global order is impractical: be able to give up. ReentrantLock.tryLock(timeout) returns false instead of blocking forever, so you can release what you hold and retry. synchronized cannot do this. It has no timeout, no interruption, and no way to abandon the attempt. That single missing capability is most of the reason ReentrantLock exists.

v4 — how do you wait for something that has not arrived yet?

Locks answer "not at the same time". They do not answer "not yet". A consumer needs to wait until there is something to consume, without holding the key while it waits. That is what the waiting room down the corridor, the wait set, is for.

synchronized (buffer) {
  if (items == 0) buffer.wait();      // <- the bug
  items--;                            
  consume();
}

🔮 Predict: Consumer 1 is inside synchronized (buffer), so it holds the lock, and it calls buffer.wait(). While it sleeps, can the producer get in to add an item?

Reveal

Yes — and it has to, or nothing could ever work. wait() releases the lock as it puts the thread to sleep, and re-acquires it before returning.

If you guessed no, picture the consequence. A consumer falls asleep holding the only key, and the producer that is supposed to wake it can never get in. That is a guaranteed deadlock on the first empty buffer.

This is the single most-forgotten fact about wait(). It is also why the thread has to queue for the lock again after being notified. Waking up and running are two different events, with an unbounded amount of other threads' execution possible in between. That gap is the entire bug in this section.

So wait() does something people consistently forget: it gives the lock back, and puts the thread in the monitor's wait set. Then notify() and notifyAll() move sleepers out of the wait set and into the entry set, not into "running". They still have to acquire the lock like anyone else.

Scenario 5 runs this with two consumers and one producer that adds one item. The run ends with items = −1. Two consumers each took an item, and one item existed.

Here is the trace from the engine. Watch step 14 and step 18, where a consumer returns from wait() and acts on a fact that was true when it fell asleep.

Step Thread What happens
1–4 Consumer 1 takes lock, reads items = 0, calls wait() → gives the lock back, sleeps
5–8 Consumer 2 takes lock, reads items = 0, calls wait() → sleeps
9–13 Producer takes lock, sets items = 1, notifyAll() wakes both into the entry set, releases
14 Consumer 1 re-acquires the lock, returns from wait(), and with if does not re-check
15–17 Consumer 1 items 1 → 0, consumes, unlocks
18 Consumer 2 re-acquires, returns from wait(), with if does not re-check
19–21 Consumer 2 items 0 → −1, and "consumes" an item that does not exist

The refinement: wait() must always sit inside a while, never an if.

while (items == 0) buffer.wait();     // correct

Turn on the while option and re-run. Now the buffer ends at items = 0, with Consumer 2 back asleep in the wait set. That is not a failure. One item genuinely cannot feed two consumers, so it is the correct outcome.

The rule is absolute because being woken tells you only that something changed, never that your condition is true. There are three independent ways it can be false. Another thread got there first, which is what you just watched. notifyAll wakes everyone, including threads waiting for a different condition. And the JVM is explicitly permitted spurious wakeups: a return from wait() with no notify() at all [JVM rule, not this lab's model — Object.wait javadoc].

The same scenario exposes a second trap. Run the producer before any consumer falls asleep, and the log says "called notifyAll() and woke nobody". A notification is not a message. It is not queued, counted or remembered. If nobody is in the wait set, it is gone. That is why the condition, the value of items, is the source of truth, and the notification is only a nudge to go and look.

v5 — why should you stop writing any of this?

Everything above is the machinery. You should almost never touch it. The refinement that ends the sequence is this: use the library that already got it right.

Instead of Use Because
synchronized + wait/notify for a producer/consumer ArrayBlockingQueue / LinkedBlockingQueue put/take block correctly, loop correctly, and cannot miss a signal
synchronized around a counter AtomicInteger, LongAdder no blocking; LongAdder splits the counter across cells to kill contention
synchronized around a map ConcurrentHashMap lock-free reads; per-bin locking for writes; compute/merge are atomic
synchronized with a timeout you cannot have ReentrantLock.tryLock(…) can time out, be interrupted, and be fair if you ask
hand-rolled thread creation ExecutorService bounded threads, a queue, and a shutdown story
hand-rolled "wait for these 3 things" CompletableFuture, or a structured-concurrency scope composition and error propagation

v6 — can you fix it with no lock at all?

For the counter specifically there is a better answer than a lock, and it is scenario 6. Ana no longer waits at the door. She writes only if the board still says what she read.

int old, next;
do {
  old  = count.get();
  next = old + 1;
} while (!count.compareAndSet(old, next));

The CPU compares and writes in one indivisible instruction, so the gap that lost the box in scenario 1 does not exist. The checker walks every interleaving to depth 18, and the answer is always 2.

The trade, stated honestly. The cost has not disappeared. It has moved from waiting to redoing. A blocked thread costs a context switch and then sleeps. A retrying thread costs CPU and stays hot. Under low contention retries are near zero and atomics win easily. Under heavy contention many threads spin, redo arithmetic and throw it away.

That waste is exactly what optimistic-vs-pessimistic-locking put numbers on in its crossover experiment. Read the middle column as "work the CPU did that nobody wanted".

ENGINEERING MODEL — stages 11 and 12

11. What are all the ways this breaks?

In one breath: Twelve failures, and each one is either "something wrong has already happened" or "nothing wrong has happened but nothing will move again". Knowing which of the two you have tells you how urgent the incident is.

The important split runs through the whole section. Safety means nothing wrong ever happens. Liveness means something right eventually happens. Almost every mechanism here trades one for the other. A safety failure has already corrupted something. A liveness failure has not corrupted anything yet.

Which six failures can you cause on screen?

1 · Race condition, the lost update. This is Ana and Ben in section 2. Drive it in scenario 1 by interleaving two reads before either write. Both threads read 0 and both write 1, because each write is based on a value that was true when read and stale when used.

Nothing detects it. Both threads report success. The program keeps running, fast, forever, and the value is gone permanently. There is no later moment at which the system notices.

In production this is a balance that drifts, a stock count that goes negative over months, or a "processed" flag set twice. Reconciliation finds it; monitoring never does. The isolation-levels lab's 8 × 40 = 320 experiment is this same bug inside a database.

2 · Visibility failure: the stale read and the non-terminating loop. This is the worker who never goes home. Drive it in scenario 2 with volatile off. He kept a private copy: memory holds true, and the run shows him looping 13 more times with every read returning false.

No timeout exists, so there is no response, ever. Safety survives untouched, because nothing incorrect is written. What is lost is termination. In production this is "the pod will not drain", a shutdown hook that never completes, one core pinned at 100%. The cure is volatile, or reading inside the same lock the writer used, or AtomicBoolean.

3 · Deadlock. Drive it in scenario 4 with the opposite lock order. Ana holds accountA and wants accountB; Ben holds accountB and wants accountA. That is a cycle in the holds-and-wants graph, and both threads end BLOCKED. Liveness is lost totally and permanently.

There is no response available, because synchronized has no detection and no timeout. Safety survives perfectly: nothing incorrect happened. Those threads are lost forever, and if they are pool workers the pool dies with them.

In production, requests time out while CPU sits at zero and the error rate looks calm. It is diagnosed with jstack <pid>, which prints "Found one Java-level deadlock" and names both threads and both monitors. That is one of the few times the JVM hands you the exact answer. Cure it with global lock ordering, with tryLock and a timeout, or by holding one lock at a time.

4 · Livelock. This one is not built into the visualization, and that gap is flagged rather than hidden. The shape: two threads each detect a conflict, politely back off, and retry in lockstep, forever. Or two tryLock users each release and retry at identical intervals.

It is worse than deadlock because CPU is high and threads are RUNNABLE. A thread dump shows nothing obviously wrong, and every automated deadlock detector says "fine". The cure is randomised back-off, which is the same trick, for the same reason, as the randomised election timeouts in the raft lab.

5 · Starvation and the convoy. This is Ana's long chat from section 6, at scale. Liveness is lost for one thread, and throughput is lost for everyone. Plain synchronized promises nothing about who enters next, so a thread can lose the race many times running. That is starvation.

The convoy is worse. One thread holds a lock across a slow call, such as an HTTP request with no timeout or a synchronized method that logs to a blocking appender. It turns its delay into everyone's delay, because they are all in the entry set. This is the classic Java incident. Latency goes vertical, CPU goes to near zero, and thread dumps show fifty threads BLOCKED on one monitor while one thread sits in a socket read.

The rule that prevents it is short: never hold a lock across I/O. The database version of exactly this appears in optimistic-vs-pessimistic-locking. There, one client pausing 2 s mid-save cost five neighbours all their saves and produced 15 lock timeouts. The optimistic version of the same run cost only the sleeper.

The cure is to shrink the critical section down to the state change, and do the I/O outside it. If fairness genuinely matters, new ReentrantLock(true) gives FIFO order, at a real throughput cost. Fairness forbids barging, which is letting a thread that has just arrived take a free lock ahead of the queue. Barging is what makes an uncontended lock cheap, so banning it is not free.

6 · The missed signal, if instead of while. Drive it in scenario 5 with if. The buffer ends at items = −1: two consumers took the single item. Nothing useful survives here, because this one corrupts state, and the invariant items >= 0 is gone.

In production the second consumer reads element −1 of an array, or processes a null, or double-charges. The cure is while, always. The better cure is BlockingQueue, which removes the opportunity. Its sibling failure is notifyAll() with an empty wait set, where the log says "woke nobody" and the signal is simply gone. The condition is the truth; the notification is only a nudge.

What breaks in the thread pool?

🔮 Predict: A pool of 2 workers deadlocks because each task submits a sub-task to the same pool and waits for it. You raise the pool to 8 workers and it now completes. Is the bug fixed?

Reveal

No — and "it completes" is the worst possible outcome. The pool tab shows both runs: 2 workers deadlock at tick 4, and the identical configuration with 8 workers finishes normally. Nothing structural changed. A task still blocks on work that needs a worker from the same pool. All you altered is how many parent tasks must be in flight simultaneously before every worker is consumed.

If you guessed "yes, it has enough capacity now", look at what you actually built. You converted a deterministic bug that fails on the first test run into a load-dependent one. It now waits for a traffic spike, a slow downstream or a retry storm, and then hangs permanently, at peak, with no code change to blame. A fix that makes a bug harder to trigger without removing it has made things worse.

7 · Thread-pool starvation deadlock. Liveness is lost, and the loss is invisible. Drive it on the pool tab: workers 2, tick "each task submits a sub-task to the same pool and waits for it", press Play. The run reaches DEADLOCK at tick 4, with every worker blockedOn a sub-task and every sub-task queued waiting for a worker.

Each worker is holding a pool thread hostage while waiting for work that needs a pool thread. There is no response: ThreadPoolExecutor has no idea this is happening. Safety survives; the entire pool is lost, permanently.

In production the classic form is a task that calls a service which uses the same executor, or a parallel stream inside a task on the common ForkJoinPool. A bigger pool does not fix it, as the 8-worker run shows, so the bug simply hides until load rises. The cure: never block, inside a pool task, on work submitted to that same pool. Use a separate pool, or make it non-blocking.

8 · Rejection, and the queue that eats your heap. Drive it on the pool tab with queue capacity 0, 12 tasks and 2 workers. Then compare the two policies.

Pool tab setting Tasks rejected Tasks completed What it costs
queue 0, default policy 10 of 12 2 one RejectedExecutionException per lost task
queue 0, CallerRunsPolicy 0 12 4 of them run by the submitting thread, which can submit nothing else meanwhile

A bounded queue makes you choose between dropping work, which is rejection, and slowing the producer down until it stops outrunning you. The second one is what "back-pressure" means, and it is exactly what CallerRunsPolicy does by making the submitter do the work itself.

An unbounded queue refuses the choice and pays in heap. Executors.newFixedThreadPool uses an unbounded LinkedBlockingQueue. Under sustained overload it accepts everything, latency climbs without limit, and the process eventually dies of OutOfMemoryError having never rejected a single task. A queue never creates throughput. It only decides who waits.

Which four failures never show up in a simulator?

9 · The exception nobody saw. Safety is lost, silently. executor.submit(task) catches any exception the task throws and stores it in the returned Future. If you never call future.get(), the exception is gone. No stack trace, no log line, and the worker thread quietly picks up the next task. Half your pipeline stops working and nothing is logged. [JVM rule, not this lab's model — AbstractExecutorService.submit wraps in FutureTask.]

Cure it by using execute() when you do not need a result, so uncaught exceptions reach the thread's uncaught-exception handler. Or always consume the Future. Or wrap every task body in try/catch-and-log.

10 · Cancellation ignored. Thread.interrupt() does not stop a thread. It sets a flag, and it causes blocking calls such as sleep, wait and take to throw InterruptedException. A catch (InterruptedException e) {} that logs and continues destroys the only evidence that cancellation was requested, because the flag was cleared when the exception was thrown.

Cure it by choosing one of two moves: either rethrow, or restore the flag with Thread.currentThread().interrupt() and return. Then shutdownNow() works. structured-concurrency's cooperative cancellation is built entirely on this, which is why that lab stressed that cancellation flows down and that side effects do not roll back.

11 · ThreadLocal in a pool. Pool threads live forever, so a ThreadLocal set during request 1 is still set during request 5000. That leaks user context between unrelated requests, and it pins the object it holds for the lifetime of the pool. Cure it by removing it in a finally, or by using ScopedValue, whose entire design is this bug's autopsy. Your scoped-values lab called these the write-from-anywhere and lifetime-until-remove diseases. This is where they bite.

12 · Unsafe publication. Writing a reference into a shared field publishes the reference. Without a happens-before edge, another thread may see the reference and not see the object's fields as initialised. Cure it by publishing through a volatile field, an AtomicReference, a lock, a final field set in the constructor, or a static initialiser. This is java-memory-model territory, and the Publication and DoubleCheckedLocking experiments in that lab are exactly this failure.

12. What does a lock actually promise, and what does it cost?

In one breath: Taking the key promises you four things and refuses you five. Learn the refusals. Almost every surprising bug in this area is somebody assuming one of the five.

What does taking the key actually promise?

Ana holds the key to the stockroom. Engineers say she has acquired monitor M. Here is everything she is owed, and nothing more.

  • No other thread executes any block synchronized on M while she is inside.
  • Everything written by any thread before its release of M is visible to her.
  • The monitor is released on every exit path, including exceptions and thread death.
  • It is reentrant. The thread already holding M can acquire it again, so a synchronized method calling another one on the same object does not self-deadlock.

What does the key explicitly not promise?

  • Fairness. No promise about who enters next. Ben can be passed over repeatedly. Barging is permitted, and it is what makes uncontended locks fast.
  • Any protection from threads that do not take M. The guarantee is per-lock. A reader that skips the key gets nothing, no matter how careful the writers are.
  • Progress. Nothing prevents deadlock, livelock or starvation.
  • Ordering across different locks. Two monitors give you no relationship at all.
  • Atomicity of anything larger than the block. Two correctly synchronized calls in a row are two atomic operations, not one.

🔮 Predict: A cache is a ConcurrentHashMap, which is genuinely thread-safe. Ben writes if (!map.containsKey(k)) map.put(k, v). Both calls are individually atomic. Is the pair safe?

Reveal

No. Ana can slip between the two calls, exactly as she slipped between a read and a write in section 2. Both of Ben's calls succeed. The invariant he meant to hold was "this key is loaded at most once", and nothing ever protected it.

If you guessed yes, you have merged two ideas that must stay apart: thread-safe per call and thread-safe per business operation. That is why putIfAbsent and compute exist. They make the whole decision one operation.

What are the three ways to be thread-safe?

In order of preference, because the first two require no reasoning at all.

  1. Do not share. Confine the state to one thread: a local variable, a ScopedValue, one owning actor. No sharing, no race, nothing to prove.
  2. Do not mutate. An immutable object, with all fields final and no setters, is safe to share with everyone, forever, with no synchronization. That is why String, Integer and records are safe.
  3. Synchronize. Only when you actually need shared mutable state. Then pick one lock per invariant, document it, and hold it for every access — read and write.

Ana and Ben never needed the third option. A per-worker tally added up at the end is option 1. A whiteboard nobody rubs out is option 2.

How urgent is each incident?

A safety failure means data is already wrong, and no amount of waiting fixes it. A liveness failure means nothing is wrong yet, but nothing will progress. That distinction sets the severity.

If the failure is… Which ones What it means for you
safety 1, 6, 9, 12 already corrupted; a data problem you may have to reconstruct
liveness 2, 3, 4, 5, 7, 10 nothing corrupted; a deadlocked pool is an outage you can restart out of

What does locking cost you?

Every critical section is a serial section. Only one worker is in the stockroom, however many workers you hire. If a fraction s of the work must be serial, then no matter how many cores you add, the speed-up is capped at 1/s. That is Amdahl's law.

The pool sweep shows the benign version of the same ceiling, with no lock in sight at all. Twelve five-tick tasks, one to six workers. The makespans run from 60 ticks with one worker down to 10 ticks with six.

Note the shape. Four workers and five workers both finish at 15, because a task cannot be cut in half. Adding capacity stops helping long before the graph looks full, and locks make that ceiling arrive much sooner.

13. What does all this look like from an on-call rotation?

What is the chain from this lab to a real service?

How many workers should the pool have?

🔮 Predict: You have an 8-core box. Each task waits 90 ms on a network call and computes for 10 ms. You want the cores busy. How many threads do you want in the pool?

Reveal

About 80. The formula is below, and the intuition is that each thread is only working one tenth of the time, so you need ten of them per core to keep one core busy.

If you guessed 8 or 9, you applied the CPU-bound rule to I/O-bound work, and your cores would sit idle at 10% utilisation. If the number 80 makes you uncomfortable, that discomfort is exactly what pushed a generation of engineers into reactive frameworks, and exactly what java-virtual-threads removed.

  • CPU-bound work: threads ≈ number of cores (Runtime.availableProcessors()), plus one. More threads add context switches, not throughput. The sweep in section 12 is this case: past the point where every task has a worker, extra workers finish nothing sooner.
  • I/O-bound work: threads ≈ cores × target utilisation × (1 + wait / compute). A task that waits 90 ms and computes 10 ms has a ratio of 9, so an 8-core box targeting full utilisation wants roughly 80 threads. That is precisely the number that used to force people to a reactive framework, and precisely what java-virtual-threads made unnecessary.
  • Always bound the queue. An unbounded queue converts overload into OutOfMemoryError instead of into back-pressure. Choose deliberately between rejection and CallerRunsPolicy; the pool tab lets you feel the difference between 10 rejections and 0 rejections with a throttled submitter.
  • Name your threads. Executors.newFixedThreadPool(n, namedFactory("payments-")). This costs nothing, and it is the difference between a readable thread dump and an unreadable one at 3 a.m.
  • Separate pools per dependency. One pool per downstream service means a slow dependency starves only its own pool, which is the bulkhead pattern. One shared pool means a slow dependency takes the whole service down.

Where does Ana's story go next?

Everything in this document exists because a platform thread is expensive and blocking it wastes it. That single fact forced pools. It forced bounded queues. It forced the whole reactive-programming detour, and it forced you to think about pool sizing at all.

java-virtual-threads removed that fact. A virtual thread's stack lives on the heap, so blocking parks it and frees the carrier. Waiting becomes nearly free, and Executors.newVirtualThreadPerTaskExecutor() makes "a thread per task" sane again at 100k concurrency. Two things carry over exactly, and both are worth stating plainly.

  • Every bug in this lab still happens on virtual threads. Same memory model, same locks, same lost updates, same deadlocks. Ana and Ben are cheaper to hire and they still lose the box. Cheap threads changed the cost of waiting, not the rules of sharing.
  • Pool starvation deadlock, failure 7, genuinely goes away when there is no pool to starve. That is the strongest single argument for the model. But CPU-bound work still needs a bounded pool. And pinning brings the old ceiling straight back, whether from native frames or from synchronized before JDK 24 and JEP 491. That is why that lab flagged it.

And structured-concurrency is what you use instead of raw threads once they are cheap. Fork subtasks into a scope, join by a policy, and leaving the block guarantees nothing is left running. Read that lab's "close guarantee" again now. It is a direct answer to failure 10 in this lab, the thread you asked to stop that never stopped.

Which pairs of ideas keep getting merged?

Five commonly confused pairs, one sentence each, and every one of them has cost somebody a weekend.

  • Concurrency versus parallelism. Concurrency is structuring a program as independent tasks so they can make progress in overlapping periods. Parallelism is actually executing things simultaneously on multiple cores. You can have concurrency on one core, and all of this lab's bugs with it. You can have parallelism with no shared state, and none of them.
  • Concurrency versus asynchrony. Async means "do not sit on a thread while waiting". It is a way to spend fewer threads, not a way to avoid races. Two async callbacks touching the same field race exactly like Ana and Ben.
  • volatile versus synchronized. volatile makes individual reads and writes visible and ordered. synchronized additionally makes a sequence of them indivisible. If your operation is read-modify-write, volatile is not enough.
  • Atomic versus thread-safe. ConcurrentHashMap is thread-safe, and a containsKey followed by a put on it is still a race. Thread-safe per call is not thread-safe per business operation.
  • BLOCKED versus WAITING. BLOCKED means queuing for a monitor somebody holds, so it will run when they leave. WAITING means deliberately asleep in a wait set, so it runs only if someone signals. In a thread dump these mean completely different things: fifty BLOCKED on one monitor is a convoy, and fifty WAITING is usually normal.

Solutions — multithreading in Java

Worked answers. Rungs 7 and 8 are design discussions, not single correct outputs — compare shape and reasoning, not wording. Figures cited as verified come from ./validate-visualization.sh (42 engine checks + 12 render checks, all passing).

Rung 1 — Explain

1.1 Each person's job is really three separate trips: read the number, change it at their own desk, come back and write it. If the second person reads before the first one writes, both of them are working from the same starting number, and the second write simply covers the first. Nobody made a mistake; the tally is wrong anyway.

The key on the door changes which sequences of events are possible: it deletes the ones where the second person reads while the first is mid-job. It does not make the three trips into one trip, and it does not make anyone faster. Everything is still three trips — there just can no longer be a second person in the middle of them.

1.2 "You fixed whether other threads can see the value, which was a real problem. You did not fix that count++ is a read, an add and a write with a gap between them — two threads can both read the same number and both write the same result, and volatile allows that." Their instinct is exactly right for a flag one thread writes and others only read, which is scenario 2 — there is no read-modify-write, so there is no gap to protect.

1.3 Safety: nothing incorrect ever happens. Liveness: something correct eventually happens.

  • Lost update — safety. Waiting cannot help; the data is already wrong.
  • Deadlock — liveness. Waiting cannot help either, but nothing is corrupted; a restart recovers fully.
  • Buffer at −1 — safety. An invariant is broken.
  • Missed stop flag — liveness. Nothing is wrong, nothing will ever progress.

The pattern worth keeping: waiting never fixes either kind. The difference is what you have to do afterwards — a liveness failure needs a restart, a safety failure needs a reconstruction.

Rung 2 — Identify

2.1 After A, B, A: count in memory is 0; A's r is 1; B's r is 0. count is a field, so it lives on the heap and every thread can reach it. Both rs are local variables, so they live on their thread's own stack — there is one r per thread, and neither thread can see or affect the other's. That is why the visualization draws them inside the thread cards and count outside them.

2.2 buffer is held by nobody (both consumers gave the lock back when they called wait()); the entry set is empty; the wait set holds both consumers.

The two ways out are different in kind, and this is the point of the question:

  • To leave the wait set, a consumer needs another thread to call notify or notifyAll. Nothing it does itself can help. Time passing does not help.
  • To leave the entry set (where it lands after being notified), it needs only the lock to become free. That happens on its own as other threads finish.

WAITING depends on someone else's cooperation; BLOCKED resolves itself.

2.3 Thread B is disabled because Thread A owns the lock monitor, so B is BLOCKED — and a blocked thread cannot execute any instruction at all, so there is no "one step of B" to run. It becomes enabled the moment the Locks panel shows lock held by nobody, which happens when A executes its UNLOCK.

2.4 The two places are (a) the Shared memory panel, which reads stop = true, and (b) the Worker's private copy row, which reads stop = false — memory says true. Together they show the write completed before the read, and the read still returned the old value. A timing failure would require the read to have happened first; here it did not. Verified: memory holds true, the worker has looped 13 more times, and every read returned false.

Rung 3 — Predict

3.1 {1, 2, 3}. Highest, 3: each thread runs to completion before the next starts — every write is based on a fresh read. Lowest, 1: all three read 0, all three compute 1, all three write 1. Two increments vanish. There is no way to reach 0 (someone writes at least 1) or 4 (nobody ever writes more than what they read plus one).

3.2 Both threads attempt their second LOCK, both are refused, and neither program counter moves. Final state: Thread A BLOCKED on accountB; Thread B BLOCKED on accountA; accountA held by A with B in its entry set; accountB held by B with A in its entry set; nothing RUNNABLE. Verified: run = STUCK, both threads BLOCKED, and each monitor owned by the thread the other one wants.

3.3 If the producer runs first, items is already 1 when the consumers arrive, so neither consumer ever calls wait() — the if/while distinction never comes into play. Consumer 1 takes the item (items 1 → 0). Consumer 2 finds items == 0 and goes to sleep, and stays asleep because the producer has already finished. Final items = 0 in both versions, with one consumer WAITING.

The surprise for most people is that the buggy version looks perfectly correct here. That is the actual lesson: the if bug is invisible on the schedule where the producer is early, and appears only when both consumers sleep first. The bug is in the set of permitted schedules, not in the code you can point at. Verified: the schedule where both consumers sleep first gives items = -1 with if and items = 0 with while.

Second thing to notice: run the producer before anyone sleeps and the log says "called notifyAll() and woke nobody" — verified. The notification was discarded, and it did not matter, because the condition (items == 1) was still true when the consumers looked. The condition is the truth; the signal is a nudge.

3.4 3 workers → finishes at tick 20. 5 workers → finishes at tick 15.

The naive formula (total work ÷ workers = 60/W) predicts 20 for three workers, which is right, and 12 for five workers, which is wrong. Tasks cannot be split: with five workers, the twelve tasks run in three rounds of at most five, so the makespan is 5 ticks × ceil(12/5) = 15. The fifth worker sits idle for the whole final round. Verified across the sweep: 60, 30, 20, 15, 15, 10 for one to six workers — note that four and five workers finish at the same tick.

The practical version of this: capacity you add stops buying anything well before the utilisation graph looks full.

3.5 Thread B's compare-and-set returns false — it expected 0 and memory holds

  1. B does not block and does not lose its increment; it loops back, re-reads (getting 1), computes 2, and its second compare-and-set succeeds. Total attempts: 3 (A once, B twice). Verified: final count 2, casFail = 1, retries = 1, and no thread ever entered BLOCKED.

Rung 4 — Modify

4.1 Without the lock and under the interleaving A, B, A, A, B, B the final count is 1 — verified. With the lock back on, you cannot drive that interleaving at all: after A's first step it holds the lock, so B's button is disabled, and there is no sequence of button presses that puts B between A's read and A's write.

"The lock made it slower" is the wrong description because nothing was slowed. The same six instructions execute. What changed is the set of executions that exist: the interleaving that produced 1 is not a legal execution of the locked program. Verified exhaustively — enumerating every possible schedule of the locked version produces 2 every time.

4.2 The four conditions are mutual exclusion, hold-and-wait, no preemption, and circular wait. Ordering attacks the last one, and only the last one — the other three are all still true after the fix.

Why ordering is sufficient: a cycle requires at least one thread holding a higher-ranked lock while requesting a lower-ranked one. If every thread acquires in ascending order, no thread ever does that, so no cycle can be drawn. Whoever gets accountA will eventually get accountB, because everyone waiting for accountB either already holds accountA (only one thread can) or is not holding anything above it. Verified: with ordering on, the same code completes.

4.3 With volatile on, the private copy row stays empty — there is never a private copy of stop to be stale, because every read goes to memory. Verified: the worker terminates.

A synchronized block around the read would also work: acquiring the monitor discards private copies, so each iteration re-reads from memory, and the writer must use the same lock. The cost is that you now take and release a lock on every loop iteration — far more expensive than a volatile read, and it introduces a lock where none is needed. volatile is the right tool precisely because this is a single read of a single field with no read-modify-write. (AtomicBoolean is equivalent here and reads better.)

4.4 Queue 0, no caller-runs: 10 of 12 rejected (verified). With CallerRunsPolicy: 0 rejected, all 12 completed, 4 run by the submitting thread (verified) — and while the submitter is running one, it cannot submit anything else.

  • Choose rejection when losing work is acceptable and latency is not — a metrics ping, a best-effort cache warm, anything with a "shed load" story. You must handle RejectedExecutionException; silently swallowing it is how requests disappear.
  • Choose caller-runs when the work must not be lost and the producer can be slowed — the classic case is reading from a queue or a file, where slowing the reader is exactly right. Do not use it when the caller is an HTTP request thread you are trying to keep responsive: you have just made an inbound thread do arbitrary background work.
  • The third option is an unbounded queue (what Executors.newFixedThreadPool gives you). It never rejects and never blocks the producer — and it buys you unbounded latency and eventually OutOfMemoryError under sustained overload. It does not remove the choice; it defers it until the heap makes it for you.

4.5 With nesting on and 2 workers the pool deadlocks at tick 4 (verified); at 8 workers the identical configuration completes (verified).

That is dangerous because nothing was fixed — the dependency is still "a task blocks on work that needs a worker from the same pool". A larger pool only means it takes more simultaneous parent tasks to consume every worker. Under production load — a traffic spike, a slow downstream that makes tasks last longer, a retry storm — the number of concurrently blocked parents rises, and the pool deadlocks then, at peak, permanently, with no code change to blame. You have converted a deterministic bug that fails in the first test run into a load-dependent one that waits for your worst day. The real fix is structural: a separate pool for sub-tasks, or not blocking at all.

Rung 6 — Spot the flaw

6.1 get() can return a stale value indefinitely, or — for a long/double on a 32-bit JVM, or for a reference published unsafely — a value that never existed.

Concrete run: writer takes the lock, sets value = 42, releases. Reader (no lock) reads value and gets 0. There is no rule broken: the reader has no happens-before edge to the writer's release, so it is permitted to see the old value, and permitted to keep seeing it forever.

The writers' diligence does not help because the guarantee is per-lock and two-sided. Releasing a monitor publishes your writes to threads that subsequently acquire the same monitor. A reader that never acquires it never collects the publication. Violated guarantee: visibility. The cheap fix if get() really is a single field read is to make the field volatile; the correct fix if get() reads two related fields is to take the lock, because otherwise you can see one field's new value and the other's old one.

6.2 Interleaving: thread 1 calls containsKey(k) → false. Thread 2 calls containsKey(k) → false. Both call expensiveLoad(k). Both call put. The second put overwrites the first.

Both calls really are individually atomic; the problem is that the invariant spans both of them — "load exactly once per key" is a property of the pair, and nothing holds any lock between them. This is the same check-then-act shape as count++; ConcurrentHashMap protects its own internal structure, not your business rule. Violated guarantee: the at-most-once loading invariant (and, if expensiveLoad has side effects, you have just done them twice).

Fix: one atomic call — cache.computeIfAbsent(k, this::expensiveLoad), which holds the bin lock across the check and the insert. (putIfAbsent fixes the overwrite but still calls expensiveLoad twice, so it is the wrong choice when the load is the expensive part.)

6.3 Three separate problems with the reasoning.

What is wrong: "thread-safe on x86" is not a thing you are allowed to conclude. The Java Memory Model, not the CPU, defines what is legal, and the compiler is a reordering agent in its own right — the JIT can publish the reference before the constructor's field writes are complete regardless of how strongly ordered the hardware is. x86's store ordering hides the hardware half of the problem and none of the compiler half.

What the reader can observe: a non-null reference to a partially constructed object — fields still at their default values. Worse than a crash, because it looks like valid data.

Why the test evidence is worthless: the failure requires a specific interleaving plus a specific JIT compilation decision that only occurs after enough invocations to trigger optimisation. Laptop and CI runs are short, single-tenant and lightly loaded — precisely the conditions under which it does not reproduce. And most Apple-silicon and Graviton deployments are weakly ordered, so the hardware half comes back in production and not on the x86 CI box.

Measured where: the java-memory-model lab, whose DoubleCheckedLocking and Publication experiments are exactly this. Fix: private static volatile Instance instance; — or, better, a holder class or an enum, which get the guarantee from class initialisation for free.

6.4 This is livelock. Concrete run: threads A and B both need locks X and Y. A gets X, B gets Y. A's tryLock(Y) fails, so A releases X and retries; B's tryLock(X) fails, so B releases Y and retries. They retry in lockstep, each grabbing the lock the other just dropped, forever.

It is harder to diagnose than the deadlock it replaced because both threads are RUNNABLE and the CPU is busy. A thread dump shows threads doing work. Automated deadlock detection reports nothing, because there is no cycle at any instant — the cycle is in the pattern over time. You detect it by taking two dumps a few seconds apart and noticing the same stacks are still churning with no progress metric moving.

The fix is the one the raft lab used for split votes, for the same reason: randomised back-off before retrying, so the lockstep breaks. Plus a bounded retry count so it eventually gives up loudly instead of quietly.

6.5 At shutdown, shutdownNow() interrupts every worker; each one logs the exception and carries straight on. The pool never terminates, awaitTermination times out, and the deploy hangs or the container is killed mid-work.

The destroyed information is the interrupt flag itself. When a blocking call throws InterruptedException, it clears the flag as it throws — the exception object is the only remaining record that cancellation was requested. Catching it and continuing throws away the sole copy, so every later check of Thread.currentThread().isInterrupted() says "nobody asked me to stop".

Two-line fix:

} catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // put the evidence back
    return;                               // and actually stop
}

This is precisely the mechanism structured-concurrency's cooperative cancellation is built on, which is why that lab insisted cancellation is cooperative and cannot be imposed.

Rung 7 — Handle failure

7.1 — The lock held across HTTP.

What happens. Thread 1 enters, holds the monitor, and blocks in a socket read for 30 s. Threads 2…51 arrive, hit the same synchronized, and go to BLOCKED in the monitor's entry set. They are not doing work and not consuming CPU. Every request now takes up to 30 s, and the pool is exhausted, so even requests that never touch this code are rejected or queued behind it. One slow dependency has become a total outage.

What the graphs show. Latency vertical; CPU near zero; error rate initially calm, then a cliff when the pool queue fills. The near-zero CPU is the diagnostic signature — a busy service looks busy, a blocked one does not.

What a thread dump shows. Fifty threads in BLOCKED (on object monitor) all waiting on the same lock identity, and exactly one thread in RUNNABLE inside SocketInputStream.read. That single thread is your answer and the dump names it.

Why more threads make it worse. They all queue on the same monitor. You have added memory and context switches and zero throughput — the serial section is the ceiling, which is Amdahl's law with a very unfriendly s.

The redesign. Shrink the critical section to the state transition only:

  1. Under the lock: check the order is in a legal state and mark it PENDING, then release.
  2. Outside any lock: call the provider, with a timeout — a call with no timeout is the actual root cause and must be fixed regardless.
  3. Under the lock again: apply the result.

The invariant to be careful about. Between steps 1 and 3 the order is observable in a half-finished state by other threads. You must ensure PENDING is a state the rest of the system understands and refuses to double-process — which means the state machine, not the lock, is now carrying the safety property. That is the same conclusion distributed-locking reached: the guarantee has to live at the resource, and the lock is only an optimisation on top.

7.2 — Bounded buffer, many producers, many consumers.

Producers wait while count == capacity; consumers wait while count == 0. Both wait on the same monitor guarding the buffer. Both signal after changing count.

Why notifyAll() becomes essential once both kinds share one monitor: notify() wakes one arbitrary thread from the wait set, and the wait set contains both producers and consumers. A producer finishing can wake another producer, which re-checks, finds the buffer still full, and goes back to sleep — while the consumers that could have made progress are never woken. The signal is consumed and lost, and the system can wedge with work available and everybody asleep. notifyAll() wakes everyone; the while loops send the wrong ones back to sleep harmlessly.

The cheaper structural fix is two Condition objects on one ReentrantLock (notFull, notEmpty), so you can signal precisely the right group — this is the main reason Condition exists and synchronized's single wait set is a limitation.

And the answer you should actually give in a code review: use ArrayBlockingQueue. It is this design, correct, tested, and with put/take that cannot miss a signal. Hand-rolling it is how the if/while bug gets written.

7.3 — Catching pool starvation.

Monitoring rule. Alert when, for a sustained window (say 60 s): active threads = pool size AND queue depth > 0 AND completed-task count is flat. Any two of those are normal saturation; all three together mean nothing is finishing while everything is occupied, which is the signature of blocked-not-working. Add the strongest single signal: queue wait time rising while execution time is flat — that separates "the dependency got slow" from "the workers are not running".

Prevention. A rule with a name: a task may not block on a future produced by its own executor. Enforce it structurally — sub-work goes to a different, explicitly named pool, and the two pools' names encode the layering.

What a reviewer greps for. .get(, .join(, .invokeAll(, .parallelStream() and CompletableFuture.…().join() inside anything submitted to an executor — especially parallelStream(), which silently uses the shared ForkJoinPool.commonPool and therefore can starve code you have never read.

7.4 — The ThreadLocal that outlived the request.

Symptom. A customer occasionally sees another tenant's data. It is a security incident, not a bug report.

Why intermittent. It requires the exception path, followed by that specific pooled thread being reused for a request that reads the value before setting it. Under low load the pool is large relative to traffic and reuse is rare; under high load it is constant.

Why worse than a crash. A crash is loud, local and self-limiting. This returns a plausible, well-formed, wrong answer, and every downstream system treats it as genuine — it propagates into caches, logs, exports and audit trails, and the blast radius keeps growing after the original bug is fixed.

Fix 1, keeping ThreadLocal: set it in a try and clear it in a finally in a single filter that wraps everything, so no application code can skip it. finally runs on the exception path; "at the end of the handler" does not.

Fix 2, removing the class of bug: ScopedValue.where(TENANT, id).run(...) — the binding is immutable, it is scoped to the block, and it is unbound on every exit path including exceptions, because unbinding is the runtime's job rather than yours. Your scoped-values lab called ThreadLocal's two diseases write-from-anywhere and lifetime-until-remove; this incident is the second one, and finally is the manual discipline ScopedValue replaces with a guarantee.

Rung 8 — Design

8.1 — The payments worker. A defensible answer.

Pools — three, not one. One per provider (the bulkhead), so provider C's 3-second timeouts cannot consume the threads that talk to A and B. A single shared pool means C's bad day is an outage for all three.

Sizing. Each call waits ~200 ms and computes ~5 ms, so wait/compute ≈ 40. The I/O-bound formula cores × utilisation × (1 + wait/compute) gives 8 × 1.0 × 41 ≈ 328 threads to saturate 8 cores. That number is the point of the exercise: it is absurd on platform threads (~328 MB of reserved stack, heavy scheduling) and it is exactly why people historically went reactive. Choose deliberately: cap each pool at something you can actually afford (say 48 per provider, 144 total), accept that you will not saturate the CPU, and let the queue absorb bursts. Give provider C's pool a smaller cap and a shorter queue than A and B — you want its failures contained, not buffered.

Queues. Bounded, always. Capacity ≈ a few seconds of arrival rate, so a brief downstream hiccup is absorbed and a sustained one is refused rather than silently buffered into unbounded latency.

Rejection. Not AbortPolicy with a swallowed exception, and not caller-runs (the caller is a queue consumer whose job is flow control — making it run a 200 ms provider call destroys that). Reject, and on rejection negatively-acknowledge the message back to the source queue so it is retried later by whoever has capacity. The source queue is the buffer; the in-process queue must not try to be one.

Shared mutable state, and how each piece is protected.

  • Per-payment status: not shared — confine each payment to one task. This is option 1 from stage 12 and it removes most of the problem for free.
  • The de-duplication record ("has this payment been sent?"): shared, and it is the one that must be right. Protect it with a conditional write in the database (a unique constraint on the instruction id, or UPDATE … WHERE status = 'NEW' with the update count as the witness) — not an in-JVM lock, because a JVM lock protects nothing against the second instance of your service.
  • Metrics counters: LongAdder, not synchronized — high write contention, reads only at scrape time, which is precisely what LongAdder is for.
  • Provider clients and config: immutable, built once at startup, shared freely.

Locks held across a network call: none. The dedup check is a single database statement; the provider call happens with nothing held. Write that down explicitly in review, because it is the failure that causes outages (rung 7.1).

Shutdown, inside 30 s. Stop consuming from the source queue first; then shutdown() each pool (not shutdownNow() — let in-flight payments finish); awaitTermination(20s); then shutdownNow() and log whatever is still running by name. Every provider client must have a request timeout shorter than that budget, or the drain cannot possibly meet it. And every worker must handle InterruptedException by restoring the flag and returning (rung 6.5), or shutdownNow() does nothing.

Dashboard — five things. Per pool: active threads, queue depth, rejection rate, and task latency split into queue wait versus execution time; plus end-to-end duplicate-send count from reconciliation. The wait/execution split is the one that tells you whether to add capacity or to fix the dependency.

What java-virtual-threads deletes. The sizing arithmetic and the three pool caps go away: Executors.newVirtualThreadPerTaskExecutor() and one task per payment, with 328 concurrent waits costing almost nothing. Failure 7 (pool starvation deadlock) becomes impossible because there is no pool to starve.

What survives unchanged. All of it that matters: bounded admission (you still must not accept unbounded work — the bound simply moves from a queue to a semaphore or to the source queue's prefetch), the dedup conditional write, "no lock across a network call", timeouts on every call, interrupt handling, and the bulkhead — provider C can still exhaust a shared downstream resource such as a connection pool. Cheap threads changed the cost of waiting, not the rules of sharing.

8.2 — 12 duplicates in 40 million.

Candidates, each with the observation that settles it:

Mechanism Confirming / eliminating observation
Lost update on a status flag (two threads both read NEW, both send) Is the send guarded by a conditional write whose update count is checked? If the code does read-then-write with no condition, this is live. If it uses UPDATE … WHERE status='NEW' and checks the count, eliminated.
Retry after an ambiguous timeout (the first send actually succeeded) Correlate duplicate timestamps with client-timeout events on the provider side. Two sends seconds apart with the first timing out points here.
At-least-once redelivery from the source queue Look for redelivery counts / duplicate message ids in broker metrics for those 12.
Two service instances processing the same instruction Are the 12 split across two hosts at the same instant? Host tags in the send log answer it immediately.
Pool task submitted twice on an exception path Is there a retry wrapper and a queue redelivery on the same failure? Count send attempts logged per instruction id.
ThreadLocal/context bleed causing the wrong id to be sent The duplicates would be of different payments with a shared thread, not the same payment twice — check whether the pairs share an instruction id.

What observation alone cannot separate: a lost update and a same-instant double-delivery both look like two sends, same id, same millisecond, different threads. Nothing in the logs distinguishes "both threads read NEW" from "two copies of the message arrived". To tell them apart in future you must record the decision, not just the action: log the update count (or the constraint violation) of the guard write with each send attempt. A send whose guard write matched zero rows and happened anyway is a lost update; two attempts each matching one row means two distinct message deliveries reached the guard.

That instrumentation point is the practical lesson, and it is the same one optimistic-vs-pessimistic-locking reached: the update count is the only witness — a conflicting conditional write is not an error, it is an UPDATE matching zero rows, and if you do not check it you cannot tell the difference afterwards.

And the argument that the fix does not belong here at all: idempotency says stop trying to make the send happen exactly once — make it safe to happen twice. Give every instruction a key the provider deduplicates on, and all six mechanisms above become harmless. Locking reduces the probability of a duplicate; idempotency removes the consequence. The first is a race you can lose, the second is arithmetic.

8.3 — The same problem at three scales.

Identical at all three. The shape is always read, decide, write, with a gap in the middle that the writer cannot see into, and a second party whose write lands in that gap. In every case the losing write is not detected by anything: no exception, no error, no log. And in every case the cure is one of exactly two things — make the gap impossible to enter (a lock), or make the write conditional on what you read (a version, a compareAndSet, an If-Match).

Genuinely different. The size of the gap and therefore what is affordable inside it. Between registers the gap is nanoseconds, so blocking is cheap and a lock is the obvious answer. Between transactions it is milliseconds and the gap contains I/O, so holding a lock starts costing other people throughput (optimistic-vs-pessimistic-locking's lunch: 0 saves and 15 lock timeouts for the neighbours of one 2-second pause). Between HTTP requests the gap contains a human — seconds to minutes — and no lock is tolerable at all, so the conditional write is the only option.

Why in-JVM can use a plain lock and cross-machine cannot. Because a JVM lock rests on a fact the network destroys: the runtime knows when a thread has died, so it can release its monitors. Across machines, death and slowness are indistinguishable from outside — silence is the only evidence and it has two meanings needing opposite responses. So a distributed lock must be a lease with a TTL, which immediately creates the stale holder: a process paused longer than its TTL wakes up still believing it holds the lock.

What the distributed version must add. A fencing token — a strictly increasing grant number checked on every operation at the resource, so a stale holder's writes are refused. Note what that admits: fencing does not restore mutual exclusion — two holders still exist — it makes the overlap harmless by refusing stale effects. The safety comes from arithmetic (the token comparison, which has no timing assumptions); only the liveness comes from the timeout. Which is the same shape as the third scale's conditional write, and the same shape as compareAndSet at the first — one primitive wearing three costumes.
