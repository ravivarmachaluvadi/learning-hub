Lab 13 · One Machine, Done Right

Redis — the database that does one thing at a time

Tell a friend: Twenty children need to change the same jars of sweets all day long. When Arjun and Bina reach for the samosa jar at the same moment, one sale quietly disappears and nobody is told. So the school puts Meera behind a counter, and nobody is allowed to touch a jar again. You shout what you want done, Meera does the whole thing alone, and only then does she listen to the next child. That one rule is Redis, and the same sentence gives you its best promise and its worst outage.

1. Why can't twenty machines just share one number?

In one breath: Some facts change every second and are needed by every machine at once. Keep such a fact in one machine's memory and the other nineteen cannot see it. Put it in your main database and every touch pays for permanence you never asked for.

Asha runs an online tuck-shop business. Her application does not run on one machine. It runs on twenty, behind a load balancer, and any request can land on any of them. Priya's click lands on server 3. Omar's click lands on server 17. Neither of them chose.

Most of the time that is fine, because most facts live in the database. A customer's address does not change while you are reading it.

But some facts are shared, change constantly, and are needed in microseconds. Read the middle column of this table: it is what makes each of these facts different from an address.

The fact Asha needs Why it cannot sit on one server What goes wrong if it does
how many requests this API key made in the last minute all twenty servers must count into the same total the limit is enforced twenty times over
what is in this shopper's basket the shopper's next click lands elsewhere the basket looks empty on the checkout page
which worker currently owns this job whoever claims it must be visible to the rest two workers do the same job
who is in the top ten this week every score changes the same ordered list ten different leaderboards, one per server

So put those facts in one place. Which place?

Put such a fact in one server's memory and the other nineteen cannot see it. That is not a subtle failure. Server 3 counts, server 17 does not, and the number is wrong by a factor of twenty.

Put it in the main database instead and something slower goes wrong. Every read and every write now travels through machinery built to make facts permanent and correct forever. Indexes. Transactions. Row locks. Disk flushes. None of that is what Asha needs here, and all of it is exactly what makes the trip slow. Worse, under contention those row locks make her twenty servers queue up behind each other. The database was protecting her from a problem she did not have, and charging her for it on every operation.

If nobody solves this, you get the concrete failures you have already met. A rate limiter that lets through twenty times its limit. A shopping basket that loses an item when two tabs are open. A job picked up twice by two workers.

Redis is the thing that fills that hole. What follows is how. More usefully, it is also what that costs.

2. What does the tuck shop need that a cupboard cannot give?

In one breath: Three jars, twenty children, and constant change. The jars must be somewhere everybody can reach, and reaching them must take a second rather than a minute.

Forget servers for a while. A school has a tuck shop. Along one wall stand labelled jars:

  • a jar holding one number — how many samosas have been sold today
  • a jar holding tokens in the order they were dropped in — the queue for the sandwich toaster
  • a jar holding names with scores — this week's chess ladder

Twenty children need to change what is in those jars, constantly, all day. Arjun sells a samosa and the count must go up. Bina joins the toaster queue. Chetan wins a chess game and their score must go up by one.

Two demands come out of that, and they pull in opposite directions.

The jars must be in the room where everyone can reach them. A jar in the staff room, behind a locked door, is a jar nobody can use during break.

And getting to them must take a second, not a minute. If Arjun has to fill in a form to touch the samosa jar, he will stop counting samosas.

Hold on to those three jars. Every mechanism in this lab is something that happens to one of them.

3. What does a reasonable person try first?

In one breath: Open shelves. Anybody walks up, takes a jar down, changes it, puts it back. It is fast, simple, and everybody can do it at once.

No counter. No shopkeeper. No rules.

Arjun walks up, takes the samosa jar down, changes what is inside, and puts it back. So does everybody else, whenever they like.

This is fast. It is simple. Everyone can do it at once, so nobody waits.

It is also exactly what your code does every single time it reads a value from a shared store, changes it in your own process, and writes it back. Read, modify, write. Three separate moments, and the store has no idea they were meant to belong together.

4. Why does the open shelf lose a sale?

In one breath: Two children read the same number, both add one to what they read, and both write back the same answer. One of the two sales is gone, and no error is ever raised.

Arjun and Bina each sell a samosa at the same moment. The jar says 5.

🔮 Predict: two samosas were sold. What does the jar say, and who finds out that anything went wrong?

Reveal

The jar says 6. One sale has vanished.

And the answer to the second half is the genuinely alarming part: nobody finds out. There is no error, no exception, no conflict, no log line. Both children did exactly what they were told to do and both believe they succeeded. The only evidence is that the number is quietly wrong, and it will stay quietly wrong forever.

This is called a lost update, and you met it in the distributed-rate-limiting lab as the reason twenty uncoordinated gateways turn "100 per minute" into 2,000 per minute.

So the school reaches for the obvious fix. Put a padlock on the shelf. A child takes the key, does their business, and returns the key. Now nothing is lost, because only one child can be at the shelf at a time.

Look at what the padlock cost, though. Three separate bills arrive.

  • Three trips instead of one. Get the key, read-and-write, return the key. If the shelf is across a field, you just tripled the walking.
  • One child at a time, for the whole shelf. Bina wants the chess jar and Arjun has the samosa jar. Irrelevant. There is one padlock, so Bina waits for a jar she does not care about.
  • A child who takes the key and goes home stops the shop forever. Somebody must now decide how long is too long to hold a key, and be wrong about it. You saw this exact shape in two-phase-commit: after voting yes, a participant holds its locks and cannot decide alone if the coordinator dies.

So the padlock trades one silent bug for three loud problems. That is not nothing. A loud problem is better than a silent one. But we can do better than either.

5. What exactly must we guarantee?

In one breath: No change may ever vanish, nobody may have to hold a key or walk three times, and the whole thing must be about as quick as shouting across a room.

Before any solution, state the target plainly. This is the promise the rest of the lesson is chasing.

Any of the twenty children must be able to change a shared jar such that (a) no change can ever be silently lost, (b) the child does not have to hold a key or make three trips, and (c) the whole thing takes about as long as shouting across a room.

Everything in the rest of this lesson is the pursuit of those three, for Arjun, for Bina, for Chetan and for Asha's twenty servers. And every strange detail of Redis's design is a scar from something that went wrong on the way.

6. What if nobody is allowed to touch the jars?

In one breath: Put one shopkeeper behind a counter. Children shout what they want done. She does the whole thing alone and finishes before she listens again, so there is no gap for anybody to slip into.

Meera stands behind a counter. The jars are behind her. The children never touch a jar again.

Instead Arjun shouts an instruction: "add one to the samosa jar." Meera does the whole thing alone. She takes the jar down, reads 5, writes 6, puts it back, and calls out "6". Only then does she turn to the next child.

Bina is next in line, and she shouts the same instruction. Meera reads 6 and writes 7. Two sales, two increments, no loss. Nothing clever happened. Bina simply could not read the jar while Meera was holding it, because Bina is not allowed to hold jars at all.

Two separate inventions are hiding in those paragraphs, and it is worth pulling them apart, because people usually only notice the first.

The first is that the instruction says what you want done, not "give me the jar". That is only possible because Meera knows what kind of thing is in each jar. You can say "add one" about the samosa jar and "add a token to the end" about the queue jar, and she knows which of those makes sense where.

The second is that there is exactly one Meera, finishing each instruction before starting the next.

The second one is what makes Arjun and Bina's lost sale impossible. Not a padlock. An absence of simultaneity. There is no gap between the read and the write for anyone to slip into, because during that gap Meera is not listening to anyone.

This is Redis. Everything else in this document is a consequence of that sentence, including all the bad parts. Hold that thought, because in section 11 you will watch the same sentence cause the most common Redis outage there is.

7. What are these things called, now that you have felt them?

In one breath: Six words, and you have already met the thing each one names. A store with one way in, jars in the room rather than the basement, one shopkeeper, an instruction nobody can interrupt, jars whose kind is known, and the cost of shouting.

You have earned all of these. Each one names something that already happened to Arjun, Bina, Chetan or Meera. So each gets the story first, the plain sentence second, and the real name last.

What is a key–value store?

The wall of jars is a very large box of labelled things. You put a thing in under a name. You get it back by that name. That is the entire arrangement.

In plain words: the only way in is the label. Engineers call the label the key and the thing the value, and a store built this way a key–value store. Its only index is the primary key. There is no query planner, no WHERE, no join. GET user:42 is the entire query language.

The word exists to mark the contrast with a relational store, which lets you ask questions the designer never anticipated. That flexibility is not free, and a relational store pays for it on every single operation. A key–value store gives it up on purpose. The database-landscape lab called this "an opinionated bet on one access pattern". Redis's bet is "you already know the key."

You can see the bet in two lines. SET cart:7 "3 items" puts the basket in. GET cart:7 takes it out. There is no way to ask "which carts have 3 items" without looking at every key, one at a time.

Why does "in-memory" change everything else?

The jars are on the shelf in the room. They are not in the basement warehouse. Arjun can reach one while he is still talking to a customer.

In plain words: the whole working set of data lives in the machine's fast memory. Engineers call that in-memory, and they mean it strictly. The disk is used only to recover after a restart. It is never used to serve a read.

That is the sharpest difference from every disk-based database, and it is worth saying the contrast precisely. Postgres keeps a cache in memory and the truth on disk. Redis keeps the truth in memory and a recovery record on disk. Those are opposite arrangements of the same two parts.

Two consequences follow immediately. Redis is fast because nothing waits for a disk. And your dataset must fit in memory, which is why "how much RAM" is the first question anybody asks about a Redis deployment.

The caching lab taught that a cache is a bounded copy whose truth lives elsewhere. So here is a correction worth carrying: Redis is not, by definition, a cache. It is frequently used as one. It can equally be the source of truth for data you would be very sad to lose. Which of the two it is for you is a decision you make, not a property of the software. You make that decision by choosing the persistence and eviction settings you will meet in section 11.

What does "single-threaded" actually claim?

One Meera. One instruction at a time. Each one finished before the next begins.

In plain words: all commands run on one worker, each running to completion before the next is taken off the queue. Engineers call this single-threaded command execution, and every word of that phrase is load-bearing.

The careful part is command execution, and the precision matters. "Redis is single-threaded" is the most over-simplified sentence in the field. Modern Redis uses other threads for several jobs. Flushing to disk. Freeing very large values. Since version 6, optionally, reading and writing sockets. What has never been parallel, and is the thing actually being claimed, is the part that touches your data.

You built the machinery for this already. In io-multiplexing you learned how one thread can serve thousands of connections by handing the whole set to the kernel and sleeping until something is ready. Redis is that lesson applied to a database. The same epoll or kqueue loop you built, with a hash table behind it.

Which "atomic" does Redis mean?

Meera's increment either fully happened or it did not. Nobody ever saw the samosa jar mid-count.

In plain words: while one instruction is being carried out, no other instruction can look at the half-finished state. Engineers call that atomic, and here the word means something narrower than you may expect. A single Redis command is indivisible with respect to other commands. No other command can observe or interleave with its intermediate state.

This one genuinely trips people up, because you already know two different things called atomicity. Read the last column: it says what does the work in each case.

what it promises how it is achieved
Redis atomicity no other command interleaves there is one thread
ACID atomicity (databases) all-or-nothing across a transaction, with rollback undo logs
JMM atomicity (java-memory-model) no other thread sees a torn read CPU instructions, volatile, AtomicLong

Redis gives you the first row. It does not give you the second. A Redis "transaction" cannot roll back, which section 12 covers in detail. Confusing those two rows is the single most common Redis mistake in production code.

Concretely: INCR visits reads 5, computes 6, writes 6. Between that read and that write, no other client's command runs. That is the whole guarantee. It is also enough to make Arjun and Bina's lost sale impossible.

Why is "the shopkeeper knows the jar" the whole trick?

Meera knows the samosa jar holds a number and the toaster jar holds a queue. So "add one" and "add a token to the end" are both instructions she can carry out.

In plain words: the server knows what kind of thing each value is. Engineers call that kind the value's data type, and each type has commands that only make sense for it.

This is the whole difference between Redis and a plain cache like memcached. Memcached stores opaque bytes. It has no idea a value is a number. So "add one to the counter" must be get-modify-set inside your client, with exactly the gap that lost Arjun's sale. Because Redis knows the value is a number, INCR can exist as one command, and the gap disappears.

Say that again, because it is the load-bearing sentence of the whole lab. The data types are not a convenience feature. They are the mechanism by which the atomicity guarantee is delivered to you.

Why does shouting cost more than the work?

Arjun's instruction takes Meera almost no time at all. Walking to the counter and waiting for her answer takes far longer than the work itself.

In plain words: the journey there and back dominates. Engineers call one request travelling out plus one reply travelling back a round trip. Sending many requests without waiting for each reply, then collecting the replies in order, is pipelining.

The word matters because Redis commands are so fast that the network dominates, and that reverses the usual intuition about what to optimise. You know the general shape from communication-protocols as round-trip-time dominance. In Redis it is unusually stark. Experiment 3 puts a number on it: 10,000 INCRs took 277 ms one at a time and 12 ms pipelined. Identical commands. Identical server work. The client just stopped waiting.

8. What is really running behind the counter?

In one breath: One process, waiting on every connection at once, running one command at a time against a hash table that lives entirely in memory. The shop is a good picture of it, and it lies to you in five specific places.

What is the picture you carry around?

One shopkeeper. One counter. A wall of labelled jars, each of a known kind. Children shout instructions. Meera does them one at a time, out loud, and answers.

That model is small enough to hold in your head during an incident, which is the whole point of having it.

Three facts describe the whole of it.

The state is one hash table, key → typed value, plus a second table, key → deadline, for the keys that have one.

The loop is: wake on ready sockets, read bytes, work out where each command ends, execute each to completion, write replies, and then tidy up. Tidying up means dropping keys past their deadline, making room if memory is full, and recording changes to disk and to the second machine. Every one of those tidy-up steps gets its own section below.

And the invariant that everything rests on: exactly one thread is ever inside the hash table.

Where does the story lie to you?

Never let an analogy quietly mislead you. Here is exactly where this one stops being true.

🔮 Predict: you set a key, memory fills up, and Redis throws your key away. What does your client see on the next read?

Reveal

A miss. Nothing else. No error, no warning, no log line on your side, and no way to tell it apart from a key you never set at all.

If you said "an error", you are still picturing Meera, who would tell you. Redis does not. That gap between the picture and the machine is the first of the five below, and it is the one that costs people data.

  1. Meera would tell you if a jar had been thrown away. Redis throws keys away silently when memory runs out (section 10). Your next read is simply a miss, indistinguishable from a key you never set. Nothing is logged to your client.
  2. Meera does everything, including writing the notebook. Real Redis does not. Flushing to disk, taking snapshots via fork(), freeing very large values, and, since Redis 6, reading and writing sockets can all happen on other threads. "Single-threaded" is a claim about command execution only. Get this wrong and you will mispredict performance.
  3. The shop is one room. Redis Cluster is many shops, and each jar lives in exactly one of them. That is why a command touching two jars may be refused outright (section 15).
  4. Shouting is instant. The network is not. On a real deployment the round trip is usually larger than the command, which is why section 14's experiment 3 matters more in practice than anything about the command itself.
  5. The jars are still there in the morning. Redis's memory is not. Without persistence turned on, a restart is an empty shop. Even with it, the recovery is not complete (section 11, F4).

10. How does a command get from the wire into the jar?

In one breath: We will build Meera's counter the way a smart person would build it, and let each version break. Every odd-looking detail of real Redis is the repair from one of those four breaks.

What does the first version look like?

forever:
    wait for a client to say something
    read the bytes
    work out which command it is
    do it
    write the reply

That really is the shape of MiniRedis.loop(). Five lines. Now let us break it four times.

Break 1: is "the socket is readable" the same as "a command arrived"?

Arjun sends SET name Redis. Your read() returns 11 bytes. Is that a command?

It looks like one. It is 11 bytes and the command is 11 bytes long. But you did not know that before you counted, and the counting is the problem.

🔮 Predict: TCP is a stream of bytes, not a stream of messages. What happens if the client's SET name Redis arrives in two packets and the server executes whatever it has when the first one lands?

Reveal

You execute SET name Re, which either stores the wrong value or is a parse error — and then the remaining bytes dis arrive and get interpreted as the start of a new command. One split packet corrupts the connection permanently.

This is the framing problem from io-multiplexing, where you measured one 512 KB message arriving as 76 separate readiness events.

The repair is why the Redis wire format looks the way it does. Every message declares its own length before its content. A reader therefore always knows exactly how many more bytes it needs, and never has to guess.

Engineers call that wire format RESP. This is what a client actually sends, with the two length declarations pointed out.

*3\r\n$3\r\nSET\r\n$4\r\nname\r\n$5\r\nRedis\r\n
 |     |                                          
 |     $4 = "the next argument is 4 bytes long"
 *3 = "this command has 3 parts"

Replies come back in five shapes, each identified by its first byte. Read the middle column: it is what the shape means.

first byte means example
+ a short status +OK\r\n
- an error -WRONGTYPE Operation against...\r\n
: an integer :6\r\n
$ a length-prefixed string ($-1 = nothing there) $5\r\nRedis\r\n
* an array of the above *2\r\n$3\r\nfoo\r\n$3\r\nbar\r\n

The parser in src/Resp.java returns null when the bytes on hand are not yet a complete command, and it never partially consumes them. The test resp_frames_a_command_split_across_two_tcp_writes sends a deliberately truncated command, checks nothing happened, then sends the rest and checks it did.

And notice the payoff you get for free. If framing is length-prefixed, a client can put ten thousand commands into one write, and the server will find all of them. That is pipelining, and it is the 23× speedup in experiment 3. Nobody added it as a feature. It fell out of fixing the framing bug.

Break 2: one slow client starves everyone, so should we add threads?

Priya's connection stalls halfway through a command. Meera waits for her. Every other child waits too. The obvious next move is a thread per connection, so that one slow child cannot hold up the others.

🔮 Predict: you switch to a thread per connection. The command code does not change at all. What have you just lost?

Reveal

Atomicity. INCR is read-modify-write; with several threads inside the hash table the read of one can land between the read and the write of another, and you are back to Arjun and Bina.

Experiment 1 measures precisely this. Eight clients, 2,000 increments each, on exactly the same command code:

expected                                : 16,000
single-threaded server                  : 16,000   -> 0 lost
same commands on many threads           : 11,124   -> 4,876 lost (30.5%)

Nearly a third of the work vanished, silently. You could get it back with a lock per key, which is what most databases do. But then you have paid for locks on every operation, and you own every deadlock you create.

The repair is to refuse the choice. Keep one thread for execution, and solve the slow-client problem a different way: never wait on a socket at all. Hand the whole connection set to the kernel, sleep, and get woken with only the ready ones.

That is exactly the Selector loop you built in the io-multiplexing lab. It is also why Redis can hold tens of thousands of connections on one thread.

This is the trade at the heart of Redis, stated honestly. One thread means perfect isolation between commands and zero lock overhead. The price is that everything shares one fate. Which brings us straight to the next break.

Break 3: what happens when the shelf runs out of room?

Memory is finite. When the keyspace outgrows it, something has to go.

The obvious answer is least-recently-used: throw out whatever has gone longest without being touched. To do that exactly, you keep every key in a linked list and move it to the front on every access.

🔮 Predict: exact LRU costs two pointers per key — on 10 million keys, roughly 160 MB of pure bookkeeping. Redis refuses to spend that and samples instead: pick 5 keys at random, evict the oldest of those, repeat. How much hit ratio does that shortcut cost?

Reveal

Almost none. Experiment 5, 200,000 requests over 20,000 keys with 80% of traffic on the hot 20%:

policy                      hit ratio   evictions
allkeys-exactlru                75.7%       48,639
allkeys-lru (samples=5)         73.7%       52,545     <- what Redis actually does
allkeys-lru (samples=10)        74.9%       50,204
allkeys-random                  66.6%       66,864

Sampling five costs 1.9 percentage points against perfect LRU. Having a policy at all is worth 7.1 against random. So Redis buys 79% of the available benefit for zero per-key memory, and maxmemory-samples 10 buys back another chunk if you want to pay a little CPU for it.

This is a good thing to internalise generally: an approximation that costs nothing per item often beats an exact algorithm that costs something per item.

Asha has to choose which victim rule her instance uses. The setting is maxmemory-policy. The right-hand column says which kind of instance each choice belongs to.

policy evicts use when
noeviction nothing — writes fail with an error Redis is your source of truth and silent data loss is unacceptable
allkeys-lru least recently used, sampled pure cache — the standard choice
allkeys-lfu least frequently used, sampled cache with a stable hot set that scans would otherwise pollute
volatile-lru / -lfu / -ttl / -random only among keys that have a deadline mixed instance: some keys are cache, some are truth

The volatile-* family is how Asha runs one instance holding both disposable and precious data. It has a nasty edge, though. If nothing has a deadline there is no candidate to evict, and writes fail exactly as if she had chosen noeviction.

Break 4: what about a note saying "throw this out at 4pm"?

Sessions expire. Caches go stale. Locks must not be held forever. So keys need deadlines.

In plain words, a deadline is the moment after which a key stops counting. Engineers call it a TTL, short for time to live.

The obvious implementation is a timer per key. On 10 million keys that is 10 million timers, and the cost is per key again.

🔮 Predict: Redis will not pay that. So: you set 50,000 keys with a 1-second TTL. Two seconds later, nobody has read any of them. How much memory has come back?

Reveal

With only lazy expiry, none at all. Experiment 4:

50,000 keys, TTL 1s   DBSIZE=50000  used_memory=15,077,780 bytes
3 seconds later:
  DBSIZE (residency)      : 50000      <- unchanged
  logically alive         : 0

Every one of those keys is dead and every one is still occupying memory.

Redis finds dead keys two ways, and you need both in your head.

The first is lazy expiry. When anything touches a key, the server checks the deadline first. If it has passed, the key is deleted right then, and the caller is told the key does not exist. This is Store.lookup(). It costs nothing. It also only ever finds keys somebody asks for.

The second is active expiry. Ten times a second, sample 20 keys that have a deadline, delete the dead ones, and if more than a quarter of the sample was dead, go round again immediately. This is Store.activeExpireCycle(), faithful to the real algorithm. It is probabilistic rather than exhaustive, and deliberately bounded so that it can never monopolise the one thread. Experiment 4 needed 157 sweep invocations to clear 50,000 dead keys. At the real ten-per-second rate, that is about fifteen seconds.

Two consequences are worth writing on a sticky note.

DBSIZE counts keys that are resident, not keys that are alive. That is faithful to real Redis, and it is why "my TTLs expired but DBSIZE didn't move" is a support question rather than a bug. The test expired_key_is_invisible_but_can_still_be_resident pins the behaviour.

And an instance can sit pressed against its maxmemory limit holding nothing but corpses, evicting live keys to make room, because the dead ones have not been sampled yet.

✅ CHECKPOINT — end of the INTERMEDIATE MODEL

You can now follow a command from socket bytes to hash table and back, and explain why RESP is length-prefixed, why execution is single-threaded, why eviction samples, and why expiry is lazy. Each of those is a scar from a break you just watched.

What the next layer adds: what happens when things go wrong. The process dies, the machine dies, the network splits, a client stalls holding a lock. And exactly which promises survive each one.

Say it back. Without using the words sampling, probabilistic or amortised, explain to a friend why Redis does not keep a perfect list of which key was used least recently, and why that is a good decision.

A good answer sounds like "Keeping a perfect order means writing something down about every single jar, every single time anyone touches one. With ten million jars that bookkeeping costs more memory than some of the jars. So instead Meera grabs five jars at random and throws out the dustiest of those five. She is wrong sometimes, but she is only about two percent worse at picking than perfect, and she pays nothing per jar to be that good."

11. What breaks, and which promise does each break bend?

In one breath: Nine failures, all real, all runnable. In most of them nothing is wrong; something is merely late, missing or gone. Telling those apart is the whole skill.

Meera's counter is now built. This section is what happens to Asha's shop on a bad day. Each failure is numbered so the exercises can point at it.

Two words will do a lot of work here, so earn them now. When nothing incorrect ever happens, engineers say safety held. When the system stops making progress in time, they say liveness was lost. A shop with a very long queue is safe and not live. A shop that hands out the wrong change is live and not safe.

F1 — why did twenty innocent reads jump to 190 ms?

Priya walks up to the counter and asks Meera to read out the name on every jar in the shop. There are two hundred thousand jars.

Meera starts reading. Behind Priya, twenty children are waiting to ask for one tiny thing each. None of them wants Priya's jars. None of them wants any jar Priya is touching. They wait anyway, because there is one Meera.

To make it happen on your machine, run java src/Experiments.java 2, or open the "list every key" scenario in the visualization. Twenty clients do tiny GETs on unrelated keys while one other client runs KEYS user:session:1* across 200,000 keys.

the KEYS command itself took            : 245 ms
GET p99 sampled before it               : p99 =   1,011 us
GET p99 sampled during it               : p99 = 191,661 us, max = 191,715 us

There is one thread and it runs each command to completion. The twenty clients were not competing for a key. They were competing for the thread. That is a 190× p99 collapse caused entirely by somebody else's connection.

Every guarantee about correctness holds here. No data is wrong. What is lost is liveness: the system stops making timely progress. Safety intact, liveness gone, which is exactly the distinction from paxos.

This is the single most common Redis outage there is. KEYS * is the famous one, and it has plenty of company. SMEMBERS on a million-member set does it. So do HGETALL on a huge hash, LRANGE key 0 -1, a DEL of a multi-gigabyte value, and a slow Lua script. Asha finds the culprit afterwards in SLOWLOG GET and in INFO commandstats.

Three fixes, in the order she should reach for them. Use SCAN instead of KEYS, because it does bounded work per call. Use UNLINK instead of DEL, because it frees on a background thread. And never let one key grow unbounded. A single key holding a huge collection is called a big key, and it is dangerous precisely because every O(n) command on it is an outage for everybody else.

F2 — what happens when the shelf is full and Asha still writes?

The shelf holds what it holds. Once it is full, Meera must throw something out before she can put anything new up.

Asha can produce this in a minute: set maxmemory low, set maxmemory-policy allkeys-lru, and keep writing. The test maxmemory_with_lru_policy_evicts_down_to_the_limit does it, and so does the eviction scenario in the visualization.

The reason is the capacity invariant. Memory used must stay under the limit, so on each write that would exceed maxmemory, victims are sampled and dropped until it fits.

Now the part that decides whether this is routine or an emergency. If Redis is a cache, nothing of value is lost. A miss just costs a trip to the source. If Redis is Asha's source of truth, this is silent permanent data loss, and nothing in her client will tell her. That is why noeviction exists. It is also why the choice of policy is really a declaration of what the instance is.

In production she watches evicted_keys in INFO. A non-zero rate on an instance she thinks of as a database is an emergency, not a graph.

One trap goes with it. used_memory counts what Redis asked for. used_memory_rss counts what the operating system actually gave it. The ratio between them is fragmentation, and it means a Redis sitting at 80% of maxmemory can still be at 100% of the machine.

F3 — the deadlines passed, so where did the memory go?

Fifty thousand jars had notes saying "throw this out at 4pm". It is now past 4pm. The shelf is exactly as full as it was.

Run java src/Experiments.java 4 and watch it happen.

The reason is section 10's fourth break. Expiry is lazy plus sampled. It is never exhaustive and never prompt. Nobody asked for those keys, so nobody triggered the lazy check, and the sweep only samples.

Correctness is fine throughout. A dead key is never visible to anybody. What is lost is Asha's ability to reason about memory from deadlines alone, which is a smaller loss than F2 and a much more confusing one.

The graph to look at is the expired_keys rate against her own write rate. If she creates keys with deadlines faster than the sweep reclaims them, memory climbs until eviction starts throwing out live keys. That is F3 turning into F2. Real Redis lets her tune the sweep's aggressiveness with hz and dynamic-hz.

F4 — the process dies. How much did you just lose?

🔮 Predict: Redis is running with appendfsync no, so it has not forced anything to disk in ages. You run kill -9 on it. How much acknowledged data do you lose?

Reveal

Nothing. Experiment 6 Part A does this for real, with a real separate process and a real kill -9:

acknowledged writes : 5,000
survived kill -9    : 5,000   -> 0 lost

Redis had already called write(), so the bytes were in the operating system's page cache. Killing a process does not empty the kernel's memory. appendfsync protects you from the machine dying, not from the process dying — and those are very different events with very different frequencies.

If this surprised you, it is because "flushed to disk" quietly conflates three separate moments: appended to Redis's own buffer, write()n to the OS, and fsync()ed to the physical device. Only the third survives a power cut.

If you guessed "everything since the last fsync", you had the right rule and the wrong villain. That answer is correct for the next failure, not this one.

F4b — and what if the machine loses power?

Now the page cache is gone too, because the page cache lives in the machine's memory. Experiment 6 Part B measures all three settings. Read the second-to-last column: it is the loss expressed as a duration of traffic.

appendfsync   acknowledged    durable       lost  lost as traffic   writes/sec
always              40,144     40,144          0             0 ms        8,920
everysec           137,121    120,949     16,172           530 ms       30,471
no                 153,137          0    153,137         4,500 ms       34,030

Read the loss as a duration, not a quantity. everysec lost everything written since its last fsync. The crash landed 500 ms into the 1,000 ms window, so 530 ms of traffic went.

That is Redis's real durability promise, stated honestly: your write is acknowledged now and becomes durable up to a second from now.

And look at the throughput column, because that is why everysec is the default. Buying the zero in the always row cost 3.4× lower throughput.

Which of the two recovery files does what?

Meera keeps a notebook of every instruction. She also, now and then, photographs the whole shelf. Those are two different ways of being able to rebuild the shop, and Redis has both.

RDB (snapshot) AOF (append-only file)
what it is a compact binary point-in-time dump of the whole dataset every write command, appended in order
written by a fork()ed child process the main process, buffered, fsynced per policy
recovery fast — load one file slower — replay every command
loses everything since the last snapshot (minutes) up to your fsync window (a second)
file size small grows forever unless rewritten

You have seen this pair before, twice. It is the write-ahead log plus checkpoint from btree-and-lsm. It is the event log plus snapshot from event-sourcing. Same idea, third context.

Production usually runs both: the append-only file for a tight loss window, the snapshot for fast restarts and backups. Redis 7 unified them into a "multi-part AOF", which is a base snapshot plus incremental files.

One production hazard belongs specifically to snapshots. BGSAVE calls fork(). The child shares the parent's memory copy-on-write, so every page the parent writes while the snapshot runs gets duplicated. On a write-heavy instance the process can approach twice its dataset size in resident memory for the duration. Sizing a box at exactly your dataset size is how you get killed by the out-of-memory killer during a backup.

F5 — the machine dies and Ben takes over. What arrives with him?

Ben keeps a second shop across the road. He copies Meera's notebook as fast as he can. He is always slightly behind, and nobody has ever promised how far.

🔮 Predict: the master acknowledged 500 writes to their clients, then died. A replica is promoted. How many of the 500 are on the new master?

Reveal

However many happened to have arrived — which you do not control. Experiment 7:

replication lag     0 ms  ->  acked 500, on the promoted replica 500, LOST 0
replication lag 1,500 ms  ->  acked 500, on the promoted replica   0, LOST 500

Both rows are the same code with the same guarantees. The only variable is how far behind the replica happened to be.

Redis replication is asynchronous. The master replies to the client and streams to replicas as two independent acts, in that order. So "Redis said OK" and "this write will survive a failover" are different statements, and the gap between them is the replication lag.

Availability survives this. There is a working master within seconds. Durability of acknowledged writes does not. This is the AP corner of cap-theorem, and it is the product, not a misconfiguration.

WAIT does not fix it, and it is worth being precise about why. WAIT numreplicas timeout tells you how many replicas already have your write. It cannot un-acknowledge one that they do not have. By the time WAIT returns a disappointing number, your client already has its OK, and Redis has no rollback. WAIT narrows the window you are exposed to. It does not close it.

Asha monitors master_repl_offset on the master against each replica's offset. She configures min-replicas-to-write and min-replicas-max-lag so that a master with no healthy replicas refuses writes rather than accepting ones it cannot protect. That is her choosing CP for that instance. And if a write must not be lost, it must not live only in Redis.

F6 — what if Meera and Ben are both open at once?

Split the road. Now some children can reach Meera and some can reach Ben, and neither shopkeeper can see the other.

The failover machinery decides Meera is gone and tells Ben he is in charge. That machinery is Sentinel, the component that watches a master and promotes a replica when it stops answering, covered in section 15. Meera has not stopped answering. She simply cannot be seen by the majority.

So Meera keeps serving the children who can still reach her, while Ben serves everybody else, and the two shops record different things. Engineers call this split brain.

Both halves keep serving, so availability survives. Their data diverges, so consistency does not. When the road reopens, Meera is reconfigured as a copy of Ben and discards her own divergent writes. Those writes are gone, and no client that received an OK was ever told.

The mitigation is the same min-replicas-to-write setting. A master that cannot see enough replicas stops accepting writes, and the minority side goes read-only. For Cluster there is cluster-require-full-coverage as well. This is the CAP dial, Redis lets Asha turn it, and the default position is AP.

F7 — how do two workers both end up holding one lock?

Dev and Omar both process invoices. Only one of them should touch invoice 42. Almost every Redis deployment eventually grows this pattern.

// take the lock: set it only if absent, with a deadline, in ONE command
SET lock:invoice:42 <random-token> NX PX 30000
   ... do the work ...
// release it only if we still own it (this must be a Lua script -- see below)

The NX PX combination in one command matters. SETNX followed by a separate EXPIRE can crash in between and leave a lock with no deadline, held forever. The test set_nx_px_grants_the_lock_to_exactly_one_client confirms that exactly one of 20 concurrent clients wins.

🔮 Predict: client A takes the lock with a 200 ms deadline, then stalls for 500 ms in a garbage-collection pause. How many clients believe they hold the lock?

Reveal

Two. Experiment 8:

A: acquired the lock, deadline 200 ms
B: acquired the lock (A's had expired) -> writing
A: woke up, still believes it holds the lock -> writing
writers that entered the critical section: 2  [B, A]

Redis did nothing wrong. It granted one lock, expired it on schedule, and granted it again. The lock was lost by A without A being told — because nothing can tell A; A was not running.

And you cannot escape by removing the deadline, because a lock with no deadline deadlocks permanently the first time a holder dies. Every lock with a timeout has this hole.

In the story: Dev takes the key, is knocked out for half a minute, and wakes up still holding it. Omar has long since been given a new key. Nobody lied to either of them.

The fix does not live in Redis. It lives at the resource. Each acquisition takes a strictly increasing number. Engineers call it a fencing token. The protected resource then refuses any write carrying a token lower than the highest it has already honoured.

B: accepted with token 2
A: REJECTED by the resource -- token 1 is stale
with fencing tokens, writers accepted: 1  [B]

The lock still failed identically. Both clients still believed they held it. What changed is that the resource can now tell which belief is stale.

So mutual exclusion is not guaranteed. What a Redis lock actually gives you is a strong probability that two workers will not do the same job at the same time. That is worth a great deal, and it is not the same thing.

Use a Redis lock to stop duplicate work, which is an efficiency goal. Do not use one as the only thing standing between you and a correctness violation. Redlock, the multi-instance algorithm, does not change this conclusion. Martin Kleppmann's critique and antirez's reply are both worth reading in full, and the durable takeaway is the fencing token.

One more detail people get wrong. A correct release must check the token and delete in one atomic step, which needs a Lua script. A plain GET followed by DEL can delete somebody else's lock in between.

F8 — why does adding machines not help Chetan's chess ladder?

Chetan's ladder is the most popular jar in the shop. Four requests in every ten are about it.

🔮 Predict: Asha's Redis is at 100% of one core because of that one jar. She adds four more machines to the cluster. What happens to the load on the jar's machine?

Reveal

Nothing at all. A cluster spreads keys across machines, and this is one key. It lives on exactly one machine before the change and on exactly one machine after it.

If you said "it drops to a fifth", you are picturing the traffic being split. Sharding splits the keyspace, never a single key.

A key taking a large share of all traffic is called a hot key. A Redis Cluster spreads keys across shards, and a single key lives on exactly one shard. So a key that is 40% of your traffic puts 40% of your traffic on one thread on one machine, and adding shards does nothing at all.

Correctness is fine. What is gone is Asha's ability to scale that particular workload horizontally.

This is the distributed-rate-limiting lab's hot-key problem in its native habitat, and the same remedies apply. Split the key into counter:{id}:0..9 and sum the parts. Put a short-deadline local cache in front of it. Or route by a different dimension entirely. Find them with redis-cli --hotkeys and --bigkeys.

F9 — why did the announcement reach nobody?

Bina shouts an announcement across the tuck shop. Everyone currently in the room hears it. Everyone else never learns it happened, and there is no record.

The test pubsub_reaches_only_clients_connected_right_now does exactly that. Publish with nobody subscribed, and the message is delivered to zero clients and is gone forever.

Redis Pub/Sub is fire-and-forget. There is no queue, no backlog, no retry and no replay. A subscriber that was disconnected, or merely reconnecting, misses everything sent in that window.

What you get is at-most-once delivery, with no durability whatsoever.

If losing a message is acceptable, Pub/Sub is perfect and very cheap. Cache invalidation broadcasts and live dashboards are the classic fits. If it is not acceptable, use Redis Streams with XADD and XREADGROUP, which keep a persistent log with consumer groups and explicit acknowledgement. That is the "queue versus log" distinction from database-landscape, living inside one product.

12. What is promised, what is not, and what did one Meera cost?

In one breath: Six things Redis will always do, six things it will never do, and one table showing that both lists come from the same design decision.

Which six promises does the design actually keep?

These hold for Arjun, for Asha's twenty servers, and for every client at once.

  1. One command at a time. No command observes another's intermediate state. This is the source of everything good here.
  2. Commands are ordered. Every client, every replica and the append-only log see the same sequence. There is one thread, so there is one order.
  3. An expired key is never visible, even if it is still resident.
  4. used_memory ≤ maxmemory, unless the policy is noeviction, in which case writes are refused instead.
  5. Only real effects propagate. A SET NX that lost the race changes nothing, so it is never written to the append-only log and never sent to a replica.
  6. Propagation is deterministic. Non-deterministic commands are rewritten before they leave the server, because a replica replaying them would diverge. EXPIRE, which is relative, becomes PEXPIREAT, which is absolute. SPOP, which is random, becomes the concrete SREM of the member actually removed. Both are pinned by tests.

That sixth one is worth a second look. Ben is not replaying what Dev asked for. He is replaying what actually happened. Those are different, and the difference is what keeps his shop identical to Meera's.

Which six things will Redis never do for you?

In order of how often each one bites people.

🔮 Predict: you send MULTI, then three increments, then EXEC. The second increment fails at run time because that key holds text. What happens to the first and third?

Reveal

They both happened, and they stay happened. There is no rollback in Redis, so the batch is not undone by a failure inside it.

If you said "the whole thing is rolled back", you are reading MULTI as a database transaction. It is not one. It is a batch that nothing else can interleave with, which is a much smaller promise.

  • Durability of an acknowledged write. Acknowledgement precedes both fsync and replication. Up to one second locally (F4), and unboundedly on failover (F5).

  • That a "transaction" can be rolled back. MULTI/EXEC runs a batch with nothing interleaved. It does not undo. If command 3 of 5 fails at run time, commands 1, 2, 4 and 5 still happened. Pinned by multi_exec_does_not_roll_back_after_a_failed_command:

    MULTI; INCR good; INCR text(<- fails); INCR good; EXEC
-> [1, error, 2]   and `good` is 2.

    Redis's own documentation is explicit that this is a deliberate choice. Errors inside EXEC are programming bugs, and supporting rollback would cost every transaction speed to protect against them.

  • Mutual exclusion from a lock (F7).

  • Message delivery from Pub/Sub (F9).

  • That a key you wrote is still there. Eviction and expiry both remove keys silently.

  • Isolation across multiple keys, when the data is spread over several machines. A multi-key command whose keys live on different shards is refused outright (section 15).

What did the single thread buy, and what did it charge?

Every row here is the same decision seen from two sides. Read them across.

bought cost
every command atomic, with no locks anywhere one slow command blocks everything (F1)
no lock contention, no deadlocks, no lost updates one CPU core per instance for command work
one total order of operations, for free vertical scaling of a single key is impossible (F8)
a dramatically simpler codebase, hence very few concurrency bugs you must reason about command complexity yourself

Which commands are safe to send, and which are outages?

The rule that falls out of that table is worth carrying into your own code: know the big-O of every command you send.

The right-hand column is the sentence to say to yourself before sending one of these on a busy instance.

Cost Commands What it means on one thread
O(1) GET, SET, INCR, LPUSH, HGET, SADD free; send as many as you like
O(log n) ZADD free in practice, even on a large sorted set
O(offset + count) LRANGE fine with a small window, an outage with 0 -1
O(n) KEYS, SMEMBERS, HGETALL, SORT, DEL of a large collection not "slow for that caller" — slow for everyone

That last row is the whole point. On a threaded database, an O(n) query is a problem for the person who ran it. On Redis it is F1.

What do you do when one command cannot express the change?

Sometimes the change Asha wants depends on a value in a way no single command captures. Read a balance, decide something in application code, then write.

WATCH is Redis's answer. It does not lock anything. It remembers a version, and EXEC refuses if the version moved.

WATCH balance          <- remember the version
GET balance            -> 100
MULTI
SET balance 90         <- queued, not run
EXEC                   -> nil, if anybody touched `balance` in between

This is the expected-version check from event-sourcing, applied per key. And like all optimism it degrades with contention. Experiment 9 puts twelve clients on one key:

WATCH/MULTI/EXEC : result=2400  694 ms, 11,606 aborted attempts (4.8 per success)
INCR             : result=2400   23 ms,      0 aborted attempts

Both are correct. One is 30× faster and cannot fail.

So: if a single command already expresses what you want, use it. Reach for WATCH only when none does. Reach for a Lua script when even that costs too many round trips.

Which seven methods carry the whole lab?

Read them in this order. Each one is short, and each one is a piece of Meera's counter made concrete.

  1. MiniRedis.loop() — accept, read, execute, reply, housekeep. Note what is absent: no synchronized, no locks, no atomics around the store. There cannot be a race because there is only ever one thread inside it.
  2. Commands.incrBy() — read, modify, write, with no possibility of interleaving. This is the entire atomicity guarantee, and it is four lines with no concurrency machinery in them at all.
  3. Store.lookup() — lazy expiry. A key past its deadline must never be visible, but may still be resident.
  4. Store.evictIfNeeded() / pickVictim() — sampling rather than an exact LRU order, plus the cost of that shortcut.
  5. MiniRedis.execute(), the propagation block — effects propagate, requests do not. Plus the EXPIRE → PEXPIREAT rewrite that keeps Ben's shop deterministic.
  6. Commands.run(), the SET case — the sharpest example of "propagate the effect, not the request". Both the NX condition and the relative PX deadline are stripped before the command leaves the server, because re-deciding a condition later against a different clock can reach the opposite answer. BrokenRedis bug 3 turns this off, and shows the live server and the recovered server disagreeing about who holds a lock.
  7. MiniRedis.appendAof() / flushAof() — the three distinct moments (buffer, write(), fsync()) whose conflation causes the F4 surprise.

Which deployment shape should Asha choose?

Consider them in this order, and stop at the first one that works.

  1. One instance, one replica, Sentinel. Correct for the overwhelming majority of workloads. One Redis on decent hardware handles well over 100,000 operations per second on one core.

  3. Managed. AWS ElastiCache, MemoryDB (which is Redis-compatible with durable multi-AZ writes, a genuinely different durability posture), Redis Cloud, GCP Memorystore.

What changes if you are wiring this into Spring Boot?

Six things, and the last two catch people who did everything else right.

  • Spring Data Redis with the Lettuce driver is the default and the right choice. It is Netty-based, and one connection multiplexes safely across threads. Jedis needs a connection pool because its connections are not thread-safe.
  • RedisTemplate and StringRedisTemplate handle direct commands. @Cacheable and @CacheEvict via RedisCacheManager generate the cache-aside pattern for you. Always set a TTL on cache entries. An unbounded @Cacheable region is F2 waiting to happen.
  • Spring Session puts HTTP sessions in Redis, which is what makes Asha's twenty app servers interchangeable. Note the durability consequence: a Redis failover can log everybody out. Decide whether that is acceptable before it happens, not after.
  • Serialization matters more than people expect. The default JdkSerializationRedisSerializer produces large, Java-only, refactoring-fragile blobs. Use GenericJackson2JsonRedisSerializer or a String serializer.
  • A Redis call is a network call, so set command timeouts. Then decide per call site whether a Redis failure should fail the request or fall through to the source. That is the fail-open versus fail-closed choice from distributed-rate-limiting, made once per call site.
  • @Transactional on a Spring RedisTemplate does not give you database transaction semantics. It maps to MULTI/EXEC, which, as section 12 established, has no rollback.

When should you not use Redis at all?

Five honest answers, any one of which is enough.

  • The data does not fit in RAM, or would be far cheaper on disk.
  • You need queries you cannot express as "I know the key".
  • You cannot tolerate losing a second of acknowledged writes and cannot tolerate losing more on failover. MemoryDB is the exception built for exactly this.
  • You need real multi-key transactions with rollback.
  • You are reaching for it as a message queue and you need delivery guarantees. Use Streams deliberately, or use Kafka.

What should you know before you deploy in 2026?

Redis's licence changed twice, and the fork it produced is now a default.

Redis left BSD in March 2024 for RSALv2 and SSPLv1, which are source-available rather than open source. AWS and Google forked the last BSD version as Valkey, now under the Linux Foundation. Redis 8.0, in May 2025, then added AGPLv3, so Redis now ships under a tri-licence of AGPLv3, SSPLv1 or RSALv2, with the line at Redis 8.8 as of May 2026. Valkey is BSD-3, wire-compatible, on its own cadence at 9.1 in May 2026, and is the default on AWS ElastiCache and MemoryDB.

Practically: everything in this lab applies identically to both. The choice is a licensing and ecosystem decision, not a technical one. Do check which one your managed provider is actually giving you.

What is Redis commonly confused with?

Six confusions, one separating sentence each.

  • Memcached stores opaque bytes, so compound operations must happen in your client, with the gap that loses updates. Redis knows the type, so they happen on the server.
  • A cache is defined by deleting it costs only speed. Redis is often used as one, but configure it as a source of truth and that stops being true.
  • Redis Cluster versus Sentinel: Cluster shards data across machines, Sentinel keeps one unsharded master highly available. Different problems.
  • Redis Streams versus Pub/Sub: Streams keep a persistent log with consumer groups and acknowledgements. Pub/Sub keeps nothing and forgets instantly.
  • MULTI/EXEC versus an ACID transaction: the first batches commands so nothing interleaves, the second can roll back. Redis has no rollback.
  • Redis versus Valkey: the same software, forked over licensing in 2024, still wire-compatible.

Redis — solutions

Try the exercises first. Rungs 7–8 are worked discussions, not single answers.

Rung 1 — Explain

1.1 Redis exists to hold shared, hot, mutable state for many machines at once.

  • A ConcurrentHashMap inside your app is fast and correct — for one process. The moment you run two app servers they each have their own map and neither can see the other's. Your rate limiter now allows 2× its limit, and 20× when you autoscale to twenty. Thread-safety was never the problem; process boundaries were.
  • A Postgres table is shared and correct, but every read-modify-write is a round trip through machinery designed to make facts permanent forever: WAL, MVCC, indexes, row locks. For a counter changing 10,000 times a second that is the wrong price, and worse, under contention your twenty servers serialise on the row lock — you have bought a distributed queue you did not want.

Redis is the middle: shared like the database, fast like the in-process map, and explicit about what it gives up (durability, and queries beyond the key).

1.2 Without the forbidden words: only one thing ever happens at a time. A command is not a sequence of steps that other commands can get between — while one command runs, no other command is running at all. So "read 5, add 1, write 6" has no gap in it, because during those three steps nothing else in the entire system is executing. There is nothing to exclude, because nothing else is there.

If you found yourself wanting to say "it's like an implicit lock around every command" — that is the right intuition for the effect and the wrong one for the mechanism, and the difference matters when you predict performance. A lock costs something and can be contended. This costs nothing and cannot.

1.3 Because "add one to the samosa jar" is only a sentence you can say if the listener knows the jar holds a number. A shopkeeper who only knows "here is a jar, here is a different jar" cannot do anything for you but hand it over and take it back — which is exactly three trips and exactly the gap Arjun and Bina fell into.

Memcached is the shopkeeper who does not know what is in the jars. That is the whole difference. The types are not sugar on top of the atomicity guarantee; they are the delivery mechanism for it.

1.4 Cache: a rendered product page under page:sku:123 with a 60-second TTL. Not a cache: a user's shopping basket, or the fencing counter fence:invoice:42.

The test, from the caching lab: delete the whole store and see what you lost. Lose the cache and you lost speed — the pages regenerate. Lose the baskets and you lost baskets; nothing else in the world knows what was in them. This is a decision you make with appendfsync, maxmemory-policy and your replication setup — it is not a property of the software.

Rung 2 — Identify

2.1 Whatever the screen says — the point is that it says it. The verdict band reads "N clients are stuck waiting. The thread is listing every key in the database, and it will not start anything else until it finishes", and the log gives you the sentence "Client A finally gets served after waiting 23 ticks — it was ready the whole time; the thread was busy." If you had to guess at any of that, the page failed.

2.2 Commands.incrBy(), and the load-bearing part is four lines: read the value, parse it, add, store. Zero of them mention concurrency. That absence is the answer to 1.2 made physical — go and look at it, because it is genuinely startling to see a lock-free multi-client counter with nothing in it.

2.3 From INFO: db0:keys=N (resident), aof_written_bytes (handed to the OS), aof_fsynced_bytes (actually durable).

The one that lies is db0:keys — like real Redis's DBSIZE, it counts keys that are resident, including ones whose deadline has passed and which no longer exist as far as any client is concerned. aof_written_bytes also misleads if you read it as "safe": it is safe from kill -9 and not from a power cut. Only the third number is a durability statement.

2.4 The header says *3 — three arguments — and HSET user:1 alice is indeed three. But HSET needs a field and a value, so this sets field alice to... nothing; there is no fourth argument. Real Redis replies -ERR wrong number of arguments for 'hset' command. The framing is valid; the command is not. Well-formed and correct are different checks, and RESP only does the first.

2.5 You cannot predict it, and that is the lesson. The policy is allkeys-lru, but Redis does not maintain a true LRU order — it samples a handful of keys at random and evicts the oldest of that sample. With 4 keys and a sample of 3 you will usually but not always get the genuinely-oldest one. Anyone who tells you Redis "evicts the least recently used key" is describing the intent, not the algorithm.

Rung 3 — Predict

3.1 DBSIZE returns 1. GET k returns nil.

Both are correct simultaneously, and that is the whole point. Passing the deadline makes a key invisible, not absent. With active expiry off, nothing has gone looking for it, so it still occupies memory; DBSIZE reports residency. GET checks the deadline first (lazy expiry), reports nil — and that read is what finally frees the memory. Run GET then DBSIZE again and you get 0.

3.2 The write fails with an OOM error, exactly as under noeviction. volatile-lru will only ever consider keys that have a deadline; with no candidates there is nothing to evict, so there is no way to make room.

It is nastier than noeviction because noeviction is what you asked for — you chose it and you expect refusal. volatile-lru looks like an eviction policy, so the instance appears configured to shed load, and it silently is not. The failure arrives the day someone stops setting TTLs on new keys, which is a code change nobody associates with a Redis outage.

3.3 Replies: 1, an error, 2. And good is 2.

The middle command failed and the ones around it committed anyway. Redis has no rollback. MULTI/EXEC guarantees only that nothing else interleaved — it is a batch, not a transaction in the ACID sense, and this is Redis's deliberate choice: an error inside EXEC is treated as a programming bug, and supporting rollback would tax every transaction to defend against one.

If you predicted [1, error] and an aborted batch, you were applying database intuition. That intuition is exactly what makes this a production bug rather than a trivia question.

3.4 With WATCH: one succeeds, one gets nil and must retry. With DECRBY: both succeed, and they are both correct — the command is atomic, so the second operates on the first's result.

Both approaches are correct. The difference is cost, measured in experiment 9:

WATCH/MULTI/EXEC : 694 ms, 11,606 aborted attempts (4.8 per success)
INCR             :  23 ms,      0 aborted attempts

30× slower, and it gets worse as contention rises, because every loser redoes its work. The rule: if one command already expresses what you want, use it — it cannot lose a race and can never need a retry.

3.5 All four cells, measured in experiment 6:

kill -9 power loss
appendfsync always 0 lost 0 lost
appendfsync no 0 lost everything since the last OS flush (4,500 ms of traffic measured)

The surprising cell is bottom-left. kill -9 with fsync off loses nothing, because Redis already called write() and the data sits in the operating system's page cache — killing a process does not empty the kernel's memory. appendfsync defends against the machine stopping, not the process stopping. Two very different events with very different frequencies, and conflating them is how people end up paying for always to solve a problem they did not have.

3.6 You know: one replica definitely has the write, so a failover to that one would preserve it.

You do not know: which replica, whether the other two will ever get it, or — most importantly — whether the failover machinery will pick the one that has it. Sentinel picks by replication offset, so it usually will, but "usually" is the operative word.

What you can do: nothing retroactive. Your client already has its OK and Redis has no rollback. WAIT is a measurement, not a mechanism. What you can do prospectively is set min-replicas-to-write 2 so the master refuses writes it cannot protect — which is you choosing CP for that instance, and accepting the write-unavailability that comes with it.

Rung 4 — Modify

4.1 Measured on this machine (same workload as experiment 5):

maxmemory-samples hit ratio gap to exact LRU
2 70.4% −5.3
3 72.3% −3.4
5 (Redis default) 73.8% −1.9
10 74.9% −0.8
20 75.4% −0.3
50 75.6% −0.1
exact LRU 75.7% —

Redis defaults to 5 because the curve is steeply diminishing and every sample is CPU spent on the one thread that is also serving your traffic. Going 5→10 buys 1.1 points; 10→50 buys 0.7 for five times the work. On an instance evicting thousands of keys a second, sampling 50 keys per eviction is real latency for every client — you would be spending the single thread, the scarcest resource in the whole design, to chase a fraction of a percentage point.

Note also where the curve starts: even 2 samples gets you 70.4% against random's 66.6%. Almost all the value is in having any preference at all.

Nothing about correctness changed in any row. Eviction never returns a wrong answer; it changes which answers require a trip to the source. This is a pure efficiency dial, which is exactly why it is safe to leave alone.

4.2 Roughly 4–5× more sweeps, because the "go round again if the sample was mostly dead" rule is what lets one sweep clear a large backlog quickly. Experiment 4 needs 157 invocations with the rule; without it each invocation does one round of 20.

On a real instance running the sweep ten times a second, that is the difference between clearing a 50,000-key backlog in seconds and in minutes — during which those dead keys still count against maxmemory and can force live keys to be evicted. Again: liveness, not safety. Nothing is ever wrong; things are late.

4.3 No. This is the single most important "careful" answer in the lab.

Setting the lag to zero removes the simulated delay. It does not make replication synchronous. The master still replies to the client and streams to the replica as two separate acts in that order, so there is always a window — now microseconds instead of 1,500 milliseconds, but never zero, and it widens under load, GC, network congestion or a slow replica exactly when you are least able to notice.

The honest statement is: the write is now very likely to survive, and still not guaranteed to. "Very likely" is a fine basis for a session and a poor one for a payment. If you wrote "yes, it's fixed", re-read F5 — the difference between narrowing a window and closing it is the entire content of that section.

4.4 Experiment 6 Part A changes: with flushAof() running rarely, a kill -9 can now lose data, because bytes are still sitting in Redis's own in-process buffer and have never reached the kernel. Part B is unchanged — power loss was already losing everything past the last fsync, and the buffer was never the binding constraint there.

This is the three-moments distinction made concrete: buffer → write() → fsync(). Your change moved the first boundary and left the second alone. Real Redis flushes its buffer every event-loop iteration precisely so that the first boundary is never the one that hurts you.

Rung 5 — Implement

5.1 GETEX. The interleaving that breaks GET-then-PEXPIRE:

A: GET session:9            -> "alice"        (still alive, 5 ms left)
                B: (the key's deadline passes; a reader reaps it)
                B: SET session:9 "bob" PX 30000
A: PEXPIRE session:9 30000                    <- A just extended BOB's session

A read a value, and then set a deadline on a different value it never saw. GETEX closes it by making the read and the deadline one indivisible act. The general shape: any time you read a value and then act on the key based on what you read, you have a gap — and the gap is only safe if a single command spans it, or WATCH guards it.

5.2 INCRCAP. GET then INCR fails for the same reason as everything else in §4: two clients both read 99 against a cap of 100 and both increment, and you are at 101 with both believing they were under.

INCR then DECR-if-over is the tempting fix and it is worse, not better. It is eventually consistent to the right number, but in between the counter genuinely exceeds the cap — so any other client reading it during that window sees an over-limit value and acts on it. You have converted a lost update into a transient lie, which is harder to reason about. If the cap is a rate limit, you have just admitted a request you were supposed to reject.

The only correct answer is to do the comparison and the increment in the same indivisible step — which is what RATELIMIT in Commands.java does, and what a Lua script does in real Redis.

5.3 LMOVE. The reliable-queue property: the job is never in neither list. A crash after LMOVE returns leaves it in processing, where a reclaimer can find it.

What is still missing before this is a production queue:

  • Reclaim by age, and therefore a heartbeat or a timestamp per in-flight job — and once you have a timeout you have F7 again: a slow worker is indistinguishable from a dead one, and reclaiming its job means the job runs twice.
  • Therefore idempotent consumers. At-least-once delivery is what you actually built; make the work safe to repeat.
  • A dead-letter path for jobs that fail repeatedly, or one poison message loops forever.
  • Fairness and backpressure across workers.

Which is a good moment to notice you are re-deriving Redis Streams (XADD, XREADGROUP, XACK, XAUTOCLAIM) — they exist because everyone builds this and everyone gets the reclaim wrong.

6.4 — why bug 2 is the quietest. Because every command, examined alone, behaves perfectly. GET correctly reports the key as gone. INCR correctly increments a key it can see. That is also why it does the most damage. A rate-limit counter that never resets throttles a customer permanently, the TTL command reports the key as gone so the first thing you check exonerates it, and every debugging session begins by ruling out the wrong component.

6.5 — the one the suite misses. It is bug 2, and it passes all 25 tests.

Why the suite missed it: every test asserts one command's behaviour. Nothing asserts that two different commands agree with each other about the same key. That is a shape of test the suite does not contain at all, so no amount of adding more tests of the existing shape would have found it.

The test to write:

static void every_command_agrees_that_an_expired_key_is_gone(MiniRedis s) throws Exception {
    try (Cli c = new Cli(s.port)) {
        c.cmd("DEBUG", "SET-ACTIVE-EXPIRE", "0");
        c.cmd("SET", "k", "41", "PX", "50");
        c.cmd("DEBUG", "ADVANCE", "60000");
        eq("GET agrees it is gone",    null, c.cmd("GET", "k"));
        eq("EXISTS agrees",              0L, c.cmd("EXISTS", "k"));
        eq("TTL agrees",                -2L, c.cmd("TTL", "k"));
        eq("TYPE agrees",            "none", c.cmd("TYPE", "k"));
        eq("and INCR agrees -- it must start from zero, not resurrect 41",
                                         1L, c.cmd("INCR", "k"));
    }
}

(DEBUG ADVANCE moves the clock forward, and each assertion needs a fresh key because the failing read reaps it — the second subtlety this exercise teaches.)

This test is deliberately not in src/Tests.java. The hole is the exercise; shipping the patch would remove it. But it is not unverified — running it both ways gives:

--- with the bug OFF ---   PASS  every_command_agrees_that_an_expired_key_is_gone   26 passed, 0 failed
--- with the bug ON  ---   FAIL  every_command_agrees_that_an_expired_key_is_gone   25 passed, 1 failed

That second line is the part that matters. A test you have not watched fail is not evidence of anything — it may be asserting something that was never possible to break, and a suite full of those is worse than no suite, because it buys confidence without paying for it.

The transferable lesson: a green suite is a statement about your tests, not about your code. The bugs that survive are the ones whose shape your tests do not have, and you find those by asking "what kind of wrongness could not possibly show up here?" rather than by writing more of what you already have.

Rung 7 — Handle failure

7.1 — Making the lock safe

The correct release, which must be one atomic step (in real Redis, a Lua script; here, a small native command):

if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end

The interleaving that GET-then-DEL allows:

A: GET lock -> "A-token"    (A still owns it)
            A stalls 400 ms; the lock expires; B acquires it
A: DEL lock                 <- A has just deleted B's lock

A now believes it released its own lock, B believes it holds one, and the next acquirer will collide with B. Note this is a second failure on top of F7: even a client that correctly gives up can corrupt the system.

The hard part — which resources can be fenced? A resource can reject a stale writer only if it can remember the highest token it has honoured and compare atomically:

  • Can be fenced: a Postgres row (UPDATE ... WHERE fence < :token), a DynamoDB conditional write, an object store with conditional-put/ETag semantics, any service you wrote that will accept a token parameter.
  • Cannot be fenced: sending an email, charging a card through a provider with no idempotency key, POSTing to a third-party webhook, writing to a filesystem with no compare-and-set, calling a legacy SOAP service.

For the ones that cannot: stop trying to make the lock correct, and make the operation idempotent instead. Give the work a stable identity — an idempotency key — and have the far side deduplicate. Payment providers offer exactly this because they know their callers cannot be trusted to hold a lock. If the far side offers nothing, you record your own intent transactionally before acting and check it on retry, which is the transactional-outbox pattern wearing a different hat. Redis's lock then reverts to what it is genuinely good at: making the duplicate rare, so the deduplication path is cold.

7.2 — The job queue that survives a dead worker

take:      LMOVE queue processing RIGHT LEFT      -- atomic; never in neither list
succeed:   LREM processing 1 <job>
reclaim:   anything in processing older than T goes back to queue

The design is correct for a dead worker and unavoidably wrong for a slow one, because nothing can tell them apart from the outside. When the reclaimer moves a job that is merely slow, that job now runs twice — concurrently, on two machines.

This is F7 exactly: a timeout converts an unknown into a decision, and the decision is sometimes wrong. And it has the same resolution: you cannot fix it in the queue, so make the job idempotent, or fence the resource it writes to. Choosing T only moves the failure between "jobs stall for a long time" and "jobs run twice more often" — it never removes it.

Production versions of this are Redis Streams' consumer groups with XAUTOCLAIM, which give you the reclaim machinery and the delivery counter, and still leave idempotency to you.

For a payment: the last row, without hesitation. order:99 paid is a fact about money; it belongs in a store whose acknowledgement means committed. Redis can hold a fast derived copy, kept in sync by the transactional-outbox pattern, and if that copy is lost you rebuild it.

For a session: min-replicas-to-write 1 plus asynchronous replication is fine. The failure mode is "some users are logged out after a failover", which is a cost you can accept because the recovery — logging in again — is cheap and well understood.

The generalisation worth keeping: the question is never "is Redis durable enough?" It is "what does losing this specific fact cost, and is that less than what protecting it costs?" The same instance can hold facts on both sides of that line — which is exactly what the volatile-* eviction policies are for.

Rung 8 — Design

8.1 — Session store, three datacentres

Sizing. 50M × 2 KB = 100 GB of payload; with per-key overhead and fragmentation, budget ~140–160 GB, plus headroom for fork() during snapshots (F4), so ~200 GB of RAM. That does not fit one machine comfortably, so this is one of the genuine cases for Redis Cluster — say 6 shards of ~35 GB, each with one replica. 40k reads/sec across 6 shards is unremarkable; a single Redis does far more.

Cross-DC replication: no. Sessions are read on almost every request, so a 60 ms cross-DC hop on the read path is unacceptable. Run an independent cluster per DC and pin users to their nearest one via the load balancer. Do not try to replicate sessions across DCs synchronously — you would be paying 60 ms to protect data whose loss costs a re-login.

When a DC goes dark: its users are routed to another DC, find no session, and log in again. That is the deliberate trade, and the thing to verify is not Redis but whether your login path can absorb a third of your users at once — which is where this design actually fails if it fails. Test that, not the Redis failover.

What survives from this lab unchanged: the single-threaded execution model, TTLs as the expiry mechanism (a session TTL is refreshed on each request), lazy plus sampled expiry, and asynchronous replication within a DC.

What must change: multi-key operations are gone (keys land in different hash slots), so no MGET across sessions unless you hash-tag them; you need a cluster-aware client; and resharding becomes an operation you must have rehearsed.

Three alerts: (1) used_memory_rss approaching machine memory on any shard — remember fork() can nearly double it; (2) replication offset lag beyond your tolerated loss window; (3) p99 latency per shard, because one hot shard is invisible in an average.

8.2 — "Top 100 products this hour"

ZINCRBY leaderboard:2026-08-28T14 1 <product> is correct and it is one command, so it cannot lose an update. The wall it hits is not memory and not the sorted set's O(log n) — it is that the whole hour's leaderboard is one key, so it lives on one shard, on one thread. 200,000 writes/sec to one key is one core's problem, and adding shards does nothing at all, because sharding distributes keys and there is only one key. That is F8 exactly.

The fix has two independent halves:

  1. Split the key. leaderboard:<hour>:<0..15>, chosen by hash(product) % 16. Now 16 shards share the write load, and a read merges 16 sorted sets — which is cheap, because you only need the top 100 from each.
  2. Do not send every event. Aggregate in the application for 1–2 seconds and send one ZINCRBY per product per window. At 200k events/sec over a few thousand distinct products this is a 100× reduction, and it is the change that actually matters. Pipelining the batch makes it one round trip.

What accuracy you trade: the leaderboard lags by your aggregation window, and a crashing app instance loses its unflushed local counts. For "top 100 products this hour" both are irrelevant — you are ranking, and the ranking is stable long before the counts are exact.

What to tell the product manager: not "no". Say that the numbers are exact within about two seconds and that the ranking is what the feature is for; then ask what decision the exact count would change. If the honest answer is "billing" or "a payout", this is the wrong store and the events belong in a durable log with a batch job behind it — which is a different feature with a different cost, and worth naming as such rather than discovering later.

8.3 — The two-paragraph reply

Moving the basket to Redis would genuinely make it faster, and the reads probably are our bottleneck, so I don't want to dismiss it. The thing that worries me is what "acknowledged" means in each store. Postgres tells us a write is committed only once it is durable; Redis acknowledges immediately and becomes durable up to a second later, and on a failover it loses whatever had not yet reached the replica — which in our setup is unbounded, because replication is asynchronous. So the failure mode is not "the basket is slow", it is "the basket silently loses the item the customer just added", during a failover, which is exactly when we are least able to notice. For a basket that turns into an order, I don't think we want that.

What I'd suggest instead: keep Postgres as the source of truth and put a read-through cache in Redis with a short TTL, invalidated on write. That gets us the read speed — which is where the pain actually is — without changing what a committed basket means. If writes turn out to be the bottleneck too, the next step is AWS MemoryDB, which is Redis-compatible with durable multi-AZ writes; it costs more and is slower on writes, but it is the one option that gives us both. Shall I measure the read/write split first so we know which problem we are actually solving?

The shape worth copying: agree with the part that is right, name one specific failure with its mechanism, quantify it, and end with a concrete proposal and a question — not a refusal.

8.4 — Reading the incident

The INFO you were given has already ruled things out: evicted_keys: 0 and memory at 60% means this is not memory pressure; healthy replication offset means it is not a struggling replica. What is unusual is 1,200 connected clients.

  1. SLOWLOG GET 25 — first, always. If one command is taking hundreds of milliseconds, everything else queues behind it (F1) and you have your answer in one step. Look for KEYS, HGETALL, SMEMBERS, LRANGE 0 -1, a large DEL, or a slow script. Rules in: head-of-line blocking. Rules out: everything else, if it is empty.
  2. redis-cli --latency and INFO commandstats — separates "one command is slow" from "everything is uniformly slow". Uniform slowness with a clean SLOWLOG points away from Redis and toward the network, a noisy neighbour, or the client side. INFO clients matters here too: 1,200 connections is a lot, and a client library that has lost its connection pool and is opening a connection per request produces exactly this picture — latency that is real but not Redis's fault.
  3. INFO persistence — is rdb_bgsave_in_progress or an AOF rewrite running? A fork() on a large instance stalls the process for the duration of the copy, and it is periodic, which fits "was 2 ms, now 400 ms" better than a code change does. Check latest_fork_usec.

The meta-point: each command should eliminate a class of cause, not just gather information. If your first three commands cannot each rule something out, you are collecting data rather than diagnosing — and on a 400 ms p99 you do not have time for that.
