Lab 3 · The Ground Floor

I/O Multiplexing — from "one thread per user" to "one thread for everyone"

Tell a friend: Meera works the front desk of a hotel with 10,000 rooms. Nearly every room is silent nearly all the time, yet any guest may speak at any moment, and someone must answer fast. Hire one person per room and the wage bill sinks the hotel. Hire one person to sprint down the row of phones asking "anything?" and she is exhausted, and still slow. The fix is to stop asking: put a light on every line, and let one person doze in a chair until a light comes on. Your server is Meera, the rooms are network connections, and this lab is how one thread comes to hold ten thousand of them for almost nothing.

The trainer for this lab is visualization.html, which races all three designs on the same traffic. The runnable servers and experiments live in src/. How the numbers were made, and where this lab sits among your others, is in section 20 at the end.

BEGINNER MODEL

1. Why is waiting the only thing your server really does?

In one breath: Ten thousand people have your chat app open, and five of them are typing. Your server spends its whole life waiting on the other 9,995. So the one question that decides your cloud bill is what waiting costs.

Asha, Arjun and Priya have your chat app open. So do 9,997 other people.

At this instant, five people in that crowd are typing. Everyone else is reading, scrolling, or has the phone face-down on a table.

You cannot hang up on the quiet ones. The moment Priya types "on my way", it has to appear on Asha's screen straight away. A connection you closed can deliver nothing.

So look at what your server is actually doing. It is not computing. It is not serving. It is waiting, on 9,995 conversations that are saying nothing.

Which gives us the uncomfortable question. The whole lab is the answer to it.

What does it cost you to wait?

Two futures follow from that answer, and they are very far apart.

If waiting costs… Then one machine holds… And your chat app is…
a thread and a megabyte per person a few thousand people an infrastructure project
a few bytes in a kernel table all ten thousand, comfortably a weekend feature

Your cloud bill would scale with the number of idle people. That is the absurdity we are trying to remove. Everything in this lab is about making the second row true.

2. What does a 10,000-room hotel have to do with it?

In one breath: Forget servers for a moment. Picture a hotel where the only way to learn whether a guest is speaking is to pick up their phone line and listen.

Meera runs the front desk of a hotel with 10,000 rooms. Every room has a phone line running down to her desk.

Guests call down rarely. Asha in room 7 wants a towel. Arjun in room 9 wants to place a dinner order. Priya in room 12 has not called all week. But when one of them does speak, somebody must answer quickly, or the bad review goes up that same evening.

Now the cruel part of the setup. There is no ringer. No light, no buzzer, no notification of any kind. The only way to find out whether a guest is speaking is to pick up that line's receiver and listen.

Meera's job is to staff that desk. That is your server's job too, one word at a time.

3. Why not simply hire one person per line?

In one breath: Give every line its own employee, holding the receiver to their ear all day. It is simple, it is correct, and it is how almost every tutorial server is written.

The obvious answer: hire 10,000 employees.

Meera becomes employee #9. She holds room 9's receiver against her ear all day, waiting for Arjun to say something. Employee #4,127 does the same on line 4,127. Nobody is ever missed, because no line is ever shared.

When Arjun finally speaks, Meera hears him instantly and handles it. Fast, simple, obviously correct.

In code this is thread-per-connection. Every connection gets its own thread. That thread sits inside a read() call which does not return until bytes arrive. Holding the receiver to your ear is read(), and Meera's whole day is one thread. The file is src/BlockingEchoServer.java, and here is its heart:

Socket client = serverSocket.accept();
new Thread(() -> handle(client)).start();   // one thread, one connection, forever
...
int n = in.read(buf);   // this thread now sleeps here until bytes arrive

This is how virtually every tutorial socket server is written, and it works.

🔮 Predict: 10,000 connections, all silent, one thread each. Roughly how much CPU is this server using?

Reveal

Almost none. This is the part people get wrong. A thread waiting inside read() is not spinning. The operating system has taken it off the CPU entirely, and will not schedule it again until data arrives. Zero CPU.

If you guessed "10,000 threads must be burning the machine down", you were picturing 10,000 people checking. They are not checking. Each one is asleep, and sleeping is free.

So if CPU is free, what actually breaks? That is the whole point of the next section, and the answer is a different resource.

4. If the CPU is idle, what actually runs out?

In one breath: Employees are not free even when they do nothing. Each thread claims memory and a slot in the operating system's bookkeeping, and those run out long before the network does.

Run it and count:

$ java src/Experiments.java threads 2000

  thread-per-connection : 2000 connections -> 2000 handler threads
  io-multiplexing       : 2000 connections -> 1 event-loop thread

Ignore that second line for now. It is the answer we have not invented yet, printed so you can see where this is heading. Only the first line is today's design.

Two thousand connections, two thousand threads. The scaling is exactly 1:1.

🔮 Predict: Meera's hotel now employs 10,000 people who each do nothing all day. Which resource gives out first — the CPU, the memory, or the network card?

Reveal

Memory, and then the scheduler. The network card is barely involved; 10,000 idle TCP connections carry almost no traffic. The CPU is idle too, as the previous prediction showed.

If you said "the network card", you were sizing the traffic. The traffic is tiny. What is enormous is the staff list, and the staff list is held in memory and walked by the scheduler.

Three separate bills arrive with a thread each, and every one of them is about staff, not about guests.

What it costs The number What that number means
Stack reserved per thread about 1 MB address space each thread claims on a 64-bit JVM

Read the first three rows together. You run out of memory long before you run out of network capacity.

The fourth row costs you differently. Switching between threads means saving one set of CPU state, restoring another, and dirtying the CPU's caches on the way. With five active users and 10,000 threads, the machine spends its time managing employees instead of serving guests.

This was famous enough to earn a name in 1999: the C10K problem. How do you serve ten thousand concurrent connections on one machine? Thread-per-connection could not.

Now look harder at what is actually being wasted. Those 9,995 employees are not doing work. They are doing waiting. Waiting is not a task; it is the absence of a task. The hotel is paying 10,000 salaries so that 10,000 people can each be individually informed of something.

Why does waiting need a person at all?

5. What if one person just runs down the row?

In one breath: Keep one employee and make her sprint. She never holds a receiver; she picks each one up, hears nothing, drops it, and moves on forever.

Fire everyone. Keep Meera.

Give her a new rule: never hold a receiver to your ear. Instead, sprint down the row of 10,000 phones. Pick up line 1 — "anything? no" — drop it. Pick up line 2 — "anything? no" — drop it. On reaching line 10,000, run back to line 1 and start the lap again.

For this to work, Meera needs a phone that answers "nothing here" instantly instead of making her wait. Otherwise the first silent line traps her for the rest of the day.

In code that phone is a non-blocking socket: a connection configured so that a read with no data returns immediately, saying "no data right now", instead of parking your thread. In Java you switch a connection into that mode with one call, and then a read of an empty connection returns 0 rather than sleeping:

channel.configureBlocking(false);   // read() now returns 0 instead of waiting
...
int n = ch.read(buf);               // 0 = nothing right now, keep running

That is src/SpinEchoServer.java. One thread, all 10,000 connections, no thread explosion. Problem solved?

🔮 Predict: 2,000 silent connections, three seconds of this. How much CPU does the single thread burn, and how many times does it hear "nothing"?

Reveal

A full CPU core, pinned at 100%, and roughly four million "nothing" answers. The exact numbers are in the next section.

If you guessed "not much, it is only one thread", you were counting threads rather than questions. One thread can ask millions of questions per second, and every question costs.

6. Why is asking ten thousand times worse than waiting?

In one breath: Meera's sprint burns a whole CPU core while absolutely nothing happens, and each new guest makes every lap slower.

Here is what the sprint costs, for 2,000 connections over three seconds:

  hot-loop polling : 2,998 ms CPU burned | 2,111 loop passes | 4,225,570 readiness questions asked
  io-multiplexing  :     0 ms CPU burned |     0 wakeups     |         0 readiness questions asked

"Readiness question" is the program's phrase for one "anything for me?". The proper name for it arrives in §9. Again, only the first line is today's design.

CPU burned in 3,000 ms of wall clock 2,998 ms one core pinned at 100%, permanently

Say that last row out loud. Meera asked "anything for me?" 4.2 million times, and heard "no" 4.2 million times.

Each of those questions is a system call — a request from your program into the operating system's core. That core is the kernel: the privileged code that owns the network card and every connection on the machine. System calls are cheap one at a time and ruinous by the million. They are the expensive part of this design.

And it degrades as you grow. Every lap costs one question per connection, so doubling the connections doubles the cost of a lap. The busier your server looks on paper, the slower each lap becomes, and the longer a guest waits before Meera reaches their phone.

We have now failed twice, in opposite directions.

One thread per connection 10,000 ~0 memory + scheduler collapse
One thread, keep asking 1 100% of a core pointless syscalls, one per connection per lap

Both failures share a cause, and it is not obvious.

🔮 Predict: Meera is standing in a room full of phones, asking each one "anything?" and hearing "no". Somebody in that building already knows exactly who is speaking, and has known since the instant they started. Who?

Reveal

The phone system itself. In code, the kernel.

The kernel receives every network packet. At the instant a packet lands it already knows which connection that packet belongs to — it had to, to file the bytes in the right place.

If you guessed "the guests know", you are right but stuck. Asha cannot reach the desk except through the phone system, and the phone system is the thing we are refusing to ask properly.

In both failed designs we are the one asking the question, and we are the worst possible party to ask it. We are standing next to the one entity that has the answer, asking everyone else, over and over.

7. What exactly do we need instead?

In one breath: One thread must be able to wait on many connections at once, and be told which of them woke it. No ordinary read can do that.

State it plainly, because the rest of the lab is the pursuit of this one sentence:

One thread must be able to wait on many connections at once, and be told which ones need attention — without asking each one individually, and without using CPU while nothing is happening.

Read the first clause again: wait on many connections at once. That is the thing an ordinary read() cannot do. A blocking read waits on exactly one connection. There is no way to say "wait until any of these 10,000 has something."

So we do not need a faster loop. We need a new kind of wait, one that covers a whole set.

8. What if the phone system switched on a light?

In one breath: Hand your entire list of connections to the kernel and go to sleep. The kernel wakes you when at least one of them has something, and hands you the list of which ones.

Install a light board.

Every phone at Meera's desk gets a light. When Arjun starts speaking, the phone system switches line 9's light on. Meera does not run and does not listen. She sleeps in a chair. The phone system wakes her the instant any light comes on, and then tells her exactly which lines are lit.

One system call does all of that:

Hand the kernel your entire list of connections and go to sleep. The kernel wakes you when at least one of them has something, and hands you the list of which ones.

That call is the whole concept. An idle connection costs the kernel a small bookkeeping entry, and costs your thread nothing. No thread, no question, no CPU.

Ten thousand silent connections therefore produce exactly zero wakeups. That is not a hope. It is the second line of the experiment you already read in §6: 0 ms CPU burned | 0 wakeups. Those are the same 2,000 connections that cost the sprinting design a whole core.

9. What are the real words for what Meera just did?

In one breath: You have already felt every one of these problems. Here are their professional names, each attached to the moment in the story where you met it.

The words arrive in the order you earned them.

Why is it called "multiplexing" rather than "sharing"?

Meera watching a whole wall of lights, alone, is I/O multiplexing. Said precisely: a kernel facility that lets a single thread block on the readiness of a set of file descriptors, returning the subset that is ready.

The word comes from telecoms, where multiplexing means sending many signals over one shared channel. Here the shared channel is one thread of execution, and the many signals are the connections. The name exists to distinguish this from having one channel per signal, which is exactly §3's design. One thread holding 10,000 chat connections is the direct answer to §4's C10K problem.

What number does the kernel know a guest by?

Meera does not think "Arjun". She thinks "line 9". The kernel is the same. It hands your program a small integer as a handle to an open thing: a file, a pipe, or a network connection. That integer is a file descriptor, almost always shortened to fd. Technically it is a per-process index into the kernel's table of open file descriptions.

Unix deliberately made network connections look like files, so that the same calls (read, write, close) work on both. That is why "everything is a file" is a Unix slogan. Asha's connection is fd 7, Arjun's is fd 9, Priya's is fd 12. Those are the numbers you hand the kernel.

In Java you rarely see the integer, because a SocketChannel wraps one. You still meet the count: the open-file limit, ulimit -n, counts file descriptors, and it is the wall you hit at high connection counts.

Who waits — your thread, or nobody?

In §3 Meera held the receiver and waited. In §5 the phone answered "nothing here" and she moved on. That is the difference between blocking and non-blocking, and it is a setting on each individual descriptor.

Blocking means the call does not return until it can make progress. Non-blocking means the call returns immediately with a "would have blocked" indication — 0 in Java NIO, EAGAIN in C. The pair of words exists to name one choice: who waits, the thread or nobody.

You set it with channel.configureBlocking(false), as SpinEchoServer does. Java's Selector requires non-blocking channels; registering a blocking one throws IllegalBlockingModeException. Note what that implies. Neither mode was enough on its own, and the real fix combines non-blocking sockets with a blocking wait on the whole set.

What does a lit light actually promise?

The light on line 9 means one thing. If you pick up that receiver right now, you will hear something instead of waiting. Engineers call that readiness.

The kernel reports it in four flavours. Readable means bytes are buffered, or the stream has ended. Writable means the send buffer has room. Acceptable means a connection is pending. Connectable means an outbound connect has finished.

The term exists to separate "you may now act" from "your action has been done for you". That single distinction defines two whole families of I/O API, and the second family arrives in §16. Here, readiness is the light: the kernel says fd 9 is readable, and then you call read(9) yourself, which returns immediately.

Read the promise again carefully, because §13 is built on what it leaves out. The light says someone is speaking. It does not say what they said, how much of it arrived, or whether they finished their sentence.

Which two sets do beginners fuse into one?

Meera's board holds two different pieces of information, and they are easy to confuse.

The interest set is "what to wake me for". It is the registration held inside the kernel: a descriptor, plus the event types you care about. It is long-lived, and you are the one who sets it. Wiring a phone into the board with channel.register(selector, OP_READ) puts fd 9 into that set and leaves it there.

The ready set is "what actually happened". It is the subset the kernel hands back from one wait call, and it is fresh every time. One wait can return a ready set of {fd 9} while fds 7 and 12 stay registered, idle and untouched.

In Java a SelectionKey is one entry in the interest set, and selector.selectedKeys() is the ready set.

What is the shape of Meera's whole day?

Sleep, get woken, handle whatever is lit, go back to sleep. That routine is an event loop. In code it is one thread running while (running) { wait for readiness; dispatch each ready event to its handler; }, which is the eventLoop() method in SelectorEchoServer.

The term names an inversion of control. You no longer write "read, then process". You write handlers, and the loop calls them when the kernel says so. This is the same shape as a UI framework's main loop, and the same shape as Node.js and nginx. Once you have seen it here, you recognise it everywhere.

Why is "asynchronous" the word that trips everyone?

This is a different axis from blocking and non-blocking, and mixing the two up causes most of the confusion around this whole topic.

The question being asked The two answers What it decides
Does the call park my thread? blocking / non-blocking who waits: the thread, or nobody
Do I perform the I/O, or does someone else? synchronous / asynchronous who copies the bytes, and when you are told

I/O multiplexing is synchronous, non-blocking I/O with a blocking wait. The kernel tells you a connection is ready. You still call read() yourself, and the bytes are copied while your thread waits for that copy. Nobody did the read for you.

It looks asynchronous because your code is callback-shaped. The data movement is still yours. True asynchronous I/O is the other thing: you hand over a buffer and are told "it is filled" later. That family is io_uring, Windows IOCP, and Java's AsynchronousSocketChannel.

The simple picture — what does Meera see?

That picture is enough to reason about cost, and it is the one to carry into a design discussion.

The engineering picture — what does the kernel hold?

One thread. A kernel object holding a set of registered descriptors, and the events wanted for each. A blocking call that returns the ready subset. A loop that dispatches each ready descriptor to a handler, then calls the wait again.

All per-connection state lives in objects on the heap, because there is no per-connection stack to hold it.

Where does the story lie to you?

Three places. Each lie is a real failure mode, and each one has a number in §13.

Lie 1: a lit light does not mean a complete sentence. The operator story suggests you pick up and hear the whole request. In reality "readable" means only "some bytes are here". Half a message is normal. A message split across 76 separate wakeups is normal, and §13.3 measures exactly that. The light also comes on when the guest hangs up, because "readable" includes end-of-stream. Forgetting that causes the bug in §13.2.

Lie 2: the operator can never leave the chair. A real operator can put a call on hold and walk to the kitchen. The event-loop thread cannot. One slow database query, one Thread.sleep, one synchronous HTTP call, and every light goes unanswered until it returns. The whole board freezes. §13.1 puts a number on it: 905 ms of collateral damage from one slow request.

Lie 3: the lights can lie. The kernel is permitted to report readiness spuriously. You wake up, read, and get nothing. Correct event-loop code treats a wakeup as a hint, never a promise, and must survive a read that returns zero bytes.

INTERMEDIATE MODEL

12. How does the wait call work, and why was the first one too slow?

In one breath: The first version handed the whole guest list to the kernel on every single call. The second version left the list with the kernel, and asked only "who is lit?". That change is the difference between C10K being impossible and being routine.

We build it in the order history did. The obvious version first, then the failure that forced the version you actually use.

Keep one concrete scene in view throughout. A chat server with three connections: Asha on fd 7, Arjun on fd 9, Priya on fd 12. Only Arjun types.

Mechanism v1 — what did select() promise in 1983?

The first system call to do this. In the hotel it is a light board that Meera has to re-wire completely before every nap.

Its contract, step by step:

  1. You build a set of descriptors: {7, 9, 12}.
  2. You call select(), passing the whole set in. Your thread sleeps.
  3. Arjun types. A packet lands. The kernel returns from select().
  4. It hands back the set, with everything not ready removed: {9}.
  5. You call read(9) and get Arjun's message.
  6. You rebuild the set and call select() again.

Follow the arrows downwards. Step 3 is the nap, and the last line is the part that will hurt later.

This satisfies §7's requirement exactly. For three connections it is perfect.

🔮 Predict: Now scale the scene up. 10,000 connections, one of which is active. How much work does the kernel do inside a single select() call?

Reveal

It examines all 10,000 — on every single call. Two costs, both proportional to the total number of connections rather than the active ones:

  1. Copy in. The whole 10,000-descriptor set is copied from your process into the kernel on every call, and the result is copied back out.
  2. Scan. The kernel walks all 10,000, checking each one for readiness.

If you guessed "one, because only one is active", you were describing the design that comes next. It did not exist yet in 1983.

We fired the sprinting employee in §6 for doing exactly this work — asking every line on every lap. select() did not delete that work. It moved it into the kernel, where it is much cheaper per item, because there is no system call per connection. It is still proportional to the total.

select() also carries a hard cap. The descriptor set is a fixed-size bitmask called FD_SETSIZE, conventionally 1024 entries. poll(), from 1986, removed the cap by using an array instead of a bitmask. It kept the copy and the scan.

The refinement — what did epoll and kqueue change in 2000–2002?

The scar from that failure produced the design you actually use. It comes from one observation:

The set of connections barely changes between calls. Why re-send and re-scan it every single time?

So split the one call into two, and let the kernel keep the list. Meera's board gets wired once, and stays wired.

  1. Register once. In the hotel, plug Arjun's line into the board and leave it there. In words: tell the kernel to remember that you care about fd 9. As a call, epoll_ctl(ADD, fd 9). It stays across calls, with no re-copying.
  2. The network stack maintains a ready list. This is the key move. When Arjun's packet arrives, the code handling the network interrupt already touches fd 9's structures, so it appends fd 9 to a ready list right there. No scan is needed, because readiness is recorded at the moment it is caused.
  3. The wait returns that ready list. epoll_wait() returns {9}, copying one entry rather than 10,000.

The cost changes from O(total connections) to O(ready connections). Ten thousand idle connections now cost nothing per call. They are entries in a kernel table and nothing more.

The refinement's own refinement — why can edge-triggering hang a connection?

One more knob, and one more failure that explains why the knob exists.

Picture the light again. Level-triggered means the light stays on while there are unread bytes, so you get woken again on the next wait if you did not consume everything. Edge-triggered means the light flashes once, on the transition from not-ready to ready, and then goes dark regardless of how much you read.

Edge-triggered means fewer wakeups. It also sets a trap. If you do not drain the socket completely, you will never be told again. That connection then hangs forever while everything else works, which is one of the nastiest bugs in this area, because it presents as a network problem.

Java's Selector is level-triggered. That is the forgiving default, and it is why SelectorEchoServer can read one bufferful and safely return. Netty's native Linux transport offers edge-triggering for throughput, and its documentation is emphatic: you must loop reading until the socket says EAGAIN.

13. What breaks, and how would you recognise each one at 3 a.m.?

13.1 Why did Arjun's ping take 905 ms when Asha placed a slow order?

Asha (client A) sends a request whose handler takes a full second — a database lookup, say. One hundred milliseconds later Arjun (client B) sends a one-word "ping". Create it with java src/Experiments.java blockedloop:

  io-multiplexing (1 shared loop) : B's ping took 905 ms
  thread-per-connection          : B's ping took   0 ms

The event loop is one thread. While Meera is standing in the kitchen sorting out Asha's order, nobody is watching the board. Arjun's bytes physically arrived at the network card within a millisecond, and then sat unread in a kernel buffer until she came back.

Read Arjun's 905 ms carefully. It is not caused by Arjun, and it has nothing to do with Arjun's request. Correctness survives — his echo is right when it finally comes. Latency isolation does not. A shared loop means shared fate, and one slow handler is a partial outage for every connection on that loop.

This is the number one event-loop bug in the world. The rule that follows is absolute. On the loop thread: no JDBC call, no synchronous HTTP client, no Thread.sleep, no unbounded loop, no synchronized block that might contend, and no large JSON parse. Slow work goes to a separate worker pool, and the result is posted back to the loop. Netty ships EventExecutorGroup for exactly this. Netty and Vert.x both log a warning when a loop thread stalls, and Vert.x's BlockedThreadChecker produces a "blocked event loop" line you will meet in real logs.

13.2 Why does a guest who hung up keep her light on forever?

Priya closes the app. Her connection ends. What does her light do?

🔮 Predict: Priya's line goes dead, and the handler treats "nothing to read" as "try again later". In half a second of otherwise total silence, how many times does the loop wake up?

Reveal

351,609 times. A correct server wakes zero times in the same window.

If you guessed "once, then it settles down", you are assuming the light turns off. It does not. A closed connection is permanently readable, and level-triggering means "keep telling me while the condition holds".

Create it with java src/EchoTest.java broken, which runs the same test suite against src/BrokenSelectorServer.java:

  correct : closed_connection_is_deregistered_and_loop_sleeps  → 0 wakeups in 500 idle ms
  broken  : FAIL — 351,609 wakeups in 500 idle ms

When the peer closes, reads return -1 forever. That value is end-of-stream: the connection is finished, not empty. The broken handler reads it as "no data, try later" and returns without cancelling the registration. So the wait call returns instantly, forever. That is 351,609 laps in half a second, one core at 100%, caused by a guest who left.

The correct code closes the loop on the condition instead of ignoring it:

if (n == -1) { key.cancel(); ch.close(); return; }   // deregister, or spin forever

Every other connection keeps working perfectly, which is exactly what makes this so hard to spot. What you lose is the CPU budget, and eventually latency for everyone. On a dashboard the symptom is 100% CPU on one core with no traffic, which looks insane until you know this. A flame graph or perf top shows the wait call returning immediately in a tight loop, and strace -c shows millions of epoll_wait calls returning instantly.

13.3 How can one message arrive seventy-six times?

Asha sends a single 512 KB photo caption in one call. Her code sent one message. How many times does Meera's light come on?

🔮 Predict: One application message, 512 KB, one write on the client. How many separate readiness events does the server see?

Reveal

76. And 108 separate read() calls to drain them.

If you guessed "one, because it was one message", you are trusting the analogy from §10. TCP is a byte stream, not a message queue. It promises your bytes arrive in order and complete, and promises nothing whatsoever about how they are grouped.

Create it with java src/Experiments.java readiness:

  bytes sent: 524,288 | bytes received: 524,288
  readiness events: 76 | read() calls: 108 | smallest chunk: 4,096 bytes | largest: 16,384 bytes
What was counted Value What it means
Bytes sent, bytes received 524,288 each nothing was lost or reordered
Readiness events 76 the light came on 76 times for one message
read() calls 108 some of those wakeups needed more than one read
Smallest chunk 4,096 bytes the kernel's receive buffer hands over what it has
Largest chunk 16,384 bytes and never the whole 512 KB at once

The kernel's receive buffer is finite, so it hands you 4–16 KB at a time. That range is the last two rows of the table, in the units people usually say them in.

Ordering and completeness within the connection survive. Any illusion of message boundaries does not.

The consequence is structural. Every protocol on an event loop must do framing: recovering message boundaries from a byte stream. The three usual ways are a length prefix (Netty's LengthFieldBasedFrameDecoder), a delimiter (HTTP's blank line, or \r\n in Redis), or a self-describing format.

And between wakeups the half-arrived message has to live somewhere. With no per-connection thread there is no per-connection stack, so it lives on the heap, per connection. That is what the ByteBuffer attached to each SelectionKey in SelectorEchoServer is for.

This is the real price of the whole approach. With a thread per connection, "read until I have a whole message" is a local variable and a loop. With one shared thread it becomes an explicit per-connection state machine, and that is the reason non-blocking code is harder to write.

13.4 What happens when Meera is the one who cannot get a word in?

Not runnable here, because this lab's echoes are small. Treat it as flagged theory rather than a number from a run.

Writes can be partial too, exactly like reads. A call to write() returns "I accepted 3 KB of your 100 KB" when the kernel's send buffer fills, because the peer is reading slowly. You must buffer the remaining 97 KB, and register interest in writability so the kernel tells you when there is room. In Java that interest flag is OP_WRITE.

Here is the trap, and it is the mirror image of §13.2. A socket is writable almost all the time. Leave OP_WRITE registered permanently and the wait call returns immediately, forever — the same busy loop, arriving from the other direction. The rule is narrow: register writability only while you have leftover bytes, and deregister the moment they drain.

The second trap is backpressure. If a client reads slowly and you keep queueing outbound data on the heap, you have built an unbounded queue and you will run out of memory. Netty's answer is a pair of watermarks, WriteBufferWaterMark and Channel.isWritable(): past a high-water mark you stop producing.

13.5 Why do ten sleeping operators all wake for one guest?

Run several event loops, one per core, all registered for new connections on the same listening socket. In Java that interest flag is OP_ACCEPT.

One connection arrives. All the loops wake. One wins the accept(). The rest find nothing to do and go back to sleep, having burned a wakeup each. Engineers call that a thundering herd.

There are two standard fixes. Use a dedicated acceptor loop that hands new connections to workers, which is Netty's "boss" and "worker" group split. Or use SO_REUSEPORT, where each loop opens its own socket on the same port and the kernel load-balances arrivals between them.

Note the correctness point riding along with it, because it is §10's third lie in concrete form. Readiness is a hint. An accept() on a supposedly acceptable socket may legitimately return null, because another thread took the connection first. Code that assumes a non-null result crashes here.

13.6 Who decides which lit line Meera answers first?

Nobody. The loop handles ready connections in whatever order the ready set gives them.

Now imagine one very chatty guest. Handled with "read until the socket says EAGAIN", that one connection can hold the loop for a long time while every other lit line waits. Netty caps the damage with maxMessagesPerRead.

This is head-of-line blocking at the event-loop level. It is the same phenomenon you met in the communication-protocols lab at the connection level, one layer up.

13.7 If nobody is waiting, who notices a guest who went silent?

Subtle, and easy to miss entirely.

With thread-per-connection, a per-connection timeout is trivial. The call socket.setSoTimeout(30_000) works because that thread is already waiting on that one connection, so it can simply give up.

With an event loop, no thread is waiting on any particular connection. So there is nothing to time out. Priya's connection goes silent forever, never appears in a ready set again, and holds its memory and its file descriptor indefinitely. Nobody is watching her line, because nobody is watching any line.

Idle detection therefore has to become an explicit, separate mechanism: a timer that sweeps connections by last-activity timestamp. Netty's IdleStateHandler and its HashedWheelTimer exist for precisely this.

13.8 What if the light board itself is faulty?

Historically, on Linux, Selector.select() could return 0 with no keys ready, repeatedly and instantly. This is the epoll spin bug, JDK-6670302 and JDK-6693490, caused by epoll reporting an event that Java's selector did not map to any interest. The result was §13.2's busy loop with no bug in your code at all.

Netty's workaround still ships today. It counts consecutive premature returns and, past a threshold set by io.netty.selectorAutoRebuildThreshold with a default of 512, it builds a new Selector and migrates every registration to it.

The bug has been reported fixed in several JDK versions. The guard remains because the failure was so severe. It is worth knowing not because you will hit it, but because it explains why production event-loop code contains defences that look paranoid.

14. What does the kernel actually promise, and what does it refuse to?

In one breath: The kernel promises Meera will not be stuck when it says "ready". It promises nothing about meaning, fairness, or how much arrived.

Everything below is a promise made to Meera (the event-loop thread) about Asha, Arjun and Priya (the registered connections).

What can you rely on?

  • If the kernel reports readable, a read will not block. It may still return 0.
  • Bytes within a connection arrive in order and without gaps. That is TCP's guarantee, inherited whole.
  • Level-triggered notification is repeated while the condition holds, so handling data incrementally is safe.
  • Interest registration is durable. Registered once, it stays until cancelled.

What is explicitly not promised?

  • That "readable" means a complete application message arrived (§13.3).
  • That readiness will not be reported spuriously. A wakeup is a hint.
  • That a "ready" operation will succeed; accept() may return null (§13.5).
  • That connections are served fairly (§13.6).
  • That a write accepts all your bytes (§13.4).
  • Any liveness property at all if a handler blocks. The loop is a single point of stalling (§13.1).

What did you trade away on purpose?

Each row is one bargain, and you signed all four when you installed the light board.

You gain You give up
~1 thread instead of N latency isolation between connections
~zero cost per idle connection the simple "read a message" programming model
cost proportional to ready, not total per-connection timeouts as a free feature
no thread-count ceiling stack-held state; you now write state machines

That last row is the honest summary of the whole technique. It converts a memory-and-scheduler problem into a programming-model problem. You get density. You pay in complexity and in shared fate. Which is precisely why §16's ending matters so much for a Java engineer today.

I/O multiplexing did not go away. It moved under the floor. Which changes the engineering advice in four specific ways.

Write thread-per-connection code again. A blocking read() on a virtual thread gives you §3's simple programming model with §8's efficiency. No framing state machines, no callbacks, and try/finally and stack traces work properly.

§13.1 stops applying to your code. Blocking a virtual thread blocks only that request, because the carrier is released. The cardinal sin is a sin only on a real event loop.

Solutions — I/O Multiplexing

Attempt EXERCISES.md first. Every number quoted here was produced by running the code in this lab on the author's machine; yours will differ in magnitude but not in shape. Rungs 7–8 are discussions, not single right answers.

Rung 1 — Explain

1. Why thread-per-connection fails at 10,000 users.

The resource that runs out is memory and scheduler capacity, not CPU.

A thread waiting inside read() uses no CPU at all — the OS has descheduled it entirely and will not touch it until bytes arrive. That is exactly why the answer surprises people. What it does consume is a call stack (about 1 MB of reserved address space per thread on a 64-bit JVM), a kernel thread structure, and a slot the scheduler must consider. Ten thousand connections means ten thousand of each, so you exhaust memory and drown the scheduler in bookkeeping while the CPU sits idle. There is also a hard OS limit on thread count that arrives regardless of how much RAM you buy.

The one-line version: we are paying 10,000 salaries for 10,000 people to each be individually informed of something.

2. Why the polling loop is also wrong.

It wastes CPU and system calls. To avoid parking, each connection must be non-blocking, so the loop asks every connection "anything for me?" and gets "no" almost every time. Measured: 4.2 million questions and a full core pinned at 100% across three seconds in which nothing happened. Each question is a real syscall — cheap individually, ruinous in millions. It also degrades as you grow: a full lap costs one question per connection, so latency for any given user gets worse as the server gets more popular.

3. What the kernel does that neither design could.

The kernel receives the packets, so at the instant data lands it already knows which connection it belongs to — no asking required. So it can hold your entire list of connections, let your thread sleep, and wake it only when something actually happens, handing back exactly which connections are ready.

4. Correcting the colleague.

"No — multiplexing tells you you may read now; you still call read() yourself and your thread waits for that copy. It is synchronous, non-blocking I/O with a blocking wait. The thing you are describing, where the kernel performs the read and notifies you on completion, is asynchronous I/O — io_uring, Windows IOCP, or Java's AsynchronousSocketChannel."

Rung 2 — Identify

1. Interest set: client.register(selector, SelectionKey.OP_READ, ByteBuffer.allocate(4096)); (also serverChannel.register(selector, SelectionKey.OP_ACCEPT) at startup). Ready set: Iterator<SelectionKey> it = selector.selectedKeys().iterator();

Registration runs once per connection; reading the ready set runs on every loop pass. That asymmetry is the whole efficiency argument for epoll/kqueue over select (README §12): the expensive list is stated once and lives in the kernel, rather than being re-sent on every call.

2. It is the attachment — that connection's private state, and here specifically its read buffer. It must exist because with one thread serving every connection there is no per-connection stack to hold a half-arrived message. README §13.3 is the section: a 512 KB message arrived across 76 readiness events, so the fragment has to live on the heap between them. This is the structural cost of the technique — stack-held state becomes an explicit state machine.

3. The thread-per-connection panel's counter climbs to match the connection count; the multiplexing panel stays at 1. The CPU meter reads roughly zero for thread-per-connection (blocked threads are free in CPU terms), pinned for the polling panel, and roughly zero for multiplexing. The lesson is that the two "cheap" designs are cheap on different axes, and only multiplexing is cheap on both.

4. The field is loopIterations. A 0 proves the thread was never woken across those 3 seconds — it was asleep inside select(), not looping quickly. This is the distinction between "efficient polling" and "not polling at all", and it is why idle connections are genuinely free rather than merely cheap.

Worth internalising, because it is a real and frequently misdiagnosed production ceiling (README §16 lists it among the operational limits): when load-testing a server from one machine, you usually measure your load generator's port limit, not your server's capacity. Real gateways see 2M connections because those arrive from millions of distinct client IPs, each with its own port range.

That is the real lesson, and it is worse than "it uses more CPU": your per-connection latency degrades linearly with popularity. A user's message waits for the loop to walk every other connection first. The design does not fall over — it gets quietly, uniformly slower for everyone.

3. A 5 KB message will almost always need one readiness event: it fits comfortably inside the kernel's receive buffer and inside a single read(). Roughly, anything below the socket receive buffer size (tens of KB by default, tunable via SO_RCVBUF) that is also sent as one write will usually arrive as one event.

But "usually" is the trap. A single TCP segment is typically ~1.4 KB on Ethernet, so even a 5 KB message physically crosses the network in several packets — you got one event only because they arrived faster than your loop came round. Under a different network, a slower sender, or a busier loop, the same 5 KB message splits. There is no message size that guarantees one event, which is why framing is mandatory rather than an optimisation.

4. Event-loop server: roughly 3 seconds — the three slow handlers run back to back on the one thread, and B waits behind all of them. It is additive. Thread-per-connection: still roughly 0 ms — B has its own thread and is unaffected no matter how many slow requests are in flight.

The general rule: on a shared event loop, latency for any connection is a function of the total work queued on that loop, not of that connection's own work. Slow handlers do not just hurt themselves; they serialise everyone.

5. A core pinned at 100% while the connection is idle. It matches README §13.2 (the busy loop) — a socket's send buffer is empty almost all the time, so it is writable almost always, so a permanently-registered OP_WRITE makes select() return instantly forever. Same failure as the unclosed dead connection, from the write side. The rule: register OP_WRITE only while you have leftover bytes, and deregister the instant they drain.

Liveness is lost, safety is kept. Nothing incorrect happens — no bytes are lost, corrupted, or mixed between connections; the echo is perfectly correct when it eventually arrives. That mapping matters: event-loop blocking is a liveness bug, which is why it produces latency alarms and timeouts rather than data corruption, and why it can hide in production for a long time.

Exception in thread "selector-loop" java.lang.NullPointerException:
    Cannot invoke "SocketChannel.configureBlocking(boolean)" because "<local1>" is null
	at SelectorEchoServer.handleNewConnection(SelectorEchoServer.java:89)

The mechanism, in interest-set/ready-set terms: the selector adds to selectedKeys() but never removes from it. Clearing handled entries is the application's job. So the accept key, handled once when the client connected, stays in the ready set forever and is re-dispatched on every subsequent pass. The second time handleNewConnection() runs there is no pending connection, so accept() correctly returns null, and the code dereferences it.

Three lessons: the ready set is a mutable buffer you own, not a fresh snapshot; readiness is a hint — a "ready" accept() may legitimately yield nothing (the same reason thundering herd is survivable, README §13.5); and the event loop catches only IOException, so a RuntimeException kills the thread and silently takes every connection with it. Real event loops wrap dispatch in catch (Throwable) for exactly this reason.

4. Thread.sleep(1) in the spin loop. CPU collapses because the loop now runs ~1,000 times a second instead of millions. It is not acceptable because it costs two things:

  • Latency. Every message now waits up to 1 ms (plus a full lap) before anyone looks at it. You have traded a CPU problem for a latency floor that no amount of hardware removes.
  • The scaling problem is untouched. Each lap still costs one syscall per connection. At 20,000 connections a lap cannot finish inside 1 ms anyway, so the sleep becomes irrelevant and you are back to §6.

This is the honest reason polling-with-a-sleep is not "good enough": it is a tunable trade between wasted CPU and added latency, and multiplexing refuses the trade entirely — zero CPU and immediate wakeup.

Rung 5 — Implement

Verified: this implementation takes FramingTest from 0 passed, 5 failed to 5 passed, 0 failed.

static byte[] nextCompleteMessage(Conn c) {
    if (c.len < 4) return null;                       // can't even read the length yet
    int n = ByteBuffer.wrap(c.buf).getInt(0);         // big-endian length prefix
    if (c.len < 4 + n) return null;                   // prefix known, payload incomplete
    byte[] payload = new byte[n];
    System.arraycopy(c.buf, 4, payload, 0, n);
    c.consume(4 + n);                                 // drop prefix AND payload
    return payload;
}

Four details carry the whole exercise:

  • Two separate incompleteness checks. c.len < 4 (cannot know the length yet) and c.len < 4 + n (know the length, lack the body) are different states and both must return null. The dribble test deliberately splits the 4-byte prefix across two writes to force the first case.
  • Returning null is the normal case, not an error. Being handed half a message is the ordinary condition of a byte stream.
  • consume(4 + n) must drop the prefix as well as the payload. Dropping only the payload leaves 4 stray bytes that corrupt every subsequent frame — a bug that presents as "the protocol desynchronises after the first message".
  • The caller loops (while ((payload = nextCompleteMessage(conn)) != null)). Handling one message per wakeup is the bug the second test is built to catch: two glued messages leaves the second stranded in the buffer until unrelated traffic arrives, which in production looks like random, unreproducible hangs.

Why a byte-for-byte echo can never pass: the contract requires replying "<n>:<payload>" where n counts complete messages. Producing that number requires knowing where messages end. An echo copies bytes without ever forming the concept of a message, so it has no n to report. That is the entire point: readiness gives you bytes, and only framing gives you messages.

3. The mechanism, step by step:

  • The client closes its socket. TCP delivers the close to the server.
  • The kernel now reports that connection as permanently readable — because end-of-stream is a readable condition. A read on it returns -1 immediately, forever. Java's Selector is level-triggered, so it re-reports the condition on every call for as long as it holds.
  • BrokenSelectorServer does if (n <= 0) return; — folding -1 (end-of-stream, permanent) together with 0 (nothing right now, transient) and treating both as "try again later".
  • But the registration is never cancelled, so the condition never clears. select() returns instantly, the handler returns instantly, select() returns instantly — 351,609 times in half a second.

The bug is fundamentally a conflation of two different meanings of "no data".

cancel() removes it from the interest set; close() releases the descriptor. Either alone is insufficient — leaking descriptors will eventually hit ulimit -n.

This is the general shape of event-loop bugs and why they reach production: they are not correctness failures but resource-consumption failures on the cleanup path. Code review sees a plausible null-ish guard; functional tests pass; staging with a handful of well-behaved clients shows nothing. It surfaces only under real traffic where clients disconnect abruptly.

The defence is the test itself: assert that the loop actually goes back to sleep. It is cheap, and it catches this bug, the selectNow() mistake in rung 4.1, the permanent-OP_WRITE mistake in rung 3.5, and the JDK epoll spin bug of §13.8 — four unrelated causes, one assertion.

Rung 7 — Handle failure

7.1 Idle timeouts

Where the timestamp lives: on the per-connection state object — the SelectionKey attachment. Extend the attachment from a bare ByteBuffer to a small Conn { ByteBuffer buf; long lastActivityNanos; } and stamp it on every successful read. This is the same "no stack, so state goes on the heap" move as framing.

How the sweep ever runs — the real subtlety. selector.select() with no argument sleeps indefinitely, so if every connection is idle, nothing wakes you and your timeout never fires. Two workable answers:

  1. select(timeout). Use selector.select(1000), and after each return — whether it woke for events or timed out — sweep selector.keys() for connections past the deadline. Simple, self-contained, and costs one wakeup per second per loop even when totally idle.
  2. A separate timer thread plus selector.wakeup(). A scheduler computes the next deadline and calls wakeup() to break the loop out of select(). More precise and no idle wakeups, at the cost of a second thread and cross-thread care (mutating a Selector's registrations from another thread needs the wakeup, or you can deadlock against a concurrent select()).

Comparison: (1) is right for almost everyone — its cost is one wakeup per second, which is nothing next to the 351,609 in rung 6. (2) is what high-end frameworks do; Netty's HashedWheelTimer amortises thousands of timers into coarse buckets so a million connections do not mean a million timer objects. Sweeping all keys every second is O(total connections) — the very cost model epoll was invented to escape (§12) — so at very large scale you need the wheel or a deadline-ordered structure rather than a linear scan.

The test: open two connections; keep one active with traffic every second; leave the other silent. Assert that after the timeout the silent one is closed (its client read returns -1) and the active one still echoes.

7.2 The write side

// on write-readiness, or when new data is produced:
int written = ch.write(pending);
if (pending.hasRemaining()) {
    key.interestOps(key.interestOps() | SelectionKey.OP_WRITE);   // more to send
} else {
    key.interestOps(key.interestOps() & ~SelectionKey.OP_WRITE);  // drained — MUST clear
}

When to deregister: the instant pending is fully drained, in the same handler pass. If you forget: a socket with an empty send buffer is writable essentially always, so select() returns immediately forever — rung 3.5, and §13.2's busy loop from the write side.

Backpressure at 100 MB pending. You are queueing faster than one client can consume, and the queue is on your heap. Options, with the trade-off named:

  • Drop the connection. Safest for the server, worst for that user. Correct for a fan-out feed where a client that far behind is useless anyway.
  • Stop reading from the source (deregister OP_READ on the upstream, or stop pulling from the producer). Correct for a proxy: propagates the pressure to whoever is producing, which is the only place it can genuinely be resolved.
  • Drop messages, keep the connection — newest-wins or sample. Correct for telemetry or price ticks, where stale data has no value.
  • Grow the buffer. Not an option; it converts a slow client into an out-of-memory kill that takes down every other connection on the machine.

The general principle: an unbounded queue is a deferred crash. You must choose in advance who suffers — the slow client, the producer, or the data — because the one unacceptable answer is "the whole process". Netty encodes this as WriteBufferWaterMark plus Channel.isWritable(), which is a mechanism for asking the question, not an answer to it.

Rung 8 — Design

Discussion answers. Yours will differ; the reasoning is what counts.

8.1 Push notification gateway, 2M connections

The binding constraint — do the arithmetic first. Traffic is trivial: 2M devices heartbeating every 30 s is ~67k heartbeats/second across the fleet, and a handful of messages per device per day is negligible. So the constraint is not CPU or bandwidth. It is memory per connection, plus file descriptors.

Budget per connection: kernel socket buffers (the dominant term — tune SO_RCVBUF/SO_SNDBUF down hard, since these are tiny messages), plus your own per-connection object (identity, subscriptions, last-seen, partial-frame buffer). Get that to a few KB and 500k connections per machine is ~2–4 GB of connection state, which is comfortable. So: 4–6 machines for capacity, more for redundancy and headroom — say 10, so losing one costs 10% and the reconnect storm is survivable.

  • Event loops per machine: one per core (8–16), each owning a disjoint set of connections so no locking is needed on connection state. Accept via SO_REUSEPORT so the kernel balances new connections (§13.5).
  • Where state lives: the connection object on the owning loop. Nothing shared, nothing locked.
  • Finding device X: a routing registry — device_id → gateway_instance, in Redis with a TTL refreshed by heartbeat. Publishers look up X and forward to that gateway. Alternative: consistent hashing on device id, which removes the registry but makes rebalancing on scale-up painful, since every connection is long-lived and must be dropped to move. Given devices reconnect anyway, the registry is the safer choice.
  • In-flight messages on machine death: connections are lost, so delivery must not depend on them. Persist per-device pending messages with an ack from the device; on reconnect, drain the pending queue. Accept at-least-once and make the client deduplicate — the same conclusion as the transactional-outbox lab. Never treat "written to socket" as delivered.
  • OS limits: ulimit -n well above 500k; net.ipv4.ip_local_port_range; net.core.somaxconn for the accept backlog; conntrack table size if a stateful firewall is in the path (a classic silent ceiling); ephemeral port exhaustion on any intermediate proxy.

Dashboard — five metrics, each tied to a §13 failure:

Metric Detects

The reconnect storm deserves emphasis: if one gateway dies, 500k devices reconnect at once. Mandatory client-side exponential backoff with jitter, or the failure of one machine cascades into the failure of the rest.

8.2 The Netty → virtual threads migration

Recommendation: do not migrate the existing service. Adopt virtual threads for new services and for any rewrite you were already going to do.

The honest reasoning:

What genuinely gets simpler: business logic that currently spans callbacks becomes straight-line code. Stack traces become readable. try/finally and try-with-resources start working. The worker-pool hop for JDBC disappears — you can block directly. Debugging and profiling get dramatically better.

What does not get simpler: framing decoders (§13.3) are still needed — LengthFieldBasedFrameDecoder does not vanish, you just write the loop by hand. Backpressure (§13.4) is still yours and is arguably harder, because a blocking write hides the queue rather than exposing a watermark. TLS, protocol codecs, idle timeouts, and connection limits are all unchanged. You would be rewriting a large amount of well-tested protocol code to get an ergonomic improvement in the business layer.

Which §13 failures disappear: §13.1 only — blocking no longer poisons neighbours, which is the big win. Which survive verbatim: §13.3 framing, §13.4 backpressure, §13.7 timeouts, fd limits. Note §13.2 transforms rather than vanishes: you will not busy-loop on a dead connection, but you can leak virtual threads blocked forever on connections nobody closes — the same resource leak wearing different clothes.

What would make me recommend against it outright: heavy use of synchronized around I/O on a JDK before 24 (pinning, from the java-virtual-threads lab, puts the old ceiling straight back); native libraries in the I/O path; or a genuinely latency-critical path where Netty's pooled, reference-counted ByteBuf is doing real work that plain blocking code would replace with garbage.

De-risking: pick one new low-traffic endpoint, build it thread-per-request on virtual threads, run both in production, and compare. Do not convert the protocol layer at all in the first step.

Measure before and after: p99 and p99.9 latency (not the mean — the whole argument is about tail behaviour), allocation rate and GC pause time, peak memory at target connection count, thread/carrier counts and pinning events (JFR jdk.VirtualThreadPinned), and — the one everyone forgets — developer time to ship a feature, since that is the actual benefit being purchased.

8.3 The 100% CPU page

First three commands:

  1. top -H -p <pid> (or jcmd <pid> Thread.print) — which thread? If it is one named nioEventLoopGroup-* / selector-loop, you are in §13.2/§13.8. If it is a GC thread, this is not an event-loop problem at all and the rest of the runbook does not apply.
  2. jcmd <pid> Thread.print a few times in a row — what is that thread doing? Repeatedly parked in epoll_wait returning instantly means a spin. Sitting in application code means §13.1 (a blocked loop), though note §13.1 usually raises latency, and this page says latency is fine.
  3. strace -c -f -p <pid> for a few seconds (or perf top, or an async-profiler flame graph) — count the syscalls. Millions of instant epoll_wait returns is the signature of a busy loop and distinguishes it from real work.

Telling the candidates apart:

Cause Distinguishing evidence
§13.2 dead connection not deregistered epoll_wait returns instantly with a ready fd; the fd maps to a closed peer; CPU stepped up at a time matching a client disconnect
§13.4 permanent OP_WRITE epoll_wait returns instantly reporting writable; correlates with a large-response endpoint
§13.8 JDK epoll spin epoll_wait returns 0 keys repeatedly — nothing is ready at all, which is the giveaway that your code is not at fault
§13.1 blocked loop thread is in application frames, not epoll_wait; latency would be elevated, so this is inconsistent with the page

The fact that throughput and latency are normal is the strongest clue: the loop is doing something pointless quickly, rather than doing something slow. That points at §13.2 or §13.8 and largely rules out §13.1.

Mitigation before root cause: take the instance out of the load balancer and restart it. That is the right first move because the CPU is being burned by accumulated bad state (a zombie registration, a wedged selector) that a restart clears, and you have N other instances serving traffic — availability first.

Why it is insufficient: the bad state accumulates again. You have bought hours, not a fix, and you have destroyed the evidence. So before restarting, capture: a thread dump, a flame graph, and the fd list (lsof -p <pid> / ls /proc/<pid>/fd). Then restart. If you skip the capture, you will be paged again at 3 a.m. with exactly the same information you have now.
