Lab 18 · The JVM Underneath: One Machine, Many Threads

Java Virtual Threads — a learning lab

A complete path from "never heard of it" to production-level understanding. Everything here runs on this machine (JDK 25) via ./run.sh. The numbers quoted below are real outputs from these demos on this laptop (16 cores).

1. Why does this exist?

Most server programs spend most of their time waiting — for a database answer, for another service's HTTP response, for a file. In Java, the thing that waits is a thread, and threads were expensive: each one costs the operating system real memory and effort. So Java programs could not afford enough threads to wait on many things at once, and enormous engineering pain (thread pools, callbacks, reactive frameworks) grew around rationing them. Virtual threads exist to make threads so cheap that you never have to ration them again.

2. The problem, as a story

Imagine a restaurant where the rule is: one waiter serves one table, start to finish. The waiter takes your order, walks it to the kitchen — and then stands at the kitchen window doing nothing for twenty minutes while your food cooks. Then he brings the plate, and waits by your table while you eat, in case you want dessert.

The restaurant has 200 tables but can only afford 8 waiters. So at any moment 8 tables are being served and 192 tables sit ignored — not because the kitchen is slow, but because every waiter is standing still, waiting.

That is a classic Java web server. Table = incoming request. Waiter = thread. Standing at the kitchen window = a blocked call like resultSet = statement.executeQuery(...). The kitchen (database) could handle far more orders — the bottleneck is the number of waiters.

3. The naive solution: hire more waiters

Just create more threads! One thread per request, as many as needed. This is in fact how servlet containers always wanted to work — "thread per request" is the simplest possible programming model: your code reads top to bottom, blocks when it needs to wait, and each request's state lives comfortably in local variables on its own stack.

4. Why that fails

A Java thread was, until 2023, a thin wrapper around an operating system thread, and OS threads are costly in three ways:

  1. Memory. Each OS thread reserves a fixed stack — around 1 MB. 10,000 threads ≈ 10 GB of address space reserved for stacks alone.
  2. Creation cost and hard limits. The OS caps how many threads a process may have. Demo 1 in this lab tries to create 5,000 plain threads on this Mac and the OS refuses at #4,044 with unable to create native thread. The 100,000 virtual threads created moments earlier ran fine.
  3. Scheduling cost. The OS scheduler juggles threads by interrupting them and switching between them (a "context switch", ~microseconds each). With tens of thousands of mostly-idle threads, the OS wastes serious CPU just deciding whom to run.

So the industry compromised: keep a small thread pool (e.g. 8–200 threads) and queue the rest of the work. That caps concurrency at the pool size — our 8 waiters. The escape hatch was asynchronous / reactive programming: never block; when you need to wait, register a callback and give the thread back. It works, and it scales — but you pay with your programming model: code becomes chains of thenCompose(...), stack traces stop making sense, debuggers and profilers show you framework plumbing instead of your logic, and ThreadLocal-based tools break. Java essentially asked developers to choose: simple code or scalability, pick one.

5. The key idea

Make the thread itself cheap, so blocking becomes harmless. A virtual thread is a thread implemented by the JVM instead of the OS: its stack lives on the heap and starts at a few hundred bytes. When a virtual thread blocks, the JVM detaches it from the OS thread it was running on and lets another virtual thread use that OS thread. Waiting no longer occupies an OS thread — so you can have a million waiters, and write plain blocking code again.

In the restaurant: when table 12's order goes to the kitchen, the waiter clips the order pad to table 12's rail and walks away to serve other tables. When the kitchen bell rings for table 12, any free waiter grabs that pad — everything needed to resume is written on it — and continues exactly where the last waiter left off. 8 waiters now serve 200 tables, because waiters only ever do work, never waiting.

6. The vocabulary (now that you can see what it names)

Term Plain-English meaning
Platform thread The old kind of java.lang.Thread: a 1-to-1 wrapper around one OS thread for its whole life.
Virtual thread A java.lang.Thread implemented by the JVM: cheap, heap-allocated, not tied to any one OS thread.
Carrier thread The platform thread a virtual thread is currently riding on. The "waiter".
Mount / unmount Attach a virtual thread to a carrier to run it / detach it (typically because it blocked).
Park / unpark Park = "this thread has nothing to do until X happens" (it unmounts). Unpark = "X happened, make it runnable again".
Continuation The saved "order pad": the virtual thread's stack frames, stored on the heap while it is unmounted. (JVM-internal; you never touch it.)
Scheduler The JVM component that decides which runnable virtual thread mounts which free carrier. A ForkJoinPool with (by default) one carrier per CPU core.
Pinning A failure mode: a virtual thread blocks but cannot unmount, so it holds its carrier hostage.
Thread-per-task The programming style virtual threads enable: create a brand-new thread for every task; never pool or reuse them.

7. The mental model to carry around

A virtual thread is not a magic fast thread — it is a cheap bookmark. The JVM runs M virtual threads on N carrier OS threads (M can be a million; N ≈ your core count, 16 here). Code that is running always occupies a carrier. Code that is waiting occupies nothing but a small heap object. Virtual threads therefore multiply how much your program can wait, and change nothing about how much it can compute.

9. The actual mechanism, step by step

The lifecycle of one virtual thread:

stateDiagram-v2
    [*] --> Runnable: Thread.ofVirtual().start(task)
    Runnable --> Mounted: scheduler assigns a free carrier
    Mounted --> Parked: blocking call → park() → stack moved to heap, carrier freed
    Parked --> Runnable: the awaited event happens → unpark()
    Mounted --> Runnable: (rare) yield
    Mounted --> [*]: task returns

Walk one concrete request through it. Setup: 2 carriers (worker-1, worker-2), and virtual thread #21 is handling an HTTP request that queries a database. Virtual thread #22 is runnable, waiting its turn.

  1. Mount. The scheduler (a ForkJoinPool dedicated to virtual threads) sees worker-1 free and #21 runnable. It mounts #21 on worker-1: worker-1 starts executing #21's code, with #21's stack frames.
  2. Run. #21 parses the request, builds a SQL query — normal execution, fully occupying worker-1, at full native speed.
  3. Block → unmount. #21 calls socket.read() to wait for the DB reply. Every blocking operation in the JDK (socket reads, Thread.sleep, locks, queues...) was retrofitted for Loom: instead of blocking the OS thread, it registers interest in the event ("tell me when this socket has data" — via the OS's readiness mechanism, kqueue on this Mac) and calls park(). Park copies #21's live stack frames into a heap object (the continuation) and returns worker-1 to the scheduler. Cost: roughly a microsecond — comparable to an OS context switch, but done in Java, in user space.
  4. Carrier reuse. worker-1 immediately mounts #22. The DB takes 5 ms to answer; in that time worker-1 can run dozens of other virtual threads. This is the entire trick.
  5. Event → unpark. The DB reply arrives; the JDK's internal poller sees the socket is readable and calls unpark(#21): #21 goes back on the scheduler's run queue.
  6. Remount — possibly elsewhere. The next free carrier — say worker-2 this time — mounts #21: copies its frames back from the heap and resumes inside socket.read(), which now returns the data. #21 never knows it moved. Same Thread object, same thread-id, same ThreadLocals (the scenario test thread_identity_is_stable_across_unmount_and_remount proves this).
sequenceDiagram
    participant S as Scheduler (run queue)
    participant W1 as carrier worker-1

    W2->>VT: resume inside socket.read(), data returned

How you create them — all of these produce ordinary java.lang.Thread objects that happen to be virtual:

Thread.startVirtualThread(task);                       // fire-and-go
Thread t = Thread.ofVirtual().name("req-42").start(task);
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    ex.submit(task);                                   // one NEW thread per task
}   // close() waits for all tasks — the normal server idiom

Scheduler facts worth knowing: parallelism (carrier count) defaults to your core count and is tunable with -Djdk.virtualThreadScheduler.parallelism=N (this lab's experiments set it to 1 or 2 to make effects visible); the pool can temporarily grow beyond that (default cap 256) to compensate when carriers get stuck in operations that cannot unmount, such as file I/O.

10. Failure scenarios — where this bites

(a) Pinning. Some operations block the carrier itself because the JVM cannot safely unmount there. Then a carrier is hostage; with few carriers and much pinning, throughput collapses — in the worst pre-fix cases, programs deadlocked with all carriers pinned waiting for a lock that only an unmounted thread could release. History matters here:

  • JDK 21–23: blocking inside any synchronized block/method (or Object.wait()) pinned the carrier. This was THE virtual-threads gotcha; whole libraries rewrote synchronized into ReentrantLock to cope.
  • JDK 24+ (JEP 491), including your JDK 25: synchronized no longer pins. What still pins: blocking while a native frame (JNI / FFM call) is on the stack, and blocking inside a class initializer. Diagnosis: the JFR event jdk.VirtualThreadPinned.

Demo 4 (./run.sh pinning) measures it: 8 threads sleep 200 ms inside synchronized blocks with only one carrier. Real output here: Elapsed: 208 ms — they overlapped; nothing pinned. On JDK 21 the same program takes ~1,600 ms because each sleeper serially holds the lone carrier.

(b) Carrier monopolization. The scheduler does not preempt: a virtual thread that computes in a tight loop keeps its carrier until it blocks or finishes. N long CPU loops freeze all N carriers and every other virtual thread starves. (Try it in the visualization: "CPU hog" mode.)

(c) ThreadLocal at scale. ThreadLocals work on virtual threads (test thread_locals_stay_isolated_per_virtual_thread passes), but the old idiom of caching a heavy object per pooled thread ("500 threads × 1 buffer each") explodes when threads number a million and live for one request. Prefer ScopedValue (final in JDK 25) for request context, and share stateless objects outright.

(d) Pooling virtual threads. An anti-pattern that silently reintroduces the old ceiling: a pool of 200 virtual threads is exactly as limiting as a pool of 200 platform threads. Never reuse virtual threads; to limit concurrent access to a scarce resource, use a Semaphore around the call.

(e) Downstream stampede. Virtual threads remove your concurrency cap — not the database's. The thread pool was, accidentally, a rate limiter; with 100,000 requests genuinely in flight you can exhaust DB connections or DDoS your own services. Cap explicitly (semaphores, connection pool sizes, bulkheads) at each scarce resource.

(f) File I/O. Ordinary file reads/writes still block the carrier (OS readiness APIs cover sockets, not files); the scheduler compensates by temporarily adding carriers, so it works, but a million concurrent file operations won't scale the way sockets do.

11. What is guaranteed, and what is not

Guaranteed — semantics are unchanged. A virtual thread is a real java.lang.Thread: same Java Memory Model, same happens-before rules, same interrupt() behavior (test interruption_works_exactly_like_platform_threads), same ThreadLocal semantics, same debugger/stack-trace experience. Correct concurrent code stays correct. (The memory-model rules themselves are the java-memory-model lab next door.)

Not guaranteed / traded away:

  • No speedup for computation — parallelism is still bounded by cores (Demo 5: 16 CPU tasks, platform pool 215 ms vs virtual 190 ms — noise).
  • No scheduling fairness — no time slices, no guarantee a runnable virtual thread runs "soon" if others compute; thread priorities ignored.
  • Always daemon — virtual threads never keep the JVM alive; you must join/await them (that's why the executor's close() idiom matters).
  • Cheap ≠ free — creation is ~microseconds and stacks are heap objects; a million simultaneously deep stacks is still gigabytes.

The deliberate trade: Loom gives up OS-enforced preemption and per-thread OS services in exchange for making blocking nearly free — betting that server workloads are dominated by waiting, which they overwhelmingly are.

14. From this lab to production

What our demos ignore, and what real deployments do:

  • Enabling it. Spring Boot 3.2+: spring.threads.virtual.enabled=true (Tomcat request handling + @Async etc. move to virtual threads). Helidon 4 and Quarkus have first-class support. Plain JDK: the newVirtualThreadPerTaskExecutor() idiom.
  • Right workloads. High-concurrency, I/O-heavy servers and crawlers: huge wins. CPU-bound services, or servers already at <1,000 concurrent requests: little to gain.
  • Limiting. Replace "pool as accidental rate limiter" with explicit Semaphores and correctly sized connection pools (a JDBC pool of 50 still only admits 50 threads — size it to what the DB can take, not thread count).
  • Old JDKs. On 21–23, audit for blocking inside synchronized (-Djdk.tracePinnedThreads=full there; the property is gone in 24+ where JFR's jdk.VirtualThreadPinned remains).
  • Observability. Millions of threads break thread-dump habits: use jcmd <pid> Thread.dump_to_file -format=json <file> (includes virtual threads), JFR events jdk.VirtualThreadStart/End/Pinned, and beware metrics libraries that assume few, long-lived threads.
  • Context. Migrate request-scoped ThreadLocals toward ScopedValue (JDK 25) and fan-out/join code toward structured concurrency (StructuredTaskScope, still preview in 25).

16. Virtual threads vs. the neighbors

Java virtual threads Go goroutines Kotlin coroutines Reactive (WebFlux/Reactor)
What blocks nothing (JVM unmounts) nothing (runtime parks) only at suspend points you must never block
Code style plain blocking Java plain blocking Go needs suspend coloring operator chains
Preemption none (runs until it blocks) yes (~10 ms slices) none n/a
Retrofit old code usually just works n/a (built in) requires rewrite requires rewrite

Rules of thumb: existing blocking Java codebase that needs concurrency → virtual threads. Need streaming semantics (backpressure, windowing, composition of event flows) → reactive still earns its complexity. Kotlin shop → coroutines interop well and now sit on solid ground since JEP 491.

Predict

P1 — sleep vs. compute on one carrier. Three virtual threads run on a scheduler restricted to one carrier. Each thread does: Thread.sleep(100) then ~100 ms of pure CPU spinning. Roughly how long until all three finish — 200 ms, 300 ms, 400 ms, or 600 ms? Reason it out from mount/unmount rules, write your answer down, then check with:

java -Djdk.virtualThreadScheduler.parallelism=1 src/P1.java

(the source is src/P1.java — resist reading the solution hints in your head before committing to a number)

P2 — when virtual threads don't help. ./run.sh throughput 8 50 runs only 8 blocking tasks. Predict both measured numbers (pool of 8 platform threads vs. virtual) before running. What is the general rule for when virtual threads make no difference to a blocking workload?

Modify

M1 — kill the hopping. In run.sh, the carriers demo uses parallelism=2. Run it with parallelism=1 instead: java -Djdk.virtualThreadScheduler.parallelism=1 src/CarrierHopping.java. Threads still sleep and wake — do they ever change carrier now? Does the program still finish quickly, and what does that tell you about the difference between releasing a carrier and switching carriers?

M2 — give the old world a fair fight. In ThroughputRace.java, the pool loses because it has 8 threads for 600 tasks. Change poolSize to 600. (a) Predict the measured time — does the pool now tie with virtual threads? (b) Then explain why this "fix" is not how you'd run a real server at 100,000 concurrent requests — Demo 1 (./run.sh cheap) already showed you this machine's hard evidence.

M3 — break a scenario test on purpose. In ScenarioTests.java, the test blocked_virtual_thread_releases_its_carrier_to_others passes on one carrier. Predict: would it still pass if thread A spun in a CPU loop for 300 ms instead of sleeping 300 ms? D2 — the vanishing output. A colleague reports that this program "sometimes prints nothing at all":

public class Vanish {
    public static void main(String[] args) {
        Thread.startVirtualThread(() -> System.out.println("saved the order!"));
    }
}

Solutions

Show the solutions (try the exercises first)

Solutions

P1 — ~400 ms

The three sleeps all overlap: each sleeper parks, unmounts, and frees the single carrier, so 100 ms of sleeping happens once for everyone. The CPU spins cannot overlap: computing code occupies the carrier, there is only one carrier, and the scheduler never preempts — so the three 100 ms spins run back to back. Total ≈ 100 (shared sleep) + 3 × 100 (serialized CPU) ≈ 400 ms. Measured on this machine: ~410 ms. If you predicted 200 ms you gave virtual threads credit for parallel computation — they never provide that; if 600 ms, you missed that waiting overlaps.

P2 — both ≈ 50 ms; the rule

With 8 tasks and 8 pool threads, every task can wait simultaneously in both setups, so both measure ~50–60 ms. Rule: virtual threads pay off only when concurrent blocked tasks > affordable platform threads. Below that line the old pool is exactly as good. (This is why low-traffic services see no gain from enabling them.)

M1 — no hopping, still fast

With one carrier there is nowhere else to wake up, so every "woke from sleep" line shows worker-1. The program still finishes in ~150 ms because all six sleeps overlap: each sleeper releases the carrier even though it can only ever return to the same one. Releasing (unmount on block) is the scaling mechanism; hopping between carriers is just an incidental, load-balancing side effect that proves the release happened.

M2 — the pool ties, and why that's no fix

(a) With 600 pool threads every task waits at once: measured ≈ 60–80 ms, essentially tying virtual threads (thread creation cost makes it slightly slower to start). (b) The fix doesn't scale: platform threads are ~1 MB of stack each and the OS caps them — Demo 1 showed macOS refusing this very process at thread #4,044. "One platform thread per task" dies around 10³–10⁴ concurrency; virtual threads carry on to 10⁵–10⁶. The pool wasn't wrong because pools are slow — it was rationing a resource that Loom makes abundant.

M3 — the test fails: spinning never parks

A CPU spin never calls a blocking operation, so A never parks, never unmounts, and holds the only carrier for the full 300 ms. B cannot run until A finishes, so a.isAlive() is false when B finally checks, and the assertion fails with "carrier was not released". This is carrier monopolization (README §10b): unmounting only happens at blocking points — the scheduler cannot rescue you from a thread that never blocks.

D1 — a pool of virtual threads

The bug: Executors.newFixedThreadPool(8, Thread.ofVirtual().factory()) — a fixed pool of 8 workers that merely happen to be virtual. Pooling reintroduces the exact ceiling virtual threads exist to remove: only 8 fetches wait at once, so 40 tasks run in ⌈40/8⌉ = 5 waves × 100 ms ≈ 500 ms (measured: 520 ms). Fix: Executors.newVirtualThreadPerTaskExecutor() — one new thread per task, all 40 wait together, ~100 ms. Anti-pattern §10(d): virtual threads are cheap enough to create per task; pooling them is always wrong (to protect a scarce downstream resource, use a Semaphore, not a small pool).

D2 — virtual threads are always daemons

Platform threads are non-daemon by default, and a live non-daemon thread keeps the JVM running. Virtual threads are always daemon (README §11; setDaemon(false) throws), so main returning ends the JVM even mid-print — whether the message appears is a race. Fixes: keep the Thread and t.join() it; or submit via try (var ex = Executors.newVirtualThreadPerTaskExecutor()) { ... }, whose close() waits for every task (that's the scenario test executor_close_waits_for_submitted_tasks).
