Lab 54 · Work That Spans Services

The Idempotent Consumer — one effect per message, from a message that has no caller

Tell a friend: Asha pays ₹2,000 once, and Meera's loyalty service gives her 50 points twice. Nothing crashed loudly and nothing was logged. The service simply read the same fact a second time, because a broker only ever promises "at least once". Everyone names the same fix: make the consumer idempotent. That is really three separate jobs. Give the message a name, record that you handled it in the same breath as handling it, and keep that record long enough. The third job is the one that fails in production. How long is long enough gets decided by Priya replaying a queue nine days later, not by anything in your code.

Keep visualization.html open beside this page; §9 maps its four designs onto the five versions built in §10. §17 says what this lab is made of and where its numbers come from.

1. Why does a message consumer inherit everyone else's uncertainty?

In one breath: A consumer is handed facts by strangers. Any of those strangers can hand it the same fact twice. None of them will mention that they did.

You already own most of the parts for this lab.

The idempotency lab built a three-part protocol. The caller mints a key. The server claims that key atomically with the effect. The server replays the stored response for a repeat. That lab also proved the claim must be an INSERT under a UNIQUE constraint, never a check-then-act.

The kafka lab established the vocabulary this one leans on. A topic is an append-only log, split into partitions. A consumer group is a set of processes sharing that log. Each partition belongs to exactly one member of the group at a time. Each group keeps one number per partition, its offset, meaning "I have read up to here". Handing a partition from one member to another is a rebalance.

That lab also showed the commit position is a forced choice with no third option. Commit the offset before processing and you get at-most-once. Commit it after and you get at-least-once.

The transactional-outbox lab ended, like eight other labs, with the same sentence: "…and therefore consumers must be idempotent."

So why a whole lab for the consumer?

Because a message consumer is not a request handler with a queue in front of it. Three things are structurally different. Each one breaks a different part of the protocol you already know.

Nobody is calling you. No caller mints a key on your behalf. No caller waits for a response. So part 1 and part 3 of the idempotency protocol have no owner at all. The name of the message has to come from somewhere else, and the first two places engineers reach for are both wrong.

The duplicate does not come from one place. On an HTTP endpoint the duplicate is a client retry, and it arrives seconds after the original. A consumer's second copy can come from six other directions, and the gap can be nine days. That spread of redelivery age turns out to be the entire story of the hardest failure in this lab.

Your bookkeeping lives in a second system. Your effect lands in Postgres. Your read position lands in Kafka. That is a dual write, in a lab series where "dual write" has been the villain since the outbox. Whether it is a dangerous dual write is worth answering precisely, because the popular answer ("store offsets in your database") is often the wrong trade.

This lab opens up the slogan for the consumer specifically. By the end you should be able to look at any consumer in your codebase and answer four questions about it, in this order.

  1. What names this message?
  2. What makes the record of processing atomic with the effect?
  3. How long must that record survive?
  4. What would the operation do if the record were gone?

Seven sources. Note two properties of that list, because the rest of the lab is built on them.

The time gap between the original and the duplicate ranges over six orders of magnitude. Milliseconds for source 2. Months for source 6.

🔮 Predict: suppose Meera keeps a table of every offset she has already processed, and skips anything already in it. Which of the seven sources does that table actually stop?

Reveal

It stops sources 3 and 4, the two where the same record at the same offset comes back. Those are exactly the two it was designed for, which is why it feels like a complete answer.

It does not stop sources 1, 5 or 6. Each of those puts the same fact at a new offset, and a new offset is honestly new. Source 2 is usually handled for you inside the cluster by Kafka's idempotent producer. Source 7 re-reads the same offsets, so the table does suppress it — and that turns out to be a different problem, waiting for you in §11 F6.

If you said "all of them, because the offset is unique", you have the right fact and the wrong conclusion. Uniqueness of the address is not stability of the name.

Any dedup scheme that only handles same-offset redelivery handles two of seven cases. That is the trap in §10 v1, and it is extremely common in real code.

2. How does Asha end up with 100 points for one payment?

In one breath: Meera's consumer adds the points, saves them, and dies one instant before it can write down how far it had read. When it restarts it reads the same event again and adds the points again.

Real values, ordered events. The consumer is the naive one everybody writes first: poll, process, commit.

t=0     relay publishes evt-9f31            → topic offset 41
t=1     loyalty polls                        → gets [offset 41 : evt-9f31]
t=2     loyalty runs UPDATE members
          SET points = points + 50           → members: M-77 points = 50   ✅
t=3     loyalty COMMITs the DB transaction   → durable
t=4     ── the pod is evicted ──                (OOM, deploy, node drain, k8s)
                                                the offset commit never happened
t=5     new pod starts, joins group loyalty-v1
t=6     group coordinator reports committed offset = 41
t=7     loyalty polls                        → gets [offset 41 : evt-9f31]  again
t=8     loyalty runs UPDATE members
          SET points = points + 50           → members: M-77 points = 100  ❌
t=9     COMMIT, then commit offset 42        → all clean, nobody alerts

Nothing crashed visibly. No exception was logged at t=8. Meera's consumer did exactly what it was told. Asha has 100 points for one ₹2,000 payment, and the only evidence is a number in a row.

That last sentence is the shape of every failure in this lab. The damage is a value, not an error.

🔮 Predict before reading on. The pod died between the database commit and the offset commit. Suppose Meera swaps the two lines. She commits the offset first, then runs the UPDATE. What is the worst thing that can now happen, and is it better or worse than what you just read?

Reveal

The window does not close. It inverts.

If the pod dies after the offset commit and before the UPDATE, the event is gone. The group's position has already moved past 41. No future poll will ever return it again. Asha gets 0 points, permanently, and again nothing is logged.

If you guessed "better, because a lost event is quieter than a wrong number", you have the right instinct and the wrong conclusion. Quiet is the problem.

Which is worse depends on a property most teams never state out loud: a duplicate is detectable and repairable downstream; a silent loss is neither. You can reconcile 100 points against a payments ledger and find the double. You cannot find a payment that produced no loyalty record by looking only at loyalty. That asymmetry is why the entire industry standardised on at-least-once delivery plus consumer-side deduplication. Not fairness. Not elegance.

3. What if the consumer simply remembers what it has seen?

In one breath: If the problem is that the consumer forgot, give it a memory. That instinct is right. Where you put the memory is where it goes wrong.

Meera writes the obvious thing.

// loyalty consumer, attempt 1
private final Set<String> seen = new HashSet<>();

void onMessage(Record r) {
    if (seen.contains(r.eventId())) return;   // skip the duplicate
    awardPoints(r);                            // UPDATE ... points + 50
    seen.add(r.eventId());
}

The field named seen is her memory: the list of event names already handled. This is the obvious solution, and it is a genuinely reasonable first attempt. It does fix a real class of problem. Two deliveries within one process lifetime, back to back, are now handled. She runs it in a test and the test passes.

🔮 Predict: Meera's test passes. Name the property of her test that makes it pass, and say which of the seven sources in §1 the test cannot express.

Reveal

The test runs in one process that never dies. Every source in §1 except source 2 involves either a process ending or a second process starting. A test that keeps one object alive for its whole duration cannot express any of them.

If you said "the test is too fast", that is close but not the property. Speed is not what saves the set. Living is.

4. Three ways that memory fails — which one is actually interesting?

In one breath: The first two failures are about where the memory lives, and both are easy to fix. The third is about when the memory is consulted, and it is the one that survives every obvious fix.

Way one: the memory is in the wrong place. The set named seen is a field on a heap, and that heap dies with the pod. The failure in §2 is precisely a pod death. The set is empty at t=5. Every duplicate that matters survives the thing that was supposed to remember it.

Way two: the memory is per instance. Meera scales the deployment to three pods. Each pod has its own seen. A rebalance moves partition 0 from pod A to pod B, and pod B has never heard of evt-9f31. Even a durable per-pod set would not help. It is not durable per partition, and partitions move.

Both of those go away if the memory moves into the database.

SELECT 1 FROM processed_messages WHERE event_id = 'evt-9f31';  -- seen?
UPDATE members SET points = points + 50 WHERE id = 'M-77';     -- effect
INSERT INTO processed_messages(event_id) VALUES ('evt-9f31');  -- remember

Way three: the memory is consulted in a gap. You have met this exact shape before. The idempotency lab called it check-then-act and killed it there. So here is only what is different about it inside a consumer.

On an HTTP endpoint, the two racers are two client retries hitting two threads. In a consumer, the two racers are two consumer instances that both believe they own partition 0. That is not a rare interleaving. It is the ordinary outcome of a rebalance. It lasts as long as the old owner's handler takes to notice it has been fenced, which can be max.poll.interval.ms, five minutes by default.

Watch the two pods interleave. Read the two columns as two clocks running at once.

        pod A (old owner)                    pod B (new owner)
t=0     SELECT → not seen
t=1                                          SELECT → not seen
t=2     UPDATE points +50   (= 50)
t=3                                          UPDATE points +50   (= 100)
t=4     INSERT processed_messages            INSERT → unique violation, rolls back

Pod A is a zombie: still executing, already replaced. Now look at the shape of the damage, because it is easy to miss. The UNIQUE constraint did fire. It fired at t=4, which is after both UPDATE statements already landed.

A constraint only protects the statements inside the same transaction as the violation. Here the check, the effect and the record were three separate decisions. Only the last one was guarded.

This is the moment the lab's real subject appears. "Make the consumer idempotent" sounds like one obligation. It is three, and they fail independently.

5. What is "make it idempotent" really asking for?

In one breath: Three promises, not one. Name the message. Record it in the same instant you act on it. Keep that record until the last possible duplicate has arrived.

Here is the real requirement, stated plainly. We will spend the rest of the lab on these three lines.

R1 — Identity. Every message must carry a name that stays the same across every path that can redeliver it.

R2 — Atomicity. The record "I have processed this name" must become durable in the same atomic act as the effect it guards.

R3 — Memory. That record must still exist when the duplicate arrives. The arrival time of the duplicate is not bounded by anything in your code.

R2 is the one you already know how to satisfy. It is the idempotency lab's single-transaction claim. For a consumer whose effect is a local database write, it is genuinely easy.

R1 and R3 are the consumer's own problems. They have no counterpart in the HTTP case. Each of them has a popular answer that is wrong in a way that produces no error message.

A good answer sounds like "The service added her points, then died before it could write down how far it had got. When it came back it read the same thing again and added them again. The looking and the writing have to be one movement, not two."

6. What is the one key idea underneath all of it?

In one breath: Stop asking whether you have seen this delivery. Start asking whether this fact is already in your state, and write the answer down in the same commit that applies it.

A consumer becomes idempotent when it stops asking "have I seen this delivery?" and starts asking "has this fact already been applied to my state?" Then it records the answer in the same commit as the application.

Everything below is the consequence of taking two words literally: fact, and same commit.

Fact is obligation R1. A delivery is a thing that happened to a wire. A fact is a thing that happened in Arjun's payments service. They are not the same object, and only one of them survives being sent twice.

Same commit is obligation R2. Not "immediately after". Not "in a transaction that usually succeeds". The same commit, so that a database, not your code, decides which of two racers wins.

Obligation R3 has no clever word. It is a duration, and §10 v3 is the story of choosing it wrong.

7. Which four words does this lab have to earn?

In one breath: Four new ideas. The first is a pair: where a copy arrived, versus what the copy says. Then the table that remembers, then how late a duplicate can be, then a trick that makes the memory problem disappear.

You already own at-least-once, idempotency key, dedup window, offset, consumer group, rebalance, DLQ, and effectively-once from kafka and idempotency. These four are new here, and each one is earned by something that has already happened in the story.

7.1 Where a copy arrived, or what the copy says?

Arjun's relay sends evt-9f31. Kafka appends it and stamps it with an address: this topic, this partition, this position. The address is payments.captured/0/41.

Then the relay restarts and sends the same outbox row again. Kafka appends it a second time and stamps a different address, payments.captured/0/58. Two addresses. One fact.

Engineers call the address delivery identity: the triple (topic, partition, offset), assigned by the broker at append time, unique per append. They call the name inside the record message identity: a value carried in the record, assigned by the producer when the fact was created, and identical across every append of that fact.

Why does the distinction need a name at all? Because a single business fact can be appended more than once. A relay republish does it. A retry topic does it. A mirrored cluster does it. Each append gets a fresh delivery identity. Deduplicating on delivery identity therefore fails on exactly the sources that produce duplicates across appends.

You have met message identity before without the name. The CDC lab's source.lsn is one. That field exists so that a sink can key on what the record says, rather than on where it sat in the stream.

7.2 What is an inbox, and why is it the outbox in a mirror?

Meera's table of facts she has already applied is called an inbox table. In code it is usually called processed_messages. Precisely: a table keyed by (consumer, message_id) with a UNIQUE constraint, written in the same transaction as the effect.

Hold the outbox next to it. The outbox makes "I decided this" and "I told someone" atomic. The inbox makes "I was told this" and "I acted on it" atomic. Same trick, opposite direction, which is why the two labs read as mirror images.

Why does it work? Because it converts "did I already do this?" from a question about your own past behaviour into a database constraint. A constraint is the only place in the system where two racers get serialized for free.

7.3 How late can a duplicate be?

Priya's replay lands nine days after the incident. That gap has a name: redelivery age, the maximum wall-clock interval between two deliveries of one message identity, taken over every redelivery source your architecture has.

It needs a name for three reasons, and the third is the uncomfortable one. It is the input to the only sizing decision in the whole pattern, which is how long the inbox must remember. It is not a configuration value anywhere. And it is usually set by a human running a dead-letter replay, rather than by software.

7.4 Can you remember everything with one number?

Instead of a list of everything seen, keep the highest number seen. That is watermark deduplication, also called high-water-mark deduplication.

Precisely: per dedup scope, usually per entity key, store the largest monotonically increasing sequence applied. Apply an incoming message only if its sequence is strictly greater. Then advance the stored value in the same transaction.

Why bother? Because it turns obligation R3 from a retention problem into no problem at all. A number that only moves forward never needs pruning. The price is that it demands monotone, per-key-ordered sequences.

It is the same move you have made twice before. It is expected_version in event-sourcing, and source.lsn in CDC, used defensively rather than for ordering.

8. What picture should you carry in your head?

In one breath: A bouncer with a ledger. He recognises the guest by name, writes the name and opens the door as one movement, and never tears out a page while that guest can still come back.

Two mental models follow. The first is a picture you can hold. The second is the same machine with the real names on it.

Simple model — can one bouncer with a ledger do the job?

A club, one door, one bouncer, one ledger. A guest may only be let in once. The bouncer must do three things, and they map exactly onto R1, R2 and R3.

He must recognise the guest by a name, not by which taxi they arrived in. That is R1. The taxi is the offset. The name is the event id.

He must write the name and open the door as one movement. If he opens the door and then writes, someone slips in during the pen stroke. That is R2, and that pen stroke is the gap in §4.

He must not tear out yesterday's page while yesterday's guest can still come back. That is R3, and Priya is yesterday's guest.

Where does the story lie to you?

The bouncer is an entry point, not the model. He hides the two hardest facts in the lab, so replace them now.

There are two bouncers, not one. Whenever a rebalance is in flight, two processes are running, and both are convinced they are the only one. The ledger is what makes them agree, not their belief about who owns the door. Any design where the bouncer decides on something he remembers is broken under this fact. The decision has to be a write that the ledger accepts or rejects.

The guest can come back wearing a different wristband. Republication gives the same fact a new delivery identity. A ledger that records wristband numbers will happily admit the same guest twice. That is §10 v1, in one sentence.

10. How do you build this, and why does each version die?

In one breath: Five versions. Each one fixes how the last one died, and then dies of something new. The last death is the interesting one, because nobody is at fault.

Meera builds the consumer five times. Read them in order; each is a real design that real teams ship, and three of the five are still shipping somewhere today.

v1 — why not dedup on the offset?

The instinct is simple. Kafka already gives every record a unique address, so use the address.

CREATE TABLE processed_offsets (
  topic     text,
  partition int,
  "offset"  bigint,
  PRIMARY KEY (topic, partition, "offset")
);

BEGIN;
  INSERT INTO processed_offsets VALUES ('payments.captured', 0, 41);
  UPDATE members SET points = points + 50 WHERE id = 'M-77';
COMMIT;

Obligation R2 is now satisfied. The record and the effect are one transaction. The primary key arbitrates between two racers, instead of a SELECT doing it.

Run the §2 trace and the §4 zombie trace against this design. Both are fixed.

t=8   second delivery of offset 41
      INSERT processed_offsets (…,41) → PK violation → transaction rolls back
      the UPDATE rolls back with it → M-77 stays at 50 points ✅

That is a real improvement, and it is where a great many production consumers stop. Now break it.

🔮 Predict: Arjun's relay crashed after send() and republished the outbox row. Kafka now holds evt-9f31 at offset 41 and at offset 58, and Meera's consumer has already processed 41. What does v1 do at offset 58?

Reveal

INSERT INTO processed_offsets VALUES ('payments.captured', 0, 58) succeeds. Offset 58 has genuinely never been seen. The UPDATE runs. Asha has 100 points.

If you said "the primary key catches it", you are trusting the table to answer a question it was never asked. The dedup table did its job perfectly, and the outcome is still wrong. It knows every delivery it has consumed. It knows nothing about which facts it has applied.

The same hole opens for three more sources. The retry topic has a different topic name, so a different key. A mirrored or migrated cluster re-assigns offsets, because they do not survive MirrorMaker. And any reprocess that re-publishes records rather than re-reading them lands at new offsets too.

v1's lesson is the lab's first main result. Offsets are delivery identity. Deduplication requires message identity, and only the producer can supply it.

Concretely, Arjun must put an id in the event at creation time. For an outbox that id is the outbox row's id, minted inside the same transaction as the state change.

-- in the payments service, one transaction
UPDATE payments SET status='CAPTURED' WHERE id='pay-8812';
INSERT INTO outbox(id, topic, key, payload)
VALUES ('evt-9f31', 'payments.captured', 'M-77', '{...}');

Republished later from the same row, that id is unchanged. That is the property that makes it usable.

v2 — what changes when you dedup on the message id?

Meera keys on what the record says, not on where it landed.

CREATE TABLE inbox (
  consumer   text  NOT NULL,      -- 'loyalty-v1'
  message_id text  NOT NULL,      -- 'evt-9f31'
  applied_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (consumer, message_id)
);

BEGIN;
  INSERT INTO inbox(consumer, message_id) VALUES ('loyalty-v1','evt-9f31');
  UPDATE members SET points = points + 50 WHERE id = 'M-77';
COMMIT;                              -- on PK violation: roll back, skip, ack

Two details in that table definition are load-bearing, and both are routinely missed.

The consumer column is part of the key. Three services consume payments.captured, and one of them is Omar's notifications. Suppose all three share one inbox table keyed only by message_id. The first service to process an event then suppresses it for the other two. Omar's welcome message never goes out, and nothing anywhere reports an error. Either key by (consumer, message_id), or give each consumer its own table. One table with a compound key is usually better: one retention job, one dashboard.

The INSERT comes first, before the UPDATE. Not because ordering matters to the database, because inside one transaction it does not. It matters because putting the insert first makes the duplicate path cost one failed insert, rather than a full effect plus a failed insert. On a hot partition that is the difference between a cheap skip and a lock-contention incident.

Meera's effect commits to Postgres. Her offset commits to Kafka. Two systems, two writes, no atomicity between them. Given how much damage the dual-write problem has done in this curriculum, this deserves a straight answer rather than a reflex.

Reveal

The bad one is: the database transaction did not commit, and the offset commit did. The event is skipped forever, and nothing records that it was.

Row 3 is the only bad one, and it is unreachable as long as you commit the offset after the database transaction. That is exactly what enable.auto.commit=false plus a manual ack after the handler returns gives you. So:

The consumer's dual write is benign, because the second write is guarded by the first. The inbox turns "the offset commit was lost" from a correctness problem into a performance problem: you re-read some records and throw them away.

This matters practically, because there is a popular alternative. Store the offset in your own database, inside the same transaction as the effect. That alternative is real and it is correct. It is also usually a worse trade than it looks, for three reasons.

It only handles same-offset redelivery. It is v1 wearing a different hat, and it inherits v1's blindness to republication. Teams adopt it believing it is stronger than an inbox. It is strictly weaker.

It requires a ConsumerRebalanceListener that seeks to your stored offsets on every partition assignment. You now own a piece of the group protocol.

And it is defeated by any deliberate replay, because your stored offset is the thing you were trying to move.

Rule: you need offsets in your database only if you have decided not to keep an inbox. Keeping both is coherent, and Spring's Kafka plus JPA chained transaction managers effectively do. It buys nothing the inbox has not already bought.

Checkpoint. v2 is a correct idempotent consumer for a local, transactional effect. If Meera's handler only writes to one database, and her inbox never forgets, she is done. Most of the internet's advice ends here. The next two versions exist because "never forgets" is not a thing a table does.

This is the most important failure in the lab, so state its lesson exactly.

The inbox's retention must exceed the maximum redelivery age — and redelivery age is set by human operational behaviour, not by any config file in your repository.

There is no software setting anywhere that bounds "how long after an incident might someone replay a dead-letter queue". Which produces an uncomfortable conclusion. For the replay source and the deliberate-reprocess source, a retention-based inbox is not a guarantee. It is a bet, and it is a bet whose losing side is silent.

There are three honest ways to respond. They are listed in order of how much they actually fix.

Write the number down, and make it bigger than the replay you allow. Set retention explicitly longer than your stated maximum replay age, and put that number in the runbook: "DLQ records older than 30 days must not be replayed; regenerate them from source instead." This is cheap, and it converts a silent failure into a documented policy. It is only as good as the human reading it.

Give replays their own dedup scope. Priya's replay run gets a fresh consumer value, loyalty-v1-replay-2026-09-01. Crucially, the results of that run are then reviewed rather than trusted. This is honest about what a replay is. It is a deliberate reprocess, not a duplicate.

Stop needing retention at all, which is v4.

v4 — can memory that never grows also never expire?

Change what is stored. Instead of a set of facts, keep one number per entity.

Arjun stamps each event with a per-key monotonically increasing sequence. For an outbox this is easy. It is a per-aggregate counter incremented in the same transaction, or the outbox row id when a single writer produces that key's events in order.

evt-9f31  member M-77  seq 17  +50 points
evt-a044  member M-77  seq 18  +30 points

In words: this is Asha's seventeenth loyalty event, then her eighteenth. The number belongs to Asha, not to the topic.

Meera stores the highest sequence she has applied, on Asha's own row.

CREATE TABLE members (
  id          text PRIMARY KEY,
  points      int  NOT NULL,
  last_seq    bigint NOT NULL DEFAULT 0    -- the watermark, IN the entity row
);

The whole dedup mechanism is now one extra line in the UPDATE.

BEGIN;
  UPDATE members
     SET points   = points + 50,
         last_seq = 17
   WHERE id = 'M-77'
     AND last_seq < 17;          -- the entire dedup mechanism, one predicate
COMMIT;
-- 0 rows updated ⇒ already applied (or superseded) ⇒ skip and ack

Read last_seq < 17 as a sentence: only apply this if the highest thing I have already applied to Asha is older than event seventeen.

Look at what just happened to the three obligations.

Obligation How v4 satisfies it What it costs
R1 identity (key, seq) is producer-minted, and survives republication exactly like an event id does the producer must have a per-key counter
R2 atomicity the guard is a WHERE clause on the row being modified: no second table, no second index, no extra write nothing
R3 memory dissolved — last_seq is one number per member and only moves forward, so it is never pruned deliberate replay becomes hard, see below

That middle row is the optimistic-vs-pessimistic-locking lab's conditional write, wearing yet another costume.

The third row is worth pausing on. There is no window any more, so Priya's nine-day replay in v3 is suppressed correctly. Storage is now O(entities) instead of O(messages): a few million rows instead of a hundred billion.

It also gives Meera something the inbox never did: reorder safety. Suppose seq 18 is processed before seq 17, because of a retry topic, a partition change, or two concurrent handlers. Then seq 17 is rejected by last_seq < 17 rather than applied out of order.

Reveal

Nothing happens. Every event in the topic has a sequence at or below the watermark already stored on its member row. So every UPDATE matches zero rows. The consumer runs at full speed through a month of data, logs nothing unusual, commits offsets, and changes no state at all.

If you guessed "everyone's points are doubled", you have v2's failure in mind. The watermark does not double anything. It does nothing at all, which is worse to discover.

If the intent was "suppress duplicates", this is a triumph. If the intent was "recompute everyone's points with the fixed formula", it is a silent no-op that will be discovered by a customer.

That is v4's honest cost, and it is the mirror of v3's. The same property that makes a watermark retention-free makes a deliberate replay impossible without an explicit reset. A well-run system therefore ships a documented procedure for both. "How to reprocess" is a first-class operation, not an improvisation.

The other three costs, stated plainly.

It needs per-key ordered delivery. With key-based partitioning (key = M-77) Kafka gives you that per partition. Lose it and events arrive out of order. You lose it by repartitioning, by parallelising a partition across threads, or by routing through a retry topic. Out of order, the watermark does not merely fail to dedup. It discards legitimate updates, which is worse than a duplicate.

It needs a monotone per-key sequence from the producer. Not every producer has one. CDC gives it free through source.lsn. A hand-written outbox needs a counter added.

It is per key and per stream. Two different event types updating Asha's row need either one shared sequence, or one watermark column each.

v5 — what does a production consumer actually do?

No single design wins. A real consumer picks per handler, from four tools, in this order of preference.

1. Natural idempotency — use it whenever the operation allows. If the effect can be written as an assignment rather than an accumulation, then duplicates need no dedup machinery at all.

UPDATE orders SET status = 'SHIPPED' WHERE id = 'ord-51';   -- idempotent
INSERT ... ON CONFLICT (id) DO UPDATE SET ...               -- idempotent
INSERT INTO shipment_events(event_id, ...) VALUES (...)      -- idempotent (PK)

Beware the standing trap: naturally idempotent is not the same as reorder-safe. SET status = 'SHIPPED' applied after SET status = 'DELIVERED' moves the order backwards, and no dedup scheme in this lab notices. Idempotence handles duplicates. Versioning handles order. Locking handles concurrency. Three orthogonal defences, and you frequently need two of them.

2. Watermark — when events for a key are ordered and carry a monotone sequence. Cheapest, retention-free, reorder-safe. It is the default choice for projections, read models, replicated caches and CDC sinks. Anything shaped like "apply this stream of changes to this entity".

3. Inbox table — when events are independent facts with no per-key order. "Send Asha a welcome email." "Award points for this specific payment." "Create a shipment." This needs a documented retention at least as long as the maximum redelivery age.

4. Claim-first plus external effect — when the effect leaves the database. This is the idempotency lab's v4 shape, unchanged. The claim commits alone as RUNNING. The external call happens next, carrying its own idempotency key. The outcome commits second. A reaper re-drives claims stranded in RUNNING.

Nothing about being a consumer changes that shape, with one twist. The "caller" who must not be left in doubt is now the broker's redelivery. A stranded RUNNING claim will be re-driven by the redelivery itself, if you let it.

11. What breaks when you live behind a broker?

In one breath: The general shape of duplicate handling is settled. Ten things still go wrong, and they go wrong because a broker sits in front of you rather than a caller.

These ten belong to the cast. Meera owns four of them, Priya one, Dev one, and Arjun one. The rest are nobody's fault, which is the point.

F1 — what if the pod dies between the effect and the offset commit?

Meera's pod is evicted. It happens for boring reasons: out of memory, a deploy, a node drain. In a busy cluster it happens several times a week.

The database transaction committed. The offset commit did not. So the group's position is still 41, and the next poll returns evt-9f31 again. You would see it in the consumer log as the same offset appearing twice.

Designs v2 and v4 suppress it. Design v1 also suppresses this particular shape, because the offset is the same one — but v1 fails the moment the redelivery arrives by republication instead. Nothing is lost here, because the offset never advanced.

F2 — what if two consumers own the same partition at once?

Meera's handler is slow today, because a downstream dependency is slow. It exceeds max.poll.interval.ms (default 5 min). The group coordinator declares the member dead and reassigns the partition — while the handler is still running, and still holding a database connection.

Two consumers now execute the same message concurrently. That is the zombie trace in §4, and it is not exotic. It is what a rebalance does for a living.

Only one thing saves Meera here: a conditional write at the database. The inbox primary key does it. So does the last_seq < predicate. The loser's whole transaction rolls back.

Three things do not save her. An in-memory check does not. A SELECT before the effect does not. And, most importantly, no assumption that partition assignment is exclusive. Assignment is exclusive from the coordinator's point of view. It is never exclusive from the point of view of code already running.

In production this correlates with a long-tail dependency. The fix that removes the cause is smaller batches, plus a max.poll.interval.ms above your p99.9 handler time. The fix that removes the damage is the conditional write.

F3 — what if Arjun's relay publishes the same fact twice?

The relay sent the record, then crashed before it could mark the outbox row published. On restart it sends again. Same fact, new offset.

Design v1 is defeated. Designs v2 and v4 hold.

Kafka's idempotent producer does not help here, and it is worth knowing why. It deduplicates a (PID, epoch, sequence) conversation within one producer session. A relay restart is a new session, so from Kafka's point of view this is an honestly new record.

F4 — what does a retry topic do to your ordering?

Spring Kafka's non-blocking retries publish a failed record to …-retry-1 with a backoff. Meanwhile the main partition carries on.

So seq 17 is sitting in the retry topic while seq 18 sails past on the main topic and is applied first. Deduplication is not violated. Both events are applied exactly once. The order is violated.

An inbox consumer produces points = base + 30 + 50, which is fine, because addition commutes. An assignment consumer produces the wrong final status, which is not fine.

What this teaches is a trade, not a bug. Non-blocking retries buy availability by trading away per-key ordering. If your handler relies on order, blocking retries are the correct choice — or a watermark that rejects the late one. Note what the watermark's "rejection" now is. It is a deliberate drop, and you must be able to explain it.

F5 — what does Priya's replay do nine days later?

This is the §10 v3 incident, and it is the only failure in this lab whose cause is a human with good intentions.

What you would see is a spike in successful applications where applied_at is far away from event_time. That gap has a name: event age at apply time. It is the metric that would have caught this before it became an incident. Almost nobody graphs it.

F6 — what if your own dedup defeats a repair you meant to run?

Meera resets the group to offset 0 after fixing a calculation bug. Design v2 skips everything with a primary-key violation. Design v4 skips everything below the watermark.

Both are working exactly as designed. Both defeat the operation.

A reprocess is a different intention, so give it a different dedup scope. Use a new consumer value, or reset the watermarks, or build a dedicated backfill path that computes the answer rather than accumulating it. The general principle from the idempotency lab holds here too: different intentions must not share a key.

F7 — what does a poison message do to a claim-first handler?

One record makes the handler throw every time. With blocking retries it head-of-line-blocks the partition. Lag climbs on that partition while throughput reads perfectly normal for every other one.

Here is the trap specific to this lab, and it is a natural instinct after reading the idempotency lab. Suppose you "claim" the message by inserting into the inbox in its own transaction, before doing the work. Then the failing message is marked processed and will never be retried. You have converted a loud poison message into a silent skip.

For a local effect, the inbox insert must be in the same transaction as the effect, so that it rolls back with it. Claim-first is only correct when paired with a RUNNING state and a reaper, which means only for external effects.

F8 — what if the effect leaves the database?

The handler writes to Elasticsearch, or S3, or Redis, or an email provider. There is no transaction to put the inbox row into, so obligation R2 cannot be satisfied the easy way.

There are three responses, and which one you pick depends on what the sink will accept.

Make the sink hold the dedup itself. An Elasticsearch document id equal to the message id does it. So does version_type=external with the event's sequence as the version, which is a watermark implemented by the sink.

Or use claim-first with a downstream idempotency key. Email providers and payment APIs accept one.

Or, for a genuinely unkeyable sink, accept at-least-once, reconcile afterwards, and publish the measured residual. That is the idempotency lab's "box G", unchanged.

F9 — what if two threads touch Asha's row at once?

Meera parallelises a partition across a thread pool for throughput. Two threads process two different events for member M-77 simultaneously.

🔮 Predict: Meera has the v2 inbox in place, and both events have distinct event ids. Does the inbox protect Asha's points here?

Reveal

No. Both inserts succeed, because the two ids really are different. Both threads then read Asha's current points, add to it, and write back. One of the two additions is overwritten and lost.

If you said "yes, the primary key protects her", you are asking the constraint a question about sameness when the problem is about timing. Two different facts arriving together is not a duplicate at all.

This is not a duplicate. It is a lost update, and deduplication does nothing about it at all. She needs row locking or a version check, and she has just given up per-key ordering as well, which brings F4 along for the ride.

Hold on to the distinction. Deduplication answers "is this the same fact twice?" Concurrency control answers "are two different facts colliding?" Same table, different problem.

F10 — what happens when the inbox itself becomes the bottleneck?

Every message now costs an extra indexed insert, and Dev's inbox is the hottest write target in the schema. Index bloat follows. Autovacuum pressure follows, which the mvcc-and-vacuum lab covers. And the retention DELETE ends up competing with the workload it exists to protect.

Dev has three moves. Partition the table by day and DROP partitions instead of deleting rows: one metadata operation, rather than a hundred million row versions. Prefer the watermark wherever the shape allows it. And never let the retention job be the thing that discovers the table is too big.

12. What exactly is guaranteed, and how does it stop holding?

In one breath: You get "the effect happens once" for one named message, in one consumer, against one database. Five assumptions hold that up, and two of them fail quietly.

What is guaranteed, for design v2 or v4 with a local transactional effect:

For a given (consumer, message identity), the effect is applied at most once. Because delivery is at-least-once, that adds up to exactly once in effect. Two consumers racing on the same message produce one application and one rolled-back transaction.

What that guarantee rests on. Each row below is an assumption, and each one is a real place where production systems break.

# The assumption How it breaks Where you saw it
1 the producer mints a stable identity that survives republication the id is generated at send time rather than at fact-creation time §10 v1
2 identities do not collide across different facts someone uses a business key such as orderId for events that can legitimately repeat §12, below
3 the dedup record and the effect are in one transaction, against one database a second sink is added to the handler §11 F8
4 the dedup record outlives every redelivery a retention job deletes it first §11 F5
5 the scope is per consumer Omar's service shares the table §10 v2

What is not guaranteed, and never was. Five things, and the first one is not achievable by anybody, ever.

Exactly-once delivery is impossible, for the reason the idempotency lab established from the two-generals result. What you have is at-least-once delivery plus at-most-once application.

Ordering is not guaranteed. Deduplication is order-blind. F4 and §10 v5 spell out the separate mechanism you need.

Protection against business duplicates is not guaranteed either. Two different events can describe the same real-world fact. A double-submitted refund produces two event ids. Those are two identities, so both will be applied. Deduplication is defined on identities. Only the producer knows which two sends are one intention.

Anything outside the transaction is not covered. The email sent in the middle of the handler was sent, whatever the transaction later decides.

Safety of a replay is not covered. Suppression is not safety, as §10 v4 and F6 both showed.

The trade Meera made. Every version above buys correctness with a write on the hot path. That is an extra insert in v2, or an extra predicate and column in v4, on every single message. It also buys a permanent operational obligation: retention, or a documented reprocess procedure.

That is the cost of at-least-once. The alternative is not "no cost". The alternative is at-most-once and silent loss.

13. What does this look like in Kafka, SQS, RabbitMQ and CDC?

In one breath: Four brokers, four different ways the duplicate arrives, and one dashboard. Every setting below quietly decides something you would rather decide on purpose.

Ben runs the platform team. He arrives with a proposal, and this section is what Meera needs before she can answer him.

Kafka and Spring — which knob decides what?

These are the pieces you will actually touch. Each one silently decides something.

enable.auto.commit. The default is true, and that default is not at-least-once. It commits on a timer during poll(). So what it means depends on code far away from the setting. With inline processing it approximates a coarse commit-after. Hand the batch to a thread pool and it becomes silent at-most-once. Set it false and ack explicitly. The kafka lab established this; it is repeated here because it is the single most common cause of the F1 family in the wild.

@Transactional on the @KafkaListener method. This puts the inbox insert and the effect in one transaction, which is exactly v2. The offset ack happens after the method returns, outside that transaction. That is the correct and intended arrangement. §10 v2's four-row crash table is why the gap is benign.

DefaultErrorHandler with DeadLetterPublishingRecoverer. Blocking retries, then the dead-letter queue. It preserves order and blocks the partition.

@RetryableTopic. Non-blocking retries. It does not block, and it gives up per-key ordering, which is F4. Choosing between these two handlers is choosing between availability and order. There is no third option.

Kafka transactions, sold as exactly-once semantics. They make read, process, write and commit-offset atomic inside Kafka. Read the next two sentences twice, because they are Ben's whole answer.

If your consumer's output is another Kafka topic, exactly-once semantics is the complete answer, and you need none of this lab. If your consumer writes to a database, calls an API, or sends an email, it covers none of that, and you need all of this lab.

That distinction is the single most valuable sentence to be able to say out loud in a design review.

SQS — how does a duplicate arrive here?

Standard queues are at-least-once by contract, and the duplicate arrives through visibility-timeout expiry. If your handler outruns the timeout, the message becomes visible again and a second worker takes it while the first is still working.

That is F2's zombie, produced by a different mechanism, and it is far more frequent than a Kafka rebalance.

FIFO queues offer a MessageDeduplicationId with a 5-minute window. Read that as one sentence: AWS deduplicates producer retries for you, and nothing else. Every source in §1 with a gap longer than five minutes is still yours to handle.

RabbitMQ — can you trust the redelivered flag?

The redelivered flag on a delivery is a hint, not a guarantee. It can be false on a genuine redelivery after a broker failover.

Never branch on it for correctness. Use it only for logging.

CDC and Debezium sinks — why are these the easiest consumers?

This is the best-behaved case in practice, because the producer's identity problem is already solved for you. Postgres gives source.lsn. MySQL gives the binlog coordinate. Either one is a monotone per-source sequence, and records are keyed by primary key.

So a sink that upserts by primary key and guards with WHERE last_lsn < :lsn is v4, with no extra work. That is exactly what the change-data-capture lab meant by "convergence under replay".

14. Which comfortable beliefs about this are wrong?

In one breath: Eight things that sound right, and the smallest concrete case that kills each one.

"We turned on the idempotent producer and exactly-once semantics, so consumers don't need this." This is Ben's proposal, and it feels reasonable because both features carry "exactly once" in their marketing. The smallest thing that breaks it: both features on, consumer writes to Postgres, pod dies between the database commit and the offset commit. Redelivery, double points. The guarantee is exactly-once within the Kafka cluster. The moment an effect leaves the cluster it is at-least-once again.

"Deduplicate on the offset." Genuinely appealing, because the offset really is unique. Arjun's relay republishes the same outbox row after a crash, and the new offset is honestly new. Applied twice (§10 v1).

"An inbox table gives exactly-once." It gives at-most-once application, given the five assumptions in §12. It stops giving it, quietly, when one of them lapses. Most often that one is retention.

"Check whether we've seen it, then process." The gap between the check and the write is not a rare interleaving. A rebalance produces two live processors as a matter of routine (§4). Only a conditional write arbitrates.

"Seven days of retention is plenty." It is plenty for every duplicate a machine produces. It is useless against the one a human produces. Redelivery age is bounded by your operational practice, not by your software (§10 v3).

"Idempotent means I can safely replay anything." Replay is suppressed, which is a different thing from safe. A reprocess intended to fix data will do nothing at all, silently (§10 v4, and F6).

"Our handler is UPDATE … SET status='PAID', so it's idempotent and we're done." It is idempotent. It is also not reorder-safe, and non-blocking retries reorder. Duplicates, ordering and concurrency are three problems with three mechanisms (F4, F9).

"The consumer's dual write is the same bug as the outbox's." It looks identical, and it is not. The consumer's failure mode is a lost offset commit, which the inbox absorbs. The outbox's failure mode is a lost event, which nothing absorbs. That asymmetry is the whole argument (§10 v2).

Solutions — The Idempotent Consumer

Attempt EXERCISES.md first. Design questions (levels 7–8) show a worked reasoning process, not a single correct answer — what is being checked is whether you reached for the right obligation, not whether you matched the words here.

Level 1 — Explain

1.1 When a sender gets no reply, it cannot tell "you never received this" from "you did it and the reply was lost", so it has to send again — and that is true of every hop, including the one between your consumer and its own bookkeeping. So copies of the same message are normal traffic, not a bug. A consumer therefore cannot be built to receive each message once; it can only be built to act on each message once, which is a different and achievable goal. Everything else in the lab is about how it recognises that it has already acted.

1.2

  • Identity — a stable name for the fact. Missing it, you deduplicate the address rather than the fact, and every republication slips through (§10-v1).
  • Atomicity — the record of processing and the effect commit together. Missing it, two racers both pass the check and both act; the constraint fires too late to prevent anything (§4).
  • Memory — the record still exists when the duplicate arrives. Missing it, the duplicate is a new fact; the classic form is a DLQ replay past the retention window (§10-v3).

1.3 Both are failure modes; only one is observable after the fact. A duplicate leaves evidence — two applications of one identity — that can be found by reconciling against the source, and repaired. A dropped message leaves nothing: you cannot query loyalty for a payment that produced no loyalty record, because the absence looks identical to a payment that never happened. The industry chose the failure it can detect.

  • (c) is an optimisation. If the ack is lost the records are re-read and (a) rejects them. See §10-v2's four-row crash table: the only bad row is "effect not committed, offset committed", which acking after the method makes unreachable.

Level 4 — Modify

4.1 Better: the duplicate path gets cheaper (one insert, no effect work), and the claim is visible to other processes immediately so a second consumer can back off rather than contend. Catastrophic: a message whose handler throws is now permanently marked processed — the claim committed, the effect did not, and the redelivery is suppressed. A loud poison message becomes a silent skip. That is F7. Claim-first is only correct when it also writes a RUNNING state that a reaper re-drives — i.e. only when the effect is external and cannot be in your transaction anyway.

4.2 The first service to process an event inserts the row; services two and three then hit the primary key violation and conclude "already processed", so they skip the message entirely. They lose data, quietly, from the very mechanism installed to protect them, and the loss is proportional to how often they lose the race — which is most of the time if service one is faster. It is noticed when someone reconciles a downstream total, typically weeks later. Fix: key on (consumer, message_id).

4.3 Three things, and the third is not code:

  1. Retention becomes ≥ 90 days plus a margin. Sizing changes accordingly — at 4,000/s that is ~31 billion rows, which forces the table to be partitioned by day with DROP PARTITION rather than DELETE (F10), or forces a move to a watermark design where the shape allows.
  2. The dedup key must be certain to be stable over 90 days — no content-derived keys, no keys that a producer redeploy could change.
  3. The runbook and the replay tool must state and enforce the limit: records older than retention are regenerated from source, never replayed. Retention is only a guarantee if something refuses the operation that would exceed it.

4.4 Designs A, B and C give the same guarantee as before — deduplication is per-message and does not depend on order. Design D breaks: two threads processing seq 17 and seq 18 concurrently for the same member can apply 18 first, after which 17 is silently dropped. You spent per-key ordering, which was Kafka's only ordering guarantee and D's precondition. If you need the throughput and the watermark, partition by key across consumers, not threads within one.

Level 6 — Spot the flaw

6.1 Nothing is wrong with the SQL. The flaw is what is missing: no consumer scoping in the key you would need if any other service shares the table (4.2), and — the intended answer — no retention policy at all, which is correct on day one and an outage by month six (F10). The smallest failing scenario is not a correctness trace, it is a capacity one: the table's index stops fitting in memory, insert latency crosses the handler's budget, handlers exceed max.poll.interval.ms, and the resulting rebalance storm produces exactly the zombies the table was protecting you from. Violates R3, in the direction nobody plans for. Dashboard: inbox size and p99 handler latency rising together, weeks before anything breaks.

6.2 Violates R1. The key is derived from content, so two legitimately distinct facts with identical content collide — Asha buys the same ₹500 coffee twice on the same day and the second purchase is silently swallowed as a "duplicate". Smallest scenario: two identical purchases, one day. Worse, it is undetectable from inside the consumer: suppressing a real event and suppressing a duplicate look identical. Only the producer knows which two sends are one intention; a consumer that invents an identity is guessing. Dashboard: nothing. Ever. That is the point.

6.3 Violates R1. Offsets are delivery identity, so this is §10-v1 with extra machinery: it survives crashes and rebalances and is defeated by the relay republish, the retry topic, a cluster migration and any replay. It is not stronger than an inbox, it is strictly weaker, and it costs you a ConsumerRebalanceListener and a piece of the group protocol. Smallest scenario: relay crashes after send(), republishes, double application.

6.4 Violates R1 and D's monotonicity precondition. currentTimeMillis() is not monotone across producers (clock skew — see clock-synchronization), not monotone across a single producer's NTP correction, and not unique under 4,000/s on one millisecond. Smallest scenario: two events for one member from two producer pods whose clocks differ by 30 ms; the later fact carries the smaller number and is silently discarded. Note the failure mode is loss, not duplication — a watermark's failures always are, and that is why its sequence source must be a real counter (an outbox row id, an LSN, a per-aggregate version), never a clock.

6.5 Violates R2, subtly, and only under a specific timing. The batching and sleeping mean the retention job is not atomic with anything: it deletes inbox rows in one transaction while the consumer is applying messages in another. That is fine. The real flaw is that the job's criterion is applied_at, which is when the consumer acted, while the risk it must bound is the redelivery age, which is measured from the event's creation. A message that sat in a retry topic for six days is applied on day 6 and its inbox row is deleted on day 13 — seven days of protection for a fact that is already thirteen days old, against a replay window everyone believes is seven days. The window you think you have and the window you have differ by the consumer's own lag. Dashboard: event age at apply time — and if that graph does not exist, nothing shows this at all.

Level 7 — Handle failure

7.1 The move is to stop trying to make one transaction cover two systems and instead give the second system its own idempotence.

  • Points: inbox row + UPDATE in the Postgres transaction, as before.
  • Elasticsearch: index with _id = eventId (or _id = memberId with version_type=external, version=seq). An index call with a fixed document id is an upsert — naturally idempotent, and the second call produces the same document.
  • Order: Postgres transaction first, ES second, and let redelivery re-drive ES if the consumer dies between them. Committing the offset only after both means the failure is a redelivery, and both sides absorb it.

Not guaranteed: that the two systems are ever consistent with each other at an instant. There is a window where points are awarded and the ES document is missing, bounded by the redelivery interval, and if the consumer is down for an hour the window is an hour. You are buying per-system idempotence, not cross-system atomicity — that would need the effect to be one system, which is what CQRS's "the read model is a lagging derived copy" was already telling you.

7.2 This is the idempotency lab's v4, unchanged.

poll → INSERT claim(eventId, state=RUNNING)   COMMIT       (alone)
     → SMS provider call, carrying idempotency key = eventId
     → UPDATE claim SET state=DONE, response=… ; effects   COMMIT
     → commit offset

Die after the SMS but before the second commit: the claim sits in RUNNING. Two things can re-drive it, and you should have both — the broker's redelivery (the offset was never committed, so the message comes back) and a reaper that sweeps RUNNING claims older than a threshold, which covers the case where the offset was committed. The re-driven call carries the same key, so the provider replays its own stored response rather than sending a second SMS. The guarantee's last mile lives in the provider, which is the recursion the idempotency lab described: each hop's doubt is absorbed by the next hop's key table.

7.3 (a) The partition stops. Nothing behind the poison record is processed. (b) Unaffected — the other partitions run normally, so aggregate throughput barely moves. (c) There is no inbox row, because the transaction rolls back every time. That is correct and is what makes retry safe. (d) Queue depth on that partition is flat and low, because one message is being retried, not accumulating.

(d) is the reason for the rule. Depth is a count; a stuck partition has a small count and an unbounded age. The alarm that fires is "oldest unprocessed message age > N minutes"; the alarm that stays silent forever is anything counting messages.

7.4 Design D suppresses replays by construction, so the procedure must make the reprocess a different intention rather than a duplicate.

  1. Decide the scope precisely: which members, which date range, which formula version. "Everyone" is a scope; "all of it" is not.
  2. Do not use the live consumer. Build a backfill job that reads the source of truth (the payments ledger, or the topic with a dedicated group id) and computes each member's correct total rather than accumulating deltas. Computed totals are assignments — naturally idempotent, safely re-runnable, and immune to whatever the watermark says.
  3. Write the result to a shadow column or table first. Diff against live. Expect the diff to be non-empty; investigate any member whose diff is zero as hard as any whose diff is large.
  4. Cut over with an assignment (SET points = :computed) that also sets last_seq to the highest sequence included, so the live consumer resumes cleanly from the right watermark and does not re-apply events the backfill already covered.
  5. Leave the live consumer running throughout; step 4's watermark write is what makes that safe.

The general principle: a recomputation is not a replay. Replay re-applies history through a path designed to suppress repetition; recomputation derives the answer and assigns it.

Level 8 — Design

8.1 The four questions, in this order, because each one's answer constrains the next:

  1. What names this message, and does that name survive republication? A bad answer (an offset, a content hash) means every other answer is irrelevant — you are deduplicating the wrong thing.
  2. What makes the record of processing atomic with the effect? A bad answer (a SELECT first, a separate transaction, an in-memory set) costs you double-application under every rebalance, i.e. weekly.
  3. How long must that record survive, and what enforces the limit? A bad answer costs the F5 incident: a repair operation that doubles data, silently, run by a human trying to help.
  4. What would this handler do if the record were gone entirely? This is the quality question. If the honest answer is "nothing bad — the operation is an assignment/upsert", the team needs far less of the machinery above. If it is "double the money", the first three answers had better be excellent.

8.2 Volume forces the choice. 20,000/s is 1.7 billion messages/day; an inbox with any usable retention is 50–150 billion rows, so design D (watermark) is the only affordable option — if events are keyed by merchant and carry a monotone sequence. Against the obligations: R1 satisfied by (merchantId, seq), producer-minted; R2 by a conditional UPDATE on the daily-total row itself, no second table; R3 dissolved. Storage is O(merchants × days), a few million rows, not O(messages). Precondition to verify explicitly: partitioning is by merchantId and retries are blocking, because non-blocking retries would reorder and the watermark converts reordering into silent loss.

Page on: event age at apply time, p99. It catches lag, stalled partitions, and out-of-window replays with one number, and it is the one that would have caught every failure in §11 except the zombie (which the conditional write handles without human involvement anyway). A daily reconciliation of the totals against the payments ledger is the backstop, and its residual is the number you publish.

8.3

Becomes unnecessary: the inbox table, its retention policy, the retention runbook line, the watermark's dedup role, and the duplicate-suppression metric.

Does not become unnecessary:

  • Ordering. Exactly-once delivery says nothing about sequence; retry topics and repartitioning still reorder, and versioning is still required.
  • Concurrency control. Two different messages touching one row still race (F9).
  • The consumer's dual write. Your effect is still in a different system from your read position; "delivered exactly once" does not mean "your database transaction committed".
  • External effects. The SMS you sent mid-handler is still sent whatever the transaction decides, and the payment API still needs its own idempotency key.
  • Business duplicates. Two distinct events describing one real-world fact are two messages; delivery semantics cannot see that.
  • Reprocessing. You still need a procedure for recomputation, and it still cannot be "replay the topic".

The second list is longer than the first, which is the exercise's point: "exactly-once" was never the whole problem, and most teams who believe they have solved it have solved the smallest part of it.

8.4 Something close to:

EOS makes read → process → write → commit-offset atomic inside Kafka, so it fully covers consumers whose only output is another Kafka topic — for those it genuinely does remove the need for an inbox. It covers nothing that leaves the cluster, so any consumer that writes to a database, calls an API or sends a message still needs consumer-side deduplication exactly as before. It also has two costs worth stating: a hung transactional producer stalls every read_committed consumer until transaction.timeout.ms, and isolation.level still defaults to read_uncommitted, so enabling it on producers changes nothing until every consumer is changed too.

The class for which the proposal is correct: Kafka-to-Kafka stream processors (Kafka Streams applications, filters, enrichments, aggregations whose entire output is topics and changelogs).
