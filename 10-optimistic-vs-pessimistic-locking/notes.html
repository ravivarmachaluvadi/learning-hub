Optimistic vs Pessimistic Locking

A learning lab. Everything measured here was measured by running the code in src/ on H2 2.4.240, JDK 25, on this machine — commands included. Numbers vary a little between runs; the shapes don't.

You already have the prerequisites. From the isolation-levels lab: lost update, SELECT … FOR UPDATE, two-phase locking, MVCC, first-committer-wins, the retry loop, and the fact that "optimistic locking" is first-committer-wins implemented in the application. From event-sourcing: the expected-version append. From linearizability: compareAndSet and the 87%-lost-increment experiment. This lab is where all of those become one decision you make in real application code — and it starts with a problem none of them can solve.

Layer map: BEGINNER (§1–9) → INTERMEDIATE (§10) → ENGINEERING (§11–14) → PRODUCTION (§15). Checkpoints at each border.

1. WHY — the conflict that outlives every transaction

Two people open the same record on their screens. Both edit. Both click Save. Both see "Saved successfully." One of their changes no longer exists, and nothing anywhere — no error, no log line, no failed request — records that it ever did.

The isolation-levels lab dealt with conflicts inside the database: two transactions overlapping for milliseconds. This conflict is different in one brutal way: the gap between reading the record and writing it back is minutes long and contains a human. No transaction spans it. No isolation level can see it. Whatever protects against it has to be built by you, in application code — and there are exactly two ways to build it. That choice — detect conflicts at write time, or prevent them at read time — is what "optimistic vs pessimistic locking" means, and choosing wrong shows up as lost customer data, deadlocked order processing, or a job queue running at a quarter speed.

2. PROBLEM — Meera, Sam, and product #42

Meera and Sam run the admin tool of a small web shop. Product #42 is a steel water bottle: description "Steel water bottle, 500ml", price 1500.

  • 10:00:00 — Meera opens the edit page. Her browser now holds a copy of the row.
  • 10:00:05 — Sam opens the edit page. His browser holds the same copy.
  • 10:02:00 — Meera fixes the description to "Steel bottle, 500ml, BPA-free" and clicks Save. The row is updated. ✓
  • 10:03:30 — Sam changes the price to 1200 and clicks Save. His form posts every field — including the description as it looked at 10:00:05. The row is updated. ✓

Final row: price 1200, description "Steel water bottle, 500ml". Meera's work is gone. She'll discover it next week, if ever. Run the kill rate yourself:

cd 10-optimistic-vs-pessimistic-locking
java -cp ../lib/h2.jar src/Experiments.java overwrite

naive last-save-wins:  Meera's edit destroyed in 100/100 rounds (0 errors shown to anyone)

This is the isolation lab's lost update — but stretched. There, the read and the write sat inside one transaction, seconds apart. Here they sit in different HTTP requests, minutes apart, with lunch in between.

3. NAIVE SOLUTION — "the database already solves this"

A reasonable engineer who just finished the isolation-levels lab reaches for the tools that fixed lost update there:

  1. Wrap each save in a transaction. Already true — every save above was a perfectly ACID transaction. Didn't help.
  2. Raise the isolation level. Set everything to SERIALIZABLE.
  3. Use SELECT … FOR UPDATE when loading the edit page, so nobody else can grab the row while Meera has it open.

🔮 Predict: Sam's save runs at SERIALIZABLE. Does the database reject it?

Reveal No — on any database. Serializability promises that concurrent transactions behave as if run one at a time. But Meera's *save* transaction committed at 10:02 and Sam's *save* transaction started at 10:03:30. They are not concurrent at all. Sam's transaction is a lone UPDATE that read nothing; run serially after Meera's, it does exactly what it did. The database is keeping its promise perfectly. The conflict isn't between two transactions — it's between two *conversations*, each spanning a read-transaction, a human, and a write-transaction. The database never sees a conversation.

4. FAILURE — and the second naive idea is worse

Option 3 — hold FOR UPDATE from page-open to save — at least targets the gap. It fails on three independent grounds:

  • A transaction is welded to one connection. Holding a transaction for minutes means holding a pooled connection for minutes. A pool of 20 connections supports 20 open edit pages. The 21st admin takes the site down. (HTTP makes it worse: Sam's save request may land on a different app server, which cannot commit a transaction living on the first one.)

  • The lock outlives the intention. Meera opens the page, the phone rings, she goes to lunch. The row is now locked until her transaction times out — and every colleague who touches product #42 queues behind her. Measured (a 2-second pause standing in for lunch, five colleagues retrying meanwhile, each willing to wait 500ms):

    === lunch — who pays for one client's 2s pause?
PESSIMISTIC: other clients landed  0 saves, hit 15 lock timeouts during the pause
OPTIMISTIC : other clients landed 170 saves, hit 0 lock timeouts during the pause

    One person's pause became fifteen other people's errors. That multiplication — someone else's delay becoming your failure — is the signature cost of holding locks.

  • Browsers don't send "I closed the tab." If Meera never comes back, who unlocks the row, and when?

5. THE REAL REQUIREMENT

What we actually need, in plain words:

Between "I read the record" and "I wrote it back" — a gap of arbitrary length that may cross transactions, connections, servers, and lunch — no other write may slip in unnoticed. And the protection must not consume any database resource during the gap.

Note what is not required: preventing the other write. Meera and Sam may both edit freely. What must never happen is the silent overwrite — a conflict nobody was told about.

6. KEY IDEA — make the write conditional on what you read

Carry, as plain data, proof of which state of the row you read. When you write, tell the database: "apply this only if the row is still the one I saw." If it isn't, the write does nothing, you're told, and you get to re-decide with fresh eyes. Proof-of-what-I-saw is one number — a counter on the row that every write increments.

Nothing is held during the gap. The number sits in a hidden form field, a JSON payload, a session — it's data, so it survives anything: connection close, server switch, a week of vacation.

And the same requirement has a second, opposite answer for a different situation: when conflicts are near-certain and retrying is expensive, stop them from starting — take the row lock before reading, do the work, commit. That only works when the whole read-decide-write fits inside one transaction; in exchange, nothing is ever wasted on a doomed attempt.

Detect at write time, or prevent at read time. Everything else in this lab is the working-out of that pair.

7. TERMINOLOGY — the professional names

Optimistic locking — the conditional-write strategy. Plain meaning: proceed assuming no one interfered; check at the end. Technical meaning: every write carries the version it was based on and succeeds only if that version is still current (first-committer-wins, enforced by the application's protocol — the same rule the isolation lab met inside snapshot-isolation engines, now hand-built one level up). Why the term exists: to name the bet — you bet conflicts are rare and pay only when you lose. Example: Sam's UPDATE … WHERE id=42 AND version=0 matches 0 rows because Meera made the version 1. The name is a lie in one detail: no lock exists. Nothing is ever held. Some texts say "optimistic concurrency control" precisely to avoid the lie; JPA calls it @Version.

Pessimistic locking — the lock-first strategy. Plain meaning: assume interference; claim exclusivity before touching anything. Technical meaning: acquire the database's row lock (SELECT … FOR UPDATE — the same row lock every UPDATE takes anyway, taken early, at read time) and hold it until commit. Why the term exists: to name the opposite bet — conflicts are likely, so pay a known cost (waiting) instead of an unknown one (redoing). Example: while Meera holds #42, Sam's FOR UPDATE queues.

Version column — the counter that makes reads provable. Any monotonically advancing value works (integer, timestamp — integers avoid clock trouble, a lesson three labs old). It answers one question: has this row changed since a given moment? — with no history, only "same or not".

Stale — describing a copy of data whose source has since changed. Meera's save made Sam's browser copy stale. Staleness is invisible to its holder; that invisibility is the whole problem.

Conflict (in this lab) — a write attempt based on a stale read. The two strategies differ only in when it surfaces: optimistic at write time (update count 0), pessimistic at read time (you wait until it can't happen).

Lock queue / lock timeout / NOWAIT / SKIP LOCKED — what a blocked locker may do: wait in the row's queue (default; give up after the timeout — error 50200 on H2), refuse to wait (NOWAIT: instant error), or pretend locked rows don't exist (SKIP LOCKED: the query returns only unclaimed rows — §14's job-queue trick).

Offline lock — Fowler's name (PoEAA) for either strategy stretched across requests, which is exactly our Meera/Sam setting: Optimistic Offline Lock is the version column; Pessimistic Offline Lock is an application-managed "checked out by Meera" claim (a row in a locks table with an owner and an expiry — NOT a database lock, precisely because database locks can't span requests).

Minor terms get one line where they first appear; everything lands in the glossary (§18).

8. MENTAL MODELS

The simple model — two ways teams share files. Optimistic is git. Everyone clones and edits freely. When you push, git checks whether the remote moved since your clone; if it did, your push is rejected — fetch first. You pull, look at what changed, redo your intent, push again. Nobody ever waited; latecomers redo work. Pessimistic is the shared Excel file on the network drive. First opener gets it; everyone after sees "locked by another user — open read-only?" and waits. Nobody ever redoes work; everybody queues — and when the holder goes to lunch with the file open, the team goes to lunch too.

The engineering model. A row (data, version) plus, per client, a conversation (readData, readVersion, decide(), write). Optimistic: writes are compare-and-swap on the version — AtomicInteger.compareAndSet from the linearizability lab, spelled in SQL, with the row lock making check-and-write one atomic statement. Pessimistic: an exclusive lock with a FIFO-ish queue, acquired at read, released at commit; hold time = read-to-commit, and every waiter's latency includes every holder's hold.

simple model engineering model
your clone of the repo the row copy + version your SELECT returned
remote moved since clone version no longer matches
push rejected, fetch first the save's UPDATE finds the version changed → rejected
pull + redo + push again re-read, re-decide, retry
Excel's "locked by user" dialog FOR UPDATE queue (or NOWAIT error)
closing the Excel file commit/rollback releasing the lock

Where the analogies break. Git merges: non-overlapping edits combine automatically, and both histories survive. A version check is all-or-nothing on the whole row — Meera edited description, Sam edited price, no overlap, still a conflict; if you want field-level merging you write it yourself in the retry (as optimistic_retry_rereads_so_both_edits_survive does), and the database keeps no history to merge from. And Excel's lock is owned by a person who can hold it overnight; a FOR UPDATE lock is owned by a transaction and cannot outlive it — which is precisely why it cannot protect a conversation (§4), and why the offline-pessimistic pattern needs an expiry-bearing claim row instead.

10. ACTUAL MECHANISM — build it, break it, harden it

CHECKPOINT — beginner → intermediate. You can now explain why the two strategies exist and which bet each one makes. Next: the exact SQL, and the three places hand-rolled implementations really go wrong.

10.1 Optimistic v1 — the conditional UPDATE

Schema change: one column, version BIGINT NOT NULL, starting at 0. Reads return it. Saves become:

UPDATE product
SET    description = ?, price = ?, version = version + 1
WHERE  id = ? AND version = ?     -- the version the form was rendered from

Walk Meera/Sam with real values. Both read (…, version=0). Meera's UPDATE matches (version is 0), writes, sets version 1. Sam's UPDATE hunts for a row with id=42 AND version=0 — no such row exists anymore.

🔮 Predict: what does the database do with Sam's UPDATE — error, block, or something else?

Reveal Something else, and it's the trap of the whole technique: the UPDATE **succeeds, affecting 0 rows**. To SQL, an UPDATE whose WHERE matches nothing is as unremarkable as a SELECT returning no rows. The *only* witness to the conflict is the update count your JDBC call returns. H2, Postgres, MySQL — all identical here.

So the load-bearing line is not the SQL — it's the Java after it (Store.java:96-97):

int count = u.executeUpdate();
if (count == 0) throw new StaleVersionException(p.id(), p.version());

Delete the if and nothing fails, ever — conflicting saves become silent no-ops. That's planted bug #1; java -cp ../lib/h2.jar src/Tests.java broken shows Sam's save vanishing without an exception or an effect.

Why can't two writers both match version 0? The check and the write are one statement, and the engine takes the row lock for that statement (the MVCC write lock from the isolation lab). If both UPDATEs arrive together, one holds the row first; the second waits the few microseconds until commit, then re-evaluates its WHERE against the new row — version is 1 now, count 0. The atomicity you'd have to build carefully in Java is free in one SQL statement. (Same shape as the isolation lab's single-statement UPDATE SET n = n + 1 — and as compareAndSet.)

10.2 Optimistic v2 — the retry loop, and the second trap

An exception is not a strategy. What should Sam's code do with StaleVersionException? Two legitimate answers:

  • Ask the human — reload, show "Meera changed this while you were editing", let Sam re-decide. Right for forms.
  • Retry in code — for machine decisions: re-read the row, re-run the decision on the fresh values, attempt again (Store.java:110-131).

The event-sourcing lab's rule — a conflict means re-decide against fresh truth, never re-send — is load-bearing here, and planted bug #3 (stale-reapply) shows why: a retry loop that re-reads only the version (so the WHERE passes) but keeps the value computed from the original read. It retries diligently and still destroys data:

bug_caught: stale-reapply loses increments despite retrying (40/320)

280 of 320 increments gone — with a version column and with a retry loop. The version check verifies where the write lands, not what it contains; only re-deciding refreshes the contents.

(Planted bug #2, no-version-bump, forgets version = version + 1: the consumed version stays current, so the next stale writer also matches. First-committer-wins quietly becomes every-committer-wins.)

10.3 Pessimistic — the queue, and its three dialects

SELECT id, description, price, version FROM product WHERE id = 42 FOR UPDATE

Same row lock an UPDATE takes — taken at read time, held to commit. Between those two moments you are provably alone on the row: read, decide, write, no version check, no retry, no wasted work. Everyone else queues. Measured queue mechanics (src/Tests.java):

  • for_update_blocks_until_commit — a second locker proceeds ~the instant the first commits (waited ≈ the 400ms hold), not before.
  • nowait_fails_immediately_instead_of_queueing — FOR UPDATE NOWAIT errors in <1ms instead of queueing: "tell me now, I'll do something else."
  • skip_locked_returns_only_unclaimed_rows — with row 0 locked by someone else, FOR UPDATE SKIP LOCKED returns rows 1 and 2 as if 0 didn't exist.

Wait / refuse / skip: those three dialects are the entire pessimistic API surface, and §14's queue experiment shows SKIP LOCKED alone is worth 4×.

11. FAILURE SCENARIOS — each one created, watched, explained

CHECKPOINT — intermediate → engineering. You can write both strategies correctly. Now: how each one fails, what each failure costs, and which guarantee survives it. Every scenario below is runnable.

a. The silent no-op (optimistic, bug #1). Create: ignore the update count. Watch: Tests.java broken. What/why: conflicting saves match 0 rows; SQL raises nothing. Response: none — that's the failure. Kept: first writer's data (conflicts lose instead of overwriting — strictly better than naive, by luck). Lost: the entire point — nobody learns their save didn't happen. Production: users report "my edits randomly don't stick"; no error rate moves. Audit every hand-written conditional UPDATE for a count check; ORMs (@Version) do it for you.

b. Version consumed but not advanced (bug #2). Watch: Tests.java broken. Why: the WHERE guards against versions changing; if writes don't change it, the guard guards nothing. Second stale save lands, first writer's edit dies. Production: hand-rolled SQL where someone "optimized away" the increment; catches fire only under concurrent editing, i.e. in production and not in tests.

c. Retry-without-re-decide (bug #3, §10.2). Lost: 280/320 updates despite detection and retry. Production rule: the retry re-runs the whole use case — the same rule the isolation lab derived for serialization failures (re-run the method, not the statement).

d. The lunch break (pessimistic). Create: any pause between lock and commit — a slow downstream call, a GC pause, a human. Watch: Experiments.java lunch. What: 0 neighbour saves, 15 neighbour timeouts during one client's 2s pause; under optimistic the same pause costs the neighbours nothing (170 saves) and the sleeper pays alone with one conflict. Why: a held lock converts one client's delay into everyone's delay — availability coupling. Kept: correctness. Lost: independence of latencies. Production: p99 spikes on hot rows whenever anything pauses; the on-call sees lock-timeout storms with no CPU or I/O anomaly. Rule: never hold a row lock across a network call or user interaction.

e. Deadlock (pessimistic only). Create: two transactions lock the same two rows in opposite orders. Watch: Experiments.java deadlock — 59 victims (SQLState 40001) in 60 opposite-order transfers; the optimistic translation of the same workload: 0 deadlocks, 14 cheap retries. Why: deadlock needs wait-while-holding; optimistic clients never wait while holding anything. Response: the engine detects the cycle and shoots one victim, which must retry (so pessimistic code needs a retry loop after all — for 40001 instead of stale versions). Kept: progress (one side wins). Lost: the victim's work; ordering-discipline debt. The isolation-levels fix still applies: lock in a global order (lower id first → 0 deadlocks, measured there).

f. Starvation (optimistic only). Create: one writer whose read-decide-write takes 30ms sharing a row with six who take ~0ms. Watch: Experiments.java starvation:

pure optimistic         : 0/5 saves in 8019ms, 263 lost races  <- STARVED (no error, no progress)
escalate after 3 losses : 5/5 saves in  603ms,  15 lost races, 5 escalations

Why: first-committer-wins has no queue and no memory — every retry faces the same race it just lost, and the slowest decider loses ~always. 263 diligent retries, zero progress, zero errors: a pure liveness failure (safety intact — nothing was ever lost). Fix: escalation — after N losses, swallow your optimism and take FOR UPDATE; the lock's queue is exactly the fairness optimism lacks. This hybrid is the production-grade default for mixed workloads.

g. The convoy (pessimistic misuse). Create: N workers each claiming "the first PENDING job" with plain FOR UPDATE. Watch: Experiments.java queue — all four workers pick the same first row, three queue behind one, processing serializes: 1397ms for 120 jobs × 10ms against a 1200ms serial floor. SKIP LOCKED: 312ms — the perfect 4-way split. Why: they don't contend on data, they contend on position. Skipping locked rows makes claims disjoint by construction. Lost with SKIP LOCKED: strict FIFO order — jobs are claimed slightly out of order; queues almost never care.

h. Write skew, revisited and finally fixed in the app. The isolation-levels lab proved H2 permits write skew at every level including SERIALIZABLE (the two doctors both go off call, each updating only their own row — no write-write conflict for first-committer-wins to see, because the thing they shared was a rule, not a row). Now you own the fix: materialize the rule as a row and force every rule-dependent transaction to bump its version:

UPDATE roster SET version = version + 1 WHERE id = 1 AND version = ?

Both doctors' transactions now collide on the roster row on purpose; the second gets count 0 and aborts. Measured (shared_version_bump_stops_write_skew): 1 doctor left on call, 1 rejection — against write_skew_survives_for_update_on_own_rows proving FOR UPDATE on your own row does nothing (0 doctors left). JPA ships this as LockModeType.OPTIMISTIC_FORCE_INCREMENT on the aggregate root. The deep point: a version column turns invisible read-dependencies into visible write-conflicts — a hand-built, targeted rw-antidependency check.

12. CORRECTNESS — what is actually guaranteed

optimistic pessimistic
lost update between your read and write impossible (if count is checked) impossible (while lock held)
works across requests/connections/servers yes — version is data no — lock dies with the transaction
write succeeds first try not guaranteed (conflict → retry) guaranteed once lock acquired
deadlock impossible (never wait-while-holding) possible (needs ordering discipline)
starvation / livelock possible (no queue) queue gives rough fairness
wasted work yes: redone decisions no; waiting instead
one client's pause hurts others no yes — that's what holding means
stale reads allowed (it's not a read guarantee) allowed for plain SELECTs too
protects against writers outside the protocol no — a raw UPDATE bypasses it no — unless they too touch the locked row

Traded away, respectively: liveness under contention and redone work (optimistic) vs latency independence and deadlock-freedom (pessimistic). Neither guarantees anybody reads fresh data — both are write-write protocols; read skew from the isolation lab is untouched by either.

The last row deserves its own sentence, because it echoes the isolation lab's constraint lesson: an isolation level protects code that asks; a version column protects code that follows the protocol; only a database constraint protects the table. The migration script and the support engineer's console feel no version checks. Where the rule can be a constraint (UNIQUE, CHECK balance >= 0), the constraint still wins.

Two Spring-specific traps, both versions of bugs you just ran:

  • The controller that "re-loads and copies". A POST handler that does Product p = repo.findById(id); p.setPrice(form.getPrice()); repo.save(p) has disabled @Version — the entity was freshly loaded, so its version is current and the check always passes. One idea, five costumes.

15. PRODUCTION — choosing, operating, and what the toy hides

CHECKPOINT — engineering → production. You can implement, break, and fix both strategies. Left: which to choose when, and how this looks at 3am.

The decision, as a flowchart:

flowchart TD
    A[write conflict possible?] -->|read & write in DIFFERENT<br>transactions - form, API, saga| B[optimistic - the only option<br>version in the payload]
    A -->|same transaction| C{can the rule become<br>a constraint or a<br>single UPDATE statement?}
    C -->|yes| D[do that - no strategy needed<br>UNIQUE / CHECK / SET n = n + 1]
    C -->|no| E{conflict probability?}
    E -->|low - most rows,<br>most of the time| F[optimistic + retry<br>escalate after N losses]
    E -->|high - hot rows,<br>costly decisions| G[pessimistic FOR UPDATE<br>global lock order, short holds]
    B --> H{humans in the loop<br>editing for minutes?}
    H -->|conflicts must be rare<br>& mergeable| B2[version + merge UI]
    H -->|conflicts common or<br>unmergeable - CMS, CAD| B3[pessimistic OFFLINE lock:<br>claim row + owner + expiry]
    G --> Q[claiming work from a queue?<br>FOR UPDATE SKIP LOCKED]

Note the two arrows that most engineers forget exist: "just write better SQL" (the isolation lab's UPDATE SET n = n + 1 — 320/320, 0 retries, 26ms — still beats both strategies whenever the decision fits in SQL), and the offline pessimistic claim (Google Docs' "someone is editing" banner, Jira's soft locks) for long human edits where a version conflict after an hour of work is cruelty.

Toy → real. This lab's H2 is in-process, which flatters pessimistic locking twice: lock acquisition is a function call (real: a network round trip per statement, with the lock held across all of them — a 3-statement locked section at 1ms RTT holds the row ≥3ms, a 100× longer window than here), and there are always spare cores to hide optimistic waste (real: peak traffic eats the spare cores precisely when hot rows are hottest). The directions of §14 survive; the exact crossover point is yours to measure on your stack — the harness pattern in Experiments.java ports to any JDBC URL.

Operations. What you watch: optimistic → conflict rate (conflicts ÷ saves; rising means a hot row or a slow decider — find it before it becomes starvation) and retry-count distribution (a growing tail IS starvation beginning). Pessimistic → lock waits (innodb_row_lock_waits, pg_locks + log_lock_waits), lock timeouts, deadlock rate. The 3am signatures: optimistic failure = one entity's error rate climbs with traffic, CPU busy on work that never lands; pessimistic failure = latency cliff with idle CPU (everyone's queued), or a deadlock storm from one new code path locking in the wrong order.

What this lab intentionally omits. Connection-pool dynamics (the real multiplier of §4). Replication: a version check is only meaningful on the primary — reading a replica's version and writing through the primary manufactures false conflicts (or worse, with no-version-bump-like schemes, false successes); the quorums lab's staleness lessons apply. Caches: a cached row + version behaves like a permanently stale form — conflict storms that look like user error. Gap/next-key locks: on MySQL RR, FOR UPDATE can lock ranges you didn't ask for (isolation lab, §MySQL) — pessimistic scope is engine-specific. Fairness of real lock queues, priority inheritance, FOR NO KEY UPDATE/FOR SHARE weaker modes, advisory locks (Postgres pg_advisory_xact_lock — pessimistic locking on a made-up name instead of a row).

The same idea beyond SQL (asserted from vendor docs, not run here): DynamoDB ConditionExpression + ConditionalCheckFailedException; MongoDB findOneAndUpdate filtering on the old value; Elasticsearch if_seq_no/if_primary_term; Kubernetes metadata.resourceVersion — every kubectl apply race returns HTTP 409 Conflict and client-go ships RetryOnConflict, §10.2's loop verbatim. Once you've seen the shape — carry proof of what you read; make the write conditional on it; re-decide on conflict — you'll find it in every system that lets two writers near one datum without a lock.

Commonly confused, separated in one sentence each: Isolation levels order operations inside transactions; this lab's strategies order conversations that span transactions — you usually need both. Rung 1

1.1 Two writers each read a record, think, and write back — and the think time crosses transaction boundaries (a form, an API call-out, a human). Each writer's transactions are individually harmless: the write transaction is a lone UPDATE that read nothing. Isolation levels order transactions; here every ordering of these transactions produces the same loss, so even a perfectly serializable database executes the overwrite faithfully. The read-write link the database would need to see exists only in the application's memory — so the application must carry it (a version) or prevent the interleaving (a lock it manages itself).

1.2 A number that changes on every write — carried out of the read as plain data. It answers exactly one question: is the row still the one I read? (Not "what changed", not "who changed it" — no history, one bit.)

1.3 MVCC is the engine keeping multiple versions so readers don't block writers — it's invisible plumbing and protects nothing across requests. Optimistic locking is an application protocol: your schema, your WHERE clause, your retry. Related only in spirit: snapshot isolation's first-committer-wins applies within concurrent transactions, while your version column enforces the same rule across conversations — Postgres gives you the first automatically and cannot give you the second.

Rung 2

2.1 (a) Store.java:96-97 — the update-count check (with the atomicity supplied by the conditional UPDATE being a single statement). (b) c.commit() at the end of pessimisticUpdate — the lock dies there; until then the transaction is alone. (c) The same lines as (a): if (count == 0) throw … — bug #1 is its absence.

2.2 The sleeper holds it (padlock on the row, holder's colour). The other five are in the row's lock queue (or erroring out at their timeout) — their state is "waiting", not "failed" until the budget runs out. The neighbour-cost figure is the timeout/zero-saves counter — 15 timeouts, 0 saves in the measured run.

2.3 Because the sharing happened serially. Each worker's claim blocked until the current holder finished processing (the lock was held through the 10ms of work), then the next waiter got the next job. Fair distribution, single-file execution: 27–33 each, but one at a time — the definition of a convoy. Throughput, not fairness, is what SKIP LOCKED buys.

Rung 3

3.1 Corrupt — in the worst way. The raw UPDATE didn't bump version (there is no trigger), so Meera's stale save still matches version=0: it succeeds and silently reverts the data-fix's price. This is bug #2 performed by hand, and it's why §12's last table row exists: the protocol only binds writers who follow it. (Mitigations: a trigger bumping version on every write, or admin tooling that goes through the same repository code.)

3.2 ~280 retries × 15ms ≈ 4.2 seconds of redone decisions inside a ~1.2-second wall clock — the spare cores run the doomed attempts in parallel with the doomed attempts of others. Measured: 301 retries = ~4515ms redone, wall 1214ms vs pessimistic 1209ms. The bill is CPU, not latency — until the machine has no spare CPU.

3.3 Same order on A and B → no deadlock between those two ever: whoever holds A wins B's race too; a cycle needs each side holding something the other wants. Adding C (touched only by transaction 1, before A) changes nothing between these two — the cycle still requires opposite ordering on some shared pair. (It can matter with a third transaction touching C and A in reverse — deadlock freedom is a property of the global order over shared resources.)

3.4 Correctness: perfect (320/320). Retries: zero — there is nothing to retry; the statement reads after taking the row lock, so it cannot act on stale data. Time: near the floor. The isolation-levels lab measured exactly this: UPDATE SET n = n + 1 at 320/320, 0 retries, 26ms — the "neither strategy" arrow in §15's flowchart. Both locking strategies exist for decisions that don't fit in one statement.

Rung 4

4.1 Saves during the pause stay ~0 (the lock is simply held — no timeout setting manufactures access to a locked row); timeouts drop to ~0 because 6000ms outlives the 2s pause — the waiters queue silently and land after the sleeper commits. The knob chose between erroring at 500ms and waiting the full pause — i.e., which bad experience the five users get, error page vs frozen page. (Availability shifted shape, not size.)

4.2 Mostly — workers scatter across ~120 pending rows, collisions become occasional, throughput approaches skip-locked's (minus the cost of RAND() sorting a scan). Paid: any pretense of FIFO — old jobs can languish (unbounded unfairness, not just reordering). A real queue refuses when jobs have deadlines/SLAs or ordering semantics (per-key sequencing, a payment's steps). SKIP LOCKED keeps approximate order for free, which is why it's the answer rather than randomization.

4.3 optimistic_race_8x40_converges_to_320 would catch it — with first-committer-wins broken, concurrent incrementers overwrite each other and the total lands well below 320. The broken mode uses the two-writer script because it isolates the mechanism: it shows the second stale save being accepted (staleAccepted=true) — a precise witness of "the version no longer advances" — where the race would only show a wrong total that all three bugs (and twenty other mistakes) can produce.

Rung 5

Working bodies (verified 6/6 in this lab):

static void yourOptimisticSave(Connection c, Store.Product p) throws SQLException {
    try (PreparedStatement u = c.prepareStatement(
            "UPDATE product SET description=?, price=?, version=version+1 " +
            "WHERE id=? AND version=?")) {
        u.setString(1, p.description());
        u.setInt(2, p.price());
        u.setInt(3, p.id());
        u.setLong(4, p.version());
        if (u.executeUpdate() == 0) throw new Store.StaleVersionException(p.id(), p.version());
    }
}

static int yourClaimJob(Connection c, String worker) throws SQLException {
    while (true) {
        int id;
        try (ResultSet r = c.createStatement().executeQuery(
                "SELECT id FROM job WHERE status='PENDING' ORDER BY id LIMIT 1")) {
            if (!r.next()) { c.commit(); return -1; }
            id = r.getInt(1);
        }
        int n = c.createStatement().executeUpdate(
            "UPDATE job SET status='RUNNING', worker='" + worker +
            "' WHERE id=" + id + " AND status='PENDING'");
        c.commit();
        if (n == 1) return id;   // count 0: lost the race — try the NEXT candidate
    }
}

The signals: optimisticUpdate's is a version mismatch on the same row (someone changed the data I'm editing — retry the same row); the claim loop's is a state-transition miss (status left PENDING — someone took this job, so retry means a different row). Same conditional-write mechanic, opposite retry targets — the status column is a version column whose values have names.

Rung 6

  • no-count-check — diff: "simplify: we don't use the return value" on executeUpdate(). Breaks: conflict is detected (row 1 of §12 holds only "if count is checked"). Single-user tests: no concurrent writer, so count is always 1 and behaviour is identical.
  • no-version-bump — diff: "perf: drop the pointless self-increment" or a hand-written UPDATE that forgot it. Breaks: first-committer-wins — all stale committers win. Single-user: your own saves never race, versions never need to advance.
  • stale-reapply — diff: a "retry helper" that caches the computed entity and re-saves it after refreshing the version (often born as a fix for "version conflict spam" in logs). Breaks: re-decide — the write contains decisions made against dead data. Single-user: retries never trigger.

Longevity ranking (defensible version): no-version-bump longest — it needs two stale writers to overlap to do damage, and its symptom (an overwritten edit) looks exactly like a user mistake; no-count-check next — damage from any single conflict, but the symptom ("my save didn't stick") at least generates support tickets; stale-reapply shortest — it needs contention to fire, but where it fires it mangles data repeatedly and mechanically (40/320 survivors), which shows up in sums and audits fast. Any ranking is fine if it argues from (frequency of trigger) × (visibility of symptom).

Rung 7 (worked design)

Schema: claims(article_id PK, owner, expires_at TIMESTAMP, generation BIGINT).

  • claim(a, o): one conditional write — UPDATE claims SET owner=?, expires_at=NOW()+INTERVAL '15' MINUTE, generation=generation+1 WHERE article_id=? AND (owner IS NULL OR expires_at < NOW()) (insert the row on first use). Count 1 → you hold the claim and its new generation, which you keep client-side.
  • save(a, o, g): UPDATE articles SET … WHERE id=? AND EXISTS (SELECT 1 FROM claims WHERE article_id=? AND owner=? AND generation=? AND expires_at >= NOW()) — or check the claim row first with the same conditions, in the same transaction.
  • The A-returns-late story: A claimed at generation 7; expiry passed; B claimed → generation 8. A's Save presents (owner=A, generation=7): the condition fails on generation, regardless of any timestamp trickery or whether A re-claims later. A gets "your lock expired and Sara took over — here's a diff of your text to merge by hand." The generation is a fencing token (redis lab: the number the resource checks so a paused ex-holder can't act on a stale claim; linearizability lab: same device). expires_at alone is insufficient — A's save could race the expiry clock; the generation makes stale authority structurally unusable.
  • Internals: optimistic conditional writes — a claims table managed with FOR UPDATE would reintroduce §4 (the claim transaction would have to span the edit). The whole point of the offline lock is that the "lock" is ordinary data; the only real locks are the row locks inside each single-statement claim/save, held for microseconds.

Rung 8 (worked discussion)

  • Dashboard forms — optimistic offline: @Version round-tripped through the form; conflict → merge UI. Accepted failure: occasional "someone else edited" friction. 3am metric: conflict rate per entity — a spike on one product = a bot or an integration writing raw UPDATEs (rung 3.1's corruption, live).
  • Ledger — expected-version append (optimistic; the event-sourcing shape). Conflict = re-derive the decision, never re-send. Accepted: retries under bursts on one account. Metric: append-retry tail per stream; a hot stream's growing tail is §11f starvation and wants escalation or stream sharding.
  • Wallet debits — neither strategy where a statement suffices: UPDATE wallet SET balance = balance - ? WHERE id = ? AND balance >= ?, count 0 = insufficient funds, plus CHECK (balance >= 0) as the constitutional backstop. If the decision outgrows one statement (multi-row risk checks), pessimistic FOR UPDATE in a short transaction with a global lock order (wallet id ascending), never spanning any external call. Accepted: hot-wallet serialization — by design. Metric: lock wait time on wallet rows; a cliff with idle CPU = a hold-time regression (someone added an API call inside the lock).
  • Payout workers — FOR UPDATE SKIP LOCKED, claim + mark RUNNING in one short transaction, process outside it, idempotency key on the transfer (transactional-outbox lab: a timeout is not a failure). Accepted: approximate ordering, and crashed-worker jobs stuck RUNNING — so a reaper re-pends stale RUNNING rows, and the idempotency key makes the reaper safe. Metric: oldest PENDING age + RUNNING-without-heartbeat count.
  • (1) Constraints replace strategy wherever the rule is about the data: non-negative balances, UNIQUE (merchant, idempotency_key) on payouts — those hold against every writer including the migration script. Strategies remain for rules about decisions (approvals, risk checks) the schema can't state.
  • (2) The replica — edit pages now read stale rows with stale versions: every save against a row that changed since replication lag ago fails, support tickets say "it never saves". (Data stays safe — false conflicts, not corruption: the conditional write still executes on the primary. The failure is availability/UX, plus rung-3.1-style danger only if someone "fixes" it by dropping the check.) Smallest fix: pin edit-page loads (reads that feed writes) to the primary — read-your-writes routing, the quorums lab's lesson that staleness fixes are routing fixes.
