Lab 43 · Copies and Agreement

Distributed Locking

A learning lab. Every number in this document was produced by running the code in src/ (plain Java, no dependencies, fully deterministic — same setup, same story, every run). Commands included.

You have met every ingredient of this lab before — but never the subject itself. The redis lab measured the headline failure (a GC pause outliving SET NX PX's TTL put two holders in the critical section) and named the fix "a fencing token checked by the resource" without opening it. The uber lab gave you leases with deadlines. The gossip lab proved that judging aliveness from silence is fragile, and gave you incarnation numbers. The optimistic-vs-pessimistic-locking lab — this morning — gave you the conditional write. This lab assembles those parts in the order reality forces them, and ends somewhere mildly scandalous: a correct "distributed lock" system turns out to be optimistic concurrency at the resource, wearing a lock as a performance optimization.

Layer map: BEGINNER (§1–9) → INTERMEDIATE (§10) → ENGINEERING (§11–14) → PRODUCTION (§15). Checkpoints at borders.

1. WHY — one job, two machines, no shared anything

Your Spring Boot app runs the invoice job every night at 02:00. Then the platform team scales the service to two instances. Both fire at 02:00. Every customer gets two invoices, and some get charged twice.

Inside one JVM this is synchronized. Inside one database it is yesterday's SELECT … FOR UPDATE. But this critical section calls a payment API, writes files to S3, sends emails — it lives outside any database — and the two competitors are separate processes on separate machines with no shared memory, no shared kernel, and a network between them. Mutual exclusion has to be manufactured out of messages. Every mechanism in this lab exists because some part of that manufacturing failed in a way someone did not foresee — and the failures are not exotic: crashed holders, garbage-collection pauses, delayed packets, and clocks that jump.

2. PROBLEM — the darkroom key

A photography club has one darkroom with one enlarger. Two members can ruin each other's prints by being inside at once, so the club has a rule: the darkroom key hangs on a hook at the front desk. Take the key, work, return the key. No key on the hook — you wait.

Pia takes the key at 14:00. Quinn arrives at 14:05 and waits. The system works — while everyone is healthy and honest about time. This whole lab is the story of what the front desk must invent as members start crashing, napping, and mailing in their work.

In code, the front desk is one small server and the key is one variable:

acquire(client) -> yes (you hold it) | no (someone else does)
release(client) -> the key returns to the hook

3. NAIVE SOLUTION — the lock server

That two-operation server is the naive solution, and it is genuinely good: one place decides, so there is never confusion about who holds the key. Run the happy path — 2 clients, 3 critical sections each, interleaved:

cd 43-distributed-locking
java src/Tests.java     # first check: lock_admits_one_holder_at_a_time

6 sections completed, resource correct, zero ticks with two holders. Mutual exclusion, manufactured. Ship it?

🔮 Predict: Pia's process crashes — kernel panic, OOM-kill — while she holds the lock. What happens to Quinn: an error, a delay, or something worse?

Reveal Something worse than either: **nothing, forever.** The key is in a dead process's pocket. The lock server is healthy, the network is healthy, Quinn retries politely — and is denied at tick 200, tick 2,000, tick 2,000,000. Measured (`java src/Experiments.java crash`): with no expiry, Quinn completes **NEVER**. Nothing is corrupted — this is a pure *liveness* failure, and it is the two-phase-commit blocking lesson wearing a padlock: any exclusive claim that only its holder can undo is a promise that the holder will live, and nobody can keep that promise.

4. FAILURE — and the fix that creates the real problem

The front desk adopts the obvious rule: if a keyholder is silent for 10 minutes, assume they're gone and hang up a spare key. In code: every grant gets a deadline; a grant past its deadline is treated as free. You already know this object from the uber lab — a lease: permission with an expiry, so that recovery needs no human. Measured recovery (Experiments.java crash): the next client finishes about one TTL after the crash, for every TTL — the TTL is the price of crash recovery:

   TTL | other client finishes at
  none | NEVER (still stuck at t1000)
     5 | t13
    10 | t17
   100 | t107

🔮 Predict: Pia didn't crash. She fell asleep in the darkroom armchair (in process terms: a 20-tick GC pause against a 10-tick TTL). The spare key is out; Quinn is inside working. Then Pia wakes. What does she do?

Reveal She *continues developing her print*. She has no idea anything happened — **a paused process does not experience its pause**, it experiences an instantaneous world that changed nothing visible. Her lease expired, the lock server granted Quinn the lock, and there are now two people in the darkroom, each certain they are alone. Measured (`java src/World.java`, Act 3): 6 ticks with two believed holders, and the resource ends at value 1 after 2 completed sections — **a lost update**, the anomaly you've now met in four labs, manufactured this time by a lock working exactly as designed. This is what the redis lab measured with real Redis and a real GC pause; now you can watch the anatomy in slow motion.

Three follow-up hopes die by measurement (Experiments.java pause, dilemma, check):

  • "Tune the TTL." Sweep it: short TTLs recover fast and corrupt under pauses; long TTLs are pause-safe and recover slowly. Every row of the dilemma table is a compromise, and the row you need — "longer than my longest pause" — requires a number nobody has. GC, swap, a stopped VM, a live-migration: unbounded. The gossip lab said it structurally: silence is the only evidence, and a bad day supplies unlimited silence.
  • "Heartbeat — renew the lease while working." Renewal (measured) lets an alive holder work past the TTL safely: the TTL bounds silence, not total hold time. But a paused holder cannot heartbeat — the heartbeat's absence is precisely why the lease expired — so the corruption cliff does not move by one tick.
  • "Check before writing." Ask the server "am I still the holder?" right before the write. Measured: saves the case where the pause ends before the check (0 lost, one honest redo) — and is worthless when the pause lands between the check and the write (1 lost). Check-then-act has a gap, and a pause can land in any gap. Any liveness answer is stale the moment it arrives.

5. THE REAL REQUIREMENT

The safety of the system must not depend on any process being fast, any message being prompt, or any clock being right. Timing may decide how quickly things happen — it must never decide whether the data is correct. Which means: the last line of defense cannot live in the lock server or the client, because both judge by time. The resource itself must be able to tell old authority from new.

6. KEY IDEA — number the keys, and teach the enlarger to count

Every key the front desk hands out — original or spare — gets a number, one higher than the last. And the enlarger gets a counter dial: every request made of it carries the requester's key number; the enlarger refuses any number lower than the highest it has ever seen, and remembers the highest.

Now the sleeper's late work refuses itself: Pia holds key #33, Quinn's spare is #34; the moment Quinn's first request touches the enlarger the dial reads 34, and Pia's request — whenever it straggles in, however long she slept, however delayed the mail — presents #33 and bounces. No timing assumption anywhere in that sentence. The lock still schedules (it keeps collisions rare); the dial guarantees (it makes the surviving collisions harmless). The whatsapp lab's phrasing transfers exactly: the queue was the guarantee and the push a latency optimization — here the token check is the guarantee, and the lock is a duplicate-work optimization.

7. TERMINOLOGY

Distributed lock — a mutual-exclusion claim between processes that share no memory, built from messages to a lock service. Why the term: to distinguish it from in-process locks, whose failure modes (a crashed holder releases automatically — the OS cleans up) it conspicuously lacks.

Lock service — the process(es) holding the authoritative "who holds what" state. The front desk. Sometimes a database table, sometimes Redis, sometimes a consensus cluster (§10.6).

Critical section — the work done while believing you hold the lock. The word "believing" is doing heavy lifting; most of this lab lives in it.

Lease (refresher — uber lab) — permission with an expiry. Every sane distributed lock is a lease; an expiry-free lock is a suicide pact with your least reliable process. TTL — the lease length: the maximum time the system stays stuck after a crash, and simultaneously the minimum pause that turns a live holder into a stale one. One number, two jobs, opposed.

Renewal / heartbeat — extending a live lease from within, conditionally ("compare-and-extend": only for the current holder). Lets honest long work exceed the TTL, so the TTL can be short. Bounds silence, not hold time.

Stale holder — a client acting on a lease that has expired without its knowledge. Not a rogue, not a bug — a victim of timing running correct code. The pause, the swap-storm, the delayed packet all manufacture one.

Fencing token — the load-bearing term of this lab, finally getting its full treatment after cameos in five labs. Plain meaning: the key's serial number. Technical meaning: a strictly monotonically increasing number issued with every grant of the lease, presented on every operation against the protected resource, where any operation carrying a lower number than the highest seen is rejected. Why it exists: it converts "who holds the lock?" (a timing question, unanswerable safely) into "which authority is newer?" (an arithmetic question, answerable atomically at the resource). Example: Pia's #33 write bounces off a dial reading 34. Connections: it is gossip's incarnation number (only newer speaks), event-sourcing's expected-version (refuse the stale write), uber's offer id, and — the unification §10.5 makes precise — the previous lab's conditional write. Google's Chubby paper calls it a sequencer; that was its first production name.

Split-brain (refresher — raft) — two parties simultaneously believing they hold an exclusive role. The lab measures it directly as overlapTicks (ticks with ≥2 believed holders). Fencing does not prevent it; fencing makes it harmless — hold that thought for §12.

Check-then-act gap — the interval between learning a fact and acting on it, in which the fact can die. §4's defensive check; also every "if lease still valid then write" you will ever be tempted to write.

Herd effect — N waiters all waking (or all polling) for one freed lock. Watch — the fix: the service notifies exactly the next waiter. Numbers in §14.

Efficiency lock vs correctness lock (Kleppmann's distinction) — is the lock there to avoid wasted duplicate work (efficiency: a TTL expiry costs a shrug) or to protect an invariant (correctness: a TTL expiry costs money)? The first question to ask of any lock in any design review, because it decides whether the TTL cliff is acceptable or fatal. §14's efficiency experiment runs the same faults under both readings.

Minor terms defined at first use; all terms land in the glossary (§18).

8. MENTAL MODELS

Simple model — the darkroom. The key on the hook (the lock), the 10-minutes-of-silence spare-key rule (the lease), the sleeping member (the pause), the numbered keys and the enlarger's refuse-lower-numbers dial (the fencing token). Carry this picture; it survives contact with the real systems.

Engineering model. Three state machines and a wire. Lock server: {holder, token, expiresAt} with grant-if-free-or-expired, token++ on every grant. Client: acquire → read → work → write → release, pausable at any point, always acting on possibly-stale beliefs. Resource: {value, maxToken}, refusing any operation with token < maxToken. Messages between them take time and can arrive after the world that sent them has ended. Invariant that holds: writes accepted by the resource are totally ordered by token, and no accepted write is based on authority older than an already-exercised newer authority. Invariant that does NOT hold: one believed holder at a time.

darkroom engineering
key on the hook holder == null
taking the key acquire() → grant, token++
10 minutes of silence → spare key now >= expiresAt → re-grant
the sleeping member a paused process (it never experiences the pause)
key serial number fencing token
enlarger's counter dial resource.maxToken
dial refuses lower numbers reject token < maxToken, atomically

Where the analogy breaks. (1) The enlarger check is atomic because it's a machine; the front desk's spare-key decision is not knowledge but a guess — silence from a sleeper and silence from a corpse are the same silence, and no rule at the desk can tell them apart (the gossip lab measured a whole cluster burying itself over exactly this). (2) A physical key can't arrive twice — a message can: a write mailed before the sleep can arrive after the spare key has been used, which is why the dial must be consulted on every operation, not just guarded at the door. (3) Humans would notice another person in the darkroom; processes have no peripheral vision — mutual exclusion that depends on noticing is already dead.

10. ACTUAL MECHANISM — five versions, four scars

CHECKPOINT — beginner → intermediate. You can explain why a naked lock blocks forever, why a lease corrupts under pauses, and what the token is for. Next: the exact rules, traced tick by tick, and the two refinements people miss — one of which this lab itself missed at first.

Run the whole arc narrated: java src/World.java (four acts, every line a full sentence with tick numbers).

10.1 v1 — grant and release (World.java:69-85)

Grant if free. Release only by the holder. Act 1's trace shows the scar being earned: Pia CRASHES holding the lock … 40 ticks of silence … Quinn completed 0 of 1. Forever is spelled: nothing left to happen.

10.2 v2 — the lease (World.java:62: free())

One added clause: a grant past expiresAt counts as free. Act 2: t011 S1: lease of C1 (token 1) has EXPIRED — granting to C2. Recovery without humans. Act 3 shows the price: the same line printed while Pia is alive and paused, then t027 RESOURCE: accepted write value=1 from Pia — value 1 after two completed sections. The server's grant was correct by its rules; the rules judge by time, and time lied.

Two rules in v2 that look pedantic and are load-bearing:

  • token++ on every grant, including expiry-takeovers — planted bug token-reused-on-expiry grants the spare key with the old number ("same lease, new tenant"), and fencing silently dies: both holders carry the same token, the dial can't order them, corruption returns with fencing on (Tests.java broken: 1/2 survive).
  • Renewal is compare-and-extend, never a plain overwrite — renew() checks holder and token and non-expiry. The Redis anti-pattern (renewing with a bare SET k me PX ttl) is a lock theft primitive.

10.3 v3 — fencing at the resource (World.java:142-166)

The resource keeps maxToken; a write with token < maxToken is refused. Act 4's trace, the moment the whole lab has been building to:

t027  RESOURCE: REJECTED write value=1 from Pia (token 1 is older than 2 already seen)
t027  Pia learns its write was rejected — its lease was stale. It must re-acquire and redo the work.
t033  RESOURCE: accepted write value=2 from Pia (token 3)

Nothing lost; the late writer paid with a redo. Note what the rejection also buys that no liveness check could: delayed_write_from_a_dead_holder_is_fenced_off sends a write, kills the sender, and delivers the packet 40 ticks later into the next holder's world — refused by arithmetic. Without fencing, the same ghost packet lands last and quietly rolls the value backwards.

10.4 v3.5 — fence the reads too (the bug this lab found in itself)

🔮 Predict: TTL 30. Pia's pause is only 25 ticks — shorter than the TTL. Fencing is on (writes checked). Safe?

Reveal No — and this row of the `pause` sweep is the finest print in the lab. Pia's *hold* is not her pause: acquire + work + pause + remaining work + **the write's travel time** crossed the 30-tick expiry by one tick. Her write was already *in flight* when Quinn was granted the lock; Quinn **read** the value before the old write landed; then both writes arrived carrying valid, *increasing* tokens — and were both accepted, in perfect token order, having together lost an update. Write-only fencing ordered the writes; nothing ordered Quinn's read against Pia's write. The fix: **every operation carries the token, reads included** — a fenced read raises the dial, so the older in-flight write bounces. Chubby's sequencers work exactly this way (checked on every request), and this is planted bug #4 (`write-only fencing`): pause < TTL, fencing "on", 1/2 survive, zero rejections — the most invisible failure in the lab.

10.5 The unification — you built this yesterday

Look at the resource's rule with yesterday's eyes: an operation carries evidence of what authority it was issued under, and the resource applies it only if no newer authority has been exercised — check and act in one atomic step at the data. That is a conditional write. The fencing token is optimistic locking's version column, issued by a lock service instead of read from a row; WHERE token >= ? instead of WHERE version = ?. Same primitive, fifth costume (expected-version, WATCH, If-Match, @Version, and now this). Which triggers the awkward question: if the resource can check conditions, why lock at all? Run Experiments.java efficiency for the honest answer: under identical faults, the lock's overlaps are corruption if they touch an invariant and a shrug if the work is idempotent — so the guarantee must live at the resource either way, and what the lock buys is not doing the work twice. A correctness lock is optimistic concurrency plus a pessimistic hint; an efficiency lock is just the hint. (This is Kleppmann's conclusion in How to do distributed locking, reached here by measurement.)

10.6 v4 — who locks the lock server?

One front desk is a single point of failure (its crash = everyone blocked until restart; its restart is planted bug #2: an in-memory token counter reborn at 0 fences off every legitimate new writer until it climbs back — safety intact, availability gone, which is why the token counter must be durable and monotonic across restarts). Two ways out:

  • N independent servers, majority acquisition — the Redlock shape, measured in Experiments.java redlock. The availability works (2 of 5 unreachable, still locks). But a client pause corrupts exactly as before — five servers agreed, the pause didn't ask them — and Redlock's leases carry no token the resource could check. Worse: one server's clock jump (NTP step, VM migration) expires a lease early, and two clients assemble overlapping majorities — Pia holds {S1,S2,S3}, Quinn assembles {S1,S4,S5}, 6 overlap ticks, 1 lost update. Safety was resting on a wall clock. This measured pair is the Kleppmann–antirez debate: the defense ("pauses are rare, bound your clocks") is an engineering bet; the critique ("safety must not rest on timing, and there's no fencing") is §5 verbatim. You now hold both positions with numbers.
  • One logical front desk, replicated by consensus — a raft/paxos cluster (your raft lab: elections, majorities, terms) storing the lock state. The service survives minority failure, and — decisive — its log index / revision is a ready-made, durable, monotonic fencing token: ZooKeeper's zxid, etcd's revision, Chubby's sequencer. This is why the standard answer to "correctness lock" is ZooKeeper/etcd, never plain Redis: not because consensus makes clients pause-proof (nothing does), but because it makes the service honest and the token trustworthy.

11. FAILURE SCENARIOS

CHECKPOINT — intermediate → engineering. You know the mechanism and its two non-obvious refinements. Now: every failure, created, watched, and tied to the guarantee it bends.

a. Holder crash. Create: a.crashed = true. Watch: Experiments.java crash. No TTL: liveness lost permanently, safety trivially intact. TTL: liveness restored in ~TTL; safety untouched by the crash (a dead client sends no stale writes — except the ghost packet, see d). Production: this is why every real lock is a lease; the TTL is your declared crash-recovery SLO.

b. GC pause / stall. Create: pauses.add(...). Watch: pause, World.java Act 3. Pause > TTL: split-brain (overlapTicks > 0), lost update without fencing, clean rejection + redo with it. Guarantee lost without fencing: the invariant. With fencing: only the stale holder's time. Production: this is the redis lab's measured Redis failure; JVM users hit it with old collectors, hostile heaps, or swap; the modern low-pause collectors shrink it and cannot bound it.

c. The check-then-act gap. Create: pause phase after-check. Watch: check. A truthful server answer, dead on arrival. Lesson: liveness checks are UX (fail fast, redo early — the mid-work variant saved a redo), never safety.

d. The ghost packet. Create: writeDelay = 40, kill the sender. Watch: test delayed_write_from_a_dead_holder_is_fenced_off. Without fencing the last arrival wins and it is a message from the past. The network is a time machine; only the resource's dial is not fooled.

e. Lock-service restart with amnesia. Create: bugTokenRestart. Watch: Tests.java broken. Counter reborn at 0 → every legitimate new writer rejected until it catches up. Safety kept, availability lost — the mirror image of every other failure here, and the reason etcd/ZooKeeper tokens are positions in a durable replicated log.

f. Clock jump at the service. Create: clockOffset = 100 on one of five Redlock servers. Watch: redlock. Overlapping majorities. Production: NTP steps and VM migrations are routine; any lease math done on wall clocks inherits them (raft's lease-read caveat, same root).

g. The herd. Create: 20 waiters polling every tick. Watch: herd — 2,740 messages where a watch queue spends 99, same completion time, plus FIFO handover. Production: ZooKeeper's sequential-ephemeral recipe exists precisely to wake only the next waiter; a naive poll loop is a self-inflicted DDoS on your own lock service at the worst moment (right after something broke).

h. The read race. §10.4. The one that gets code-reviewed in, because "we fence our writes" sounds complete. Pause < TTL, zero rejections, data gone.

12. CORRECTNESS — what is actually guaranteed

design after a crash under any pause/delay split-brain possible? corruption possible?
lock, no TTL blocked forever safe (nothing expires) no no
lease (TTL) recovers in ~TTL corrupts past the cliff yes yes
+ renewal recovers in ~TTL cliff unmoved (can't renew while paused) yes yes
+ defensive check recovers gap remains yes yes
+ fencing, writes only recovers read race remains (§10.4) yes yes (silently)
+ fencing, all operations recovers in ~TTL safe — stale effects refused yes no

Read the last row carefully, because it says the honest thing most descriptions blur: fencing does not restore mutual exclusion. Two believed holders still happen (split-brain, measured every time). What fencing guarantees is at-most-one-effect lineage: the resource applies operations in token order and refuses everything from superseded authority — overlap becomes harmless instead of impossible. Safety now rests on one atomic comparison at the data and on token monotonicity (durable counter, bumped every grant) — zero timing assumptions. Liveness still rests entirely on timing (the TTL) — and must, because distinguishing slow from dead by silence is impossible in principle; you can only choose how long to wait. Safety by arithmetic, liveness by timeout, never the reverse: that division is the whole design.

Still not guaranteed, same as yesterday: nothing binds a writer that talks to the resource outside the token protocol; fairness (a poller can starve — the watch queue is FIFO, polling is not); and the lock protects only resources that can check. §15 faces that last one squarely.

15. PRODUCTION

CHECKPOINT — engineering → production. You can build, break, and fix the mechanism. Left: choosing, operating, and the uncomfortable cases.

The decision procedure:

flowchart TD
    A[you think you need a distributed lock] --> B{efficiency or correctness?}
    B -->|duplicate work is just cost| E[efficiency lock: ShedLock, SET NX PX<br>TTL sized generously; expiry = shrug<br>work must be idempotent anyway]
    B -->|an invariant is at stake| C{can the resource check a condition?}
    C -->|it's a database| D[conditional write / constraint IS the guard<br>- yesterday's lab; lock optional, for cost]
    C -->|API with If-Match, etcd Txn, versioned store| F[fencing: consensus-backed lock,<br>token checked on EVERY operation]
    C -->|it cannot check - legacy FS, dumb API, email| G[the honest corner: no lock makes this safe.<br>make the operation idempotent, or route it<br>through one owner process - consensus-elected,<br>fenced at ITS inputs - or accept measured risk:<br>short TTLs, pause monitoring, reconciliation]
    E --> H[monitor: duplicate-work rate]
    F --> I[monitor: token rejections, session expiries,<br>hold time p99 vs TTL, queue depth]

The box people avoid is G. An email cannot be un-sent and cannot check a token; no lock — Redis, ZooKeeper, or carved in stone — makes "send exactly one email" true on an asynchronous network. Real systems shrink the blast radius (idempotency keys at the provider, an outbox with a single fenced drainer, reconciliation jobs) and then measure the residual. Saying "the lock guarantees it" in that design review is how double payouts happen.

Operations. What the on-call sees, by failure: lock service down = everything queues (availability, loud). Sessions expiring in bursts = GC or network trouble at clients — and every expiry is a potential stale holder: alert on hold time p99 approaching TTL long before corruption. Token rejections > 0 = fencing is working; investigate the pauses it caught. Herd symptoms = connection spikes at the service on every release. ZK/etcd specifics: watch session_expired vs connection_loss (Curator treats them differently for good reason — a connection loss might still be the holder; an expiry definitely is not), and never do lock bookkeeping on wall clocks.

What this toy omits, and who handles it. Real partitions (client↔lock vs client↔resource can fail independently — the toy's wire only delays writes; real systems face a client that can reach the resource but not renew, exactly when fencing earns its keep). Consensus internals (raft lab has them; etcd/ZK are that plus a lock API). Durable storage at the resource. Sessions multiplexing many locks (ZK/Chubby: one heartbeat, many claims — cheaper, and one session expiry drops them all, a coarser blast radius chosen deliberately; Chubby further adds a lock-delay — a grace period before a broken session's locks free — as a belt against non-fencing-capable clients). Reentrancy, read-write locks, fairness policies, security. And scale: a lock service is a coarse-grained, low-throughput tool (Chubby's stated design point); locking per-row at high rate is yesterday's lab's job, inside the database.

Commonly confused, one sentence each. A distributed lock vs a database row lock: the row lock's holder is a transaction the database itself kills on disconnect — holder death is solved by construction, which is exactly the property a network lock loses. Fencing vs preventing split-brain: fencing permits two believers and disarms the stale one; consensus leadership (raft) prevents two commits, not two believers either — the same shape one level down. Redlock vs consensus: majority acquisition is not majority agreement — Redlock's servers never talk to each other, so nothing reconciles their divergent clocks; raft's do, about every entry. Lease vs lock: every distributed "lock" you will ever use is a lease; the word "lock" is nostalgia for the single-machine case.

Solutions

Attempt each rung first — EXERCISES.md.

Rung 1

1.1 Two facts do all the damage. First, a process cannot observe its own delays: between any two of its instructions the world may have moved arbitrarily far (GC, swap, migration), so "I hold the lock" is always a belief about the past. Between threads, a stalled thread's lock stays correct — the OS keeps it held; nothing else can enter. Second, death and slowness are indistinguishable from outside: the only evidence anyone has about a remote process is silence, and silence has two meanings with opposite correct responses (wait forever vs take the lock away). A machine lock never faces this — the kernel knows when a process dies and cleans up. Distributed locking is the art of living without those two certainties.

1.2 Job one: the TTL is the recovery deadline — after a holder crashes, the system is stuck for at most one TTL (measured: recovery ≈ TTL for every value). Job two: it is the pause tolerance — any stall longer than the TTL turns a live holder into a stale one. Short helps job one and sabotages job two; long, the reverse. "Long enough to be safe" cannot be finished because it means "longer than my longest future pause", and the longest future pause (GC, swap, VM migration, human with a debugger) has no upper bound you can know. The dilemma experiment prints the compromise row by row.

1.3 Consensus bought an honest, highly available lock service: the service itself survives minority failure, never disagrees with itself about who holds the lock, and can mint a durable, monotonic fencing token (ZooKeeper's zxid, etcd's revision). It bought nothing about the client: a GC-paused holder still doesn't know it lost the session, still wakes, still writes. ZooKeeper prevents the service from being wrong; only a fencing check at the resource prevents the stale client from doing damage. (Measured equivalently in the lab: the pause corrupts under any lock service; only the resource's check ends it.)

Rung 2

2.1 (a) The expiry clause in LockSrv.free() — ttlEnabled && now >= expiresAt (World.java:76). (b) token++ on every grant in acquire, including expiry-takeovers (bug #1 is its absence on that path). (c) The single comparison in Res.write: tok < maxToken → reject. (d) resource.observeRead(this, tok) in startWork — the read fence, added after the P=25 row of the pause sweep lost an update with fencing "on" (§10.4).

2.2 Pia's card still believes she holds token n and is mid-work — her belief is frozen, which is the point. The lease bar shows expired/re-granted to Quinn. The split-brain is the "believed holders: 2" counter (the Java's overlapTicks is its time integral).

2.3 The 2,641 extra messages bought load on the lock service at its busiest moments — every release triggers a stampede of retries — plus unfairness (whoever polls at the lucky tick wins; the watch queue is FIFO). Same completion time here only because the service is a free in-process object; a real lock service melting under poll storms is §11g and the reason ZooKeeper's recipe watches the previous holder only.

Rung 3

3.1 Zero updates lost, at 300 ticks or 3 million. The arithmetic doesn't care about duration: Quinn's grant carries a higher token; her first fenced operation raises the resource's floor; Pia's eventual write presents the smaller number and bounces. Pia experiences: wake, write, rejection, re-acquire (fresh token, fresh read), redo, success. One redone section, no corruption — the redo cost scales with the pause count, never the pause length.

3.2 No double-majority. Work the masks: Pia holds {S1,S2,S3}. A jump on S4 expires nothing of Pia's (S4 never granted her anything). Quinn can reach {S1,S4,S5}: S4 and S5 grant (free), but S1 still holds Pia's unexpired lease and refuses — Quinn has 2 of 5, no majority, and polls until Pia's leases genuinely lapse. The failure needs the jump on a server inside the holder's majority (any of S1–S3), because two 3-of-5 majorities must share at least one server — the quorum-overlap rule from the quorums lab, now working against safety: the shared server is exactly where a single clock error breaks the intersection argument. Edit the test to servers[3].clockOffset = 100 and the assertion fails (no overlap).

3.3 Accepted: the check is token < maxToken, and 7 < 7 is false — equal tokens pass. For the value write in this lab that re-apply is harmless-looking but wrong in general: "same token" means "same lease", not "same request". The right outcome needs a per-request idempotency key (dedup within a lease) alongside the token ordering (fencing across leases) — the two checks answer different questions, which is exactly planted bug #3's lesson run in reverse: dedup is not ordering, and ordering is not dedup; real systems need both.

3.4 The ghost packet / stale holder failures (§11b, §11d) now apply to the index unfenced: a paused holder's index update lands after the next holder's, and the index diverges from the file silently. "Updated together" doesn't help because together-ness was a property of the holder's intent, not of the messages — they travel separately and the pause splits them. Every protected resource needs its own fence (or a single fenced front door both writes go through).

Rung 4

4.1 With msgDelay = 0 the write lands the instant it is sent, so a send that happens while the lease is still (barely) alive can no longer cross the expiry in flight — the P=25 row goes to 0 lost in the plain column. That row was teaching the lab's own discovered bug: hold time includes the write's travel time, so an in-flight write can be stale on arrival even though the pause was shorter than the TTL — and only a fenced read catches it.

4.2 Unconditional renew = expiresAt = now + ttl regardless of caller. Scenario: Pia holds and pauses; her lease expires; Quinn is granted; Pia's client-side heartbeat timer (which survived the pause) fires and extends Quinn's lease window under Pia's belief — or, in the nastier variant where renew also sets holder, steals the lock outright. First failing test: renewal_extends_a_lease_while_the_holder_is_alive still passes (happy path!), but pause_longer_than_ttl_makes_two_believed_holders and its siblings change shape — the honest catch is a new test asserting a non-holder's renew returns false. (That the happy-path test stays green is the lesson: theft bugs live outside the happy path.)

4.3 watch_mode_beats_polling_and_keeps_fifo_order — notify-all multiplies messages per release by the queue length, so the watchMsgs * 2 < pollMsgs margin collapses as N grows. The recreated production symptom is the thundering herd: every release wakes every waiter, N-1 of which immediately fail and re-sleep — ZooKeeper's "watch the previous node, not the lock" recipe exists to prevent precisely this.

Rung 5

Working bodies (verified 6/6 in this lab):

static long yourAcquire(Srv s, int now, int cliId) {
    if (s.holder == null || now >= s.expiresAt) {
        s.holder = cliId;
        s.token++;                     // strictly larger on EVERY grant
        s.expiresAt = now + s.ttl;
        return s.token;
    }
    return -1;
}

static boolean yourFenceCheck(ResState r, long token, boolean isWrite) {
    if (token < r.maxToken) return false;
    r.maxToken = token;                // reads raise the floor too
    return true;
}

Why the bump on expiry-takeovers specifically: an expiry-grant is the ONLY kind where the previous holder may still be alive and about to act — a released lock's ex-holder is done by definition. Reusing the token there hands both actors the same credential at the exact moment they must be distinguishable (planted bug #1). Why check 6 feeds a read into the fence: a new holder's read must raise the floor so that older writes still in flight are refused on arrival — otherwise the read races the ghost packet and write-only fencing accepts both writes in perfectly increasing order (§10.4).

Rung 6

  • token-reused-on-expiry — diff: "cleanup: only bump the version on a real ownership change". Breaks safety, silently: fencing reports nothing wrong because both holders are equally credentialed. Symptom: rare corruption that looks like an application bug, near GC events.
  • token-counter-in-memory — diff: "the counter doesn't need to be in the DB, it's just a number". Breaks availability: after a service restart every legitimate writer is rejected until the counter climbs back. Loud — error rates spike immediately after the restart.
  • dedup-instead-of-ordering — diff: a "replay protection" feature that keeps a seen-set instead of a floor. Breaks safety: a stale holder's first write always carries an unseen token. Symptom: same as bug #1 — quiet, pause-correlated corruption.
  • write-only fencing — diff: none; it's the absence of a line nobody knew to write. Breaks safety in the narrowest window (in-flight write vs new read), zero rejections logged, pause can be shorter than the TTL. The nearly perfectly silent one.

Time-to-detection ranking (defensible): token-counter-in-memory first (minutes — it fails loudly and reliably on the next restart), then token-reused-on-expiry and dedup-instead-of-ordering (weeks — need a pause coinciding with contention, and the corruption is deniable), with write-only fencing last (months-to-never — needs pause + in-flight write + immediate re-grant, and even then the logs show two accepted writes and nothing else). Any order is fine if argued from trigger frequency × symptom visibility.

Rung 7 (worked design)

The email API accepts no tokens, so the guarantee cannot live at the resource — push it as close as possible and name the residue.

Design: (1) The digest job is gated by an efficiency lock (ShedLock on Postgres is fine — the DB is already there). (2) The lock does not guard the send; it guards the claim: a digest_runs(date PRIMARY KEY, owner, token) row created with an idempotent conditional insert — yesterday's lab's mechanism, INSERT ... ON CONFLICT DO NOTHING, count 1 = mine. The date is the natural idempotency key; the DB is the fenceable front door. (3) Only the claimant calls the API, and it records sent_at in the same row before acknowledging completion, passing the provider an idempotency key (digest-2026-08-29) if the API supports one (many mail providers do — that moves the dedup into the resource after all). (4) A reaper re-opens claims with no sent_at after a deadline.

The residual failure, written down: the claimant can crash (or pause) after the API accepted the send and before sent_at committed — the reaper then re-claims and the digest goes out twice. Without provider-side idempotency this window cannot be closed, only shrunk (claim → send → record, with the record immediately after the send). Monitor: provider-side send count per digest date (reconciliation query against their API/logs), alerting on count > 1 — you detect the double-send you cannot prevent.

Rung 8 (worked discussion)

  • (1) Payout workers / merchant queues — this is not one lock, it's assignment: a claim per merchant. Correctness (a merchant drained twice = double payouts). Mechanism: the claim IS a conditional write on a merchant_claims row (owner, lease expiry, generation — the previous lab's rung 7 verbatim), and every payout the worker writes carries the generation, checked by the payments DB. The lock-service version (etcd lease per merchant, mod_revision as token) is equivalent; pick whichever store you already operate. Monitor: claims with expired leases still receiving writes (= fencing rejections), payouts per merchant per window.
  • (2) Nightly interest batch, writes only to Postgres — the easy one, and the trap is over-engineering it: the work lives inside the fenceable resource. pg_advisory_xact_lock (or ShedLock) to avoid duplicate cost, and the batch's writes made idempotent/conditional (WHERE last_interest_date < :today) so a duplicate run is a no-op. Efficiency lock + conditional writes; no external lock service earns its keep. Monitor: rows updated per run (a duplicate run updating 0 is healthy; updating >0 twice is the alarm).
  • (3) Month-close, minutes long, external tax APIs — correctness, long hold, and a box-G component. Consensus-backed lock (etcd/ZK) with session
    • renewal for the long hold; every internal write fenced with the lock's revision; the external calls get idempotency keys (close-2026-08) and a reconciliation step, because no token protects an API that doesn't check one. Also add the previous lab's shared-version bump on the ledger-month row so even a bypassing writer collides. Monitor: session expirations during a close (a paused closer mid-month- close is the nightmare scenario — page on it), reconciliation diffs.
  • The Redisson-wrapper review comment, two paragraphs: "RLock gives us a lease with watchdog renewal and no fencing token — as a duplicate-work suppressor it's fine, so (2) can use it. But (1) and (3) protect invariants: RLock has no token the database or the ledger could check, so a GC pause longer than the watchdog interval silently gives us two holders (we measured this shape in the locking lab — and Redis's own docs route correctness cases to fencing). Standardizing it 'for consistency' standardizes our failure mode. Counter-proposal: one internal library with two entry points — efficiencyLock() (Redisson/ShedLock, documented as best-effort) and fencedClaim() (etcd lease + revision, or the DB-row claim with a generation column, returning a token the caller MUST write with). The consistency worth having is that every correctness path returns a token and every store we own checks it."
