Lab 8 · One Machine, Done Right

Isolation levels — what a transaction promises about the neighbours

Tell a friend: Asha has 100 in her account, and two deposits of 10 land at the same moment. Devi handles one deposit and Omar handles the other. Each of them reads 100, adds 10 and writes 110, so Asha ends with 110 and one deposit is simply gone, though every step succeeded and nothing complained. An isolation level is the dial that decides which of those endings your database is allowed to give you. This lab turns the dial through every setting on a real database and shows you what comes out.

Open the ledger at visualization.html or https://claude.ai/code/artifact/76051a1f-7357-4e66-9c6d-897f76c6004a. How to run the code, and where this lab sits next to your other labs, is in section 19.

1. Why does this problem exist at all?

In one breath: Two people change the same number at the same moment. Each does the sensible thing. Together they can leave the database holding a number that was never true, and nothing will complain.

Two things happen to the same data at the same instant. That is not an edge case. On any system with more than one user, it is Tuesday.

Here is what it costs when nobody has thought about it.

  • A customer's two deposits arrive together, and one of them silently does not exist.
  • Two people book the last meeting room, and both get a confirmation.
  • A monthly report adds up four account balances and prints a total that no moment in history ever had.
  • A doctor rota empties itself, because two doctors signed off at once. Each had checked that the other was still on.

Every one of those is a real, common bug. None of them involves a crash, a network failure, or a mistake in your code. Every statement succeeded. And in almost every case the fix is one word in a configuration file. But only if you know which word, and why.

The first of those four is about to happen to Asha.

2. What happens to Asha's two deposits?

In one breath: Two clerks each read Asha's balance, each add 10, and each write the answer back. The second write lands on top of the first, and one deposit vanishes without a trace.

Asha has 100 in her account. Two deposits of 10 arrive at the same moment. Two clerks handle them: Devi takes one, Omar takes the other.

Each clerk does the obvious thing:

Look up the balance. Add 10. Write the new balance back.

The trouble is entirely in the gap. Between Devi looking up the balance and Devi writing it back, the world changed underneath her. She had no way to notice.

3. Why not just wrap it in a transaction?

In one breath: "Make the look-up and the write one unit" sounds like exactly the fix. Devi and Omar both do it, both succeed, and Asha still has 110.

This is what everyone reaches for, and it is not a silly answer:

BEGIN;
  SELECT balance FROM acct WHERE id = 1;   -- 100
  UPDATE acct SET balance = 110 WHERE id = 1;
COMMIT;

A transaction is the database's word for "these statements are one unit". It sounds exactly like what we need. Make the look-up and the write into one indivisible act, and the gap disappears.

4. What does a transaction promise, and which promise is missing?

In one breath: A transaction promises four things. Two of them are about crashes, and Devi gets those for free. The one about Omar running at the same time is separate, costs extra, and you have to ask for it by name.

BEGIN … COMMIT really does give Devi something. It gives her all-or-nothing: if the second statement fails, the first is undone. It gives her survives-a-crash: once the database says committed, the change is on disk. Those are worth a great deal. They are what most people mean when they say "transaction".

Neither of them has anything to do with Omar running at the same time.

That is a separate promise, and it is the one you have to ask for by name. The database does not give it to you by default, because it is expensive. So it gives you a cheap approximation and lets you buy more if you say so. Almost nobody says so, because almost nobody knows the dial exists.

The name of that dial is the isolation level. The default setting in PostgreSQL, SQL Server and Oracle is one that permits exactly the bug Asha just suffered.

5. What do we actually want? "As if they had queued"

In one breath: We do not need Devi and Omar to take turns. We only need the ending to be one that taking turns could have produced. 120 passes. 110 fails.

State what we actually want, in plain words:

However the work actually interleaves, the result must be one that could have happened if the transactions had run one at a time, in some order.

Note what that does and does not say. It does not demand that Devi go before Omar. Either order is fine: Asha ends on 120 both ways. It only forbids endings that no single-file order could have produced. 110 is such an ending, which is exactly why it is a bug.

Yes. The requirement says "in some order", and it means it. If you said no, you are thinking of the rule from the linearizability lab, which has a real-time clause: what finished first must count first. Serializability drops that clause. You have met this shape before. In the linearizability lab the requirement was "there must exist an order of the operations that explains what every client was told". This is the same sentence with one word changed: transactions instead of operations. That word is doing an enormous amount of work. Sections 10 and 12 are about how much.

6. What is the key idea? A ladder of partial promises

In one breath: Making everyone queue would fix Asha's bug and make the database serve one user at a time. So the industry sells a ladder instead. Each rung forbids more bad endings and costs more. You pick a rung.

Running everything one at a time really would fix this. It would also make your database serve one user at a time, which no one will accept.

So the industry did something pragmatic and slightly regrettable:

Offer a ladder. Each rung forbids more of the bad endings than the rung below it, and costs more. You pick a rung.

Two consequences follow, and they cause most of the confusion in this topic:

  1. The rungs are named after which bad endings they forbid, not after how they work. Two databases can implement the same rung name with completely different machinery and give you different behaviour.
  2. The list of bad endings in the standard is incomplete. It was written in 1992 with three phenomena in mind. The most dangerous ones in practice were not on that list. So there is no rung name for stopping them, which is why a level called SERIALIZABLE may not be serializable.

The rest of this lab is: what the bad endings actually are, which rung stops each one on your database, and the three mechanisms underneath.

7. What do engineers call the things in Asha's story?

In one breath: Six words, and you have already watched every one of them happen. A transaction is Devi's unit of work. Isolation is how much she may pretend Omar is not there. The other four name the order things happened in and the endings that are wrong.

Only the words needed to talk about the ladder. The bad endings get their names in section 11, where you can watch each one happen.

What is a transaction, and what are its four promises?

Devi's "look up, add 10, write back" is a group of statements the database treats as one unit. Engineers call that a transaction. The word exists to name work that must not be half-done. A transfer is the classic case: BEGIN; UPDATE acct SET balance = balance - 50 WHERE id = 1; UPDATE acct SET balance = balance + 50 WHERE id = 2; COMMIT;. Half of that is money destroyed.

A transaction makes four promises. Engineers remember them as ACID. Read the last column: it is what each promise means for that transfer.

Letter The promise For Devi's transfer
Atomic all or none both updates happen, or neither does
Consistent it moves the data from one state satisfying your constraints to another no balance rule is broken by the pair
Isolated the next paragraph Omar's work stays out of Devi's
Durable once committed, it survives a crash "committed" means on disk

The A and the D are what the two-phase-commit lab was fighting to preserve across several machines. This lab is entirely about the I, on one machine.

What is isolation, and why is it a dial?

How much the database lets Devi pretend nobody else is running: that is isolation. Precisely, it is the degree to which transactions running at the same time are prevented from seeing each other's intermediate states, and from interfering with each other's decisions.

It is the one ACID property that is a dial rather than a yes/no. Nobody offers "80% atomic". Everybody offers four or five degrees of isolated. At one setting Devi can see a balance Omar has not committed. At another she cannot. At another the database refuses to let them both finish.

The saga lab said sagas "trade atomicity and isolation for availability" and left it there. This is the thing being traded.

What is a schedule?

The order the two clerks' steps actually happened in is the schedule. Precisely: an interleaving of the operations of several transactions, preserving each transaction's own internal order.

Why does it need a name? Because the statements are fixed and the interleaving is not. All the interesting behaviour is a property of the interleaving, so it needs a name of its own.

Schedule Asha ends on
Devi reads · Omar reads · Devi writes · Omar writes 110
Devi reads · Devi writes · Omar reads · Omar writes 120

Same two transactions. Only the second one gives Asha her money. The two columns in the visualization are a schedule, and the ▲▼ buttons let you change it.

What is the difference between serial and serializable?

Serial means the clerks genuinely ran one after another: no two transactions overlap. Serializable means they overlapped, but the result is one that a serial run could have produced. Precisely: a schedule is serializable if it is equivalent to some serial schedule of the same transactions.

The two words exist to separate the guarantee (looks single-file) from the implementation (is single-file). Only the first is affordable. Devi-then-Omar and Omar-then-Devi both give 120. Any schedule giving 120 is serializable. The schedule that gives 110 is not.

You already have this word from linearizability. That lab's map entry recorded: "linearizability is strict serializability where every transaction is a single operation on a single object." Here the transactions are real ones, and the real-time clause is dropped. Serializability is happy with any serial order, including one that puts your committed transaction after a later one. That is the answer to the Predict in section 5.

What is an anomaly?

A specific way the ending can be wrong is an anomaly, also called a phenomenon. Precisely: a pattern of interleaving whose outcome no serial schedule could produce. Isolation levels are defined by which patterns they forbid.

Why define levels that way? So the ladder can be specified without specifying an implementation. That was a deliberate choice in the SQL standard. It is both why the standard is portable and why it is so often misread. Asha's missing deposit is the lost update anomaly. Section 11 is a list of eight of them, each one runnable.

8. What picture should you carry in your head?

In one breath: Nobody rubs anything out. Every change is a new line in the ledger with a note saying from when it counts. "What is Asha's balance?" becomes "as of when?", and two clerks who started at different moments can both be right.

Carry two pictures. The first is the one you will think in. The second is the one you will ship from.

The simple picture: the ledger nobody erases

There is one ledger. Clerks do not rub anything out. A change is a new line, with a note saying from when it counts. An old line stays on the page as long as anyone might still be reading by it.

So "what is Asha's balance?" is not one question. It is "what is Asha's balance as of the moment I started looking?" Devi and Omar started looking at different moments, so they are entitled to two different answers, both correct.

An isolation level is the house rule for three things:

  1. which line you read;
  2. whether you may write a line while someone else's is unfinished;
  3. what happens when two clerks' decisions turn out to be incompatible.

The engineering picture: versions, snapshots, and three decisions

Now the same ledger in the engineer's words. Each line carries three facts: the value, the moment it starts counting, and the moment it stops counting. Engineers call each line a version, and write it as [value, visible-from, visible-until]. Each row of the table is a chain of those versions.

The "moment I started looking" is a timestamp. Engineers call it the transaction's snapshot. A transaction reads the version whose window contains its snapshot. Writes are private until commit. At commit they are stamped and become visible.

A level is then three decisions. Read down each column: it is one level's house rule.

Decision Read committed Snapshot Serializable (tracking) Serializable (locking)
which version do I read? newest committed, re-decided every statement the one at my start timestamp same as snapshot the current one, under a shared lock
may I write over an unfinished change? no — wait no — wait no — wait no — wait for the lock
what if two decisions clash? nothing is checked if someone committed my row after my snapshot, I am refused that, plus: if I read something they changed and changed something they read, I am refused it cannot happen; locks made us take turns

That last row deserves its own sentence, because your code will meet it constantly. When the database decides Devi and Omar cannot both be right, it refuses one of them. Engineers call that refusal a serialization failure, and SQL reports it as the error code 40001.

Where the story lies to you

1. A clerk does not hold a photocopy. "Snapshot" sounds like a copy taken at the start. Nothing is copied. The version chain is shared, and each read picks a line out of it using your timestamp. This matters, because it means a snapshot costs nothing to take and everything to keep. See section 11, F8.

2. Read committed re-reads every time, and that is not a compromise, it is a different thing. Under read committed there is no single moment your transaction is "as of". Statement one may be as of 10:00:01 and statement two as of 10:00:04. The ledger picture makes it feel like a slightly blurry snapshot. It is not a snapshot at all.

3. The clerks are not peers. The picture suggests Devi and Omar negotiating. In fact the database is free to throw one of them out entirely, at commit time, after all the work is done. That is not a failure. At the top of the ladder it is the mechanism, and your application is expected to handle it. Any mental model that leaves out "and then one of them is simply killed" will mislead you about what buying SERIALIZABLE actually costs.

10. What is the machinery underneath? Three inventions, each forced by the last one's failure

In one breath: First idea: lock the row and hold it, which is correct and makes everyone wait. Second idea: keep old versions so readers never wait, which is superb and misses one bug. Third idea: also remember what was read, which catches that bug by throwing a clerk out at the last moment.

10.1 Mechanism v1: what if Devi locks the row and holds it to the end?

The obvious fix for Asha: before reading a row, lock it. Before writing it, lock it harder. Hold every lock until you commit. Nobody can slip into your gap, because there is no gap.

Engineers call this two-phase locking, or 2PL. There is a growing phase where you only acquire locks, then a shrinking phase at commit where you only release them. It is genuinely correct. Here is the lab's toy engine doing it to Devi and Omar, who appear as transaction 1 (T1) and transaction 2 (T2). Run java src/MiniLab.java lost-update:

    T1 begins at snapshot 3
    T2 begins at snapshot 4
    T1 reads acct:1 = 100
    T2 reads acct:1 = 100
    T1 must wait: T2 holds a read lock on acct:1
    T2 must wait: T1 holds a read lock on acct:1
    deadlock: T1 is waiting for T2 and T2 is waiting for T1
    T2 is thrown out: chosen as the deadlock victim
    T1 writes acct:1 = 110
    T1 commits at 5

Two things to notice, because both become permanent features of the topic. First, the result is correct: one transaction did its work, the other was told to try again. Second, the way it got there was a deadlock. Each clerk was holding what the other needed. Deadlocks are not a bug in locking. They are what locking feels like.

Before the next question, four words the lab's tables use. When a bad ending was stopped by making a clerk wait, the table prints safe(wait). When it was stopped by refusing a clerk, safe(err). When it was stopped at no cost at all, safe. When it happened and nobody complained, ALLOWED. Section 11 has the full legend.

🔮 Predict: Locking is correct. What is the thing about it that made the entire industry go looking for something else?

Reveal

Readers block writers, and writers block readers. If you said "deadlocks", that is a real cost, but it is not the one that ended the era. Deadlocks are occasional; waiting is constant.

Run a report that reads a million rows under two-phase locking. It holds a shared lock on every one of them until it commits. Nothing can be updated for the whole minute your report runs. Meanwhile a single row being updated stalls every reader who touches it.

Look at the toy engine's own matrix: under SERIALIZABLE(2PL) almost every row is safe(wait). Correct, and every single one paid in waiting. On a busy OLTP database that is not a tuning problem, it is a non-starter. That is why the default level in every mainstream database is not this.

10.2 Mechanism v2: what if nobody ever overwrites a row?

The insight that changed databases: never overwrite a row. Add a new version beside it instead. Then a reader does not need a lock at all. It reads the version that was current when it started, and writers can carry on.

Readers never block writers. Writers never block readers. That sentence is the reason MVCC won. The letters stand for multi-version concurrency control: the version chains from section 8, used for exactly this. It is why Postgres, Oracle, MySQL/InnoDB and SQL Server's snapshot modes all work this way.

Run java -cp ../lib/h2.jar src/Experiments.java versions and watch Asha's row grow a chain while a report holds an old snapshot open:

  acct:1: [100 from 1 onwards]
  after write 1: acct:1: [100 from 1 to 4] [110 from 4 onwards]
  after write 2: acct:1: [100 from 1 to 4] [110 from 4 to 6] [120 from 6 onwards]
  ...
  the report still reads: 100   (its snapshot is older than every one of those versions)

Two transactions writing the same row still have to be resolved. The rule is first committer wins. At commit, if any row you wrote gained a version after your snapshot was taken, someone beat you to it and you are refused. That refusal is where the 40001 in the matrix comes from.

This is snapshot isolation, and it is superb. In one move it stops five things. A reader seeing unfinished work. The same query returning two different answers. Rows appearing mid-count. A report totalling two rows from two different moments. And Asha's deposit vanishing. No reader ever waits for anything. Look at the toy engine's SNAPSHOT column: five rows of safe and safe(err), and not one safe(wait) on a read.

10.3 Which failure forced v3?

Two doctors are on call. The lab calls them Alice and Bob. The rule is that at least one must stay. Each checks the rota, sees two people on call, and signs off. In the visualization Devi (Clerk 1) is handling Alice's sign-off and Omar (Clerk 2) is handling Bob's.

🔮 Predict: Both transactions run under snapshot isolation. Each reads the rota, sees 2, and updates its own doctor's row only. Does first-committer-wins catch this?

Reveal

No, and it never could. If you said yes, you have given the check a power it does not have. Devi's transaction writes Alice's row (row 1). Omar's writes Bob's row (row 2). They wrote different rows, so there is no row for the first-committer-wins check to fire on. Both commit. Nobody is on call.

java src/MiniLab.java write-skew        # look at the SNAPSHOT section

    T1 scans [on_call] -> 2 rows  (as of 3)
    T2 scans [on_call] -> 2 rows  (as of 4)

    T2 writes doc:2 = 0

    T2 commits at 6
  outcome: ALLOWED   final state: 0

Snapshot isolation checks what you wrote. The information that made this wrong is what you read, and nobody was keeping that.

This anomaly is called write skew, and it is the reason the last rung of the ladder exists.

10.4 Mechanism v3: what if we remember what was read, not just what was written?

The fix is to write down the reads too. When a transaction writes a row, look for any concurrent transaction that already read that row, or asked a question this row would have answered. Record an arrow from the reader to the writer. The arrow means: "in any single-file story, the reader has to come first, because it did not see this change." Postgres's documentation calls that arrow an rw-antidependency. It is the only kind of conflict snapshot isolation does not already handle.

A transaction with an arrow coming in and an arrow going out is sitting in the middle of a loop that cannot be untangled. That shape is called a pivot, and refusing it is enough.

Here is the toy engine doing exactly that to Devi and Omar, arrows and all:

java src/MiniLab.java write-skew        # the SERIALIZABLE(SSI) section

    T1 scans [on_call] -> 2 rows  (as of 3)
    T2 scans [on_call] -> 2 rows  (as of 4)
      ! T2 had read doc:1, T1 is writing it  ->  arrow T2 -> T1
    T1 writes doc:1 = 0
      ! T1 had read doc:2, T2 is writing it  ->  arrow T1 -> T2
    T2 writes doc:2 = 0
    T1 is refused: it has an arrow in AND an arrow out — it is the pivot of a cycle
    T2 commits at 5

  outcome: safe(err)   final state: 1

One doctor left on call, one transaction told to try again. This is serializable snapshot isolation, SSI for short. It is how PostgreSQL implements SERIALIZABLE, and the reason Postgres can offer real serializability without going back to locks.

Notice what it does not do: it never makes a reader wait. It pays for correctness in refusals at commit time rather than in waiting, and that is the trade. Which is better depends entirely on how contended your data is. Experiment 2 in section 14 puts a number on exactly that.

Three mechanisms, three prices. There is no fourth option where you pay nothing.

Mechanism Pays in Who pays, in the story

The column headings are the five levels: RU read uncommitted, RC read committed, RR repeatable read, SNAP snapshot, SER serializable.

Read the bottom two rows before anything else. The column headed SER is the level called SERIALIZABLE, and it permits write skew. That is not a bug in this lab. H2's own pull request adding these levels says the implementation "prevents all three read phenomena, but doesn't ensure equivalence of sequential and concurrent execution of transactions" (h2database#2148). The name is aspirational. This is the single most important habit this lab can give you: run the table against your own database instead of trusting the column heading.

F1. Dirty write: how can 120 come to rest on a change that was withdrawn?

Make it happen with java -cp ../lib/h2.jar src/Matrix.java dirty-write.

Devi (Clerk 1) sets Asha's balance to 110 and does not commit. Omar (Clerk 2) sets it to 120 and commits. Then Devi rolls back. Asha's balance is 120, and it is resting on a change that was withdrawn. Devi's undo cannot undo what Omar has already built on.

Why did the database allow it? At READ UNCOMMITTED, H2 takes no row locks at all. Every other level makes Omar wait until Devi has finished. Nothing is kept at RU. What is lost is the ability to roll back meaningfully.

In production this one is special. Every standard says a dirty write must be prevented at every level. H2's READ UNCOMMITTED does not prevent it. That is one more reason nobody should ever select that level.

F2. Dirty read: what happens when Omar reads a number nobody has agreed to?

Make it happen with src/Matrix.java dirty-read.

Devi sets Asha's balance to 999 and has not committed. Omar reads 999 and acts on it. Seconds later Devi rolls back. Omar acted on a number that never existed.

Why? At RU, reads look inside other transactions' unfinished work. Every level above RU reads only committed versions. Nothing is kept at RU. What is lost is any meaning at all.

Here is the production twist. PostgreSQL will not do this even if you ask. SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED is accepted and silently behaves as READ COMMITTED, because its MVCC design has no way to produce a dirty read. Whole categories of advice about "avoiding dirty reads" are irrelevant on Postgres.

F3. Non-repeatable read: how can the same question get two answers?

Make it happen with src/Matrix.java non-repeatable-read.

Devi reads Asha's balance twice inside one transaction. She gets 100, then 200. Omar committed a change in between.

Why? At read committed, every statement gets a fresh view. Snapshot isolation freezes the view at transaction start. What Devi keeps at read committed: she never sees uncommitted data. What she loses: internal consistency. Any total she computes across two statements may be nonsense.

In production this is the everyday reason to raise the level for reports. Experiment 4 counts it: a report reads four balances while transfers run.

Level Wrong totals What it means
read committed 96 of 300 about one report in three added up numbers from two different moments
snapshot 0 of 300 one moment for all four reads, so the total always existed

F4. Phantom read: how does a row appear in the middle of a question?

Make it happen with src/Matrix.java phantom-read.

Devi asks "how many accounts hold more than 50?" and gets 2. She asks again and gets 3. In SQL the question is SELECT COUNT(*) WHERE balance > 50. Omar inserted a new account between her two questions.

Why could nothing stop him? The new row did not exist when the first count ran, so there was nothing to lock. A snapshot prevents it for free: the new version is after Devi's timestamp. Under locking you need range or predicate locks, which lock the question, not the rows. Existing rows are kept stable. What is lost is the meaning of any aggregate.

In production this is the anomaly the ANSI standard says REPEATABLE READ may permit. On most MVCC engines it does not, because their REPEATABLE READ is really snapshot isolation. The level name tells you nothing here; the implementation does.

F5. Lost update: how many of Asha's 320 deposits survive?

Make it happen with src/Matrix.java lost-update, and at scale with src/Experiments.java increment.

This is Asha's story from section 2, run 320 times. About 60 of 320 increments survived at read committed. Read-then-write is two statements with a gap, and Omar slips into Devi's gap almost every time. At snapshot and above, first-committer-wins refuses the second clerk with 40001. At read committed nothing is kept. The update is lost, silently.

In production this is the single most common data-corruption bug in ordinary CRUD applications. It has three fixes, and experiment 1 runs them side by side.

F6. Read skew: how does a report find money that is not there?

Make it happen with src/Matrix.java read-skew and src/Experiments.java stability.

Devi is writing a report. She reads Asha's balance: 100. Omar commits a transfer of 50 from Asha to Bob. Devi reads Bob's balance: 150. Her total is 250, for a pair of accounts that always held 200.

Why? Two statements, two different moments. A snapshot makes all reads one moment. Each individual read was of committed data and was correct; that much is kept. What is lost is any invariant across rows.

In production this is why reporting and batch jobs are the classic customers for REPEATABLE READ. It is also why "our nightly reconciliation is off by a few pennies and we can never make it happen again" is so often this.

F7. Write skew: why does the top rung exist?

Make it happen with src/Matrix.java write-skew, src/Experiments.java skew, and java src/MiniLab.java write-skew for the mechanism.

Both doctors signed off. You watched the mechanism in section 10.3. Experiment 3 runs it on H2 unscripted, 200 rounds at each level.

Level Rounds broken What it means
every H2 level, including SERIALIZABLE 196 to 200 of 200 the rota emptied almost every time, and the level name changed nothing

Why? Devi and Omar wrote different rows, so no write-write check can fire. The shared thing was a rule they both read. Only read-tracking (SSI) or locking the predicate can stop it. Every row is individually fine. What is lost is the invariant across rows, the thing your business actually cares about.

In production this is the anomaly behind double-spends, over-booked resources, two people assigned one seat, and rota holes. The reason it survives review is that the rule lives in an if statement in the application, where the database cannot see it.

F8. The long transaction: what does the snapshot you took cost?

Make it happen with src/Experiments.java versions.

Devi opens a snapshot transaction and leaves it open. Every write Omar makes after that leaves another version of the row alive, because Devi might still read the old one. An old version may not be removed while any transaction might still read it. There is no automatic response; the versions accumulate. Correctness is kept, perfectly. Disk and scan speed are lost.

In PostgreSQL this is what VACUUM cleans up, and one forgotten idle in transaction session stops cleanup for the whole database. Tables grow while the row count does not, and queries slow down for reasons that look nothing like a transaction bug. The setting idle_in_transaction_session_timeout exists precisely for this. It is also why long-running analytics against your OLTP primary is an isolation-level decision, not just a load decision.

12. What are you actually buying?

In one breath: Each rung stops a fixed list of bad endings and permits the rest. Isolation is not about crashes, not about replicas, and not a substitute for a constraint. What you pay is waiting, or old versions, or refusals. The refusals depend on how hot your rows are, not on the level.

What does each level guarantee?

Level Stops Still permits
read uncommitted (in principle, dirty writes — but see F1) everything else
read committed dirty reads, dirty writes non-repeatable read, phantom, lost update, read skew, write skew
snapshot / most engines' repeatable read + non-repeatable read, phantom, read skew, lost update write skew
serializable (SSI or 2PL) everything above nothing — but you must retry

What is isolation not?

Three things people buy an isolation level for, and get nothing.

  • Not atomicity or durability. Those are about crashes; this is about neighbours. Raising the isolation level does nothing for a power cut in the middle of Devi's transfer.
  • Not a replication guarantee. Everything here is one node. Reading a serializable transaction from a lagging replica gives you a consistent view of a stale moment. linearizability is the axis that covers that, and the two are independent. This is why Spanner needs a separate word (external consistency) for having both.
  • Not a substitute for a constraint. Write skew happens because a rule lived in application code. A CHECK, a UNIQUE index or an exclusion constraint moves that rule into the database, where it holds at every level and costs nothing. The cheapest fix for write skew is usually not an isolation level at all. For the double-booking case, UNIQUE (room, day) ends the argument.

What do you trade?

Waiting is the price of locking. Throughput falls under contention, and deadlocks appear. Deadlocks are a lock ordering problem, and experiment 6 shows it with two opposing transfers.

Lock order Retries What it means
whatever the transfer needs 57 the two transfers keep holding each other's second account
always the lower id first 0 no cycle can form; same level, same work

Version accumulation is the price of snapshots. That is F8: Devi's open snapshot pins every old line in the ledger.

Refusals are the price of SSI, and here is the sharpest number in the lab. Same level, same code, only the spread of the data changed (experiment 2).

Contention is a property of your data access pattern, not of the isolation level. "We turned on serializable and the app fell over" is almost always a hot-row problem wearing an isolation-level costume.

Safety and liveness: which one does the retry loop protect?

Preventing an anomaly is a safety property: nothing bad happens. Every mechanism here delivers safety. What they differ in is the liveness cost. Locking can stall Devi indefinitely, and deadlock. SSI can refuse her repeatedly under contention. Neither can corrupt Asha's data by trying too hard; both can stop Devi making progress. That asymmetry is why the retry loop is not optional decoration but part of the guarantee.

Why is the standard's own ladder broken?

ANSI SQL-92 defined the ladder by three phenomena: dirty read, non-repeatable read, phantom. Berenson and colleagues showed in 1995 (A Critique of ANSI SQL Isolation Levels) that the definitions are ambiguous. They also showed that snapshot isolation does not fit anywhere on the ladder. It is stronger than REPEATABLE READ (no phantoms) and weaker than SERIALIZABLE (write skew). Vendors mapped it onto whichever rung name was closest. That is exactly why REPEATABLE READ means different things in PostgreSQL and MySQL, and why Oracle's SERIALIZABLE is snapshot isolation (Mihalcea).

Do not learn the ladder as a hierarchy of names. Learn it as a list of anomalies, and find out which ones your database actually stops.

The lines that carry the concept. Read these five and you have read the lab. Each is a moment in Asha's story, in words first and then in code.

  1. Which moment does a read see? MiniDb.readTs decides: t.level == READ_COMMITTED ? clock : t.startTs. In words: read committed looks at the clock now; everything else looks at the moment Devi started. One ternary, and it is the entire difference between read committed and a snapshot.
  2. Did someone beat me to this row? The first-committer-wins loop in MiniDb.commit asks if (v.begin > t.startTs). In words: if a version of this row began after my snapshot, I am refused. This is where 40001 is born.
  3. Where is a read remembered? MiniDb.noteReadWriteConflicts is the only place a read is written down. Delete this method and SERIALIZABLE(SSI) becomes snapshot isolation, and both doctors go off call again.
  4. Who gets thrown out? MiniDb.isPivot returns in && out. In words: an arrow coming in and an arrow going out. The whole of SSI's decision rule.
  5. How does the harness know Omar is waiting rather than done or failed? Runner.play's submit-then-move-on loop. Without this the matrix cannot tell safe(wait) from safe.

Deliberate simplifications, flagged. MiniDb stores one integer per key. That is enough: every anomaly here is about when you see a value, never its type. Its 2PL locks the whole table for a predicate read, where a real engine locks index ranges: coarser, same idea. Its SSI aborts on the pivot shape without the full read-only-transaction optimisations Cahill's algorithm has. So it can refuse a transaction a real implementation would let through; it never lets a bad one through.

15. What happens in production?

In one breath: The toy engine is the shape of Postgres. Real engines add cleanup, index locks and decades of tuning. You choose the level per transaction, not per database, and every level above the default needs a retry loop or it is a bug.

From this lab to an on-call morning

MiniDb is structurally what Postgres does: versioned rows, a snapshot timestamp per transaction, first-committer-wins, and read-tracking at the top level. What real engines add is everything around it: durability, cleanup, index-level locking, and decades of tuning.

  • This lab: versions in a HashMap, cleaned up never.
  • Real: versions in the heap pages themselves, with VACUUM (Postgres) or a separate undo/rollback segment (Oracle, InnoDB) reclaiming them.
  • Architecture: the level is chosen per transaction, not per database. Devi's monthly report gets a snapshot; Asha's payment path gets serializable; the feed page gets read committed.
  • On-call: you watch deadlock rate, serialization-failure rate, long-running transaction age, and table bloat. A spike in 40001 is not an incident by itself. It is contention, and it is telling you which row is hot.

What does each real database actually do?

🔮 Predict: On MySQL/InnoDB at its default level, Devi's plain SELECT reads a snapshot. What does her UPDATE in the same transaction read?

Reveal

The latest committed row, not her snapshot. If you said "the snapshot, obviously, same transaction", you have just met the split personality that surprises everyone. It is why read-then-write behaves differently on InnoDB and on Postgres at the same named level. The table below has the rest.

Database What its levels really are
PostgreSQL READ UNCOMMITTED silently means read committed — it cannot produce a dirty read. READ COMMITTED (default) = per-statement snapshot. REPEATABLE READ = snapshot isolation: no phantoms, but write skew is allowed. SERIALIZABLE = SSI, the real thing, and it raises 40001 that you must retry.
MySQL / InnoDB Default REPEATABLE READ. Plain SELECT reads a snapshot; SELECT … FOR UPDATE, UPDATE and DELETE read the latest committed row instead — a split personality that surprises everyone, and the reason read-then-write behaves differently here than on Postgres. Gap/next-key locks stop phantoms for locking reads. SERIALIZABLE turns every plain SELECT into a locking read, i.e. back to 2PL.
Oracle Offers only READ COMMITTED and SERIALIZABLE, and its SERIALIZABLE is snapshot isolation — write skew is permitted (Mihalcea). If you need real serializability on Oracle you enforce it yourself with SELECT … FOR UPDATE or a constraint.
SQL Server Default READ COMMITTED using locks, unless READ_COMMITTED_SNAPSHOT is on, which switches it to MVCC — a database-wide setting that changes your application's concurrency behaviour without changing a line of code. CockroachDB SERIALIZABLE by default; READ COMMITTED added later as an opt-out for migrating applications.
H2 (this lab) READ UNCOMMITTED allows dirty writes. REPEATABLE READ, SNAPSHOT and SERIALIZABLE are all snapshot-based and all three permit write skew — vendor-confirmed (h2database#2148).

How does this look in a Spring Boot application?

// The level is per transaction. Choose it where you know the use case.
@Transactional(isolation = Isolation.REPEATABLE_READ, readOnly = true)
public MonthlyReport build(YearMonth month) { … }        // needs a stable view

@Transactional(isolation = Isolation.SERIALIZABLE)

Three things that bite in practice:

  1. @Transactional(isolation = …) without a retry is a bug. Spring will not retry a CannotAcquireLockException for you. Wrap the whole transaction, with @Retryable or an explicit loop. The retry must re-run the method, not just the failed statement, because the data Devi's decision was based on has changed. See Retry.java.
  2. JPA's @Version is the same idea in the application. Optimistic locking raises OptimisticLockException on exactly the situation first-committer-wins catches, and it works at read committed. This is the same expected-version check you met in event-sourcing: one pattern, three names.
  3. Watch out for the read that escapes the transaction. A lazy-loaded association fetched after the transaction closes is a new transaction with a new snapshot. None of your isolation guarantees apply to it.

Solutions — isolation levels

Every measured number here came from running the code in this lab against H2 2.4.240 or the toy engine. Where something is reasoning or vendor documentation rather than a measurement, it says so.

Rung 1 — Explain

1.1 They have fixed half-done work: if the second statement fails, the first is undone, and once it commits it survives a crash. They have not fixed anything about the other clerk, because "one unit" says nothing about who else is running at the same time. Isolation is a separate promise with its own dial, and the default setting of that dial permits exactly the bug they closed — measured, roughly 60 of 320 increments survive at read committed, every transaction committing successfully.

1.2 Serializable means: however the work actually overlapped, the ending is one that could have been reached by doing the transactions one at a time, in some order. It does not say which order, and it does not say they actually ran one at a time.

Running them genuinely one at a time is not the answer because it means serving one user at a time. The whole field exists to get the appearance without the cost.

1.3

  • Isolation vs atomicity — atomicity is about your transaction being all-or-nothing across a failure; isolation is about other people's transactions being invisible to yours.
  • Isolation vs linearizability — linearizability is one operation on one object, across machines, with a real-time rule; isolation is many operations on many rows, on one machine, with no real-time rule at all.
  • Snapshot isolation vs serializable — snapshot checks what you wrote; serializable also checks what you read. The gap between them is exactly write skew.
  • Optimistic locking vs first-committer-wins — the same rule, enforced in different places: your application comparing a version column, versus the engine comparing version timestamps.

1.4 Because the database can see every row you touched, but it cannot see the rule you were checking. Lost update is two transactions writing the same row, which the engine notices for free. Write skew is two transactions writing different rows after both reading a shared condition — and that condition lives in an if statement in your application, somewhere the database has never looked. The only way to catch it is to record what was read, which is the one thing snapshot isolation does not do.

1.5 It is a feature, and the sentence is: "The database noticed that two requests would have corrupted each other, stopped one of them before any damage was done, and told us to run it again — which we do automatically." If you cannot say the last clause truthfully, you have bought the isolation level and thrown away what it bought you.

Rung 2 — Identify

2.1 (a) non-repeatable read · (b) lost update · (c) write skew · (d) read skew · (e) dirty read.

The one worth dwelling on is (c): it is the only one where the two transactions never touch the same row, which is why it is the only one that survives snapshot isolation.

2.2 Clerk 1 reads the version of dr alice and dr bob valid at moment 3; Clerk 2 reads the versions valid at moment 4 — in this scenario the same two versions, because nothing has been committed in between.

The first-committer-wins check does not fire because it only looks at the rows you wrote. Clerk 1 wrote dr alice; no version of dr alice appeared after Clerk 1's snapshot. Clerk 2 wrote dr bob; same story. Each check passes honestly. The information that would have condemned them — that each had read the row the other was about to change — was never recorded.

2.3

  • read committed versus snapshot: MiniDb.readTs, the single line return t.level == Level.READ_COMMITTED ? clock : t.startTs;
  • first-committer-wins: the loop in MiniDb.commit guarded by if (v.begin > t.startTs)
  • the only place a read is recorded: MiniDb.noteReadWriteConflicts (fed by the t.readKeys.add(key) and t.readPreds.add(...) lines in get and scan, both of which run only under SERIALIZABLE_SSI)
  • who gets refused: MiniDb.isPivot — return in && out;

2.4 In the H2 matrix, safe(err) appears in the RR, SNAP and SER columns for all three lost-update rows — nine cells.

What the application must have for every one of them: a retry loop around the whole transaction, keyed on SQLSTATE 40001 (and 40P01 for deadlocks). Without it, safe(err) is not "safe" from the user's point of view — it is a 500. See src/Retry.java.

Rung 3 — Predict

3.1 All 320 survive, with zero retries — and it is the fastest option measured (26 ms, against 131 ms for the broken read-then-write version).

A single UPDATE takes the row lock and then reads the current value, so there is no gap for anyone to slip into. The lost update was never really about the isolation level; it was about the application holding a value across a gap it did not own. Check whether the read can move into the write before you reach for the dial.

3.2 ALLOWED at all five levels — including the one called SERIALIZABLE.

What that means for vendor documentation: a level name is a label, not a specification. H2's own pull request adding these levels says the implementation "prevents all three read phenomena, but doesn't ensure equivalence of sequential and concurrent execution of transactions." The behaviour is documented; it is just not documented in the name. Run the table against your own database.

3.3 Measured: 282 retries on 1 hot row, 1 retry on 16. Roughly two orders of magnitude, for identical work at an identical isolation level. Wall clock went from 247 ms to 17 ms.

3.4 ALLOWED · ALLOWED · ALLOWED · safe(err) · safe(err).

SERIALIZABLE(SSI) is the first to stop it. What it is doing that snapshot cannot: it recorded the question each clerk asked ("is room 1 free on Monday?"), and when the other clerk inserted a row, it checked that row against every remembered question. Snapshot isolation only compares row versions — and when both clerks looked, there was no row to compare. That is why row locks are no help here either: you cannot lock a row that does not exist.

3.5 The anomaly disappears, at every level.

That is the most important control on the page. Nothing about the database changed — the two transactions simply stopped overlapping. Concurrency is the input; the isolation level only decides what to do about it. The cheapest fix for a contention problem is often to stop the two things being concurrent at all.

Rung 4 — Modify

4.1 Exactly one cell changes: write skew at SERIALIZABLE(SSI) goes from safe(err) to ALLOWED. (Double-booking too, if you count it — both write-skew rows.) SERIALIZABLE(SSI) has become snapshot isolation.

That is the whole of SSI in one method. Everything else — snapshots, first-committer-wins, version chains — is shared with the level below. The difference between "prevents everything" and "prevents everything except the dangerous one" is a single piece of bookkeeping about reads.

4.2 Three cells change, all in the READ COMMITTED column: non-repeatable read, phantom read and read skew all go from ALLOWED to safe. Read committed has become snapshot isolation, because that ternary was the only difference.

The one that does not move is lost update, still ALLOWED at read committed. A frozen view does not help you: both transactions read 100 from their snapshots and both write 110. What fixes lost update at the snapshot level is not the snapshot — it is the first-committer-wins check at commit, and this edit did not touch that. Two independent mechanisms, often confused because they arrive together in the same level.

4.3 Read skew is a property of the reader, not the writer. The transfer is already atomic — it commits both updates together, and no reader ever sees half of it. The problem is that the reader took two separate looks at the world, and the atomic transfer landed between them. Making the writer more atomic cannot help, because the writer was never the one that was split.

The two things that fix it: give the reader one snapshot for both statements (raise its level), or make the reader ask one question instead of two (SELECT SUM(balance) FROM acct WHERE id IN (1,2) — a single statement is a single moment at every level).

4.4 Unreliable: the distinction between safe, safe(wait) and safe(err), because it is inferred from how long a step took. At a 1 ms timeout, ordinary statements get misreported as blocked.

Completely trustworthy: ALLOWED versus everything else. That verdict is computed from the values the transactions were actually given and the final state of the table, neither of which depends on a clock.

So: you can quote the ALLOWED cells from any machine, in any state. If you want to claim "this level prevents it by waiting" rather than just "prevents it", run it on a quiet machine and raise the timeout.

Rung 5 — Implement

5.1 The method is a lock acquisition plus an ordinary read:

Integer getForUpdate(Tx t, String key) {
    check(t);
    lockExclusive(t, key);          // at EVERY level, not just 2PL
    if (t.writes.containsKey(key)) return t.writes.get(key);
    return versionAt(key, db.clock);  // the newest committed, not your snapshot
}

Two details carry the whole idea. The lock is taken at every level — that is what "pessimistic locking" means, and it is why SELECT … FOR UPDATE works even at read committed. And it reads the newest committed value rather than your snapshot, because reading your stale snapshot under a lock would give you a correctly-locked wrong number.

Expect safe(wait) at READ_UNCOMMITTED and READ_COMMITTED, and safe(err) at snapshot and above — which is exactly the H2 row Lost update, with SELECT ... FOR UPDATE: safe(wait) safe(wait) safe(err) safe(err) safe(err). Two independent implementations, same answer.

5.2 At commit, before stamping the writes, scan the rows this transaction is adding and reject if another committed row already matches the predicate.

When a constraint beats an isolation level: whenever the rule can be expressed about the data rather than about the decision. A constraint is checked on every path into the table — including the migration script, the admin console and the colleague's psql session — costs nothing at read committed, and cannot be forgotten by a future caller. An isolation level protects only the code paths that remember to ask for it.

5.3 Expected shape: backoff increases wall-clock time at 1 hot row (you are deliberately sleeping) but reduces total retries, because retrying instantly into the same collision is what produced 282 attempts. At 16 rows it changes almost nothing, because there was barely any contention to back off from.

The lesson worth writing down: backoff trades latency for throughput, and it is only worth it where contention is real. Measure before adding it.

Rung 6 — Debug

6.1 Nothing changes because no version can ever have begin == startTs. Both values come from the same clock++ counter, so every timestamp in the engine is unique: a version's begin and a transaction's startTs are two different draws from the same sequence and can never collide. The >= branch is unreachable.

Could a test catch it? Not without breaking the invariant that makes it unreachable — you would have to hand-construct a version and a transaction sharing a timestamp, which the public API does not let you do. So the honest answer is: the bug is invisible because a stronger invariant holds elsewhere, and the right response is to write that invariant down as a comment next to the counter, not to write a test for an impossible state.

This is worth internalising, because the reverse case is what kills you: a "harmless" change becomes a real bug the day someone makes timestamps non-unique — for example by taking them from a wall clock.

6.2 The doctors table ends with 2 on call instead of 1, and both transactions are refused. Failing tests: ssi_leaves_exactly_one_doctor_on_call and ssi_refuses_exactly_one_transaction.

It is a waste, not a safety bug: no incorrect state was ever committed. Once Clerk 1 has been thrown out, its arrows describe a transaction that never happened, so Clerk 2 is no longer part of any cycle and could safely have committed. Counting the dead transaction's arrows refuses it for nothing.

In production this is the difference between one retry and two under contention — and because each retry re-enters the same contention, the cost is worse than linear. Real SSI implementations spend considerable effort on exactly this: refusing as few transactions as possible while still refusing enough.

6.3 Dirty write — writing over a change nobody has committed. Failing tests: dirty-write at READ_COMMITTED, SNAPSHOT and SERIALIZABLE_SSI.

It is the one anomaly every standard forbids at every level because it breaks something more basic than isolation: it breaks rollback. If Clerk 2 can build on Clerk 1's uncommitted value, then Clerk 1's ROLLBACK cannot restore the world — the undo would have to reach into a transaction that has already committed. Atomicity itself stops being well-defined. Everything else on the ladder is a matter of degree; this one is a matter of the model working at all.

6.4 Something like:

Nothing is broken — 40001 is what serializable is. It means the database caught two transactions that would have corrupted each other and stopped one before any damage was done. The fix is a retry loop around the whole transaction, not around the failing statement, and not a lower isolation level.

Before changing anything, measure two things. First, which rows the failures cluster on: in our own measurements, the same workload spread over 1 row versus 16 rows went from 282 retries to 1 — with no change to the isolation level. Contention is a data-access-pattern problem wearing an isolation costume. Second, the retry rate per transaction type: if one endpoint is responsible for all of it, fix that endpoint.

And check the cheaper fixes first: can the read move into the write (SET n = n + 1)? Can the rule become a UNIQUE constraint? Both are free and neither needs serializable at all.

Rung 7 — Handle failure

7.1 Two transactions, both under snapshot isolation, transferring out of the same account with an overdraft rule:

T1 read balance → 100          T2 read balance → 100
T1 checks 100 >= 80, OK        T2 checks 100 >= 80, OK
T1 UPDATE balance = 20
                               T2 UPDATE balance = 20   -> refused, 40001

Retrying only the failed UPDATE re-runs balance = 20, which succeeds this time — and the account has paid out 160 from a balance of 100. The decision 100 >= 80 was made against data that is no longer true, and re-running the statement carries that stale decision forward.

The general rule: a serialization failure invalidates everything your transaction read, not just the statement that failed. The retry must go back to the reads, which means re-running the whole transaction — which in turn means your transaction body must be a pure function of the data it reads, with no side effects outside the database. That last clause is what makes retry loops hard in real applications: the email you sent halfway through does not roll back.

7.2 In order:

  1. Reduce the contention. Find the hot row. Shard the counter, batch the updates, or move the read into the write. This is nearly always the real fix and it costs a code change, not throughput.
  2. Lower the level for this transaction and protect it differently — a UNIQUE constraint, a conditional UPDATE … WHERE status = 'free', or SELECT … FOR UPDATE on one row. Costs some correctness surface, which you must be able to name.
  3. Shed or queue the load. If a hundred requests genuinely need the same row, they are going to take turns whatever you do; a queue makes the waiting explicit and fair instead of turning it into retries and timeouts. Costs latency and a component.

Raising the budget is wrong because retries are the contention: each attempt re-enters the same collision, so more attempts make the collision worse. You are adding load to a system that is failing from load.

7.3 Lock the two accounts in a fixed order — always the lower id first — regardless of the direction of the transfer. Then no two transactions can hold what the other one wants, so the cycle cannot form.

Measured (Experiments.deadlock, 60 rounds of two opposing transfers):

lock order retries gave up
whatever the transfer needs 57 0
always lowest id first 0 0

Same isolation level, same work. Deadlocks are a lock-ordering bug, not an isolation-level problem, and this is the fix that costs no throughput.

7.4 The report holds an open snapshot for 40 minutes. Every version of every row that anything overwrites during those 40 minutes must be kept, because your report might still read it. Cleanup cannot advance past the oldest open transaction, so 40 minutes of the whole database's writes accumulate as dead versions — and they stay accumulated after your report finishes, until cleanup catches up. The table grows while the row count does not, and every scan reads the bloat.

The two settings: idle_in_transaction_session_timeout (kill sessions holding a snapshot open while doing nothing) and autovacuum's aggressiveness (autovacuum_vacuum_cost_limit, autovacuum_naptime). The structural fix is to run long reports against a replica or a separate analytical copy so their snapshots never pin the primary's cleanup — which is the point at which an isolation-level decision becomes an architecture decision.

Rung 8 — Design

One defensible position, with the reasoning exposed.

8.1 — A payments ledger

Job Level and mechanism Why
balance check + debit read committed + conditional update: UPDATE acct SET balance = balance - :amt WHERE id = :id AND balance >= :amt, then check rows-affected one statement, one row, no gap. The rule is inside the write, so there is nothing to skew. No retries, no locks held across a round trip
idempotency-key check read committed + UNIQUE constraint on the key, insert-first the constraint decides the race, not the isolation level. A duplicate insert fails with a key violation you can catch, at every level, forever

Which would I make constraints instead? The idempotency key, the single active subscription, and any uniqueness rule. The reason is not performance — it is reach. An isolation level protects the code paths that remember to ask for it; a constraint protects the table. Six months from now, the data migration and the support engineer's manual INSERT will both go through the constraint and neither will go through your @Transactional annotation.

8.2 — PostgreSQL and MySQL/InnoDB

(Vendor behaviour, from documentation — not measured in this lab.)

  1. REPEATABLE READ does not mean the same thing. On Postgres it is snapshot isolation throughout. On InnoDB, plain SELECT reads a snapshot but SELECT … FOR UPDATE, UPDATE and DELETE read the latest committed row. So a read-modify-write behaves differently on the two engines at the same named level. What I would do: never rely on REPEATABLE READ for a read-modify-write on either engine — use the conditional update, which is identical on both.
  2. SERIALIZABLE is a different mechanism. Postgres uses SSI: it never blocks readers, and it fails at commit with 40001. InnoDB turns every plain SELECT into a locking read: it blocks, and fails with lock-wait timeouts and deadlocks. What I would do: make the retry loop catch both families of error — serialization failure and deadlock — because which one you get depends on the engine, not on your code.
  3. Phantom prevention comes from different places. Postgres gets it from the snapshot; InnoDB gets it from gap and next-key locks on locking reads, which also means InnoDB can deadlock on ranges where Postgres would not. What I would do: prefer constraints for uniqueness rules so neither mechanism is load-bearing.

The general lesson: write the application against anomalies, not against level names. "This transaction must not lose an update" ports; "this transaction uses REPEATABLE READ" does not.

8.3 — Not an isolation problem

A customer-facing balance that looks briefly stale after a payment. The symptom is identical to a read skew or a non-repeatable read complaint — "I paid and the balance is wrong" — and raising the isolation level will not fix a single one of them, because the read is coming from a replica that is seconds behind, or from a cache. Isolation is a one-node property; staleness across nodes is the axis the linearizability lab covers, and no isolation level touches it.

What I would do instead: route the read that follows a write to the primary for a short window (or pass the write's log position and wait for the replica to reach it), and show an "as of" timestamp in the UI. What I give up: some of the read-replica offload I bought the replica for, and a little latency on exactly the requests that matter most.

The reason this belongs in the exercises: the two axes have almost identical symptoms and completely different fixes, and reaching for the isolation dial when the problem is replication is a very common and very expensive mistake.

8.4 — Proving what you have

  1. Run the matrix. java -cp ../lib/h2.jar:<driver>.jar -Ddb.url=… src/Matrix.java against a scratch schema on a copy of the real database, at the real version. Ten anomalies, five levels, one command.
  2. Check the defaults you actually get — not just the server default but what your connection pool, ORM and framework set. SHOW transaction_isolation from inside a real application transaction, not from psql.
  3. Find the write skews. Grep the codebase for the shape: a SELECT whose result feeds an if, followed by an UPDATE/INSERT of a different row. Every one of those is a candidate, and no level below serializable protects any of them.
  4. Check for the retry loop. If any code path uses a level above read committed and there is no retry on 40001, that path is already broken and nobody has noticed yet, because it only fails under load.
  5. Measure contention on the rows those paths touch, so you know what raising a level would cost before you raise it.

In the runbook: the matrix output with the database version next to it; the list of transactions that run above read committed and where their retry loop lives; the invariants currently protected by application code rather than constraints (the write-skew candidates); and the alert thresholds for serialization-failure rate, deadlock rate, and oldest-open-transaction age.

Re-run step 1 on every major database upgrade. These behaviours change between versions, and the level names do not.
