1 · WHY — the sentence you cannot check

Open any distributed database's documentation and you will find a sentence like one of these:

"Transactions are fully ACID and serializable."

"Reads with readConcern: majority never return data that could be rolled back."

"Acknowledged writes are never lost."

Each of those is a claim about behaviour under failure. Not under normal operation — under normal operation almost everything works. The claim is about what happens when a switch reboots, a leader's process is stopped for nine seconds by a garbage collection pause, a disk lies about fsync, or a clock jumps backwards.

Here is the uncomfortable fact that motivates this entire field:

Those sentences are frequently false, and they are false in systems written by careful people, reviewed by good engineers, and used in production by companies you have heard of.

Not because the authors are dishonest. Because the property is very hard to implement, and — this is the part that matters — very hard to test. A bug that only appears when a network partition heals during a leader election, on the third of five nodes, while a client is retrying, is not going to be found by a unit test.

So the question this lab answers is not "what is serializability". You know that. The question is:

Given a running cluster and a claimed guarantee, what procedure produces evidence that the guarantee is broken?

The answer, developed by Kyle Kingsbury from 2013 onward and now the de facto standard, is called Jepsen.

2 · THE CONCRETE PROBLEM — you are about to bet a ledger on FerrousDB

Let us make this specific.

FerrousDB is fictional. It is a stand-in for a real product so that we can be rude about it. Every failure it exhibits in this lab is modelled on a documented, published finding in a real system; those are named in section 18.

You work on payments. You need a store for the ledger. FerrousDB is fast, has a good client library, and its documentation says:

FerrousDB provides linearizable reads and writes for single keys when consistency=strong is set. Acknowledged writes survive the failure of any minority of nodes.

You have three nodes: n1, n2, n3. You have four client processes hammering it. Before you commit the company to this, you want to check the claim.

What do you do?

Hold that question for a moment, because the first answer everybody gives is wrong, and understanding why it is wrong is most of this lab.

3 · THE OBVIOUS SOLUTION — assert the final answer

Here is what a good engineer writes first. It is not a straw man; it is what I would write, and probably what you would write.

# Pseudocode. Illustrative only — this lab has no runnable code.
set x = 0
run 8 threads for 60 seconds:
    each thread does 100 increments:  read x, then write x+1
assert x == 800

This is a stateful assertion test. It is a completely reasonable instinct: do a lot of work, then check the arithmetic at the end.

Run it against FerrousDB. It passes. x == 800.

Run it a hundred times. It passes a hundred times.

You ship.

Six weeks later a customer's balance is wrong.

🔮 Predict: Before reading on — name at least two distinct reasons this test could pass a hundred times against a database that violates its linearizability claim. Not "it got lucky". Structural reasons.

4 · FAILURE — three separate reasons the final-state check is blind

Reveal

Reason 1: nothing bad ever happened, because nothing bad was ever attempted.

The test ran against a healthy cluster. No node died. No cable was cut. No process was paused. The claim you wanted to check — "acknowledged writes survive the failure of any minority" — was never put under any stress at all. You tested the happy path and concluded something about the unhappy one.

Reason 2: the final state is a terrible detector, because errors cancel.

Suppose two increments were lost, and separately, one increment was applied twice due to an internal retry. Final value: 799 + ... it depends. Errors in opposite directions cancel. Worse, some anomalies leave no trace in the final state at all: a stale read — a client seeing yesterday's value — corrupts a decision that client made, then vanishes. The final number is perfect. The customer's balance is not.

This is the single most important structural point:

Many correctness violations are events in the middle of the run that leave the final state completely normal. If you only look at the end, you are looking at the one place the evidence isn't.

Reason 3: x == 800 is the wrong question.

Think about what assert x == 800 actually encodes. It encodes: "I expected this exact outcome." But a correct concurrent system has many legal outcomes. And an incorrect one can produce a legal-looking outcome. Equality against a predicted value only works when the answer is deterministic — which is precisely what a distributed system under load is not.

So you cannot assert on the answer. You have to judge the behaviour.

5 · ATTEMPT TWO — inject faults, and immediately drown

Reason 1 has an obvious fix. Break things while the test runs.

Add a background process that, every 15 seconds, cuts the network in half for a while, then heals it. Now you are actually exercising the claim.

Run the test.

It fails instantly, and not in the way you hoped:

thread 3: java.net.SocketTimeoutException: Read timed out
thread 5: FerrousException: not the leader, try again
thread 1: java.io.IOException: Connection reset by peer
thread 7: FerrousException: no quorum available

And now you are stuck, because you have to answer a question that sounds trivial and is not:

Which of these is a bug?

Think it through. A SocketTimeoutException during a network partition is correct behaviour. The database is supposed to become unavailable to a minority — the cap-theorem lab settled that. Refusing to serve is the good outcome. If you treat errors as failures, your test reports a catastrophe every single run, you stop believing it, and you delete it.

But you also cannot ignore errors, because some of them are hiding real damage.

The instinct now is to write a big list of "acceptable exceptions". That way lies madness — it makes your test's verdict depend on your guesses about which error strings are benign, and a database's error taxonomy is not a safety specification.

The real lesson is that you have been asking the wrong kind of question all along.

6 · THE THING NOBODY EXPECTS — the operation that neither succeeded nor failed

Stare at this line for a moment:

thread 3: java.net.SocketTimeoutException: Read timed out

Thread 3 sent a write. It waited. It got nothing back.

Did the write happen?

You do not know. And here is the crucial part — you cannot ever find out. The request may have been dropped on the way out (no effect). It may have been applied and the response lost on the way back (full effect). It may be sitting in a queue on n2 right now and will be applied in eight seconds (effect, but later). Every one of those is consistent with everything you observed.

This is not a gap in your tooling. It is the fundamental condition of talking to another machine over a network, and it is the same fact that forced idempotency keys to exist and made the two-phase-commit coordinator's silence so expensive.

Jepsen's founding insight is to take this seriously and give it a name and a place in the data model:

Every operation has three possible outcomes, not two:

  • :ok — it definitely happened. It has a logical effect on the system.
  • :fail — it definitely did not happen. It has no logical effect.
  • :info — indeterminate. It may or may not have happened, now or at any point in the future.

Those are the actual keywords in Jepsen. From the Jepsen documentation:

:invoke denotes the start of a logical operation; :ok denotes its successful completion. :fail denotes its definite failure… An operation which completes with :fail must have no logical effect on the system. :info denotes an indeterminate result: the operation either may or may not have completed.

Almost every home-grown consistency test in the world gets this wrong, in one of two directions, and the two directions fail differently:

Mistake What it does to the judgement Consequence
Over-claiming — recording an indeterminate op as :ok or :fail The checker is given a fact that isn't one False alarms. You report bugs that aren't there, lose credibility, and stop trusting the test
Under-claiming — recording a definite failure as :info because it was easier The checker loses a constraint it was entitled to Missed bugs. The test goes green over a real violation

The second one is the dangerous one, because it looks responsible. "I wasn't sure, so I marked it unknown" feels like humility. It is actually throwing away evidence, and a checker with less evidence finds fewer violations.

Section 12 makes this concrete, and the simulator lets you watch the same history get three different verdicts depending on how :info is read. If you take one thing from this lab, take this one.

There is a second consequence of indeterminacy, and it is a rule people find surprising the first time:

A process that gets an :info is retired forever. Jepsen never issues another operation on that process ID.

Why? Because that operation might still be in flight. If the same process issued a new write, and the old one landed afterwards, the history would contain two overlapping operations from a "single-threaded" process — which breaks the one modelling assumption the checker depends on. So Jepsen burns the process number and starts a fresh one on the same thread. From the docs: "Processes are logically singlethreaded… If a process crashes it can never invoke an operation again."

That single rule tells you a lot about how seriously this framework takes uncertainty.

7 · THE REAL REQUIREMENT

Let us now state plainly what we actually need, having watched two attempts fail.

We cannot assert on final state (section 4). We cannot classify errors as pass/fail (section 5). We cannot even say for sure whether individual operations occurred (section 6).

What we can do is write down exactly what we observed, including our uncertainty, and then ask a question with a yes/no answer:

Is there any way this system could have behaved like the thing it claims to be, and produced everything we saw?

If yes → we found no evidence of a bug. That is all it means. If no → the claim is false, and we hold the proof.

This is the whole idea. Three things follow from it, and they are the three pillars of Jepsen:

  1. Record, do not assert. The output of a run is a history, not a pass/fail.
  2. Judge afterwards, against a model. Correctness is decided by searching for an explanation, not by comparing to an expected value.
  3. The evidence is a counterexample. A failure is not "assertion failed on line 42"; it is a concrete list of operations that no correct system could have produced.

That third point is why Jepsen reports are so persuasive and why vendors generally fix the bugs. You cannot argue with a history.

8 · TERMINOLOGY — the five words the rest of this lab uses

These are earned now; each solves a problem you just watched appear.

Operation

A single request from a single client, recorded as two entries in the log: an invocation and a completion. Not one entry — two. Because the thing that matters is that an operation occupies an interval of time, and both ends of that interval are constraints.

In Jepsen's notation:

{:process 3, :type :invoke, :f :write, :value 1,   :time 1042}
{:process 3, :type :ok,     :f :write, :value 1,   :time 1187}

:f is which function (:read, :write, :cas, :txn), :value is the argument or result, :process is the logical client, :time is nanoseconds since the run started.

History

The complete, time-ordered log of every invocation and completion from every process in one run. This is the artefact of a Jepsen run. It is written to disk. It is the thing that gets attached to the bug report.

Process

A logical single-threaded client. Only one operation in flight at a time. Retired permanently on :info (section 6).

Consistency model

The thing the history is judged against: linearizability, serializable snapshot isolation, "a set that never loses elements", and so on. You already own these definitions. Jepsen adds no new ones — it consumes yours.

Checker

A program that takes a history and a consistency model, and returns either valid? true or a counterexample.

Note what the checker does not get: it does not get to see inside the database. No internal logs, no replica state, no timestamps from the servers. Only what a client could observe. This is deliberate, and it is where the phrase in Jepsen's own repository comes from — Knossos verifies "experimentally accessible histories". If a violation is invisible from outside, it is by definition not a violation of a client-facing guarantee.

9 · MENTAL MODELS

The simple model: a courtroom

  • The history is the transcript of testimony. Each witness (process) says "at 10:04 I asked for the balance, and at 10:05 I was told £70."
  • The consistency model is the law: "the account behaves as if there were one ledger, updated one entry at a time."
  • The checker is the judge, and the judge's job is narrow: is there any single sequence of ledger entries consistent with all of this testimony?
  • A witness with a timeout is a witness who says "I filed a form; I never heard whether it was accepted." The judge must consider both worlds.
  • A verdict of guilty requires a proof that no sequence works. A verdict of not-guilty means only that the prosecution failed to find a contradiction today.

The engineering model

Where the courtroom analogy breaks — and it breaks in three places

  1. There is no presumption of innocence over time. In a real court, repeated acquittals mean something. Here, a thousand green Jepsen runs is not evidence of correctness in any strong sense — it is evidence that this particular workload, with these particular faults, on this hardware, for this duration, did not trigger the bug. Section 17 makes this precise.

  2. The judge can run out of patience, and that is not an acquittal. Deciding linearizability is NP-complete. Real checkers time out. "Checker did not finish" is a third outcome that the courtroom has no analogue for, and it is not a pass.

  3. The witnesses are the ones who decide what is admissible. The client library chooses whether to record :ok, :fail, or :info — so a sloppy client can hand the judge a transcript in which the crime is unprovable (section 12, scenario 6). The judge is only as good as the testimony.

11 · THE MECHANISM, PART ONE — running a checker by hand

Time to do the judge's job manually. This is the exercise that makes everything else click, and it takes about four minutes.

The system: one register x, starting at 0. The claim: linearizable.

The history (this is scenario S2 in the simulator):

# process operation invoked completed result
1 p1 write(1) t=0 t=9 :ok
2 p2 read() t=1 t=3 :ok → 1
3 p3 read() t=5 t=7 :ok → 0

Draw it:

p1  |=========== write(1) ===========|          t=0 .. t=9
p2      |== read → 1 ==|                        t=1 .. t=3
p3                  |== read → 0 ==|            t=5 .. t=7
        ^                        ^
        └── these two do NOT overlap ───────────┘

The rule of the game. Every operation must be assigned a single instant — its linearization point — somewhere inside its own bar. Then, reading those instants left to right must produce a sequence that a single-threaded register would actually produce.

Work it:

  • p2 read → 1. For a read to return 1, the most recent write before its point must be write(1). So write(1)'s point is before t=3.
  • p3 read → 0. For a read to return 0, the most recent write before its point must be… nothing, i.e. the initial value. So write(1)'s point is after t=5.
  • Contradiction. We need write(1) to be linearized before t=3 and after t=5. There is no such instant.

Verdict: not linearizable. And notice the shape of the proof — it needed exactly three operations. Jepsen reports quote exactly this: a minimal set of operations and the constraint that has no solution.

What just happened, in one sentence: two reads that did not overlap each other saw the value go backwards, and time is not allowed to run backwards.

That is the same violation the linearizability lab taught you to define. The difference is that here you derived it from an observation log of a black box, which is the only access you have to somebody else's database.

🔮 Predict: Now change one thing. Suppose p3's read had been invoked at t=2 instead of t=5, so that it overlaps p2's read. Is the history still a violation?

Reveal

No — it becomes perfectly legal. If p2's and p3's reads overlap in time, then a valid order exists: linearize p3's read (returning 0) first, then write(1), then p2's read (returning 1). All three points sit inside their own bars, and the sequence read→0, write(1), read→1 is exactly what a single register does.

This is the most important thing to internalise about linearizability checking, and it is why the checker cannot be replaced by "did the values look weird":

Concurrent operations are unordered, and therefore almost anything is allowed between them. Constraints come only from operations that do not overlap.

A history in which everything overlaps everything is nearly unfalsifiable. A history of neatly separated operations is highly constrained. This has a direct practical consequence in section 13: how you generate the workload determines how much power your test has.

12 · THE MECHANISM, PART TWO — where :info changes the verdict

Now we do the same exercise on a history containing an indeterminate operation, because this is where home-grown tests die.

Scenario S3 — "the timeout that was not a bug"

# process operation invoked completed result
1 p1 write(1) t=0 t=8 :info (timed out)
2 p2 read() t=2 t=4 :ok → 1

Three ways to read that :info, three verdicts:

Reading Reasoning Verdict
:info = it failed Nothing ever wrote 1. p2 read a value that was never written. ❌ VIOLATION
:info = it succeeded write(1) happened somewhere in [0,8]; put it at t=3, read at t=3.5. ✅ fine
:info = may or may not (Jepsen) Try both branches; the "did happen" branch works. ✅ fine

The naive-but-tempting first reading reports a bug in a database that did nothing wrong. Do this once a run and your test is noise.

Scenario S4 — "the timeout that was a bug"

The reverse case, so you do not learn the wrong lesson (:info is not a get-out-of-jail card):

# process operation invoked completed result
1 p1 write(1) t=0 t=20 :info
2 p2 read() t=2 t=4 :ok → 1
3 p3 read() t=6 t=8 :ok → 0
4 p4 read() t=10 t=12 :ok → 1

The only two values that can ever exist are the initial 0 and the single write(1). Three non-overlapping reads observed 1, then 0, then 1. That needs the value to change twice, and only one write exists. No reading of the :info saves this. Violation, and a real one.

The generalisable rule: :info grants the write freedom about when and whether it took effect. It never grants the reads freedom about what they saw. Reads that returned :ok are hard facts, and enough hard facts convict on their own.

A detail that surprises people: an :info never ends

When Knossos considers whether an indeterminate operation took effect, it does not confine it to the interval you recorded. The operation may still be sitting in a queue somewhere and land in ten seconds' time — so its interval is extended to the end of the history.

That is why, in the simulator, an :info bar is drawn as a dashed box with an arrow running off the right-hand edge. It is not a stylistic choice; it is the model. In scenario S6 this matters directly: the checker is free to say "the write may have landed after the read", which is one of the two ways that history escapes conviction.

Scenario S6 — the one that should worry you

Same shape as a genuine lost-write bug, but the client library was lazy:

# process operation invoked completed result
1 p1 write(1) t=0 t=4 :info ← the server actually replied "committed"
2 p2 read() t=8 t=10 :ok → 0

FerrousDB acknowledged that write and then lost it during a failover. That is precisely the "acknowledged writes are never lost" claim, broken.

But the client recorded :info — perhaps it wrapped everything in a try/catch that could not distinguish "server said no" from "no reply" — and so the checker reasons: the write may never have happened; a read of 0 is therefore fine. Verdict: valid. Bug missed.

This is under-claiming (section 6), and it is the reason serious Jepsen clients put real effort into error classification: mapping each of the database's error codes onto :ok / :fail / :info correctly is a substantial part of writing a test, and getting it wrong in the "safe-looking" direction silently disables your safety check.

Run S3, S4, S5 and S6 in the simulator and watch the three chips. S3 is the false alarm, S4 is the true conviction, S6 is the missed bug. The simulator shows you all three readings at once precisely so you can see that the history alone does not determine the verdict — the history plus your honesty about uncertainty does.

13 · WHY THE CHECKER IS EXPENSIVE — and what that costs you in practice

You just checked a 3-operation history by inspection. Real histories have tens of thousands of operations. How does the search scale?

Badly.

Deciding whether a history is linearizable is NP-complete in general.

The intuition is immediate once you have done section 11 by hand: at each step the checker must pick which of the currently-pending operations to linearize next, and if that choice leads to a dead end it must back up and try another. With k operations overlapping at once, there are up to k! orders to explore.

Jepsen's linearizability checker is called Knossos — named for the ruins where the Linear B script was found, a pun on whether a history "be linear". It implements the WGL algorithm: Wing & Gong's backtracking search with Gavin Lowe's extension, whose key move is to prune states equivalent to one already seen, so the search explores a graph of distinct register-states rather than a tree of orderings. Knossos additionally pre-compiles the model's state space into pointer arrays so the inner loop is pointer-chasing rather than interpreting model code, and runs a graph search and a tree search in parallel, taking whichever finishes first.

The simulator measures this for you. Scenario S8 lets you slide the number of concurrent operations and shows states explored, with pruning on and off. Measured in this lab's own checker, on a history of k mutually-overlapping writes plus one unsatisfiable read:

k concurrent ops states explored, no pruning with pruning ratio
4 65 53 1.2×
5 326 166 2.0×
6 1,957 487 4.0×
7 13,700 1,352 10.1×
8 109,601 3,593 30.5×

Two things to read off that table. The unpruned column is tracking k! (it is almost exactly e·k!), so it is not going to survive k=15. And the ratio roughly doubles with every additional concurrent operation — pruning is not a constant-factor win, it changes the growth rate, which is why WGL made linearizability checking practical at all. Below k=4 pruning saves nothing, because the search has not yet found two routes to the same state.

⚠️ Honest framing: the simulator implements the idea of WGL — search with a visited-set — in about sixty lines of JavaScript, on histories of a dozen operations. It is not Knossos and its numbers are the lab's model, not measurements of Knossos. The shape of the curve is the real lesson; the absolute numbers are not.

Three consequences that matter in practice, and they are why real Jepsen tests look the way they do:

  1. Short tests, many of them. You cannot check a one-hour history. Jepsen tests typically run for tens of seconds to a few minutes and are repeated.
  2. Few keys, low concurrency, small value spaces. Five processes on one key produces a far more checkable — and far more constrained (section 11's reveal) — history than five hundred processes on ten thousand keys.
  3. Independent keys are checked independently. Linearizability is local — your linearizability-vs-serializability lab measured this as the composition property: if every key is linearizable the whole store is. So the checker splits the history by key and checks each separately, which turns one enormous problem into many small ones. This is not an optimisation trick; it is a theorem being cashed in.

And note what point 3 implies: the same trick is unavailable for serializability, which does not compose. That is the crack that Elle exists to get through, and we reach it in section 16.

14 · ANATOMY OF A JEPSEN TEST

Now that you know what the machine has to produce, its parts are predictable. Jepsen is a Clojure library; a test is a map of six things. You will not write Clojure here — the point is to know what each part is for, because these are the six decisions you make when you test anything.

Part Job The decision you are really making
db Install, configure, start, stop, tear down the database on each node. Also collects logs. Are you testing the product or your deployment? Jepsen insists on installing from scratch every run so results are reproducible.
client Turn an abstract operation ({:f :write :value 3}) into a real request, and turn the response into :ok / :fail / :info. The error-classification decision from section 12. This is where tests are won and lost.
nemesis Inject faults. It is also a client — it receives operations from the generator and writes to the history — so faults are timestamped alongside data operations. Which failures do you believe your system survives?
generator Decide what operation happens next, on which process, and when the nemesis fires. Composable: (gen/nemesis ...), (gen/time-limit 60 ...), staggered rates. The concurrency/checkability trade-off from section 11.
checker Judge the history. Composable — one run can be checked for linearizability and for "no acknowledged write was lost" and for latency graphs. Which claim are you actually testing?
os / remote Set up the operating system; run commands on nodes over SSH. Infrastructure realism.

Two structural details worth pausing on, because they are easy to miss and they are load-bearing:

All timestamps come from one machine. Every client thread and the nemesis run on the control node, not on the database nodes. So the real-time ordering in the history is measured by a single clock. This is what makes the "these two operations did not overlap" claim in section 11 trustworthy even when the nemesis is deliberately skewing the clocks on the database nodes. Clock chaos on the cluster cannot corrupt the transcript.

The nemesis is in the history. Because faults are recorded as operations, every Jepsen report can say things like "the stale reads began 200ms after the partition started and ended 1.8s after it healed" — and that timeline is usually what tells the vendor where the bug is.

15 · THE NEMESIS — choosing faults on purpose

A "chaos monkey" that randomly breaks things is a weak test. Each fault type exists to attack a specific mechanism you have already studied. Here is the standard catalogue, with what each one is for:

:kill SIGKILL — process dies with no warning, no clean shutdown Durability: was it actually fsynced? Crash recovery acid
:pause / hammer-time SIGSTOP then SIGCONT — the process freezes, then resumes believing no time passed Lease and lock expiry. A frozen leader is the split-brain case that fencing exists for distributed-locking
:clock / clock-scrambler Jumps node clocks forwards and backwards Anything using wall-clock time for correctness: leases, TTLs, LWW conflict resolution, TrueTime imitations hybrid-logical-clocks
:packet Delay, loss, corruption, duplication of packets Timeout tuning, retry logic, duplicate delivery idempotency
:file-corruption (bitflip, truncate-file) Flips bits in data files; truncates them Checksums; "durable" meaning what you think; recovery from a torn write btree-and-lsm
:membership Adds and removes nodes during the run Reconfiguration, the hardest part of every consensus protocol raft

Two things to notice about this table.

First, :pause deserves special attention. It is the cheapest fault to run and it finds an enormous number of bugs, because a SIGSTOPped process is exactly a long garbage-collection pause — which happens in production constantly, without anyone injecting it. A node that freezes for 12 seconds and then resumes still believing it holds the lock is the canonical distributed systems bug, and your distributed-locking and split-brain labs both measured it. If you only ever inject one fault, inject this one.

Second, faults compose. Jepsen's nemesis.combined lets you throw partitions and pauses and clock skew simultaneously — the documentation's own phrasing is that it lets you throw "a broad array of simple failures" and see "what sticks". Real bugs frequently need two faults at once: a partition during a membership change, a pause during a leader election.

🔮 Predict: You are testing a system that uses leases — a leader holds authority for 10 seconds and must renew it. Which single fault from that table is most likely to break it, and what would you expect to see in the history?

Reveal

:pause (SIGSTOP) is the killer, and :clock is the accomplice.

A lease is a bet that my clock and yours advance at roughly the same rate. A SIGSTOPped leader does not notice that 12 seconds passed; it wakes up, sees a lease it believes is still valid, and writes. Meanwhile the rest of the cluster timed the lease out and elected someone else. That is two leaders, both sincerely believing they are entitled to write.

In the history you would expect: a window where the old leader's writes are :ok after the new leader's writes are :ok, followed by a read that shows one set of them vanished — an acknowledged-write loss, or a value going backwards as in section 11.

Clock skew attacks the same assumption from the other side: move a node's clock forward and its lease expires early; move it back and the lease outlives its grant.

The defence is the one your split-brain lab landed on: fencing tokens — the resource refuses work carrying an epoch older than one it has already served. Note that fencing does not stop the old leader from believing; it stops its writes from counting. Jepsen cannot detect belief. It detects effects — which is the only thing that was ever the problem.

16 · TRANSACTIONS BREAK KNOSSOS — and Elle is the answer

Everything so far judged single operations on single objects. That is the left half of your linearizability-vs-serializability 2×2 grid. Now take the other axis: transactions.

Two things go wrong at once.

Problem 1: the search explodes past all hope. Section 13's NP-completeness was survivable because linearizability is local — check each key separately. Serializability does not compose (you measured this: two locally-serializable banks plus a cross-bank transfer have no global serial order). So you cannot split the history by key. You must search orderings of whole transactions across all keys at once. That is hopeless at any useful scale.

Problem 2: you cannot see what happened. Consider a transaction that writes x = 5. Later another transaction reads x = 5. Fine. But if a third transaction also wrote x = 5, you now have no idea which one the reader saw. Register writes destroy the information you need. The history is under-determined not because of timing, but because of the datatype.

Elle's move, and it is genuinely clever

Elle (Kingsbury & Alvaro, VLDB 2020) attacks both problems with two ideas.

Idea one: change the datatype so writes stop destroying evidence.

Instead of registers, use lists, and the only write is "append a unique value". Now a read of x does not return one value — it returns the entire write history of x, in order:

read x → [1, 4, 9, 2]

That single observation tells you: the transaction that appended 1 came before the one that appended 4, which came before 9, which came before 2. One read recovers the complete write-write order for that key. Elle's own documentation calls list-append the workload with "the most powerful inference rules"; the rw-register workload is offered too, with "weaker inference" but "broader applicability".

This is the most reusable idea in the lab. If you ever need to make a system's behaviour observable, do not ask "how do I get better logging". Ask "can I choose a datatype whose reads reveal their own history?"

Idea two: stop searching for an order. Look for a cycle instead.

You are not required to find a serial order to prove one does not exist. Build a graph where the nodes are transactions and the edges are the orderings that must hold, then look for a cycle. A cycle means the required orderings contradict each other, so no serial order exists. Cycle detection is cheap. Searching permutations is not.

Elle infers three kinds of edge (these are Adya's dependencies, and Elle implements every non-predicate anomaly in that framework):

Edge Read as Inferred when
ww T1 wrote this key before T2 did With list-append: directly, from a read showing […a…b…]
wr T2 read what T1 wrote T2's read contains T1's appended value
rw T1 read a version older than the one T2 wrote — so T1 must come first T1 read [1], T2 appended 2. T1 did not see 2, so T1 precedes T2

That third one — the anti-dependency — is the subtle one and the one that catches the hard anomalies. It is a "must have happened before" that comes from what a transaction did not see.

The anomalies Elle names

These are exactly the ladder from your isolation-levels lab, now stated as graph shapes:

Name Graph shape Plain meaning
G0 Cycle of ww edges only Write cycle: two transactions wrote two keys in opposite orders
G1a — Aborted read: read a value from a transaction that failed
G1b — Intermediate read: read a value the writer later overwrote within the same transaction
G1c Cycle of ww/wr edges Circular information flow: T1 saw T2's write and T2 saw T1's
G-single Cycle with exactly one rw edge Read skew: saw some but not all of another transaction's effects
G2-item / G2 Cycle with two or more rw edges Anti-dependency cycle — the write-skew family

Elle also reports things that are not in Adya at all but indicate a broken system: duplicate writes (a value appended twice when the client appended it once — a retry bug), garbage reads (a value nobody wrote), dirty updates, and internal inconsistency (a transaction contradicting itself).

Open the simulator's Elle tab. It shows small transactional histories, the graph Elle would infer, the cycle highlighted, and the anomaly named. Then use the datatype toggle to switch from list-append to registers, and watch edges disappear — the anomaly is still in the system, but the evidence is gone. That toggle is the whole argument for Elle in one control.

✅ Checkpoint. You can now explain both checkers and why there are two of them: Knossos searches for an order over single-key operations; Elle searches for a cycle over transactions. The rest is production reality.

17 · WHAT A JEPSEN RESULT ACTUALLY MEANS

This section is short and it is the one people get wrong.

A red result is very strong

valid? false means: there exists a set of client-observable operations that no correct implementation could have produced. It does not depend on load, on hardware, on the phase of the moon. The counterexample is self-contained, and it is checkable by hand — as you did in section 11.

This is why Jepsen reports produce fixes rather than arguments. The vendor cannot say "works on my machine" to a history.

Two caveats that keep a red result honest:

  • The claim must be the vendor's claim. Finding that a system with readConcern: local returns stale data is not a bug; that is what local means. Every good report states the configured settings, and the interesting findings are the ones at the strongest settings.
  • The bug might be in the test. A client that misclassifies an error (section 12) can manufacture a false violation. This is why reports publish the test code and why vendors reproduce before fixing.

A green result is very weak

valid? true means: this workload, with these faults, at this concurrency, on this version, for this duration, did not produce a violation.

It does not mean the system is correct. It does not mean it is likely correct. Testing shows the presence of bugs, not their absence — and Jepsen is a falsification instrument, nothing more. Concretely, a green run is compatible with all of these:

  • the bug needs a fault you did not inject;
  • the bug needs two faults simultaneously;
  • the bug needs a longer run, or a larger cluster, or slower disks;
  • the bug is real but your client under-claimed and destroyed the evidence (section 12, S6);
  • the checker timed out and someone recorded that as a pass;
  • the workload never issued the operation that triggers it (no cas, no transactions spanning keys, no deletes).

The asymmetry is the whole point. Jepsen is built to falsify. If you want a positive claim about correctness you need a different instrument entirely — a proof, a model check (TLA+), or a deterministic simulation that can exhaustively explore a defined fault space. Jepsen deliberately does not pretend to be those.

Therefore: "Jepsen-tested" is not a certification

There is no pass mark. There is no badge. A Jepsen analysis is a dated report about a specific version — "MongoDB 4.2.6", "PostgreSQL 12.3", "NATS 2.12.1" — usually commissioned and paid for by the vendor, published in full including the bugs, and immediately out of date the moment a new version ships.

When a vendor's homepage says "Jepsen tested", the correct response is: which version, and what did the report say? Read it. The findings section is the interesting part, and it is always published.

18 · WHAT THIS HAS ACTUALLY FOUND

Some real, published results, chosen because each one teaches a different lesson. All are from jepsen.io analyses.

PostgreSQL 12.3 — even the boring, trusted, single-node database

Jepsen found that PostgreSQL's SERIALIZABLE isolation level allowed G2-item — an anti-dependency cycle — during normal operation, without any faults at all. The report's sentence: "PostgreSQL's 'serializable' isolation level isn't serializable: it allows G2-item during normal operation."

Every instance involved a read-write conflict on a freshly inserted row. The cause was a conflict-detection flaw that had been present for over a decade: the mechanism could attribute an updating transaction's own transaction ID to both the original and the updated version of a tuple, rather than the ID that originally created it. PostgreSQL developers wrote a patch and a regression test for the next minor release.

Lesson: this is not an exotic new distributed database. It is the most scrutinised open-source RDBMS in the world, its most conservative isolation level, no network faults, a decade-old bug. Nobody had checked — because until Elle there was no practical way to check.

MongoDB 4.2.6 — the settings you thought protected you

At the strongest settings the report tested (read concern snapshot, write concern majority), Jepsen observed read skew (G-single), cyclic information flow (G1c), duplicate writes, and transactions reading their own future writes — roughly 10% of transactions showed anomalies without faults. Two causes: the transaction API silently ignored database- and collection-level read/write concerns, defaulting to local and w:1; and a bug in the transaction retry mechanism. MongoDB patched the retry bug for 4.2.8.

Lesson: a system can implement a strong guarantee correctly and then fail to apply it, because the setting you configured was not the setting that took effect. Always test the configuration you actually deploy.

NATS 2.12.1 (December 2025) — crashes alone

Jepsen's NATS analysis reported that in JetStream version 2.10.22, process crashes alone could cause the total loss of a stream and all its data, with further data-loss and replica-divergence findings in 2.12.1 relating to file corruption and power failure.

Lesson: the humblest fault in the catalogue — :kill — remains one of the most productive. Durability claims are claims about fsync, and they are routinely wrong.

Others worth reading

Historically: Elasticsearch losing acknowledged writes under partition, Redis Sentinel's failover behaviour (which your redis lab measured), Kafka's unclean leader election, Cassandra's lightweight transactions, etcd/Consul, RethinkDB, and more recently Bufstream, Amazon RDS for PostgreSQL 17.4, and TigerBeetle 0.16.1. The archive is at https://jepsen.io/analyses and reading two or three end-to-end is worth more than another lab.

19 · PRODUCTION — should you run this, and how

Being honest about cost first: writing a good Jepsen test is a serious project. It is Clojure, it wants five machines (LXC, Docker, or VMs) plus a control node, and the hard part is not the framework — it is the error-classification work from section 12 and knowing which model to check against. A rough, credible test is a week; a good one is longer.

So here is the ladder, cheapest first.

Rung 1 — read reports (an afternoon, enormous return)

Pick the two databases you actually run. Read their Jepsen analyses. You will learn more about your production risk in three hours than from any amount of documentation, because the reports describe what the system does when it breaks, which the documentation never does.

Rung 2 — Maelstrom (a weekend, and genuinely fun)

Maelstrom is a workbench built on Jepsen for writing toy distributed systems. You write a node as a program in any language that reads JSON messages on stdin and writes them on stdout; Maelstrom simulates the network, routes messages, injects faults, and runs the real Jepsen checkers against the result.

This means you can experience the entire Jepsen machine — history, nemesis, Elle, a counterexample — without a cluster, without Clojure, and in Java. The Gossip Glomers challenge set (Fly.io, built with Kingsbury) is a guided sequence through exactly this: broadcast, a grow-only counter, a replicated key-value store, a transactional store.

Given the raft, crdts, and causal-consistency labs you already have, this is the natural next thing to actually do. Note that it does involve writing code — which is why it is a recommendation here rather than part of this lab.

Rung 3 — Elle standalone against your own system

You do not need all of Jepsen to use Elle. If you can make your application issue list-append transactions against your database and record a history in the right shape, Elle will check it. Several teams use exactly this to verify their ORM/connection-pool/proxy stack does not weaken the isolation the database provides — a real risk, since a pooler that reuses sessions or a read-replica router can quietly downgrade your guarantees below what the database offers.

This is often the highest-value thing to check, because the bug is usually yours, not the vendor's.

Rung 4 — a full Jepsen test

Worth it if you build or operate infrastructure that other teams depend on for correctness.

The neighbouring technique you should know exists

Jepsen tests a real system with real faults and non-deterministic results — so a bug found may be hard to reproduce. The complementary approach is deterministic simulation testing (DST): run the whole system on a simulated, seeded scheduler and network so that any run can be replayed exactly. FoundationDB pioneered it; TigerBeetle, Antithesis and others use it now.

Jepsen Deterministic simulation
System under test The real binary, real OS, real network Usually needs the code written for it
Reproducibility Hard — a rare bug may not recur Perfect — replay by seed
Retrofitting to existing software Yes, from outside Usually no
Fault space Whatever you inject Can be explored systematically

They answer different questions. Jepsen's superpower is that it needs no cooperation from the system under test — which is exactly why it can be pointed at someone else's database and produce a report they cannot dismiss.

20 · COMMON WRONG MODELS

❌ "Jepsen is a test suite you run to certify a database."

There is no suite and no certificate. Jepsen is a library for building a test for one system against one claim, plus a body of published analyses. Each analysis is a dated report on one version. Correct model: Jepsen is a falsification instrument and a report archive, not a benchmark or a badge.

❌ "Passing Jepsen means the system is correct."

A green run means "we did not catch it this time" (section 17). Correct model: red is strong evidence; green is weak evidence.

❌ "Jepsen tests network partitions."

Partitions are the famous fault and were the original one, but the catalogue in section 15 is much broader, and process pauses and crashes find more bugs than partitions do — because they are more common in production and attack timing assumptions directly. Correct model: the nemesis injects whatever you ask for, and partitions are one entry in a long list.

❌ "A timeout in the history is a bug."

No. A timeout under a partition is often correct. It is an :info, which is a statement about your knowledge, not about the system's behaviour. Correct model: errors and timeouts are data, not verdicts. Only the checker issues verdicts.

❌ "The checker compares results against expected values."

This is the deepest one, and the reason people build the wrong tool. There is no expected value. The checker searches for any explanation consistent with the model, and only reports a violation when none exists. Correct model: checking is a search for an explanation, not a comparison to an answer.

❌ "If I'm unsure whether an operation happened, marking it :info is the safe choice."

It is the sound choice only when you genuinely do not know. If the server told you it aborted, recording :info throws away a fact and makes the checker weaker — it can then explain away real bugs (section 12, S6). Correct model: record exactly what you know, no more and no less. Both over-claiming and under-claiming break the test, in opposite directions.

❌ "Elle is a linearizability checker for transactions."

Elle checks transactional isolation — serializability and the anomaly ladder below it — by cycle detection. Linearizability is a recency property about single operations and is Knossos's job. They live on different axes of the grid from your linearizability-vs-serializability lab, and Elle can also check the real-time variants (strict serializability) when asked. Correct model: two axes, two checkers.

❌ "A history where operations interleave weirdly is suspicious."

Concurrent operations are unordered; almost any result between overlapping operations is legal (section 11's reveal). Constraints come from operations that do not overlap. Correct model: the violation is never "this looks odd"; it is "no order exists".

Commonly confused with

  • Jepsen vs chaos engineering. Chaos engineering asks "does the service stay up?" — an availability question, usually in production, judged by metrics. Jepsen asks "is the data still correct?" — a safety question, in a lab, judged by a checker. Netflix's Chaos Monkey and Jepsen look superficially similar and answer opposite questions.
  • Jepsen vs fuzzing. Fuzzing hunts for crashes and memory errors from malformed input. Jepsen hunts for correctness violations from adverse timing and failure. Both generate randomly; only one has a formal model as its oracle.
  • Jepsen vs property-based testing. Closely related — Jepsen is a property-based test whose property is a consistency model and whose generator includes failures of the environment. The difference is the fault injection and the real cluster.
  • Knossos vs Elle. Order-search over single-object operations vs cycle-detection over transactions. Different axis, different algorithm, different cost.
  • Jepsen vs TLA+. TLA+ checks your design exhaustively; Jepsen checks your implementation by sampling. A system can be verified in TLA+ and still fail Jepsen, because the bug was in the code, not the design. Several have.

Jepsen — Exercises

Eight rungs, from saying it back in your own words to designing a test for a real system. None of them ask you to write code. Rungs 2 to 6 are checkable against visualization.html — open it and keep it open.

Worked answers are in SOLUTIONS.md. Attempt each rung first. Rungs 7 and 8 are discussions rather than single answers, so compare reasoning rather than checking a box.

Simulator reminders. Tab 1 (One register) has eight recorded runs, S1–S8, judged by three chips that differ only in how they read an :info. Tab 2 (Transactions) has six histories E1–E6 and one toggle: list-append vs register. The register always starts at 0; in the Elle tab, keys always start as empty lists.

Rung 1 — Explain

No simulator. Write the answers out; the point is to find the places where you can only gesture.

1.1 A colleague says: "we already have integration tests that check the data is right at the end. Why would we need Jepsen?" Give them three structurally different reasons, not one reason three ways.

1.2 Explain :ok, :fail, and :info to someone who has never seen them, in a way that makes clear why two outcomes are not enough. Then say what a checker is allowed to assume about each.

1.3 In one sentence each, say what a red Jepsen result means and what a green one means. Make the asymmetry between them explicit.

1.4 The lab claims a checker "searches for an explanation" rather than "compares against an expected value". Explain the difference to someone who writes ordinary unit tests, and say why the ordinary approach cannot work here.

1.5 Why does Jepsen permanently retire a process after it receives an :info? What would break if it did not?

Rung 2 — Identify

Read-off-the-screen questions. Open tab 1.

2.1 Run S2. Which two operations do not overlap, and what does that non-overlap force? Which single operation would you delete to make the history legal?

2.2 Run S3. Look at p1's bar. Why is it drawn dashed with an arrow running off the right edge rather than ending at t=8? State the modelling rule that arrow encodes.

2.3 Run S3 and read all three verdict chips. Which one is red, and which one does the page mark as Jepsen's? What is the practical consequence of shipping a test that behaves like the red one?

2.4 Run S7. Both writes are in flight when p3 reads. Which pairs of operations in this history are actually constrained relative to each other, and which are free? Give the rule you used.

2.5 Switch to tab 2 and select E4. Two edges are shown. One is derived from something a transaction read; the other from something it did not read. Which is which, and what is the second kind called?

Rung 3 — Predict

Commit to an answer before pressing anything.

3.1 In S4, p1's write timed out — the checker has total freedom about whether and when it took effect. Predict the verdict under Jepsen's reading, then run it. If your prediction was "valid", say exactly which fact defeats it.

3.2 In S6, the write is recorded :info and the later read returns 0. Before running: which of the three chips will be red? Then explain why the pattern here is the mirror image of S3.

3.3 Tab 2, E2 in list-append mode: predict whether Elle finds a cycle. Now predict what happens when you flip to register. Run both.

3.4 Tab 2, E5 (write skew): predict whether flipping to register mode hides this anomaly the way it hid E2's. Run it, then explain the difference in one sentence about what each anomaly's evidence depends on.

3.5 S8 with k=8: before dragging, predict roughly what factor separates the pruned and unpruned columns — 2×, 30×, 3000×? Then predict what happens to that factor at k=9, and say why you cannot check that on this page.

Rung 4 — Modify

Change one thing and say what breaks.

4.1 Take S2 and move p3's read so it starts at t=2 instead of t=5. Is it still a violation? Answer from the rule, then verify by reasoning through the checker's search by hand. What general principle about test design does this demonstrate?

4.2 Take S5 (a confirmed write, then a read of 0) and change the write's result from :ok to :info. You have now built S6. Which chip changes, and what does that tell you about where a Jepsen test's power actually comes from?

4.3 In S3, change p2's read result from 1 to 0. Work out all three verdicts by hand before checking your reasoning against the rules in the README.

4.4 Suppose Jepsen recorded only completion times and not invocation times — one timestamp per operation instead of two. Which scenarios in tab 1 could still be judged, and which become unjudgeable? What property of linearizability does the invocation timestamp carry?

4.5 In E4, suppose T2 had read y = [1] instead of y = []. Redraw the edges. Is there still a cycle? Name what T2 would then have observed.

Rung 5 — Trace

Do the checker's job by hand. Write the state after each step.

5.1 Run the linearizability search on S2 manually. At each step list the candidate operations (those not blocked by the real-time rule), the one you pick, and the register value afterwards. Show both branches dying.

5.2 Do the same for S7, and produce the winning order. Show at least one branch you had to abandon before finding it.

5.3 Trace Jepsen's handling of S6 explicitly as two branches: "the :info write took effect" and "it did not". Show why both branches are needed to reach the verdict, and which one succeeds.

5.4 For E3 (G1c), write out the two edges as sentences of the form "X must have committed before Y, because …". Then state the contradiction in one sentence without using the word "cycle".

Rung 6 — Spot the flaw

Each of these is a plausible design with a subtle defect. Find the smallest concrete scenario where it fails, and name the guarantee or property it violates.

6.1 A team writes their own checker. To keep it fast, they drop every :info operation from the history entirely — both the invocation and the completion — before checking. They argue this is conservative: "we're just ignoring the ones we're unsure about." Construct the smallest history where this produces the wrong verdict, and say in which direction it is wrong.

Jepsen — Solutions

Attempt EXERCISES.md first. Rungs 7 and 8 are worked reasoning, not single answers — if yours differs and survives the same scrutiny, yours is fine.

Rung 1 — Explain

1.1 Three structurally different reasons:

  1. It never attempted the thing you care about. The claim is about behaviour under failure. A test on a healthy cluster exercises the happy path and concludes nothing about the unhappy one.
  2. The final state is where the evidence isn't. Many violations — a stale read above all — are transient events that corrupt a decision and then vanish, leaving the final state perfect. Errors in opposite directions also cancel.
  3. "Right" is not a single value. A correct concurrent system has many legal outcomes and an incorrect one can produce a legal-looking outcome. Equality against a predicted value only works when the answer is deterministic.

1.2 A request either succeeded, definitely failed, or you never found out — and the third case is not rare, it is what every timeout is. :ok = definitely happened, has a logical effect. :fail = definitely did not, has no logical effect. :info = may or may not have, now or at any later time.

What the checker may assume: an :ok operation must appear in the linearization; a :fail operation must not; an :info operation may be placed or omitted freely, and if placed, may go anywhere from its invocation to the end of the history.

1.3 Red: there exists a set of client-observable operations that no correct implementation could have produced — a self-contained proof, independent of hardware or luck. Green: this workload, these faults, this concurrency, this version, this duration produced no violation. The asymmetry is falsification: a counterexample settles the question forever; its absence settles nothing.

1.4 A unit test knows the answer in advance and compares. A checker does not know the answer and cannot — there isn't one. It searches for any ordering of the recorded operations that a correct implementation could have produced, and only reports a violation when the search is exhausted. The ordinary approach cannot work because the set of legal outcomes is enormous and depends on timing you do not control.

1.5 Because the operation may still be in flight. If the same process issued a new operation and the old one landed afterwards, the history would contain two overlapping operations from a supposedly single-threaded process — breaking the one modelling assumption the whole search rests on. Jepsen burns the process number and starts a fresh one on the same thread.

Rung 2 — Identify

2.1 p2's read [1,3] and p3's read [5,7] do not overlap — p2 was finished two ticks before p3 asked. That forces p2's read to be linearized before p3's, which means the value went 1 → 0 with no write of 0 available. Delete either read and it becomes legal; the checker confirms that deleting p3 leaves a valid history. Three operations is the minimum for this violation.

2.2 Because an :info operation's interval is extended to the end of the history. The request may still be queued somewhere and take effect in ten seconds. Confining it to [0,8] would be claiming knowledge you do not have — and would make the checker reject histories that are actually fine.

2.3 Red: :info → it failed. Jepsen's is the middle one, :info → may or may not. The consequence of shipping the red one: it reports a violation every time a partition causes a timeout — which is every run — so within a week nobody believes the test, and the real violation, when it comes, is dismissed with the rest.

2.4 Constrained pairs are exactly those where one completed before the other was invoked:

  • w1 [0,10] before r4 [14,16] (10 < 14) ✓
  • w2 [2,12] before r4 (12 < 14) ✓
  • r3 [4,6] before r4 (6 < 14) ✓

Everything else overlaps and is free — in particular w1, w2 and r3 may be arranged in any order. The rule: A must precede B in the linearization if and only if A's completion is earlier than B's invocation. Overlapping operations are unordered.

2.5 T1 → T2 on x is a wr edge, derived from what T2 read (x contained T1's value 1). T2 → T1 on y is derived from what T2 did not read — it saw y = [], the version before T1 appended — so T2 must precede T1. That second kind is an anti-dependency (rw edge). It is the one that catches the hard anomalies, because it extracts an ordering from an absence.

Rung 3 — Predict

3.1 VIOLATION under all three readings. The fact that defeats "valid": only two values can ever exist here — the initial 0 and the single write of 1. Three non-overlapping reads saw 1, then 0, then 1, which requires the value to change twice. :info grants the write freedom; it grants the reads nothing, and three :ok reads are three hard facts.

3.2 Red chip: :info → it succeeded. Verified: fail=valid, ok=VIOLATION, jepsen=valid.

The mirror image of S3: there, the naive-restrictive reading manufactured a bug that did not exist (false alarm). Here, the correct reading lets a bug that does exist go unreported — because the client destroyed the evidence by recording a known success as unknown. S3 punishes over-claiming; S6 punishes under-claiming. And note the trap in S6: the red chip is "right" only by accident. Jepsen's verdict is correct given this transcript. The transcript is the defect.

3.3 list-append: G0, a write cycle. register: no cycle found — Elle reports a clean run against a database doing exactly the same wrong thing. Both ww edges came from reading x = [1, 2] and y = [1, 2], and a register read returns only the latest value, so the order of everything before it is unrecoverable.

3.4 Register mode does not hide E5. Both its edges are anti-dependencies derived from reading the initial (empty/nil) version of a key, and "I saw the version before you wrote" is just as visible with a register.

The one-sentence difference: E2's evidence is the order of past writes, which a register destroys; E5's evidence is the absence of a write, which a register preserves.

3.5 At k=8 the measured factor is 30.5× (109,601 unpruned vs 3,593 pruned). At k=9 it would be roughly 60–100× — the ratio has been doubling with each step (1.2, 2.0, 4.0, 10.1, 30.5). You cannot check it on this page because the slider is capped at 8: unpruned growth tracks k!, so k=9 is ~1M recursive calls and k=12 would hang the browser. That cap is the lesson, not a limitation of the page.

Rung 4 — Modify

4.1 No longer a violation. Verified valid; the checker's order is read→0 @p3 → write(1) @p1 → read→1 @p2. All three points sit inside their own bars, and the sequence is exactly what one register does.

The design principle: constraints come only from non-overlapping operations. A history in which everything overlaps everything is nearly unfalsifiable. This is why Jepsen keeps client concurrency low and deliberately staggers operations — a test that maximises concurrency maximises the checker's freedom to explain the results away.

4.2 The :info → may or may not chip flips from red to green — that is, Jepsen's own verdict flips. Verified: S5 is FFF (violation under all readings), S6 is TFT.

What that tells you: a Jepsen test's power comes from the client's honesty, not from the checker. The checker is a fixed piece of mathematics. The variable is how well the client library maps the database's responses onto :ok / :fail / :info. Get that wrong in the "safe-looking" direction and you have a green test over a broken database.

4.3 All three valid. With read → 0, the read is returning the initial value, and the write overlaps it, so the order read→0, write(1) works under every reading — including :info → it succeeded, where the write is forced into the history but is free to sit after the read. Under :info → it failed the write simply is not there.

4.4 Erasing invocation times destroys the real-time precedence relation entirely (no operation can be shown to have completed before another started). Measured consequence:

Scenario With invocation times Without
S2 stale read VIOLATION valid — invisible
S4 value changes twice VIOLATION valid — invisible
S5 lost acknowledged write VIOLATION valid — invisible
garbage read (value nobody wrote) VIOLATION VIOLATION — still caught

Every ordering violation becomes unjudgeable. Only value-provenance violations survive. The invocation timestamp carries the entire real-time axis of linearizability — the "time must not run backwards" half. Without it you are left checking little more than "did the database invent a value", which is a far weaker claim than any vendor makes.

4.5 If T2 read y = [1], it saw both of T1's appends. The rw edge T2 → T1 disappears (T2 no longer read a version older than T1's write), leaving only T1 → T2 on x. No cycle — the history is fine. T2 would have observed T1's transaction atomically: all of it rather than half of it. The anomaly in E4 was precisely the "half".

Rung 5 — Trace

5.1 — S2. Ops: w1=write(1)[0,9], r2=read→1 [1,3], r3=read→0 [5,7]. Value = 0.

Candidates initially: w1 (nothing completed before t=0) and r2 (nothing remaining completed before t=1). r3 is blocked, because r2 completes at 3 and 3 < 5.

  • Pick w1 → value 1. Remaining {r2, r3}; r3 still blocked by r2. Pick r2: wants 1, value is 1 ✓ → value 1. Remaining {r3}: wants 0, value is 1 ✗. Dead.
  • Pick r2 → wants 1, value is 0 ✗. Dead immediately.

No candidates left. Not linearizable.

5.2 — S7. Ops: w1=write(1)[0,10], w2=write(2)[2,12], r3=read→1 [4,6], r4=read→2 [14,16]. Candidates: w1, w2, r3. r4 is blocked by all three.

  • Abandoned branch: pick w1 → value 1; pick w2 → value 2; now r3 wants 1 but value is 2 ✗. Back up.
  • Winning branch: w1 → value 1; r3 wants 1 ✓; w2 → value 2; r4 wants 2 ✓.

Order: write(1) → read→1 → write(2) → read→2. Linearizable.

5.3 — S6. Ops: w1=write(1)[0,4] :info, r2=read→0 [8,10] :ok.

  • Branch A — "the write did not take effect": history is just r2. Value is the initial 0; r2 wants 0 ✓. Succeeds.
  • Branch B — "the write took effect": its interval becomes [0, ∞), so it is unconstrained. Place it after r2: order read→0, write(1) ✓. Also succeeds.

Both branches are needed in general because either alone can be the only one that works — S3 is rescued by branch B, S6 by branch A (and here also B). Jepsen returns valid if any branch succeeds, which is what makes it sound: it never convicts on an assumption it was not entitled to make.

5.4 — E3.

  • "T1 must have committed before T2, because T2 read x containing the value 1, and only T1 appended 1 to x."
  • "T2 must have committed before T1, because T1 read y containing the value 1, and only T2 appended 1 to y."

Contradiction without the word cycle: each transaction must have finished before the other one started, which is impossible.

5.5 — the extra history. Verified: VIOLATION under all three readings.

The reasoning that matters is the Jepsen branch where w2 = write(2) did take effect, since that is the permissive one. Its interval becomes [1, ∞), so it is completely free. But:

  • w1 completes at 6, before r3 is invoked at 8 → w1 must precede r3.
  • r3 completes at 9, before r4 is invoked at 10 → r3 must precede r4.
  • r3 returned 2, so the last write before it is w2.
  • r4 returned 1, so a write of 1 must fall between r3 and r4.

The only write of 1 is w1, and w1 is pinned before r3. There is nothing left to produce the 1 that r4 saw. Violation.

The trap: it is tempting to think a fully-unconstrained :info write can rescue anything. It cannot. Here the conviction comes from the pinned :ok write and the ordering of the two reads — the indeterminate operation is irrelevant to the proof.

Rung 6 — Spot the flaw

6.1 Smallest failing history is two operations — S3 itself: write(1) recorded :info, then read → 1. Drop the write and a client has read a value nobody wrote; the checker reports a violation against a database that did nothing wrong.

Direction: false positives only, never missed bugs — and you can prove that. "Drop all :info ops" is exactly Jepsen's mask = 0 branch. Jepsen returns valid if any branch succeeds, so dropping-everything valid ⇒ Jepsen valid. The naive strategy is strictly more restrictive, so it can only ever convict more often, never less.

That sounds harmless and is not: a checker that raises a false alarm on every timeout raises one every run, and a test nobody believes is worse than no test, because it occupies the slot where a real one would go.

6.2 The mishandled class is a definite, server-issued rejection delivered as an exception — "aborted", "constraint violation", "rejected: not the leader, nothing was written". Those are :fail, not :info. The catch (Exception e) lumps them in with genuine timeouts.

Smallest history where a real bug goes unreported (two operations):

process operation result recorded truth
p1 write(1) :info server explicitly replied aborted, no effect
p2 read() → 1 :ok —

With the truth recorded as :fail, this is a dirty/garbage read — the client read a value from an operation the database said it had rejected. That is a serious violation. With :info recorded, the checker reasons "the write may have happened after all" and returns valid. The bug is invisible.

The fix is unglamorous and is most of the work in a real Jepsen client: enumerate the database's error codes and classify each one deliberately, with a comment explaining why. :info is the correct answer only for genuine unknowns.

6.3 From 2.4: ordering constraints come only from operations that do not overlap. At 500 concurrent processes on one key, almost every pair of operations overlaps, so almost no pair is constrained, so the checker has near-total freedom to arrange them into an explanation. The extreme case: if every operation overlaps every other operation, any history whose values are individually producible is linearizable — the test can no longer fail for ordering reasons at all.

There is a second, independent cost: the search is exponential in concurrency (3.5), so the checker will also time out. You get a weaker test that takes longer to run.

6.4 Two independent reasons:

  1. Datatype. An rw-register workload has, in Elle's own words, weaker inference. As E2 demonstrates, whole classes of anomaly (anything whose evidence is the order of past writes) are structurally invisible to it. Finding nothing with registers is partly a statement about the instrument, not the system. Re-run with list-append.
  2. Falsification. Two weeks of green is the weak half of the asymmetry. It is consistent with: the bug needs a fault they did not inject, or two faults at once, or a longer run, or a client that under-claims, or a checker that timed out and was recorded as a pass.

The defensible sentence is: "Over N runs with faults X, Y, Z at concurrency C against version V, we observed no serializability violation." Everything stronger is not supported.

6.5 The smallest missed failure needs no clock error at all: a process pause. A leader SIGSTOPped — or GC-paused, or descheduled on a noisy host, or live-migrated — for 12 seconds wakes up believing its 10-second lease is still valid and writes, while the rest of the cluster has already elected a successor. Every clock in the fleet was within 200ms of correct the entire time. NTP has nothing to say about a process that was not running.

Two further gaps: "synchronised within 200ms" is an assertion about the healthy case, not a bound the system enforces — a failed ntpd, a VM snapshot restore, or a leap-second handling bug produces unbounded skew with no alarm; and NTP corrects by stepping the clock, so a node can observe time jumping backwards, which breaks any code that assumes monotonicity. If you take a lease's expiry from the wall clock and have no fencing at the resource, this is your outage.

Rung 7 — Handle failure

7.1 — before blaming the vendor. In priority order:

  1. Error classification. The most likely defect and the easiest to make. Audit every path that produces :ok and :fail: is each one definitely true? Rule out by re-running with the suspect operations forced to :info — if the violation survives, it did not depend on your classification.
  2. Configuration. Are you running the consistency settings you think you are? The MongoDB 4.2.6 finding was partly a case of settings silently not applying. Rule out by asserting the effective settings from inside a session at runtime, not from the config file.
  3. Whose claim is it? Check that the model you are checking is the one the vendor promises at these settings. A stale read at a weak read concern is not a bug.
  4. The nemesis exceeded the contract. If you killed 3 of 5 nodes, a system promising minority tolerance owes you nothing. Check what the fault actually did, not what you meant it to do.
  5. Clock on the control node. Your real-time ordering is only as good as that one clock. Confirm nothing is stepping it during the run.

Only then: minimise the history, reproduce, and file.

7.2 — the checker that did not finish.

Why "pass" is wrong: the checker returned no verdict. valid? true means a search completed and found an explanation; a timeout means the search was abandoned. Recording "unknown" as "pass" is the same error as recording a definite failure as :info — throwing away the distinction between knowing and not knowing, which is the one thing this entire methodology exists to preserve. Report it as indeterminate and treat it as a broken test run.

Three changes, each with its price:

Change Why it helps What you give up
Shorten the run (60s not 30min) and do many more of them Cost is superlinear in history length; ten short histories check far faster than one long one and cover more fault timings Bugs that need a long build-up — log growth, compaction, disk filling — become unreachable
Cut client concurrency (5 processes, not 50) Search cost is exponential in overlap; also makes the history more constrained and therefore stronger (6.3) Fewer simultaneous races; some concurrency bugs need many writers
Spread over more keys and check each key independently Linearizability is local, so per-key checking is sound and turns one huge problem into many tiny ones Nothing for linearizability — this one is nearly free. It is not available for serializability, which does not compose; there you must move to Elle

A fourth, if the claim allows it: switch from Knossos to Elle with a list-append workload. Cycle detection is polynomial; permutation search is not.

7.3 — two claims, two tests.

"Acknowledged writes are never lost" — this is a durability/availability claim, not a recency one, and it does not need a linearizability checker at all. Workload: a grow-only set — clients add unique elements and, at the end, one client reads the whole set. Checker: a set checker comparing acknowledged adds against the final read. Faults: :kill (does fsync mean what they say), partitions, and membership changes. Counterexample: an element whose add returned :ok and which is absent from the final read. This is a cheap, fast, extremely productive test and it is where I would start on any system. Note the deliberate design: elements added with :info are excluded from the "must be present" set but permitted to appear — the same three-outcome discipline, applied to a set.

"Reads never return uncommitted data" — this is an isolation claim at transaction scope. Workload: list-append transactions. Checker: Elle, watching for G1a (aborted read) and G1b (intermediate read). Faults matter less: as PostgreSQL 12.3 showed, isolation bugs often appear with no faults at all. Counterexample: a read containing a value appended by a transaction that returned :fail.

7.4 — making an irreproducible finding persuasive. Send:

  1. The history file itself — the raw log of every invocation and completion with timestamps. This is the evidence; everything else is commentary.
  2. The minimised counterexample — the smallest set of operations that cannot be explained, with the constraint written out as in section 11 of the README. A vendor can verify three operations by eye in a minute; they cannot verify 20,000.
  3. The nemesis timeline, aligned to the anomaly: "partition started at 14.2s, healed at 21.7s, first bad read at 22.1s." Because the nemesis writes into the same history, this alignment is free — and it is usually what tells the vendor which code path to look at.
  4. The exact version, configuration, and effective consistency settings.
  5. The complete test code, so they can run it themselves.
  6. The failure rate — "1 in 40 runs" is information, not an apology. It tells them how narrow the window is, which is a clue about the mechanism.
  7. Their server logs for the window, which Jepsen collects from every node.

What makes it persuasive is that (1) and (2) together are checkable without trusting you or your tooling. That is the whole reason this methodology produces fixes rather than arguments.

Rung 8 — Design

8.1 — Spring Boot + PgBouncer + read replica.

The key insight to state first: you said you trust PostgreSQL, and you should — but the guarantee you get is the weakest link in the path between your code and the storage engine, and you have deliberately installed two components in that path that can weaken it. The bug you are hunting is almost certainly yours, not PostgreSQL's.

Where the guarantee is likely lost:

  • The read replica. Replicas are asynchronous. A transaction routed to a replica reads a stale snapshot. Your linearizability-vs-serializability lab's F1 exactly: the result may still be serializable (there is an order that explains it) while being badly stale. If your routing layer sends reads to a replica and writes to the primary within one logical unit of work, you have built read skew into the architecture.
  • PgBouncer in transaction mode. Server connections are handed back to the pool at each commit. Anything whose scope is the session rather than the transaction — SET TRANSACTION ISOLATION LEVEL issued once at connect, session-level advisory locks, prepared statements, SET variables — can silently apply to the wrong connection or be lost. A service that sets SERIALIZABLE at connection setup may be running at READ COMMITTED.
  • Spring's @Transactional. Boundaries are a declaration. Reads outside the annotation, a readOnly = true that routes to the replica, or a lazily-initialised entity loaded after commit all put operations outside the group the database was asked to protect. Your isolation-levels lab's central point: the guarantee cannot protect a group it was never told about.

Workload: list-append over a small key space (say 8 keys), transactions of 2–4 operations mixing reads and appends, issued through the real application stack — your repository layer, your @Transactional boundaries, your pool, your router. Not through a raw JDBC connection. The whole point is to test the stack, not the database.

Checker: Elle, list-append, checking serializability — and also the strict variant, because a stale replica read is invisible to plain serializability and is probably your most likely real defect.

Do you need a nemesis? Not at first, and this is the important answer. PostgreSQL 12.3 and MongoDB 4.2.6 both produced anomalies with no faults at all. Configuration and pooling bugs are steady-state bugs. Run clean first; if that is green, add replica lag (the most realistic fault here), then :kill on the primary to exercise failover.

Assert the effective isolation level at runtime from inside a transaction, not from config. That single check catches the PgBouncer class of bug on its own.

In production, monitor: replication lag as a correctness signal rather than a performance one, with an alert threshold derived from what your reads can tolerate; serialization-failure retry counts (a sudden drop can mean you silently stopped running at SERIALIZABLE); and the fraction of transactions routed to replicas.

8.2 — a world with no :info.

Both errors from section 6 become unavoidable rather than optional, because the client is forced to guess on every timeout, and the guess is wrong roughly half the time.

  • False positive: guess :fail on a write that actually landed. A later read returns the value, the checker sees a value nobody wrote, and reports a violation against a healthy database. This is S3, and under partition it happens constantly.
  • False negative: guess :ok on a write that never landed. The checker now must place it in the order, which is usually harmless — but the mirror case is the real danger: an acknowledged write recorded as :fail because the ack was lost. Now the checker cannot see that a genuinely lost write was ever promised, and the system's central durability claim becomes untestable. This is S6 without any option to do better.

Which is worse: the false negative. A false positive is loud — you investigate, find your own bug, fix the client. A false negative is silent, and it converts a safety test into a ritual. The deeper point is that :info is not a convenience: without it, the framework cannot represent the actual epistemic state of a network client, and a tool that cannot represent what you know cannot reason correctly about it.

8.3 — four hours a night against a Raft key-value store.

Rank Fault Reasoning
1 :pause / hammer-time Cheapest to run, closest to a real production event (a GC pause or a descheduled process), and attacks the assumption Raft leases and leader liveness rest on. Assumption it encodes: a leader can stop executing for longer than its election timeout, and production will do this to you without being asked.
2 :kill + restart Directly tests durability — whether the log was actually fsynced — and crash recovery, which is the least-exercised code path in most systems. NATS 2.10.22 lost entire streams to this alone. Assumption: processes die abruptly and must recover from disk, not from memory.
3 partition-majorities-ring Nastier than plain halves precisely because every node sees a majority — it breaks the common shortcut "I can see a majority, therefore I am the only leader". Assumption: partitions are not always clean two-way splits.
… partition-random-halves, :membership, :packet Valuable, especially membership changes (the hardest part of Raft), but slower to run and to diagnose
Bottom :clock Raft's safety does not depend on wall-clock time — only its liveness does. Clock skew should cause elections and unavailability, not data loss. Worth running occasionally to confirm exactly that, but it should find little. If it finds a safety bug, someone put a lease or a timestamp somewhere it does not belong — which is worth knowing, just not nightly.
Bottom :file-corruption Real and serious, but slow, noisy, and usually diagnosed as "checksums missing" once rather than nightly. Run it quarterly.

The general principle for ranking: inject the faults production will inject anyway, in rough order of how often production does it. Exotic faults find exotic bugs; pauses and crashes find the ones that will actually page you.

8.4 — when Jepsen is the wrong instrument.

  1. A property with no finite counterexample — liveness. "The cluster always eventually elects a leader" cannot be falsified by any finite history: no matter how long you waited, it might have elected one a second later. Jepsen can only measure availability (how long it was down), which is a different, weaker statement. Use a model checker such as TLA+ for the design-level liveness argument, and SLOs plus production monitoring for the operational one. Your flp-impossibility lab explains why the theoretical version of this question has no answer at all.

  2. A rare bug you need to reproduce, not just find. Jepsen's non-determinism is the price of testing the real binary. Once a bug appears once in forty runs, Jepsen is a poor debugging tool — you cannot replay it. Deterministic simulation testing (FoundationDB, TigerBeetle, Antithesis) replays exactly from a seed, at the cost of needing the system built for it. The two are complements: Jepsen to find it from outside, DST to hold it still while you look at it.

Also defensible: single-machine data-structure correctness (use property-based testing — faster and exhaustive-ish); security properties (a different threat model entirely); and performance regressions (Jepsen deliberately runs at low concurrency, so its latency numbers are not a benchmark).
