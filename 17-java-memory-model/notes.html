Lab 17 · The JVM Underneath: One Machine, Many Threads

The Java Memory Model — the rules that decide which of your writes another thread is allowed to see

Tell a friend: Ana and Ben share one whiteboard in a stockroom. Ana rubs out the number and writes a new one, and Ben can carry on reading the old one — not for a moment, for ever. Nobody made a mistake. The compiler is allowed to give Ben a private copy in his pocket. The CPU is allowed to leave Ana's new number in her out-tray. Both are legal, because each of those workers alone still sees a sensible story. The Java Memory Model is the short list of handshakes that force those two to line up, and happens-before is its name for "you must see what I did". Skip the handshake and you do not have a slow program or an unlucky one. You have a program whose answer the language declines to define.

Step the two threads yourself in Store Buffer Theatre: visualization.html — every button is a legal next move. What this lab is made of, and which command printed which number, is section 22.

BEGINNER MODEL — sections 1 to 8

1. Why isn't "the same variable in the same program" enough?

In one breath: Two threads sharing one field feels like two people sharing one whiteboard. It is not. Each of them may be reading a private copy, and each may be writing into a tray that nobody has emptied yet.

You already know this stockroom. In java-multithreading, Ana and Ben each added a box of paper and each wrote the new total on the whiteboard. Both read 10, both wrote 11, and one box vanished from the record. That bug was about overlap: two people doing a three-step job at the same time.

This lab is about something worse, and it starts with a question that sounds silly.

When Ana writes 11 on the board, is Ben looking at the board at all?

Meet the third person in the building. Omar is the efficiency manager. His whole job is to make the work faster, and he has exactly one rule:

Rearrange the work however you like, as long as a person working alone ends the shift with the same answer.

That rule is not a loophole. It is the deal that makes fast code possible. Engineers call it as-if-serial semantics: the optimiser must preserve what a single thread would compute, and it owes nothing at all to anybody else.

Read the next table as three things Omar is allowed to do. The middle column is why a solo worker never notices. The right column is what it does to a second worker in the room.

What Omar does Why a solo worker cannot tell What it does to a second worker
copies the board's number onto Ben's notepad once, then has him reuse it nobody else changes the board on a solo shift Ben never sees Ana's update, ever
lets Ana drop her new number in an out-tray and walk away the tray reaches the board eventually the board is stale while the tray is full
swaps two of Ana's unrelated steps the end state is identical Ben sees them in the swapped order

Those three rows are the whole lab. Everything after this is one of them, made concrete, with a command you can run.

And notice what none of them is: a bug. Every row is the optimiser doing its job correctly. The problem is that you were reasoning as if there were one whiteboard and no trays.

2. What did Ana and Ben leave unfinished in the last lab?

In one breath: The last lab found two separate promises hiding inside one bug. It nailed the first one and pointed at this lab for the second. This is the second.

java-multithreading ended up with two questions, and it was careful to keep them apart.

  1. Can Ana and Ben both be inside the stockroom at once?
  2. Is either of them guaranteed to see what the other did?

A lock answers both. volatile answers only the second. And the second question never got a precise answer in that lab — it got a name, happens-before, and a pointer to this door.

So this lab has one job: turn "is either guaranteed to see the other" into a rule you can apply to a specific piece of code and get a yes or a no.

3. Can Ana write on the board and Ben never see it?

In one breath: Yes. Not "after a delay". Never.

Ben's job today is simple. Keep counting until the board says stop. Ana will write stop on the board in a second or so.

Omar looks at Ben's loop and notices something true: Ben's loop never changes the board. So why should Ben walk to the board a billion times? Omar has him copy the value onto his notepad once, before he starts, and check the notepad each time round instead.

Ben is now roughly a hundred times faster and permanently wrong.

The experiment is Visibility.java. One field, plainFlag, is a plain boolean. The same field declared volatile is volatileFlag. A worker thread spins on whichever one you picked. The main thread waits one second, writes true, then waits three more seconds and reports.

🔮 Predict. The main thread writes true at one second and then waits three whole seconds. What does the plain worker do? (a) stops immediately · (b) stops within a few milliseconds · (c) is still spinning three seconds later.

./run.sh Visibility plain            # the plain boolean
./run.sh Visibility volatile         # the same field, declared volatile
./run.sh -Xint Visibility plain      # plain again, with the JIT switched off

The answer is (c), and the program says so out loud. Here is what those three commands printed on one run.

Command How the flag was declared What the worker did What that tells you
Visibility plain plain boolean still spinning 3 s after the write the load was lifted out of the loop; it will spin for ever
Visibility volatile volatile boolean exited after 1,820,894,830 spins picked up on the very next pass of the loop
-Xint Visibility plain plain boolean exited after 147,698,840 spins same source, same CPU, only the optimiser changed

If you guessed (b), you were thinking about cache latency — the small delay before one core's write shows up in another core's cache. That delay is real and it is measured in nanoseconds. It is not what happened here. Caches are coherent: they agree with each other automatically, and quickly. What happened here is that Ben never read a cache at all. He read his notepad.

The engineers' name for Omar's trick is hoisting the load out of the loop, and the notepad is a CPU register. Once the value is in a register, no cache, no bus and no other core can change it. Only Ben's own code can.

4. Why did switching the optimiser off fix the program?

In one breath: Because the bug was never in the source you wrote. It is in the faster program the optimiser is allowed to build out of your source.

-Xint tells the JVM to interpret every bytecode and never compile anything. Omar goes home. Ben walks to the board on every single pass. The program is maybe a hundred times slower and completely correct.

Stare at rows one and three of the table in section 3 until it is uncomfortable. Same file. Same laptop. Same JVM. One is correct and one hangs for ever, and the only difference is whether the optimiser was allowed to work.

That is why "it worked on my machine" is not evidence of correctness here. It is evidence about one optimiser's mood on one afternoon.

🔮 Predict. Your service hangs in production. You add a System.out.println inside the spinning loop to see the stale value. What happens to the hang?

It usually disappears. Two reasons, and neither is the one people expect. System.out is a synchronized stream, so the print itself is a handshake of the kind section 10 lists. And a loop with a call in it is no longer simple enough for Omar to rewrite the way he wanted to.

If you predicted "the print will show me the stale value", you assumed the print is a passive observer. It is not. It joins in, and it fixes the thing you were trying to watch.

A bug that vanishes when you look at it has a name: a heisenbug. Almost every memory-model bug is one. Almost every debugging tool you would reach for adds synchronisation or defeats an optimisation: a print, a breakpoint, a sleep, a profiler attach.

The practical rule that falls out of this: never let a print statement, a sleep, or a debugger be your fix. They change the odds. The rules in section 10 change the guarantee.

5. Can both of them read the old number, when both wrote first?

In one breath: Ana writes her number, then reads Ben's. Ben writes his, then reads Ana's. Both can come away with zero. No ordering of those four steps explains that.

Two boxes on the board, one for Ana and one for Ben. Both start at 0. Each of them does exactly two things, in this order.

Ana does Ben does
write 1 in her own box write 1 in his own box
read Ben's box, remember it read Ana's box, remember it

Now reason about it the way everybody naturally does. Assume the four steps get shuffled together in some order, but that neither person's own two steps swap places. There are only three shapes of answer.

How it played out What Ana read What Ben read
Ana finished completely first 0 1
Ben finished completely first 1 0
they interleaved 1 1

There is no shuffle at all that gives 0 and 0. For Ana to read 0, she must have read before Ben wrote. For Ben to read 0, he must have read before Ana wrote. But each of them wrote before they read. It is a flat contradiction.

🔮 Predict. Reordering.java runs that pair of threads a million times and counts the outcomes. How many times does 0-and-0 come up? (a) never · (b) a handful · (c) tens of thousands.

./run.sh Reordering volatile            # the same variables, declared volatile
./run.sh -Dtrials=5000000 Reordering plain

6. Where does the impossible answer actually come from?

In one breath: Ana's write never went to the board. It went into her own out-tray, and she walked away without waiting.

Writing to memory is slow. A core that waited for every write to land in the shared cache line would spend most of its life stalled, on the order of a hundred cycles at a time. So it does not wait. It posts the write into a small private queue and carries straight on. That queue is the store buffer, and it is Ana's out-tray.

Two things about the out-tray decide everything in section 5.

  • Ana can read her own out-tray. If she looks up her own number, she gets the new one even though the board still shows the old one.
  • Nobody else can read Ana's out-tray. Ben sees the board, and only the board.

Now replay the four steps with the tray in the picture.

The stores never sit in a tray. A volatile write forces the core to drain its whole buffer to memory before it is allowed to run another instruction, so steps 3 and 4 read numbers that are already on the board. The forbidden row stays at zero no matter how you click. If you predicted "it becomes rarer", you have the model backwards: this is not a probability being lowered, it is a move being removed from the board.

One more thing to hold on to. Sections 3 and 5 are two different machines producing two different symptoms, and people merge them constantly.

Who did it What they did Which experiment showed it What stops it
the JIT compiler kept the flag in a register for the life of the loop Experiment 1, section 3 volatile forbids caching the field in a register
the CPU core let a store sit in its own private buffer Experiment 2, section 5 a volatile write drains the buffer before continuing

Neither of those is "the CPU running your lines out of order", which is the phrase everybody reaches for. Out-of-order execution is real and it is a third mechanism again. The model does not care which of the three did it. It defines what you are allowed to observe, and leaves the implementers to hit that target however they like.

7. So is volatile the fix for everything?

In one breath: No. It fixes whether you can see a value. It does nothing about somebody changing that value between your read and your write.

Back to the original stockroom bug. Eight workers, each adding one to the board a million times. The board should end on eight million.

The experiment is LostUpdate.java, and it has four modes.

🔮 Predict. The counter is declared volatile long. Every read and every write now goes to real memory. What does the board say at the end? (a) exactly 8,000,000 · (b) a bit under · (c) wildly under.

./run.sh LostUpdate plain
./run.sh LostUpdate volatile
./run.sh LostUpdate synchronized
./run.sh LostUpdate atomic

The answer is (c). One run of all four modes:

Mode Final total Increments lost Share lost Elapsed
plain 1,954,887 6,045,113 75.6% 69 ms
volatile 2,237,736 5,762,264 72.0% 328 ms
synchronized 8,000,000 0 0% 1,254 ms
atomic 8,000,000 0 0% 302 ms

Look at the volatile row twice. It lost nearly six million increments and it took nearly five times as long as the plain version. It paid the entire bill and bought nothing.

Why? Because count++ is not one action. It is three:

  1. read the board into a register,
  2. add one in the register,
  3. write the register back to the board.

volatile makes step 1 and step 3 hit real memory. It does absolutely nothing about the gap between them. Two workers can both read 41, both compute 42, and both write 42. Two increments happened and the board moved by one.

If you predicted (a), you merged two promises that the model deliberately keeps apart. Visibility is "does my write ever reach you". Atomicity is "can anyone observe my job half-done". volatile sells the first one only.

Two more things from that table are worth carrying. The atomic version was about four times faster than the lock on this run, because a compare-and-set retries in user space instead of parking a thread. And synchronized, the slowest of the four, was still finishing eight million contended increments in about 1.25 seconds — "correct" is rarely as expensive as people fear.

INTERMEDIATE MODEL — sections 9 to 12

9. What promise does the model actually make?

In one breath: The model never promises that threads see each other's writes. It promises something narrower and far more useful: make one specific kind of handshake, and everything you did before it is visible after it.

Here is the rule of the building, written on the stockroom door.

When you take the key from someone, you must first go and read the board. Before they hand it over, they must first empty their out-tray.

That is the whole idea. The handshake is what drags the memory along with it. Without a handshake, Ana's work and Ben's work are simply two unrelated piles of events, and nothing connects them.

Engineers call the relation happens-before, and it is the single most important term in this lab. Said in words first:

If Ana's action happens-before Ben's action, then every write Ana made before that point is guaranteed visible to Ben after it. And no optimiser is allowed to move Ben's action in front of Ana's.

Only now the shape of it. It is written A → B, read aloud as "A happens-before B". Three properties, and each of them is doing work.

Property In words In the stockroom
program order your own steps are ordered with each other Ana's second step is after her first
transitivity if A is before B and B is before C, then A is before C Ana hands to Ben, Ben hands to Dev, Dev sees Ana's work
partial order most pairs of actions are ordered by nothing at all Ana and Ben on separate jobs are simply unrelated

That third row is the one people never believe, so say it plainly. Most pairs of actions in a running program have no order between them, and that is legal. The model is not a timeline with some gaps. It is a sparse graph of edges you deliberately created, floating in an enormous cloud of events that are related to nothing.

🔮 Predict. Ana writes to a plain field at 10:00:00 exactly, by the clock on the wall. Ben reads that field at 10:00:05, five seconds later. Is Ben guaranteed to see Ana's value?

No. Five seconds of wall clock creates no edge whatsoever. Ben has an excellent chance in practice, which is precisely what makes this so dangerous — it will work in every test you write.

If you said yes, you used a clock. There is no clock in the model. Time is not one of the things happens-before is made of. This is the exact point that causal-consistency picks up and carries across a network, where wall clocks stop being merely irrelevant and become actively harmful.

10. Which handshakes create the promise, and which only look like they do?

In one breath: There is a short list of things that create an edge. Everything on the list works. Everything not on the list is a coincidence that your tests will reward you for believing.

Read this table as: if the left column happened, the right column is guaranteed. These are the edges you will actually use.

The handshake In the stockroom What it guarantees
release a monitor, then acquire the same monitor Ana hangs the key back, Ben takes it everything Ana did before letting go is visible to Ben after he takes it
write a volatile field, then read that same field Ana writes in permanent ink, Ben reads that spot everything Ana did before the write is visible to Ben once he sees the new value
Thread.start() Ana hires Ben everything Ana did before starting him is visible to Ben from his first instruction
Thread.join() returning Ana waits for Ben to clock off everything Ben did is visible to Ana once the wait returns
the end of a constructor, for final fields Ana pins a finished card to the board section 14
interrupting a thread Ana taps Ben on the shoulder the interrupt is visible to whatever detects it

Now the look-alikes. Every row here is something engineers say out loud in code review, and every one of them is wrong.

What people believe Why they believe it What is actually true
"a Thread.sleep gives the write time to land" it nearly always does sleeping creates no edge at all; it changes odds, not rules
"the value printed, so it arrived" it did print the print synchronizes on the stream and hides the bug (section 4)
"they both take a lock, so they are ordered" both are locks an edge exists only between threads using the same monitor
"later on the wall clock means visible" it looks sequential there is no clock (section 9)
"reading a volatile orders everything for me" it orders a lot only what the writing thread did before that write

The transitivity row deserves a worked example, because it is where the rule earns its keep. Bring in Dev, a third worker on a later shift.

  1. Ana writes three numbers on scrap paper, then writes ready in permanent ink. Her three plain writes are before her ink write, by program order.
  2. Ben reads the ink, sees ready, and therefore sees all three numbers. That is the volatile edge.
  3. Ben then takes the stockroom key, does some work, and hangs it back.
  4. Dev takes the same key later. That is the monitor edge, so Dev sees Ben's work — and by transitivity, Ana's three numbers too.

Dev and Ana never interacted. Ana may have clocked off before Dev arrived. The guarantee still holds, because there is an unbroken chain of edges between them. That chain is the only reason it holds, and if you break any link in it the guarantee evaporates silently.

11. What does one volatile field actually buy?

In one breath: Four separate things. People buy one of them and assume they got all four, which is why the word has such a bad reputation.

Ana's permanent ink does four jobs at once. Here they are one at a time.

One: every read and write really touches memory. No register copy, no hoisting out of a loop. That is Experiment 1 in section 3, and it is the job most people know about.

Two: the read and the write are indivisible, even for 64-bit values. A plain long or double is allowed to be written in two halves, so another thread can legally read a value made of the top half of one write and the bottom half of another. Declaring it volatile forbids that. This is a real rule of the specification, not a hardware detail, and it is the one part of volatile that has nothing to do with ordering.

Three: release on write, acquire on read. No write you made before the volatile write can be moved after it. No read you make after the volatile read can be moved before it. Those two halves are what make the handshake in section 10 work at all.

Four: the piggyback. This is the one worth paying attention to. Plain writes made before a volatile write ride along with it. Any thread that reads that volatile field and sees the new value sees those plain writes too.

Rule four has a test of its own. In Tests.java, a writer sets three plain integers and then sets one volatile boolean gate. A reader spins on the gate and, the moment it sees the gate open, checks whether all three integers are the ones it expected.

🔮 Predict. Two hundred thousand rounds of that. How many times does the reader see the gate open but a stale number behind it?

Zero. Not "almost never" — the model forbids it, and the test is written as an assertion for exactly that reason. If you guessed "rarely", you treated the model as a probability distribution. It is a list of prohibitions.

Reordering.java is quietly the same trick, used for real. Its two threads coordinate through a pair of volatile ticket counters. One thread writes its result into a plain field and then bumps its volatile ticket; the other reads the volatile ticket and then reads the plain field. That is rule four doing the work, and it is why the harness can count outcomes correctly while measuring a race. The tool that catches the bug is built out of the fix.

And here is what volatile does not buy, stated as flatly as possible.

It does not give you Because Reach for
atomic read-modify-write count++ is three steps and the gap is unguarded AtomicLong, or a lock
mutual exclusion it never blocks anybody synchronized, or ReentrantLock
an invariant across two fields each field is ordered on its own a lock around both

Finally, the bill. A volatile write costs a fence, and a fence is not free. Both figures below come from the same experiments you already ran, comparing the same work with only the declaration changed.

Same work, two declarations plain volatile Where the gap comes from
8 threads × 1M increments, section 7 69 ms 328 ms every read and write forced to real memory

12. What is a data race, and why is "undefined" the honest word?

In one breath: Two threads touch the same field, at least one of them writes, and no handshake orders them. At that point the language stops telling you what your program does.

Three conditions, all of which must hold:

  1. two threads access the same memory location,
  2. at least one of those accesses is a write,
  3. the accesses are not ordered by happens-before.

That is a data race. Notice what is not in the definition. Nothing about frequency. Nothing about timing. Nothing about how many cores you have. It is a property of the program text plus the edges in it, and you can decide whether you have one by reading.

Now, what does "undefined" mean here? Java is not C++, and the difference matters enough to be precise about.

What you are protected from, always What you lose when you race
values that were never written by anybody any guarantee about which written value you get
memory corruption, wild pointers, a crashed VM any guarantee about the order you see writes in
the type system being violated any guarantee that you ever see a write at all

So the honest phrasing is not "your program becomes random". It is this:

A data race does not make your program slow, or unlikely to work. It makes the set of answers the language permits larger than the set you reasoned about.

You reasoned about the three rows in section 5's shuffle table. The language permits a fourth. Your program is not wrong on 6% of runs; your model is wrong on 100% of them, and 94% of the time that does not show.

And now the deal the model offers you in exchange, which is the single most useful sentence in the whole specification:

If your program contains no data races, it behaves exactly as if it were sequentially consistent.

Engineers write that as SC-DRF: sequential consistency for data-race-free programs. In plain words: put the handshakes in, and your naive interleaving intuition becomes correct again. You do not have to think about store buffers and hoisting in day-to-day code. You have to think about them exactly long enough to make sure every shared field is reached through an edge — and then you get your simple mental model back, with a guarantee behind it.

That is the bargain. The whole of the Java Memory Model exists to make that one sentence true.

One more distinction, because these two terms are constantly swapped.

What it is Can you have one without the other?
data race unordered concurrent access, at least one a write yes — a correctly locked program can still be logically wrong
race condition the result depends on timing nobody controls yes — check-then-act on a ConcurrentHashMap has no data race and is still broken

A data race is a mechanical property you can check. A race condition is a bug in your reasoning about your own invariants. Fixing the first does not fix the second.

ENGINEERING MODEL — sections 13 to 17

13. How do you hand a finished object to somebody else?

In one breath: Building an object is several writes. Publishing it is one more. Nothing about a plain field forces the building to land before the publishing.

Ana fills in a stock card. Three boxes on it, all of them getting the same number today. Then she pins the card to the board where Ben can reach it.

From Ben's side that is one action: there is a card, take it. From the machine's side it is four:

  1. get a blank card,
  2. write the first box,
  3. write the second box,
  4. pin the card to the board.

Step 4 is a plain write of a reference. Steps 2 and 3 are plain writes of fields. Nothing orders them. Ben is allowed to see a card on the board whose boxes are still blank. The object is published, and it is half-built.

The experiment is Publication.java, and it comes with an unusually honest warning in its own header, which is worth reading before you run it.

./run.sh Publication unsafe          # plain fields, plain reference
./run.sh Publication finalfields     # final fields, plain reference
./run.sh Publication volatileref     # plain fields, volatile reference

If you predicted "a few thousand", you assumed the experiment is a detector. It is not. It is a demonstration that a clean run is not evidence.

Why did nothing break? Because of the chip, not the code. An x86 core never lets one store overtake another store in hardware. So on this laptop the only thing that could have broken the unsafe run was the JIT compiler choosing to reorder the writes, and it chose not to. An ARM core reorders stores freely, so the same bytecode really does break there. That means Apple Silicon, AWS Graviton, and essentially every phone. Section 18 is what that costs in practice.

Now look at the right-hand column, because it is telling you something else entirely. "Never seen at all" is a different symptom from a half-built card, and the experiment counts it separately on purpose. It means the reader spun 5,000 times and never saw a non-null reference in that round — the plain write never became visible in time, or the plain read got hoisted. That is section 3's bug, showing up inside section 13's experiment.

With a plain reference the reader missed 18,048 rounds out of 200,000. With a volatile reference it missed four. The tearing never showed on this hardware, but the visibility difference is enormous and it showed immediately.

One caveat on that column, stated plainly because the honest answer is "I do not know": the finalfields mode missed the most rounds of all, 70,589, and it also ran three times longer than unsafe. I did not establish why, and the experiment is not designed to answer it. The column the experiment is actually about is the half-built one, and it read zero everywhere.

So how do you publish an object safely? Four ways, and they are the whole list.

The safe way What creates the edge When to use it
a static initialiser the JVM's own class-initialisation lock constants and singletons
a volatile field or an AtomicReference the volatile write, and its piggyback (section 11) a reference that changes over time
all fields final, and this never escapes the constructor freeze (section 14) immutable value objects
written and read under the same lock the monitor edge (section 10) anything already guarded

Anything else is unsafe publication, whatever your laptop says. That includes a plain field, a plain array slot, and a plain map entry.

14. Why do final fields get a promise of their own?

In one breath: A final field written in a constructor is frozen the moment the constructor ends. Anyone who ever sees the reference at all sees those fields already set.

This is the only place in the model where you get a guarantee without a handshake. Ben does not have to read a volatile, take a lock, or do anything at all. If he can see the card, he can read its final boxes.

The specification calls the moment the constructor ends a freeze action. It is the reason String is safe to pass between threads with no synchronisation whatsoever. It is the reason records and value objects are the easiest concurrency strategy there is. And it is why java-multithreading listed immutability as one of its three ways to be thread-safe.

There is exactly one way to lose it, and it is worth knowing by name.

If this escapes during construction, the promise is void.

In the story: Ana must not let Ben peek at the card while she is still filling it in. If she hands it over halfway, or pins it to the board and then keeps writing, Ben is looking at an object whose freeze has not happened yet. In code, this escapes when a constructor registers a listener, starts a thread, passes itself to a collection, or calls an overridable method that a subclass has overridden.

Publication.java builds this into the experiment: its FinalConfig class has three final fields set in the constructor, and its PlainConfig has the same three left plain. Same shape, one keyword apart.

The practical shape to remember: make the fields final, set them all in the constructor, and let nothing out of the constructor except the finished object. Then you can share it with anybody, for ever, with no volatile and no lock.

15. Why did double-checked locking ship broken for a decade?

In one breath: The fast path deliberately skips the lock. A lock only orders two threads that both take it. So the fast path is ordered with nothing at all.

This is the most famous memory-model bug in Java's history. It was published as a recommended idiom, it appeared in books and in production code everywhere, and it was quietly broken for years. Nobody's tests caught it.

The goal is reasonable: build a singleton lazily, but do not pay for a lock on every call after the first. So you check, take the lock, and check again.

static class BrokenDcl {
    private static Service instance;          // NOT volatile — this is the bug

    static Service get() {
        if (instance == null) {               // fast path, no lock
            synchronized (BrokenDcl.class) {
                if (instance == null) {
                    instance = new Service("broken", 1);
                }
            }
        }
        return instance;
    }
}

That last assignment is four steps, exactly like Ana's card in section 13: allocate the memory, write the name, write the id, publish the reference. Now suppose the publish lands before the two field writes. A second thread running the first check is outside the lock, so it is ordered with nothing. It sees a non-null reference and returns it. It gets a Service whose name is null and whose id is 0.

The lock does not save you, and that is the part worth sitting with. The whole point of the fast path is that it skips the lock, and a monitor creates an edge only between threads that both acquire it.

🔮 Predict. Sixteen threads hammer each of four versions, 200,000 calls each. How many half-built objects does the broken version report?

Zero. So do all the others.

Three of those are correct by the rules of the model. One is correct by accident of running on x86 today. Nothing you can run on this machine tells the two apart. That is the point of the experiment, and it is the point of the lab.

What fixes it, and what to write instead:

  • volatile fixes it, and has done since Java 5. The volatile write at the end of construction releases everything before it; the volatile read on the fast path acquires it. Before Java 5 and JSR-133, volatile did not carry the piggyback rule, and double-checked locking genuinely could not be fixed at all.
  • The local variable in VolatileDcl is not cosmetic. Reading the volatile field once into a local turns two volatile reads on the hot path into one. That used to matter a great deal and still matters a little.
  • Use the holder idiom instead. The JVM already initialises a class exactly once, under a lock it manages itself, with correct publication. The nested class is not loaded until get() is first called, so it is genuinely lazy. After that first call the field access is a plain static read with no synchronisation cost at all. No volatile, no lock, no double check.

If you take one practical thing from this section: stop writing double-checked locking. The idiom exists to save a lock you no longer need to take.

16. What can a test prove here, and what can it never prove?

In one breath: You can test that a guarantee holds. You can never test that a race is absent.

Tests.java is built around that split, and it labels every check with which kind it is.

  • [ASSERT] — a safety property. The model forbids the bad outcome, so seeing it even once is a genuine failure. These are real tests.
  • [OBSERVE] — a permitted-but-not-required outcome. The model allows the bad thing but does not demand it, so a quiet run proves nothing. Asserting on these would be a lie, so the file reports what happened instead.

So what do professionals actually do?

  • Read the code. Memory-model bugs are found by checking that every shared field is reached through one of section 10's edges. That is a review activity, not a test activity.
  • Run on weak hardware. An ARM core reorders stores; an x86 core does not. Running your concurrency tests on Apple Silicon or Graviton is the single cheapest way to turn a hidden bug into a visible one.
  • Use jcstress. The OpenJDK Java Concurrency Stress harness enumerates outcomes of tiny programs across millions of runs and classifies each as expected, acceptable-but-interesting, or forbidden. It is the right tool for exactly the questions this lab asks. It was not run here; that claim is about the tool, not something this lab demonstrates.

Which pairs of ideas keep getting merged?

Six pairs, one sentence each, and every one of them has cost somebody a week.

  • happens-before versus happened earlier. The first is an edge you created on purpose. The second is a wall clock, and the model does not have one. This is the exact distinction causal-consistency carries across a network.
  • Visibility versus atomicity. Visibility is whether your write ever reaches me. Atomicity is whether I can catch your job half-done. volatile sells the first only, which is section 7 in one line.
  • A memory barrier versus a GC write barrier. The first is a CPU instruction that constrains reordering. The second is bookkeeping code the JIT injects so the collector learns about a pointer. Same word, no shared mechanism, and jvm-garbage-collectors calls this the most confused pair in its own subject.
  • Java's volatile versus C's volatile. In C it means "this address may change outside the program, do not optimise the access" and it carries no thread guarantees at all. In Java it is a full ordering contract. Code translated between the two languages on the strength of the keyword is broken.
  • Compiler reordering versus CPU reordering. Section 3 was the compiler, section 5 was the chip, and they need different explanations but have the same fix. The model deliberately does not distinguish them, which is why one rule covers both.
  • A data race versus a race condition. Section 12 has the full version. The short one: the first is mechanical and checkable, the second is a bug in your own reasoning, and fixing either leaves the other untouched.

Where does this show up in real systems?

AtomicInteger and ConcurrentHashMap in essentially every Java service. CompletableFuture's completion, which publishes a result across threads. Netty's event-loop confinement rules, which exist so that most of its state needs no synchronisation at all. Kafka's consumer, which is single-threaded by contract and throws if you break it. Every Executor submission and every Future.get, each of which is a happens-before edge you are using without naming.

Solutions — the Java Memory Model

Worked answers. Rungs 7 and 8 are design discussions, not single correct outputs — compare the shape and the reasoning, not the wording.

Every figure quoted here comes from the runs recorded in README section 22: one machine, one run per command, OpenJDK 25.0.4.1 on amd64. Where an exercise asks you to predict something that was never run, the answer says so instead of giving you a number.

Rung 1 — Explain

1.1 The worker is not looking at the signal. Somebody decided that since the worker's own loop never changes the signal, there was no point walking over to check it every time, so the value was copied once at the start and the worker has been checking that copy ever since. The real signal did change. Nothing is ever going to go and look again.

-Xint switched off the part of the system that made that decision. Every pass of the loop now genuinely goes and reads the signal, so the change is picked up immediately. On one run it exited after 147,698,840 passes.

What it did not change is the program's correctness. The code is still broken; it is just being run by something too simple to exploit the breakage. Move it back to a normal JVM, or to a different chip, or to next year's compiler, and it is a hang again. -Xint removed one optimiser's permission to use a right the language had already granted.

1.2 "You fixed whether other threads can ever see the value, which was a real problem. You did not fix that count++ is a read, an add and a write with a gap in between — two threads can both read 41, both compute 42, and both write 42, and volatile allows exactly that."

Their instinct is right for a flag that one thread writes and others only read. That is section 3's experiment, and volatile is the correct and complete fix there. The difference is that a flag has no read-modify-write: there is no gap to protect, because nothing is computed from the old value.

Worth adding, because it lands harder than the argument: on one run the volatile counter still lost 5,762,264 increments and took 328 ms against the plain version's 69 ms. It paid the whole bill and bought nothing.

1.3

  • Visibility — whether one thread's write is ever seen by another thread's read at all.
  • Atomicity — whether another thread can observe an operation half-done.
  • Ordering — whether two writes become visible in the order they were written.

The classification:

Symptom Which one failed
spinning worker that never stops visibility
counter ending on 1,954,887 of 8,000,000 atomicity
the 0-and-0 outcome ordering
non-null reference with zero fields ordering, which is what makes publication unsafe

The fourth is the interesting one. It is not an atomicity failure: nobody caught the constructor mid-write. The four writes each completed. They just became visible in the wrong order.

1.4 "Random" would mean the answer is drawn from a distribution each time you run. That is not what happens. What happens is that section 5's shuffle table has three rows in your head and four rows in the specification.

Your program is not wrong 6% of the time. Your reasoning is wrong 100% of the time, and 94% of the time that does not show. That is why the fix is never "make it happen less often" and always "delete the extra row".

Rung 2 — Identify

2.1 After one press of Core 0: run next line:

  • shared memory says x = 0,
  • Core 0 believes x = 1, because it can read its own store buffer,
  • Core 1 believes x = 0, because the buffer is private.

The three places one value can live at that instant are: shared memory, a core's private store buffer, and a core's register. Only the first is shared. That is the entire lab in one sentence.

2.2 The experiment is about partially-visible objects observed. That is the count of times the reader held a reference to an object whose fields were not the ones the writer had just put in it. On this hardware it read 0 in all three modes.

Publication never seen at all is a different symptom: the reader spun 5,000 times and never saw a non-null reference in that round. The write never became visible in time, or the read was hoisted. That belongs to README section 3, not section 13.

The contrast is worth quoting anyway. Plain reference: 18,048 rounds missed out of 200,000. Volatile reference: 4. The tearing never appeared, and the visibility difference appeared immediately.

2.3 The rule is: [ASSERT] for things the model forbids, [OBSERVE] for things the model permits but does not require.

You can see it from the output because the observations report a number and no verdict, while the assertions report pass or fail. A quiet run of an observation proves nothing, so asserting on it would be a lie, and the file refuses to tell that lie.

The line that would be a genuine JVM bug if it flipped is any of the five assertions. The sharpest is volatile_write_publishes_the_plain_writes_before_it: it reported 0 torn reads in 200,000 rounds, and the model allows exactly 0. A single torn read there would be a specification violation, not bad luck.

2.4 It is rule four, the piggyback. Thread B writes its result into the plain field r2 and then writes its volatile ticket. Thread A reads the volatile ticket and then reads r2. Because A saw the new ticket value, everything B did before writing it — including the plain write — is guaranteed visible.

If the tickets were plain, the harness would have no edges at all. The two threads would not reliably start each trial together, and thread A would be counting outcomes out of a field it has no guarantee of seeing. The measuring instrument would have the same bug it is measuring. The tool that catches the bug is built out of the fix.

2.5 The JIT compiler kept a flag in a register, which Experiment 1 (section 3) exposed. The CPU core let a store sit in its private buffer, which Experiment 2 (section 5) exposed.

The one-sentence field test: does the thread ever see the new value, at any point, ever? A hoisted load never does — it will spin for the rest of the process's life. A store-buffer delay always resolves; the buffer drains in nanoseconds. So "stuck for ever" is the compiler, and "briefly saw the old value and then caught up" is the hardware.

Rung 3 — Predict

3.1 Predict greater than zero, and expect it to be small and erratic.

The confidence caveat is the point of the question, and there are two halves to it. First, this run was never done, so nothing here is evidence — README section 22 lists ARM behaviour among the things this lab claims but does not demonstrate. Second, and more importantly, even a real ARM run showing zero would not tell you the code is safe. That is the same trap as the x86 run in section 13, one chip further along. The prediction is about hardware; the conclusion has to come from the rules.

3.2 Proportional scaling gives roughly 1.2 million, and you should write that down and then immediately distrust it.

The reason it can be off by five is that the rate is not a property of the program. README section 5 has three counts of the same phenomenon on the same machine: 1 in 4 from the Tests suite, 1 in 16 from Reordering plain, and 1 in 42 from the figure on the visualization page. Anything that changes how tightly the two threads are coupled — core scheduling, JIT warm-up, another process on the box — moves the rate by more than the trial count does.

3.3 With 2 threads the percentage lost falls sharply. Fewer workers means fewer chances that another one lands in the gap between your read and your write.

With 64 threads on a 16-core box the percentage rises further, and the reason is worth stating carefully: it is not that more threads run at once — only 16 can — but that each thread is descheduled far more often, and every deschedule lengthens the window between its read and its write.

Neither variant was run. The direction is safe to assert; a number is not.

3.4 After the first call, Eager and HolderIdiom are fastest: both reduce to a plain read of a static final field, which the JIT can constant-fold outright. VolatileDcl is slowest, because the fast path still performs one volatile read on every call.

And now the important half: that fact does not matter. The performance gap between a volatile read and a plain read is nanoseconds on a path that is called after a lock-free check. Section 15 recommends the holder idiom because it is simpler and impossible to get wrong, not because it is faster. If the ranking changed your answer, you have optimised the wrong axis.

3.5 Zero. None of the 200 threads can see a half-built Service.

The rule is class initialisation. The JVM initialises a class exactly once, under a lock it manages itself, and every thread that touches the class either performs that initialisation or waits for it. That gives a happens-before edge from the static initialiser to every subsequent read of the field. It is a guarantee in the specification, not a probability, and it is the reason the holder idiom in section 15 works.

Rung 4 — Modify

4.1 Three that work, and they are not equally honest:

  1. Run with -Xint. Changes the rule for that process: no compiler, no hoisting. Correct, and roughly a hundred times slower.
  2. Put a System.out.println in the loop. Changes the rule by accident — the stream is synchronized, so the print is a real happens-before edge. It also stops the loop being simple enough to optimise. Correct for reasons you did not intend, and it will stop being correct the moment somebody removes the log line.
  3. Call Thread.sleep(1) in the loop. Changes only the odds. sleep creates no edge whatsoever. In practice the loop is no longer hot enough to be compiled the same way, so it usually works, and it is the worst of the three because it looks deliberate.

The grading is the answer: one changes the rule on purpose, one changes it by side effect, and one changes nothing but the probability. Only the first is a fix, and it is not one you can ship.

4.2 To get 1-and-1 you must press flush on both cores after the two writes and before the two reads. The full sequence is: Core 0 run, Core 1 run, Core 0 flush, Core 1 flush, Core 0 run, Core 1 run.

The flush models a store buffer draining to the shared cache line. In real hardware nothing in your program triggers it. It happens when the buffer fills, when a fence forces it, or whenever the core gets round to it. Java says nothing at all about when it happens, which is exactly why the page makes it a button you press rather than a timer.

4.3 Three correct fixes, ranked:

Rank Fix Why it ranks there
1 the holder idiom lazy, free after the first call, and there is nothing to get wrong
2 static final, eager bulletproof and simplest, but you pay the cost even if it is never used

The justification that is not taste: rank by how many ways a future edit can break it. Someone deleting the volatile keyword from option 3 breaks it silently, and no test on x86 will notice. There is no keyword to delete in options 1 and 2.

4.4 LongAdder keeps a per-thread cell and sums them only when you ask for the total. Under heavy contention that removes the compare-and-set retry storm, so it should be substantially faster than AtomicLong and the final total should still be exact.

Not run, so no number is given here. The LostUpdate atomic figure that was run is 8,000,000 exact in 302 ms, against synchronized at 1,254 ms.

What LongAdder gives up: a meaningful instantaneous read. AtomicLong.get() returns one value at one moment; LongAdder.sum() walks the cells while they are still being written, so it is not a snapshot of any instant. It also has no compare-and-set, so you cannot build a conditional update on it.

4.5 In volatile mode the What the JIT runs panel stops showing a single load before the loop and starts showing a real load from memory inside the loop, on every pass.

In one sentence about registers: the optimiser is no longer allowed to keep the field in a register across loop iterations, so the value the loop tests is always the value in memory rather than a copy taken once.

This is the failure people find hardest to believe, because on the screen both threads visibly took a lock.

Rung 6 — Spot the flaw

6.1 What is safe: seeing the reference, and seeing the object's state as it was when it was published. The volatile write publishes everything the builder did before it (section 11, rule four).

What is not safe: the counter. Once the object is shared, a plain field inside it that several threads increment is section 7's bug, and the volatile reference is in completely the wrong place to help. The reference orders how you got to the object. It says nothing about what happens to the object's insides afterwards.

The sequence: two threads both read the counter as 41, both compute 42, both write 42. One increment is gone. The reference was volatile throughout.

6.2 The reasoning is wrong in one specific way: it treats absence of evidence as evidence of absence, on a machine that is structurally incapable of producing the evidence.

A reader can legally observe a non-null instance whose name is null and whose id is 0. On x86 it will essentially never happen, because the hardware does not reorder one store past another and the JIT chose not to either.

The test evidence is worth nothing because CI runs on x86. Ten million passes on a machine that cannot produce the failure is ten million passes of a test that was never able to fail.

README section 15 produced exactly that evidence on purpose: all four versions, including the broken one, reported 0 half-built objects across 16 threads and 200,000 calls each.

6.3 The four steps are: allocate, write name, write id, publish the reference. Doing all four while holding a lock genuinely orders them with respect to other threads that take the same lock.

The reader on the fast path does not take the lock. That is the entire purpose of the fast path. So the writer's diligence buys an edge to a thread that never turns up to collect it.

Put the two facts next to each other and the flaw is obvious: a lock creates an edge between two threads that both acquire it, and the design is built around one of them not acquiring it.

6.4 The rule broken is this escaping during construction (section 14).

The case: the constructor registers the object somewhere — a listener list, a static registry, a thread it starts — before it reaches the final line. Another thread pulls it out of that registry, and now it is holding a reference that never passed through the ready flag at all. The volatile write at the end of the constructor is a fine edge for anybody who reads ready. It is no edge at all for somebody who got the reference by another route.

The general shape: a safe-publication scheme protects the route, and it protects only the route it was built for. Any second route around it is unprotected.

6.5 Three wrong assumptions:

  • About ordering: sleep creates no happens-before edge. Nothing about sleeping makes a write visible.
  • About timing: "definitely up" is not something 50 milliseconds buys. Under load, thread start can take longer than that.
  • The edge used backwards: Thread.start() is a real edge, and it is the one they should have used — but it orders writes made before start(), not after. Writing the config after starting the worker points the guarantee the wrong way round.

The fix is one line: write the config before worker.start(). Then the edge they already had does the job, and the sleep can go.

6.6 The data shows the opposite of progress. Section 7's run:

Mode Lost Elapsed
plain 6,045,113 69 ms
volatile 5,762,264 328 ms

The drop from 6.05 million to 5.76 million is noise on a non-deterministic race, not a trend. The elapsed time nearly five-doubled. They bought a fence and got nothing for it, and a tighter loop would make it worse rather than better, because a tighter loop means more contention per second.

The next step was to stop tuning and change the operation: AtomicLong gave 8,000,000 exact in 302 ms on the same run. The bug is atomicity, and no amount of visibility fixes it.

Rung 7 — Handle failure

7.1 First look: which thread, and is it making progress. A thread dump taken twice, thirty seconds apart, is the whole diagnosis. A hoisted-flag spin shows the thread RUNNABLE, in the same tiny frame, both times.

Telling it apart from an infinite retry loop: a retry loop moves. It allocates, it logs, it makes syscalls, and successive dumps show different frames. A spin on a stale register does none of that — no allocation, no I/O, no GC pressure, one frame, for ever.

The fix is to make the flag volatile. If the flag is also being tested and set, it needs an atomic instead.

For the postmortem: the tests could not have caught it. The bug requires the JIT to have compiled the loop, which needs the loop to have run hot for seconds, and it needs no synchronization to have crept in anywhere in the loop body. A unit test satisfies none of those. Say that plainly rather than adding a test that would not have caught it either.

Before migrating, run the full test suite on an ARM box. That is the highest-value single action, and it is also the one most likely to give you a false green.

7.3 The three candidates and the observation that kills each:

Candidate Eliminate it by observing
lost updates the drift scales with concurrency and not with elapsed time; hold load flat and double the thread count, and the drift should roughly track it
visibility failure the count would be wrong in a sticky way — a reader stuck on a stale value stops moving entirely rather than drifting by a fraction
logic bug in the business rule the drift appears at low load too, once you look at enough volume; it does not care about concurrency at all

The discriminator that does the most work is low load. A concurrency bug that is exact at low load and 0.3% off at peak is a concurrency bug. A logic bug is 0.3% off at every load, and you only noticed it at peak because that is where the volume is.

7.4 What it does to the rest of the suite: the stuck daemon thread spins at full speed on one core for every check that follows. On a 16-core box that is one core gone, plus cache and scheduler pressure. Every subsequent timing is affected, and the contended increment tests are affected most because they are exactly the ones sensitive to how often a thread is descheduled.

Which figures not to quote: the elapsed times of anything after the plain-flag observation, and — more carefully — the rates in the later observations. The counts of lost updates are still valid as demonstrations that updates are lost. They are not valid as measurements of how many.

A harness change that keeps the observation: give the flag a second, volatile kill switch that the spinning loop also tests. Set it after the observation is recorded. The loop then exits on the volatile flag whether or not it ever saw the plain one, the observation is unchanged, and no thread is left running. This costs you nothing, because the thing under observation is the plain flag, and adding a separate volatile exit does not give the plain one any new visibility.

7.5 The reply, in three parts.

What it would tell you: if the hang disappears under -Xint, you have confirmed that the optimiser is exploiting a right the language gave it. That is real information. But it is not a JIT bug; it is your code being incorrect in a way the JIT is entitled to exploit.

What it would cost: interpreting every bytecode costs roughly two orders of magnitude in throughput. You would need a hundred times the fleet, and the experiment would be running in front of customers.

What to do instead, in an hour: take a thread dump twice, thirty seconds apart. If the thread is RUNNABLE in the same frame both times, with no allocation and no I/O, you have your answer without touching production. Then read the loop and find the plain field. The whole diagnosis is in the code, and it is faster to read it than to run the experiment.

The read-by-hand phase: for every shared field, name the happens-before edge that orders it. Section 10 has six. If a field cannot be assigned to one of them, it is unsafe. This is the only item on the list that is a proof rather than a heuristic.

The question you ask authors: "which edge orders this field?" not "is this thread-safe?". The second question invites reassurance; the first has a checkable answer.

Third-party code you cannot review: check versions, check release notes for ARM issues, and rely on the fact that the widely-used libraries have run on ARM in other people's production for years. Label this as the weakest item and do not count it as coverage.

Before the migration: run the full suite on an ARM box, and run any concurrency stress you have for far longer than usual.

The item that would have caught section 15's bug: the double-checked-locking grep, followed by reading it. Not the ARM test run — a broken singleton can easily pass on ARM too, because the reorder has to actually happen at the moment a second thread is on the fast path.

Evidence versus reassurance, honestly: the by-hand edge review is evidence. The greps are triage that tells you where to look. Everything else — the ARM test run, the library versions, the stress duration — is reassurance. The ratio is roughly one item of evidence to five of reassurance, and pretending otherwise is how teams migrate confidently into an outage.

8.2 — Hot-reloadable configuration.

Build it as a fully immutable object: every field final, every collection copied and wrapped, nothing mutable reachable from it, and this never escaping the constructor. That is section 14's freeze, and it means the object needs no synchronization of any kind once it exists.

Publish it through a single volatile reference, or an AtomicReference if you ever need compare-and-set on a swap. That is route two of section 13's four.

Readers do one thing: read the reference into a local variable, once, at the top of the request, and use that local for the whole request.

That local is the answer to "what happens to a request halfway through". It keeps the old object. The old object is immutable, so it stays internally consistent for as long as anyone holds it, and it becomes garbage when the last request holding it finishes. There is no tearing, no lock, and no window.

Why this route and not the others: a static initialiser cannot be reloaded; final fields alone give you no way to swap the object; a lock would serialise every request against a change that happens twice a day. The volatile reference is the only one of the four that supports replacement.

If a single field inside it needed independent update, the design breaks, and it is worth being clear about why. You would lose immutability, so every reader would need an edge to that field specifically, and you would immediately have a consistency question the current design does not have: can a request see the new value of field A and the old value of field B? With whole-object replacement the answer is structurally no. With per-field updates you have to define an answer and enforce it, which usually means a lock or a version number, and you are back to paying on every request.

8.3 — The same idea at three scales.

What is identical: all three are answers to "which writes must a reader see?", and all three answer it by naming an ordering relation rather than by appealing to time. In the JVM it is happens-before between two cores. In causal-consistency it is happens-before between two machines, carried by version vectors. In redis and acid, "atomic" is the related question of what a reader may observe half-done. In every case the naive model — one global order, wall-clock time — is the thing that fails.

What is genuinely different: the JVM knows when a thread has died and can enforce an edge with a single instruction, because everything is inside one failure domain. Across machines there is no shared clock, no reliable failure detection, and no instruction that reaches both ends. So the distributed version has to carry its ordering in the data: version vectors, dependency metadata, causal delivery buffers. What costs one fence inside a JVM costs a metadata field on every write and a delivery check on every read.

Why a single instruction is enough here: the fence is executed by hardware that both parties are physically part of, and cache coherence guarantees the result propagates. There is no equivalent across a network, which is why causal-consistency spends its whole length on machinery this lab gets for one keyword.

8.4 — The test you would actually write.

What you deliver is two things, and the second is the important one.

The test: a stress loop that exercises the fixed path from many threads and asserts the invariant that was violated. Structure it like section 16's split. Anything the model forbids becomes an assertion — those are real tests, and a failure is a real bug. Anything the model merely permits becomes an observation that reports a count and never fails the build.

What it can prove: that the invariant held under the schedules this machine happened to produce. If you also assert something the model forbids, it can prove a genuine violation the day one appears.

What it cannot prove: that the race is gone. A race that does not appear has not been shown to be absent — README section 13's zero-anomaly run is exactly that result, obtained deliberately.

What you name it: something that tells the truth to a future reader, such as observes_no_torn_config_under_load, not configIsThreadSafe. The name is the main defence against over-trust, because the name is what somebody reads at 3am when it goes green.

What goes in the review checklist instead: the field-by-field edge review from 8.1. "Every shared field names its happens-before edge" is a check that can actually fail for the right reason, and it is the only one on this page that scales to code nobody has run yet.
